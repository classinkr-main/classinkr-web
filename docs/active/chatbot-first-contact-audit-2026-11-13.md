# 챗봇 첫 방문자 질문 점검 — 이상 답변 11건의 원인과 답변 경로 정리

기준일: 2026-11-13 · 담당 파트: 챗봇/CS([플레이북 05](./playbook/05-chatbot.md))

## 문제

공개 챗봇이 첫 방문자가 한 줄로 묻는 사실 질문에 엉뚱한 답을 냈다. 모아 둔 화면 11장(질문 10개)은 아래와 같다.

| 질문 | 변경 전 답 |
|---|---|
| 클래스인은 어느나라 제품인가요? | 드라이브 수업 자료 관리 문서 조각 |
| 전자칠판 꼭 사야하나요? | "일반 전자칠판과 다른 점" 설명 |
| 클래스인 대표는 누구인가요? | 스타터 가이드 문서 조각 |
| OPS 원가와 전자칠판원가는? | OPS 구성 설명 |
| 녹화본은 몇 달 저장되나요? | 수업 녹화와 현장 녹화의 차이 |
| 한 교실에 최대 몇 명까지 접속할 수 있나요? | "로그인이 안 되시는군요" |
| 줌보다 얼마나 싸요? | 가격 없는 일반 비교 |
| 대치동 세정학원도 클래스인 사용하나요? | 스타터 가이드 문서 조각 |
| 중국회사죠? 학생들 영상은 어느 서버에 저장되나요? | 실시간 수업과 녹화 수업 문서 조각 |
| 맥북에도 깔리나요? | "어떤 상황인지 알려 주세요" |

## 원인

1. **모델 호출이 통째로 실패하고 있었다.** 기본 모델(`gemini-2.5-flash`·`2.5-pro`·`2.5-flash-lite`)이 `generateContent`에서 404("no longer available")를 돌려준다. `models.list`에는 계속 보여 목록만 봐서는 알 수 없다. 답을 다듬는 단계가 조용히 건너뛰어져 검색 초안이 그대로 나갔다.
2. **낱말 하나가 주제를 정했다.** '접속'은 로그인 문제로, 'OPS'는 장비 구성 점검표로, '녹화 … 저장'은 녹화 권한 안내로 갔다.
3. **근거가 약할 때의 안전장치가 없었다.** 검색 점수가 낮은 문서 조각을 "관련 안내를 정리해드리면"으로 붙여 내보냈다.
4. **정해 둔 답의 패턴이 길고 구체적인 상황 질문에 맞춰져 있었다.** "맥북에도 깔리나요?" 같은 짧은 질문은 어느 답에도 걸리지 않았다.
5. **모델에게 문서가 제대로 전달되지 않았다.** 모델이 받는 근거는 문서 본문이 아니라 출처 카드용 220자 요약 두 개였다. 실측한 조각 110개 중 83개가 문장 중간에서 끊겨 있었고, 모델은 끊긴 뒷부분과 빠진 단계를 지어 채웠다. 문서에 답이 없을 때도 모델은 답을 썼다.

1~4는 화면 11장의 직접 원인이고, 5는 1을 고쳐 모델을 되살린 뒤 드러났다.

## 바꾼 것

### 결정 경로

- `lib/chatbot/quick-answers-basics.ts`(신규): 첫 방문자의 기본 사실 질문에 답하는 정해 둔 답 68개. 회사·대표·법인, 전자칠판 필수 여부, 지원 기기, 인원·시간 한도, 보관 기간, 원가·할인, 고객사, 다른 도구와의 비교를 다룬다. 기존 정해 둔 답이 모두 빗나간 뒤, 45자 이하이고 증상 표현이 없는 질문에만 쓴다. 두 가지를 함께 물으면 두 답을 잇는다.
- `lib/chatbot/service.ts`: '접속'·'OPS'·'녹화 저장'·'망할 일'·'해외로 나가요'가 다른 주제로 새던 조건을 좁혔다. 회사·기기·설치·비용·사례·한도 낱말이 든 질문은 일반 잡담으로 넘기지 않고 검색한다.
- 검색 점수가 낮은 문서만 있을 때 공개 경로의 초안은 조각을 붙이지 않고 못 찾았다고 밝힌다(`WEAK_SOURCE_DRAFT_ANSWER`).

### 모델 경로

- `lib/chatbot/llm.ts`: 기본 모델을 `gemini-3.5-flash`(빠른 답)·`gemini-3.1-pro-preview`(깊은 답)로 바꾸고, 실패하면 `gemini-3.1-flash-lite`, 마지막에 별칭 `gemini-flash-lite-latest`로 넘어간다. env에 종료된 모델명이 남아 있어도 무시한다. 모델마다 받는 `thinkingLevel`이 달라 확인된 값만 보낸다.
- `lib/chatbot/source-grounding.ts`(신규): 출처마다 문서 본문을 따로 실어 모델에게는 문장이 온전한 근거를 준다. 본문은 심볼 키에 두어 API 응답·저장에는 실리지 않는다.
- **근거 선별(기본 동작)**: 모델은 답을 새로 쓰지 않는다. 문서 문장에 번호를 붙여 보여 주면 질문에 직접 답하는 문장의 번호만 고르고, 챗봇은 그 문장을 그대로 이어 답한다. 답이 되는 문장이 없으면 엉뚱한 조각을 내보내지 않고 못 찾았다고 답한다. 이 답은 미해결로 남아 문서 보강 대상이 된다.
  - 검색이 고른 출처 2개만이 아니라 상위 5개(문서당 2개)를 후보로 넘긴다. 답이 같은 문서의 다른 섹션에 있는 경우가 많다.
  - 정해 둔 문장으로 만든 초안은 건드리지 않는다. 검색 조각으로 만든 초안만 선별 결과로 바꾼다.
  - 선별 호출이 실패하면 초안을 그대로 둔다.
- 못 찾았다고 답할 때는 "순서대로 알려 드릴게요" 같은 첫마디와 규모·도입 시기를 묻는 끝 질문을 붙이지 않는다(`lib/chatbot/tone.ts`, `lib/chatbot/follow-up.ts`).
- `lib/chatbot/eval.ts`: 심판에게 220자 요약이 아니라 모델이 실제로 받은 본문을 근거로 준다. 심판 모델도 답변과 같은 방식으로 정한다.

### 운영 스위치

`CHATBOT_FINAL_ANSWER_LLM`으로 모델 사용 방식을 고른다. 검색과 임베딩은 어느 값에서나 그대로 쓴다.

| 값 | 동작 |
|---|---|
| 비움 또는 `select` | 모델은 문서에서 답 문장만 고른다. 답은 문서 문장 그대로 나간다. |
| `generate` | 고른 문장을 근거로 모델이 상담 말투로 답을 다시 쓴다. 답 문장이 없으면 쓰지 않는다. 문서가 하나도 안 걸린 질문은 기본 지식 범위에서 답한다. |
| `off` | 모델을 쓰지 않는다. 정해 둔 답과 문서 요약 초안만 나간다. |

## 측정

모든 수치는 Supabase를 끄고 정적 문서 검색으로 잰 것이다. 운영의 벡터 검색 경로는 재지 못했다(아래 "확인하지 못한 것").

### 결정 경로 — 첫 방문자 질문

화면 11장과 같은 유형으로 만든 질문 180개를 더해 192문항으로 쟀다(`data/chatbot-first-contact-set.json`). 채점은 서로의 결과를 보지 않는 하위 모델 심사관 4명이 같은 기준표로 했다.

| | 좋은 답 | 일부만 답함 | 엉뚱한 답 | 불필요한 되묻기 |
|---|---|---|---|---|
| 변경 전(180문항) | 43 (24%) | 57 | 51 | 29 |
| 변경 후(같은 180문항) | 170 (94%) | 9 | 0 | 1 |
| 변경 후(192문항, 화면 11장 포함) | 182 (95%) | 9 | 0 | 1 |

화면 11장의 질문은 모두 좋은 답으로 판정됐다. 기존 평가 질문 1,223개(골든셋 79·증상 184·페르소나 960)의 답은 2개만 바뀌었고 둘 다 의도한 변경이다(서버 위치, 카메라 대수). 근거 선별을 넣은 뒤에도 결정 경로의 답은 1,223개와 192개 모두 그대로다.

### 모델 경로 — 문서에 없는 말을 하는가

모델까지 가는 질문 69개로 쟀다. 기존 평가 질문 중 모델 경로로 가는 43개, 첫 방문자 질문 4개, 문서에 없는 기능·지역 도입 분위기·영업 화법을 일부러 건드린 질문 22개다. 답마다 모델이 받은 근거(검색 문서, 초안, 시스템 지시의 기본 지식)와 대조했고, 심사관 3명이 23개씩 나눠 채점했다. 심사관이 회차마다 달라 몇 건의 오차는 있다.

모델이 답을 쓰는 방식:

| 단계 | 근거에 맞음 | 표현만 부풀림 | 근거 밖 단정 |
|---|---|---|---|
| 모델만 되살림 | 24 | 10 | 35 (51%) |
| 요청마다 근거 범위를 다시 적음 | 26 | 22 | 21 (30%) |
| 문서 본문을 근거로 연결 | 35 | 8 | 26 (38%) |
| 선별 뒤 재작성(`generate`) | 28 + 결정형 21 | 8 | 12 (17%) |

근거 밖 단정의 예: 문서에 없는 "카메라 아이콘을 누릅니다" 같은 단계, "휴대폰을 잠그는 기능은 제공하지 않습니다" 같은 근거 없는 부정, "대치동의 많은 학원이 적극 검토하고 있습니다" 같은 지역 추세, "유지율을 높일 수 있어요" 같은 성과.

문서에 답 문장이 있는지가 결과를 갈랐다. 같은 답을 선별 결과와 겹쳐 보면, 답 문장이 있던 32건에서는 근거 밖 단정이 5건(16%)이었고 없던 32건에서는 18건(56%)이었다.

모델이 문장만 고르는 방식(`select`, 기본값):

| | 건수 |
|---|---|
| 문장을 골라 답함 | 38 (좋은 답 24, 일부만 답함 14, 엉뚱한 답 0) |
| 못 찾았다고 답함 | 21 (후보 문장에 답이 있었는데 놓친 경우 0) |
| 선별 없이 정해 둔 답 | 10 (좋은 답 3, 일부만 답함 3, 엉뚱한 답 4) |

답은 문서 문장 그대로라 지어낸 문장이 없다. 정해 둔 답의 엉뚱한 답 4건은 모두 문서가 하나도 안 걸려 "어떤 상황인지 알려 주세요"로 되묻는 경우다(플립러닝 가능 여부, 출석부 자동 생성, 투자자, 대치동 추세).

응답 시간(검색 포함, 중앙값 / 90% 지점): `select` 1.3초 / 1.5초, 선별 없는 생성 2.0초 / 2.6초, `generate` 2.8초 / 4.4초.

### 기본값을 `select`로 둔 이유

`generate`는 문장이 자연스럽고 더 많은 질문에 답하지만, 다시 쓴 답 48건 중 12건에 문서에 없는 내용이 섞였다. `select`는 답이 문서 말투 그대로이고 이 69문항에서는 열에 셋을 못 찾았다고 답했지만, 틀린 안내가 나가지 않는다. 이 경로까지 오는 질문은 정해 둔 답에 걸리지 않은 질문뿐이다(기존 평가 질문 1,223개 중 43개). 틀린 단계나 근거 없는 "안 됩니다"는 고객이 알아채기 어렵고, 못 찾았다는 답은 미해결로 집계돼 문서를 채울 근거가 된다. 상담 말투가 더 중요하다고 판단하면 스위치를 `generate`로 바꾸면 된다.

## 정해 둔 답의 기준(확인 필요)

기본 사실 답을 쓰면서 아래처럼 정했다. 영업·법무 기준과 다르면 `lib/chatbot/quick-answers-basics.ts`의 해당 답을 고친다.

1. **회사 국적**: "중국 회사다/아니다"로 답하지 않고 회사 소개 페이지에 실린 사실을 그대로 말한다(글로벌 HQ 싱가포르, EEO 본사와 R&D 센터 베이징, 한국 법인 서울 목동).
2. **특정 학원의 사용 여부**: 쓴다고도 안 쓴다고도 확인하지 않고 공개 도입 사례 페이지를 안내한다. 홈페이지 사례 페이지에는 학원 실명이 실려 있고, 문서센터와 모델 지시는 이름을 가려 쓴다.
3. **최대 인원**: 도움말은 요금제에 따라 다르다고 하고 소개 자료는 최대 2,000명이라고 한다. 답은 둘을 함께 적는다.
4. **금액**: 체크아웃 화면에 금액이 있는 항목(전자칠판, 설치)도 채팅에서는 숫자를 말하지 않는다.
5. **무료 체험**: "무료 체험 있나요?"는 기존의 유보적인 답을 유지했다. 다른 답과 문서는 "2주 무료 체험"을 말하고 있어 서로 어긋난다.
6. **요금제 이름**: 문서마다 Pro·비즈니스, Standard·Plus, Learning Space·Business로 다르다.
7. **무대 인원**: 도움말은 1v0~1v12, 소개 자료는 카메라 49개다.

## 확인하지 못한 것

- **운영 검색 경로.** 모든 측정은 정적 문서 검색으로 했다. 운영의 Supabase 벡터 검색에서는 검색되는 조각과 점수가 달라 "못 찾음" 비율이 다를 수 있다. 배포 뒤 어드민 평가 화면이나 `chatbot_answer_events`의 미해결 비율로 확인한다.
- **운영 env.** 운영에 `GEMINI_FAST_MODEL` 등이 어떤 값으로 들어 있는지 보지 못했다. 종료된 모델명이면 코드가 무시한다.
- **빌드.** `npm run build`는 postbuild가 운영 DB를 읽어 이번 점검에서 돌리지 않았다. typecheck, eslint, vitest는 통과했다.
- **저장소의 골든셋 심판 게이트.** 정적 검색 환경에서는 정해 둔 답까지 환각으로 세어(출처 문서에 없는 문장이라) 통과 기준으로 쓸 수 없었다.

## 남은 일

- 문서가 하나도 안 걸리는 구체적인 질문("투자자가 누구예요?")은 `select`에서 일반 되묻기로 나간다. 못 찾았다는 답이 더 맞는지 정한다.
- 도입 사례·후기 질문은 문서에 "과목을 붙여 물어보세요"라는 문장만 있어 답이 빈약하다. 사례 문서에 과목별 사례 문장을 넣으면 선별이 그 문장을 고른다.
- `generate`를 쓰려면 시스템 지시의 영업 문구부터 손본다. "강사 공수를 0으로", "딴짓 원천 차단", 사례의 "변화를 짚어 주어라"는 지시가 근거 없는 성과 표현을 끌어낸다.
- 챗봇 밖의 Gemini 호출(마케팅 브리핑, 지사 인사이트, 메일 자동화, 어드민 마케팅 AI)은 아직 `gemini-2.5` 기본값을 쓴다.
- 남은 일부 답(9건): 소프트웨어만 쓸 때의 기능 제한, "채팅 기록도 저장되나요", 삼성 전자칠판과의 비교, 줌 무료 버전과의 비교 등은 기존 정해 둔 답이 질문의 일부만 답한다.

## 다시 돌리는 법

```bash
npx vitest run tests/chatbot/basics-quick-answers.test.ts
```

```bash
npx vitest run tests/chatbot/evidence-selection.test.ts tests/chatbot/source-grounding.test.ts tests/chatbot/model-chain.test.ts
```

- 첫 방문자 질문 평가셋은 `data/chatbot-first-contact-set.json`이다. 새 이상 답변이 나오면 여기에 질문을 먼저 넣고 테스트가 깨지는지 본다.
- 모델을 바꾸거나 점검할 때는 `models.list`가 아니라 실제 `generateContent` 호출로 확인한다.
- 모델 경로를 다시 잴 때는 Supabase env를 비우고 실제 Gemini 키로 `evaluateChatbotQuery`를 돌려 답과 프롬프트를 남긴 뒤, 답의 사실 주장이 프롬프트의 근거에 있는지 대조한다. 모델 경로로 가는 질문은 정해 둔 답에 안 걸리는 질문이므로, 평가셋 질문보다 문서에 없는 기능을 묻는 질문을 섞어야 문제가 드러난다.
