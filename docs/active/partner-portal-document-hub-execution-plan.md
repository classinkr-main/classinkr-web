## 1. 문제 정의

현재 문서 경험은 기능이 부족해서가 아니라, 진입점과 책임이 흩어져 있어서 느리다.

- 전역 문서 허브와 거래 상세 문서 탭의 역할이 겹친다.
- 견적서, 계약서, 영수증이 각각 다른 화면과 다른 액션 규칙을 가진다.
- 만들기, 발송하기, 보기, 정리가 같은 화면 언어로 읽히지 않는다.
- 문서 상태와 전달 상태가 충분히 분리되어 있지 않아 운영 판단이 흔들릴 수 있다.
- 링크, PDF, 출력, 카카오, 서명 같은 전달 수단이 공통 규칙으로 보이지 않는다.

이 결과 사용자는 다음 질문을 매번 다시 하게 된다.

- 지금 어디서 새 문서를 만들어야 하지?
- 이 문서는 어디서 보내야 하지?
- 최신 버전과 발송 버전은 같은 건가?
- 출력은 링크와 같은 건가, 다른 건가?

이 문서의 목표는 위 질문을 화면 구조에서 제거하는 것이다.

## 2. v1 범위

v1은 `문서 운영의 핵심 루프`만 완성한다.

- 문서 생성 진입점 통합
- 공통 발송 흐름 통합
- 문서 목록/상세/버전 보기 통합
- 상태와 전달 상태 분리
- 링크 복사, PDF 열기, 출력용 보기, 재발송 기준 정리

v1에서 포함하지 않는 것:

- 자동 발송 최적화
- AI 기반 채널 추천
- 승인 워크플로우의 다단계 협업
- 문서 템플릿 디자이너
- 상세한 권한 매트릭스 확장

v1의 성공 기준은 `문서를 만들고, 보내고, 보고, 정리하는 기본 루프`를 더 이상 헷갈리지 않게 만드는 것이다.

## 3. 선행 결정사항

구현 전에 아래 결정을 먼저 고정해야 한다.

- 전역 메뉴에서 `견적서 / 계약서 / 영수증` 개별 메뉴를 유지할지, `문서`로 통합할지
- 전역 문서 허브와 거래 상세 문서 탭의 역할 분리를 어디까지 둘지
- `문서 상태`와 `발송 상태`를 어떤 명칭으로 고정할지
- 고객 공개 버전의 기본 단위를 `버전 고정 링크`로 둘지 `버전 고정 PDF`까지 동일한 정책으로 볼지
- 출력 허용을 기본 허용으로 둘지, 문서 종류별로 다르게 둘지
- 발송 수단의 우선순위를 어떻게 둘지
  - 견적: 링크 우선
  - 계약: 서명 링크 우선
  - 영수증: PDF 우선
- 발송 대상의 기본값을 마지막 수신자 재사용으로 둘지, 항상 재선택으로 둘지
- 문서 row의 대표 지표를 무엇으로 둘지
  - 최신 버전
  - 마지막 발송
  - 마지막 열람
  - 다음 액션

결정이 필요한 이유는 간단하다.

- 이 값들이 고정되어야 프론트, API, 로그, 알림이 같은 말을 한다.
- 이 값들이 흔들리면 구현은 빨라도 운영이 느려진다.

## 4. 구현 스트림

### 4-1. IA

목표는 `무엇을 해야 하는지`가 바로 보이게 하는 것이다.

- 전역 구조는 `문서` 하나로 압축한다.
- 문서 허브 상단에는 `만들기 / 발송하기 / 보기·정리` 모드를 둔다.
- 문서 종류 필터는 허브 내부에만 둔다.
- 거래 상세 문서 탭은 `작성 맥락`과 `최근 액션`을 보여주는 보조 허브로 유지한다.
- 리스트 row는 문서의 현재 상태를 읽는 단위로 만든다.
- 상세 패널은 작업 실행 단위로 만든다.

IA 기준 산출물:

- 전역 문서 허브 정보 구조
- 거래 상세 문서 탭 정보 구조
- 문서 row 필드 우선순위
- 상세 패널 고정 블록

### 4-2. Frontend

목표는 `한 화면에서 행동이 끊기지 않게` 만드는 것이다.

- `app/partner/(portal)/documents/page.tsx`를 문서 허브의 기준 화면으로 유지하거나 재구성한다.
- 상단 모드를 토글이 아니라 작업 모드로 읽히게 한다.
- 공통 발송 모달을 만든다.
- 문서 종류별 화면 차이를 최소화하고, 종류 차이는 데이터와 옵션으로 표현한다.
- 문서 row 액션은 가능한 한 동일한 위치에 둔다.
- `링크 복사`, `PDF`, `출력`, `재발송`, `버전 보기` 같은 액션을 일관된 버튼 배열로 만든다.

프론트 우선순위:

- 목록과 상세의 정보 밀도 정리
- 상태 배지 정리
- 미리보기와 버전 이력 노출
- 발송 모달 공통화
- 모바일에서 한 줄 액션이 깨지지 않게 압축

### 4-3. API/Data

목표는 `문서 원본`, `문서 버전`, `전달본`을 분리해서 운영 기준을 명확히 하는 것이다.

- 문서 본체는 거래 단위의 원본 엔티티로 둔다.
- 문서 버전은 발행 시점의 스냅샷으로 둔다.
- 전달본은 `링크 / PDF / 카카오 / 이메일` 같은 외부 전달 단위로 둔다.
- 전달본은 수신자, 만료, 비밀번호, 출력 허용, 열람 로그를 가진다.
- 문서 상태와 전달 상태를 분리해서 저장한다.

API/Data 우선순위:

- 문서 목록 응답에 `최신 버전`, `최근 발송`, `최근 열람`, `다음 액션`을 포함한다.
- 발송 생성 API는 공통 입력 형식을 받도록 맞춘다.
- 보기 전용 API와 쓰기 API를 분리한다.
- 전역 문서 허브와 거래 상세 문서 탭이 같은 응답 스키마를 재사용하게 만든다.

### 4-4. Logging

목표는 운영 판단과 감사 추적이 남는 것이다.

- 문서 생성 로그
- 버전 생성 로그
- 발송 생성 로그
- 발송 성공/실패 로그
- 열람 로그
- 출력 로그
- 만료 로그
- 재발송 로그

로그는 단순 이벤트 기록이 아니라 운영 상태를 복원하는 원장이어야 한다.

로그 기준 원칙:

- 행위자
- 대상 문서
- 대상 버전
- 전달 채널
- 상태 변화 전후
- 발생 시각
- 요약 메시지

### 4-5. Rollout

목표는 한 번에 다 갈아엎지 않고, 작업 단위를 작게 배포하는 것이다.

- 1차: 문서 허브 IA 정리
- 2차: 공통 발송 모달 도입
- 3차: 상태 분리 및 row 정리
- 4차: 출력/PDF/링크 정책 정리
- 5차: 로그와 리마인드 규칙 연결

롤아웃 원칙:

- 기존 화면은 바로 삭제하지 않는다.
- 새 흐름이 준비되기 전까지는 기존 진입점을 유지한다.
- 사용자 혼란을 줄이기 위해 기능 플래그 또는 점진 노출을 우선한다.

## 5. 우선순위 티켓

### P0

- 문서 허브의 상단 작업 모드를 `만들기 / 발송하기 / 보기·정리`로 정의한다.
- 전역 문서 허브와 거래 상세 문서 탭의 역할을 분리한 뒤 중복 액션을 정리한다.
- 문서 row에 `최신 버전`, `최근 발송`, `최근 열람`, `다음 액션`을 넣는다.
- 발송 상태와 문서 상태를 분리한 스키마 초안을 만든다.

### P1

- 공통 발송 모달을 만든다.
- 링크 복사와 PDF 열기를 공통 액션으로 통일한다.
- `견적 / 계약 / 영수증`의 생성 진입점을 문서 허브 안에서 통합한다.
- 출력용 보기와 링크용 보기를 분리한다.

### P2

- 재발송, 만료 연장, 출력 허용 조정 같은 후속 액션을 같은 패널에서 다룬다.
- 열람 이력을 상세 패널에서 읽을 수 있게 한다.
- 문서 정리 큐를 상태 기반 필터로 구현한다.

### P3

- 자동 추천, AI 보조, 채널 최적화, 예약 발송을 붙인다.
- 운영 지표 기반의 다음 액션 추천을 추가한다.

## 6. 리스크와 보류 항목

### 리스크

- 전역 문서 허브와 거래 상세 문서 탭이 다시 중복되면 사용자는 같은 작업을 두 번 찾게 된다.
- 문서 상태와 발송 상태를 섞으면 운영 로그가 맞지 않는다.
- 출력/PDF/링크의 의미가 섞이면 고객 공개 버전 관리가 흔들린다.
- 발송 대상과 발송 버전의 기본값을 정하지 않으면 재발송 실수가 늘어난다.
- 모바일에서 row 액션이 많아지면 정리 경험이 오히려 나빠질 수 있다.

### 보류 항목

- 자동 재발송
- 채널 추천
- 예약 발송
- 템플릿 빌더
- 세부 권한 분기
- 대량 문서 처리

보류 항목은 v1의 핵심 루프가 안정된 뒤 붙인다.

## 7. 바로 다음 액션

1. 선행 결정사항 8개를 먼저 고정한다.
2. IA와 화면 블록 정의를 승인한다.
3. 공통 발송 모달과 상태 분리 스키마를 먼저 구현한다.
4. 문서 허브와 거래 상세의 중복 액션을 정리한다.
5. 로그와 롤아웃을 붙여 운영 안정성을 확보한다.
