## 1. 정체성 (Identity)

- **한 줄 정의**: 클래스인 하드웨어(전자칠판/IFP·카메라·스탠드·부자재)의 **재고·입출고·예상 출고를 한 화면에서 추적하고 기록하는 운영 콘솔**.
- **주인공 엔티티**: 품목(`item`) · **물류 번호(lot)** · 입출고 기록(`movement`) · 예상 출고(`planned`) · 샘플 유닛(관리번호).
- **진실의 원천**
  - 수량은 `hardware_movements` **원장**이다. 재고는 따로 저장하지 않고 원장에서 파생 계산한다. 기록은 수정/취소(void)로 보정한다.
  - 사무실·샘플 재고는 **샘플 유닛**이 정본이다(§3-8). 원장의 사무실·샘플 잔량은 교차 확인용이다.
- **두 데이터 출처**
  - `admin_manual`: 어드민에서 수기 입력
  - `sheet_import`: Google 시트(`branch_hw_*` 미러) → 가져오기 RPC가 시트 이관분을 교체
- **무엇이 아닌가**: 단순 수량 입력표나 파트너 목록이 아니다. **물량 진실표 + 운영 워크플로**(입고→예약→확정→출고/취소)다.
- **사용 맥락**: 본사 운영자가 데스크톱과 모바일(창고·현장)에서 빠르게 기록한다. 모바일 입력을 1급으로 본다.

## 2. UI 구조

### 2-1. 하위탭 (헤더 탭 스트립, 3개)

| 탭 | 정체성 | 구성 |
| --- | --- | --- |
| **홈** | 현황 + 예상 출고 워크플로 | 요약 밴드 5칸(창고·가용·예정 대기·부족/주문 검토·시트 이관 신선도) · 이관 경고 · **예상 출고 큐**(등록·부분/전체/선택 일괄 확정) · 품목 카드·현재 재고(lot 칩) · 판매 요약 · 검색 · **사무실·샘플 재고**(2-4) · 샘플 트래커 · 알림 · 스냅샷 복원 |
| **입출고** | 기록 진입 | 입고 · 물량번호(lot별 입고 목록) / 출고 · 기간 집계. "빠른 기록"은 입고 보기에서 **입고표**(2-3), 출고 보기에서 빠른 기록 시트(2-2)를 연다 |
| **내역** | 전체 원장 | 유형·제품 칩 필터 · lot/금액 표시 · 행별 수정·취소 |

### 2-2. 빠른 기록 시트 (슬라이드오버)

- 우측 드로어(모바일은 전체 폭). 재고 행·예상 큐·제품 칩·우하단 FAB가 같은 시트를 그 자리에서 미리 채워 연다(탭 전환 없음).
- 담당 범위: **출고(판매·배송 예정·샘플 대여)**, 상세 모드 5종(샘플 반환·샘플 배정·고객 반납·수리·실사 조정), **기존 기록 수정(editingId)**.
- 새 입고는 받지 않는다. 시트의 "입고" 탭을 누르면 입고표(2-3)로 넘어간다. 담아 둔 바구니는 닫아도 유지된다.
- 접근성: `role="dialog" aria-modal`, Escape 닫기, body 스크롤 잠금, 포커스 트랩·복원, 백드롭 클릭. 안쪽(고객사·품목 목록)에서 먼저 처리한 Escape는 시트를 닫지 않는다(`defaultPrevented`).
- 모드: 단건 / 작업건(바구니). 판매 출고는 단건 저장만 CRM 오더 확인 게이트를 탄다.
- **고객사는 고른다**(2026-09-20, `CustomerPicker`): 도착(고객사)·샘플 대여 고객사는 자유 텍스트 + datalist가 아니라 검색 콤보박스다. 제안은 **최근 출고 순**이고, 목록에 없는 이름은 "새 고객사로 기록" 줄로 그대로 저장된다. 저장 형식은 그대로 `toLocation` 문자열이다.
- **품목도 고른다**(`ProductPicker`): 주요 4종 칩 아래의 전 품목 선택이 검색 목록이다. 목록에 없는 품목은 "직접 입력"이 담당한다(품목 생성 경로는 하나).
- **저장은 기다리지 않는다**: 저장 응답의 원장 줄을 즉시 화면에 넣고 재검증은 배경에서 돈다. 재고·가용·알림 등 파생 숫자는 재검증이 도착할 때 바뀐다(서버 계산이 정본).
- **키보드**: 시트에서 Cmd/Ctrl+Enter 저장. 목록 화면에서 `i`=입고표, `o`=출고 시트(입력 중·오버레이·예정 선택 중에는 동작하지 않는다).
- **저장 대기 바구니는 새로고침에도 남는다**: localStorage에 24시간 보관하고 줄별 형태를 다시 검사해 되살린다(§2-7).

### 2-3. 한 화면 입고표 (`InboundSheet`)

2026-09-15 운영자가 시안 A를 골랐다. 새 입고는 전부 이 시트로 연다. 진입점은 입출고 탭 "빠른 기록"(입고 보기), 재고 표·알림·검색의 "입고" 퀵버튼, 빠른 기록 시트의 "입고" 탭이다.

- **위에서 한 번 고르는 값**
  - 물량번호: 새 물량 추천, 최근 lot 칩(날짜·대수), 직접 입력. 추천은 날짜가 가장 최근인 `영문+숫자` lot의 번호를 올린다(C2→C3, H8→H9). `H7(과사람)`·`FY24-25`·`Sample`은 올리기에서 제외한다.
  - 입고일: 오늘·어제(로컬 날짜) · 수입자 칩 · 기본 보관처 칩(오산 창고·인천 더조은·클래스인 사무실·고객사 직송)
- **품목 표**: 품목 | 수량 | 단가 USD | 금액 | 보관처
  - 단가는 최근 입고 단가로 미리 채우고, 금액은 자동 계산한다. 보관처는 행마다 바꿀 수 있다.
  - 주요 품목 5종이 먼저 나오고, 나머지는 "품목 추가"로 넣는다.
- **보조 기능**
  - "{직전 lot} 구성 불러오기"
  - "엑셀에서 붙여넣기": 품목 이름은 정확 일치만 인정한다(T1이 DT1·T1(promoted)에 걸리지 않음).
  - Enter로 다음 행 이동, 한글 조합 중 Enter 무시, Cmd/Ctrl+Enter로 저장
- **저장**
  - `POST /api/admin/hardware/movements` 한 번으로 보낸다. 일부만 실패하면 실패한 행만 시트에 남긴다.
  - 보관처 라벨은 `toLocation`(재고 위치, 서버가 정규화)과 `storageLocation`(원문) 양쪽에 싣는다.
  - 사무실 보관 행이 있으면 "사무실 입고분 N대를 샘플 유닛으로 등록"(기본 켬)이 행마다 office 상태 유닛을 발급한다.
- **이관 지연 안내**: 시트 이관이 신선도 기준을 넘기면(홈 스트립과 같은 판정) 새 물량 추천 아래에 "그 뒤에 들어온 물량번호가 빠져 있을 수 있다"는 안내를 붙인다. 원장에 C2가 없어 C2를 추천한 사례(2026-09-15)에서 나왔다.
- **작성 중 초안 복구**(2026-09-20): 수량을 적은 줄이 있으면 자동 보관하고, 다시 열 때 "작성 중이던 입고표 {물량번호} N줄" 배너로 [이어서 작성] / [새로 시작]을 **사람이 고른다**. 조용히 되살리지 않는다 — 어제 쓰다 만 물량번호가 오늘 저장으로 새면 원장이 틀어진다. 저장에 성공하면 보관 초안을 지운다(§2-7).
- **모델**: 순수 함수 `inbound-sheet-model.ts`에 있다. 테스트는 `tests/admin/hardware-inbound-sheet-model.test.ts`.
- 금액(CNY)·메모·상태 같은 드문 필드는 기존 기록 수정(빠른 기록 시트 단건)에서 고친다.

### 2-4. 사무실·샘플 재고 섹션 (`OfficeSamplePoolSection`)

홈의 옛 "재고 위치 맵" 자리를 2026-09-15에 대체했다. 규칙은 §3-8에 있다.

- 타일 3개: 판매 재고·창고(보유·가용·배송 예정) / 클래스인 사무실(보유·가용·전시) / 나간 샘플(대여·90일+·회수 예정 14일)
- 품목 표: 창고·가용 | 사무실·가용·전시 | 샘플·90일+ | [대여] [반납]
  - 대여·반납은 빠른 기록의 샘플 프리셋으로 연다.
  - 원장과 차이가 있으면 "원장과 N대 차이" 배지를 붙인다.
- 행을 펼치면 유닛 목록이 나온다. 여러 대를 골라 **전시로 / 사무실 보관으로 / 상태 정정(메모 필수)**을 한 번에 한다.
- 집계는 순수 모델 `office-sample-pool.ts`가 한다. 판촉형은 합계에서 빼고 따로 표시한다.

### 2-5. 보조 오버레이

- **CRM 오더 확인 모달**: 실제 출고 저장 시 CRM 실제 오더와 연동할지 확인한다(배송 예정 등록 시에는 뜨지 않음).
- **기록 취소 확인 모달**: 사유 입력 + 파괴적 액션 스타일.
- **샘플 유닛 상세 시트**: 타임라인·메모. 대여·반환·전시로·사무실 보관으로·판매 전환·수리·폐기·정정(상태 바로잡기 포함).
- **샘플 트래커 원장 백필 확인창**: "원장 차이 N대 확인" → 품목별 수량 목록 → 모두 등록.

### 2-8. CRM 오더 대사 (`CrmOrderBacklogSection`)

홈 예상 출고 큐 **바로 위**. 등록할 것을 먼저 보고 그 아래에서 확정하는 순서다. 기본 접힘이고, 펼칠 때 한 번 조회한다(원장 스캔이 붙어 대시보드 기본 왕복에 얹지 않는다).

- 목록 = CRM 딜 라인·견적 라인 중 **참조번호가 원장에 없는 것**. 품목·수량이 있어야 오른다(외부 CRM 오더는 품목·수량이 없어 제외).
- 행에서 `[예정 등록]` 한 번에 배송 예정을 만든다 — 고객사·품목·수량·참조번호·CRM 링크가 그대로 들어간다. 새 엔드포인트가 아니라 `POST .../movements`를 쓴다.
- **겹침 의심 배지**: 시트 이관 행에는 딜 참조가 없어 참조로 대사할 수 없다. 고객사·품목이 맞는 실제 출고가 원장에 있으면 배지를 붙이고 **첫 클릭은 경고만** 한다("그래도 예정 등록"을 다시 눌러야 저장). 시트가 이미 실어 온 물량을 다시 등록하면 §8-6 자동 정리가 닿지 않는 이중 계상이 되기 때문이다.
- 같은 CRM 오더를 두 번 등록하는 것은 서버가 막는다(`ensureNoDuplicateCrmMovement`).

### 2-7. 작성 중 입력 보관 (`inventory/draft-storage.ts`)

브라우저에만 남는 값이고 원장이 아니다. 규칙은 셋이다 — 스키마 버전이 다르면 버리고, 24시간이 지나면 버리고, storage가 막힌 환경(프라이빗 모드·용량 초과)에서는 조용히 기능만 포기한다.

| 대상 | 되살리는 방식 | 이유 |
| --- | --- | --- |
| 입고표 | 배너로 [이어서 작성]/[새로 시작] | 어제 물량번호가 오늘 저장으로 새면 원장이 틀어진다 |
| 저장 대기 바구니 | 조용히 | 시트가 "저장 대기 N건"으로 이미 보여 준다. 줄별 최소 형태(품목명·유형·양수 수량·시리얼 배열)를 다시 검사해 옛 값이 저장 요청에 실리지 않게 한다 |

빈 입고표는 보관하지도, 보관된 초안을 지우지도 않는다(열자마자 덮어쓰면 복구할 것이 사라진다). 복원은 렌더 중이 아니라 마운트 후 1회 읽는다(하이드레이션 불일치 방지).

## 3. 기능 (Functions)

### 3-1. 입출고 프리셋 (`ENTRY_PRESETS`, shared.tsx)

| 프리셋 | 유형 | from → to | 비고 |
| --- | --- | --- | --- |
| 판매 출고 | outbound | 창고 → 고객 | 저장 시 CRM 오더 확인 |
| 배송 예정 | outbound(예정) | 창고 → 고객 | 가용에서 미리 차감(예약) |
| 샘플 대여 | outbound | 사무실(기본)·창고 → 샘플 | 고객사 필수, 사무실 가용 유닛 칩에서 고름 |
| 입고 | inbound | → 보관처 | **입고표**로 연다(2-3) |
| 샘플 반환 | return | 샘플 → 사무실 | 상세 모드 |
| 샘플 배정 | transfer | 창고 → 사무실 | 상세 모드, 수량만큼 사무실 유닛 발급 |
| 고객 반납 | return | 고객 → 창고 | 상세 모드 |
| 수리 | repair | 창고 → 수리 | 상세 모드 |
| 실사 조정 | adjust | ± 창고 | 상세 모드 |

### 3-2. 입고

입고표(2-3)가 품목·수량·입고일·물류No(lot)·단가(USD)·금액(USD)·보관처·수입자·시리얼을 한 번에 받는다. 서버는 lot 형식·중복 입고를 검사하지 않는다. 매칭되지 않은 품목 이름은 새 품목으로 만든다.

### 3-3. 예상 출고 워크플로 (핵심)

- **등록**: 배송 예정 movement를 만든다. 가용에서 차감되고 홈 큐에 뜬다.
- **확정**: 예정을 실제 출고로 **전환(convert)**한다. 출고일을 고르고, **부분 수량 확정**도 된다(출고 N대 생성 + 잔여는 예정 유지).
- **선택 일괄 확정(2026-09-14)**
  - 행·딜 체크박스(Shift 범위 선택), 빠른 선택("전체 N건"·"30일+ 미확정"·해제), 하단 작업 바의 공통 확정일로 **순차** 확정한다.
  - 순차인 이유: 각 확정이 로트 잔량을 바꾸므로 다음 건의 배정이 앞 건을 반영해야 한다. 건별 권한 검사(`hardware.finalize`)와 감사 로그도 그대로 남는다.
  - 실패 건은 사유를 행에 남기고 선택에 남겨 재시도한다.
- **로트가 모자라도 확정을 막지 않는다(운영자 결정 2026-09-14).**
  - 해석 가능한 만큼 FIFO로 배정하고, 나머지는 로트 미지정(`lot_no` NULL) 한 줄로 기록한다.
  - 로트 기록이 전혀 없는 품목(OPS·케이블 등)도 출고를 남길 수 있다.
  - 운영자가 로트를 **직접 지정**한 경우만 그 로트 잔량을 검사한다.
- ⚠️ 시트 이관분을 어드민에서 확정한 뒤 교체 가져오기를 하면 같은 물량이 두 번 잡힌다(§8-6). 정책 결정 전에는 **가져오기를 먼저 하고, 그 뒤 시트에 아직 예정으로 남은 행만 확정**한다.

### 3-4. lot(물류 번호) 추적

- lot 키는 수기 `lot_no`이고, 시트 행은 `reference_no`(물류No)로 폴백한다. 운영 원장(시트 이관)은 `lot_no`가 비어 있고 로트는 `reference_no`에만 있다(2026-09-14 실측 385건 전부).
- **lot 잔량 정본 = `resolveHardwareLotBalances`**(`lib/repositories/hardware-inventory.ts`). 화면 표시, 새 출고 자동 배정, 예정 확정 배정이 **모두 이 함수 하나**를 쓴다. 규칙(순서 무관·결정적):
  1. 로트 키가 있는 이동을 로트별로 합산한다: 입고/반납(+) · 출고(예정 포함, −) · 보정(방향대로) · 이동/수리(0).
  2. **음수가 된 로트의 초과분은 FIFO(가장 오래된 양수 로트부터)로 흡수**한다. 설치 기록에 현행 세대 이름을 붙여 로트를 넘겨 출고한 물량(예: STD1 H8 입고 19 · 출고 28)은 실제로 옛 로트에서 나간 것이다.
  3. **로트 없는 감소분(출고·음수 보정)도 FIFO로 차감**한다. 로트 없는 증가분은 귀속시키지 않는다.
- FIFO 순서: `FY` < `H숫자` < 그 밖(`C1`·`C2`·`Sample` 등, 처음 본 날짜순).
- 예전 규칙(단순 합산 + 음수 숨김)은 실물에 없는 옛 로트를 재고로 보여줬다(STD1 H4·H5·H6, T1 H6. 운영자 확인: 실제는 H8·C1뿐). 날짜순 재생을 쓰지 않는 이유는 시트 원장에 출고일이 입고일보다 앞서는 행이 흔하기 때문이다.

### 3-5. 기록 수정·취소

- **수정(update)**: `admin_manual`·미전환·미취소 기록만. 내역·예상 큐의 `수정`은 새 기록이 아니라 같은 행을 갱신한다. 실현된 기록 수정은 `hardware.finalize` 권한이 필요하다.
- **취소(void)**: 사유와 함께 무효화한다. 시트 이관 기록은 직접 취소할 수 없다(가져오기가 관리).

### 3-6. 시트 가져오기 · 재고 계산 · 알림

- **가져오기**: 헤더의 "싱크·백업 후 가져오기"가 Google 시트 강제 싱크 → 스냅샷 백업 → `hardware_movements`의 시트 이관분 교체를 한다.
  - 자동이 아니다. 크론은 시트 → `branch_hw_*` 미러까지만 매일 돌고, 원장 반영은 이 버튼을 눌러야 일어난다.
  - 가져오기 전 스냅샷은 홈 맨 아래 "스냅샷 복원"에서 되돌릴 수 있다.
  - **가져오기 뒤 정리(§8-6)**: 시트 행에서 전환된 어드민 확정을 사유와 함께 취소한다(교체 모드만). 결과 문구에 건수가 붙는다.
- **재고 파생**: 원장에서 위치별 잔량·예상 가용(예정 차감)·30일 출고·주문 시점(리드타임 반영)을 계산한다(`computeHardwareStockRow`).
- **알림**: 부족·주문 검토·배송 예정·원장 점검 필요(판촉형 음수 등).

**시트 → 원장 규칙** (2026-09-14 운영 시트 실측으로 확정) — `buildHardwareSheetImportRows`(순수 함수)·`parseStock`

1. **재고현황 입고·출고 블록은 로트 열 합이 정본이다.**
   - "합계" 셀은 시트 수식이라, 새 로트 열을 붙일 때 범위를 늘리지 않으면 조용히 틀린다.
   - 실측: 86" IFP 입고 합계 344인데 로트 열 합은 359(C2 15대 누락). 그래서 현재고가 30이 아니라 15로 싱크됐다.
   - 두 값이 다르면 로트 열 합을 쓰고, `raw.sheet_total_mismatch`에 시트 합계를 남긴다.
   - 재고 현황 블록(OPS "사무실 보유" 등)은 로트 열에 글자가 있어 합계 셀을 그대로 쓴다.
2. **재고현황 출고는 진행 상태를 가리지 않고 로트 열별로 합산한다.** 로트가 적힌 "배송 예정" 행도 이미 빠진 수치다.
   - 실측: 75" IFP H8 출고 10 = 설치 완료 5 + 배송 예정 5. 같은 형태가 6개 로트에 16대 있었다.
   - 원장은 예정 출고를 창고에서 빼지 않고 가용에서 따로 뺀다. 그래서 **보정 목표 = 시트 현재고 + 시트가 이미 뺀 로트 지정 예정 수량**이다.
   - 로트 없는 예정(날짜·물류No 없는 수주 대기, 실측 67행·163대)은 시트 재고현황에 안 잡히므로 더하지 않는다.
3. **30일 출고 추세는 실제 출고만, 날짜가 있는 시트 행만 센다.** 예정은 가용에서 이미 빠진다. 날짜 없는 시트 행은 `created_at`(임포트 시각) 폴백 때문에 가져올 때마다 "최근 출고"가 됐다(드라이런 86" IFP 9 → 93).
4. **입고·출고 탭은 행 끝을 열어 읽는다**(`A1:Z`). 예전 고정 500행이면 약 한 달 뒤 가장 최근 행부터 에러 없이 잘릴 참이었다(출고 409행, 37일에 94행 증가).
5. 시트 수입자는 회사명이라 위치 정규화를 거치지 않는다(`from_location` 원문).

### 3-7. 위치 정규화 (`normalizeLocationName`)

쓸 때와 읽을 때(잔량 키) 모두 적용된다. 규칙을 바꾸면 기존 행도 즉시 새 위치로 읽히므로 대시보드 캐시 키를 함께 올린다(현재 `hardware-dashboard-v3`).

1. 샘플·대여·데모·demo·sample → **샘플** (가장 먼저 판정)
2. 사무실·office·**클래스인·ClassIn** → **사무실** (2026-09-15). 시트 보관처 "클래스인"(본사 사무실·쇼룸 보관분, 원장 28대)이 예전에는 이름 없는 별도 위치로 남아 어디에도 안 보였다.
3. 수리 → **수리 표기에만** 맞춘다: repair, A/S, 독립 단어 AS(·AS 센터), `수리`(뒤에 학원·논술·영역·수학·과학·탐구·교육·아카데미가 오면 제외). 예전 `/수리|a\/?s/`는 "ClassIn"·"Master"의 as와 "대치수리학원"을 수리 위치로 보냈다.
4. 창고·warehouse·인천 더조은·FPL → 창고, 고객·고객사 → 고객, 나머지는 원문 그대로(고객사 이름)

### 3-8. 사무실·샘플 재고 풀 — 유닛(관리번호) 기준

운영자 결정(2026-09-15): 사무실·샘플은 유닛으로 세고, 전시 유닛은 가용에서 뺀다.

- **상태**
  - `office` = 사무실 보관 = **가용**(대여할 때 여기서 고른다)
  - `showroom` = 전시·사내 사용(쇼룸·KC인증 등) = 사무실 보유지만 가용이 아니다
  - `loaned` = 대여 = 나간 샘플
  - `repair` · `converted`(판매 전환) · `retired`(폐기)
- **원장은 교차 확인용이다.** 시트는 샘플이 사무실에서 나갔는지 기록하지 않는다. 같은 FY24-25 사무실 샘플이 입고(보관처 클래스인) 16대와 출고(목적지 클래스인, Sample) 15대로 두 번 적힌 사례도 있다. 원장 수량으로는 사무실 재고를 맞출 수 없다.
- **상태 전이** (`SAMPLE_EVENT_TRANSITIONS`, `lib/repositories/hardware-samples.ts`)
  - loan: office·repair → loaned. 전시 중에는 먼저 사무실 보관으로 옮겨야 한다.
  - return: loaned → office
  - showcase: office → showroom
  - store: showroom·repair → office
  - repair·convert·retire는 showroom에서도 허용한다.
  - adjust에 `nextStatus`를 주면 상태를 정정한다. 이때 사유 메모가 필수다.
  - 사무실로 들어오는 전이는 고객·대여일·회수 예정일을 비운다.
- 샘플 API는 규칙 오류를 400/404/409로 응답하고 감사 로그(`hardware.sample.*`)를 남긴다. 유닛 액션은 원장 기록을 만들지 않는다.
- **원장 백필은 확인창을 거친다.** 사무실 정규화 뒤 원장 사무실 잔량이 28대 늘어, 원장과 유닛의 차이가 32대가 됐다. 예전처럼 한 번 누르면 실물 없는 유닛이 생길 수 있었다. 정합 대조의 사무실 유닛 수에는 전시 유닛도 센다.
- **운영 데이터(2026-09-15)**: 유닛 33대가 **전부 loaned**다(고객 미상 16, 클래스인 쇼룸 2, 클래스인 (KC인증) 1). 그래서 지금 사무실 가용은 0으로 보인다. 정리 방법은 §8-4.
- 시트 가져오기의 창고 보정은 사무실 보관 유닛을 빼지 않는다. 유닛 상태가 정리된 뒤 재검토한다.

RPC
- 확정: `confirm_hardware_planned_movement_v3(uuid,text,date,int,jsonb)` → `_v2` → 레거시 순으로 앱이 폴백한다. v3는 **앱이 계산한 로트 배정을 받아 기록**하고 로트 미지정을 허용한다. v2는 SQL 내부 FIFO라 `lot_no`만 본다.

API
- `GET /api/admin/hardware` — 대시보드(items/stock/movements/recentOutbound/plannedMovements/alerts/totals/importRun/viewer)
- `POST /api/admin/hardware/movements` — 기록 생성(단건 또는 `{movements:[...]}` 최대 50줄, 줄별 결과 201/207/422). 배치는 **왕복 한 번**이다(2026-09-20, `createHardwareMovementsBatch`): 품목 해결 1회 · CRM 중복 조회 1회 · 품목 원장 읽기 품목당 1회 · INSERT 1회 · 캐시 무효화 1회. 로트 배정은 앞 줄이 만든 행을 원장 뒤에 이어 붙여 같은 해석기로 다시 계산해 줄 단위 저장과 결과가 같다. 한 번에 넣지 못하면 줄 단위 INSERT로 물러나 부분 저장을 지킨다.
- `PATCH /api/admin/hardware/movements/[id]` — `{action: confirm-planned | void | update}`(confirm은 `confirmQty` 옵션)

## 7. 추가형(누적) 시트 인제스트 — 설계 · cutover 런북

목표: 시트를 매번 통째 교체(delete+insert)하지 않고 동기화가 **누적**되게 한다. 대시보드는 이미 DB(`hardware_movements`) 기준이라 바뀌는 곳은 인제스트뿐이다. 멀티에이전트 워크플로 + 적대적 검증으로 설계를 확정했다(검증 4종 모두 초기안을 breaks 처리).

핵심 설계
- 시트엔 안정적 행 키가 없다(물류No 공란/임시·lot 다행, 비정규 날짜). 콘텐츠 키 UPSERT는 **서로 다른 출고를 묵음 병합(과소집계)**할 위험이 있다.
- 해법은 **fingerprint(정체성) + digest(콘텐츠)**다.
  - `source_key = hash(제품·날짜·물류No·그룹 내 안정 ordinal)`. 같은 그룹은 ordinal로 항상 유일하다(구성상 충돌 불가).
  - `source_digest` = 콘텐츠 해시(편집 감지). 재고현황 보정은 제품당 1행(product-only 키).
- `merge_hardware_sheet_import` 4-pass: 신규 INSERT / 시트-tombstone 부활 / 변경분 in-place UPDATE / 사라진 행 soft-tombstone.
  - **부재가 40%를 넘으면 fail-closed**로 중단한다.
  - converted·human_locked·다른 사유로 void된 행은 건드리지 않는다. admin_manual과 무관하다.
- 부분 확정 잔여행은 `confirm`이 `human_locked_at`을 찍어 머지가 덮어쓰지 않는다.
- 플래그 `HARDWARE_SHEET_ADDITIVE_MERGE`(기본 off). 롤백은 off(구 `replace`/`restore` RPC 그대로).
- ⚠️ 머지 RPC도 금액 컬럼을 넣지 않는다(§6-2 merge_costing 미적용). cutover 전에 금액 마이그레이션부터 적용한다.

cutover 런북(코드 배포 후, 순서 중요)
1. 코드 배포(플래그 off). 머지 RPC 마이그레이션은 이미 라이브다.
2. **백필**: 가져오기 1회(아직 replace 경로). 기존 행이 fingerprint `source_key`로 다시 기록된다. 충돌하면 unique index가 요란하게 실패한다(구성상 충돌 없음, 안전망).
3. `HARDWARE_SHEET_ADDITIVE_MERGE=1`
4. 가져오기 재실행 → merge 경로. 카운트 `{inserted,updated,tombstoned,revived}`를 확인한다(첫 머지는 digest 백필로 updated가 큼 = 정상).
5. 패리티 확인: 직전 replace 결과와 첫 merge 결과의 `warehouseStock/availableStock/plannedOut/lotBalances`가 같아야 한다.
- 문제가 생기면 즉시 플래그 off. 다음 가져오기가 replace로 자가 치유한다.

최적화(누적이 천장을 없애므로 fast-follow): `listAllHardwareMovements` 투영/기간 플로어 또는 `HARDWARE_INVENTORY_CACHE_TAG` 캐시 연결, 스냅샷 retention RPC.

## 8. 운영 조치 체크리스트 (순서대로)

"승인"은 운영 DB나 원장을 바꾸는 작업이라 실행 전에 운영자 확인이 필요하다는 뜻이다.

1. **운영 배포(승인)**: 위 코드는 main 에 있고 Preview 빌드도 성공했다. main 푸시는 Preview 만 만들므로, 운영은 Vercel 배포 API(`POST /v13/deployments`, `target: "production"`, `gitSource.ref: "main"` + 커밋 sha)로 따로 빌드한다. 가져오기 규칙 수리가 배포돼야 3번 가져오기가 맞는 숫자로 들어간다.
2. **시트 정리(사람)**
   - 재고현황 86" IFP 입고 "합계" 수식 범위에 C2 열을 넣는다. 코드는 이미 로트 열 합을 쓰지만, 시트 자체 합계도 틀려 있다.
   - 2025-02~03 날짜의 로트 지정 "배송 예정" 10행을 정리한다. 같은 물류No·제품의 설치 완료 행이 모두 있어 묵은 행으로 보인다.
3. **시트 가져오기(승인)**: 헤더 "싱크·백업 후 가져오기". 스냅샷이 먼저 뜬다.
   - 드라이런(쓰기 0, 수리된 코드) 예상 가용: 86" IFP 18 → **−46**, STD1 17 → −8, 75" IFP 1 → −14, T1 30 → −1.
   - 마이너스는 오류가 아니라, 날짜 없는 수주 대기(갈무리국어 86" 40대 포함)가 예정으로 들어오기 때문이다. 주문 검토 신호로 읽는다.
   - 가져오기를 해야 원장에 C2가 생기고, 입고표의 새 물량 추천이 C3로 바로잡힌다.
4. **전시 상태 마이그레이션 적용(승인) → 샘플 유닛 정리(운영자)**
   - §6-2 `20260915_hardware_sample_showroom_status.sql`을 적용한다.
   - 홈 "사무실·샘플 재고"에서 행을 펼쳐 정리한다: 클래스인 쇼룸 2대·KC인증 1대 → "전시로"(또는 상태 정정 → 전시), 고객 미상 16대 → 실사 후 "사무실 보관" 또는 실제 고객으로 정정.
   - 샘플 트래커의 "원장 차이 N대 확인"으로 한꺼번에 등록하지 않는다. 유닛 정리가 먼저다.
5. **금액·복원 마이그레이션 3종(승인)**: §6-2 순서대로. 적용 후 가져오기를 한 번 더 하면 금액 컬럼이 채워지고 "raw 백업에서 복구" 경고가 사라진다.
6. **이중 계상 정책 — 결정됨: "가져오기 때는 시트가 이긴다"** (운영자 결정 2026-09-21, 구현 완료)
   - 문제: `replace_hardware_sheet_import`는 시트 이관 행을 통째로 지우고 다시 넣는다. 전환된 예정 행도 지워지지만, 어드민 확정으로 생긴 `admin_manual` 출고는 남는다. 그래서 시트 행을 어드민에서 확정한 뒤 가져오면 같은 물량이 두 번 잡힌다. 시트에 안정적 행 ID가 없어 행 단위 대조로는 풀 수 없다.
   - **적용**: 교체 가져오기가 끝난 뒤, **시트 행에서 전환된 `admin_manual` 기록만** 사유와 함께 void한다(`converted_from_movement_id`가 `sheet_import` 행을 가리키는 것). 지우지 않고 취소로 남겨 되돌릴 수 있게 한다. 결과에 "취소한 어드민 확정 N건"을 실어 화면 문구로 보여준다.
   - 순서가 규칙이다: 링크는 가져오기가 시트 행을 지우면 따라갈 수 없으므로 **대상은 가져오기 전에 모으고, 취소는 가져오기 성공 뒤에** 한다. 가져오기가 실패하면 어드민 확정은 그대로 남는다.
   - 교체 RPC는 건드리지 않았다 — 앱 층에서 처리한다. 미적용 마이그레이션(§6-2의 금액 3종)이 같은 함수를 재정의하고 있어, RPC 본문을 다시 쓰면 적용 순서에 따라 결과가 갈린다.
   - **추가형 머지 모드에서는 하지 않는다**: 머지는 시트 행을 지우지 않고 확정된 행을 `human_locked`로 보호한다(§7).
   - 링크가 없는 어드민 기록(사람이 직접 만든 예정·출고)은 자동으로 건드리지 않는다. 시트와 겹치는지 알 방법이 없기 때문이다 — 대신 **등록 시점에** 홈 "CRM 오더 대사"가 고객사·품목이 겹치면 배지로 막는다(§2-8).
