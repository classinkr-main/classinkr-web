# Classin 3대 블로커 의사결정 지원서

> **생성일: 2026-07-03**
> **결정 지원 문서 — 대표 결정 대기**
>
> 이 문서는 **확정이 아니라 결정 지원**이다. 참모(전략팀)가 권고안·근거·반대편(steelman)을 제시하고, **대표가 이번 주에 3개를 고른다**. 각 결정은 되돌리기 난이도가 다르고 서로 물려 있으므로, "무엇을 먼저"가 "무엇을"만큼 중요하다.
> 표기 규약: 코드 실측으로 확인한 사실은 그대로, 계측·정책상 미확정 추정은 **(가정)** 으로 남긴다 — 대표가 검증할 지점이다.

## 0. 왜 이 3개가 최상위 블로커인가 + 권고 결정 순서

### 0.1 세 결정의 공통 성격 — "만들지 말고 켜라"

세 블로커의 코드 실측 결과는 놀랍도록 일관된다. **셋 다 대체로 '무엇을 새로 지을까'가 아니라 '이미 지어진 것을 켤 권한/정책/영속성을 확보할까'다.** 자동화 설계 플랜(`classin-automation-design-plan-2026-07-03.md`)이 6개 워크스트림(W1~W6)의 라스트마일을 세 지점에서 동시에 막고 있다고 지목했는데, 실측해 보면 그 라스트마일 코드는 대부분 이미 배선돼 있고 막힌 것은 **① 정본 라벨(어느 숫자를 믿을지) ② 환경변수·채널정책 ③ API 키·영속 저장** 뿐이다.

| 블로커 | 실측된 '막힌 진짜 이유' | 이미 배선된 것 |
|--------|------------------------|----------------|
| **A. 매출 정본** | `crm_orders` 코드 0건(Grep 확인), 앱은 `branch_rev_deals`(시트 미러)만 읽음 → **어느 숫자를 정본으로 부를지 선언이 없음** | `lib/admin-crm-revenue.ts`가 이미 색분해 3단 확도로 집계, `branch/pipeline/route.ts`가 `listBranchRevDeals` 직결 가동 중 |
| **B. 발송 서비스** | Resend 환경변수 2개 미설정(simulation 모드), 채널정책 미확정 | `lib/email.ts`(3-tier), `lib/notifications/emit-event.ts`(wecom/kakao/email 라우팅), `lib/server/lead-response-alerts.ts`(W2가 이미 `wecom_webhook` 발송 배선) |
| **C. 채널톡 적재** | `CHANNEL_TALK_ACCESS/SECRET` 미설정, 저장소가 JSON 폴백(4바이트 빈 배열 실측) | `lib/channel-talk-api.ts`, `lib/channel-talk-sync.ts`, `app/api/cron/channel-talk-sync/route.ts`(매일 00:15 UTC 크론), 어드민 수동 sync 버튼 |

### 0.2 왜 이 셋이 '최상위' 블로커인가

**하드 선행(hard prerequisite)의 밀도** 때문이다. 각각이 여러 워크스트림의 **분모·입력·라스트마일**을 동시에 결정한다.

- **A(매출 정본)** 는 자동화 설계 §0.4·§2.5·§6이 "6개 워크스트림의 하드 선행 블로커"로 명시한 지점. 편중(top10 매출 비중)·채널 LTV·커버리지·매출 델타 브리프가 **모두 이 정본 위에 formula를 얹는다.** 미결 시 W1/W3/W5/W6이 **각자 다른 분모로 굳어** 재작업이 불가피 — 되돌리기가 특히 어렵다.
- **B(발송)** 는 §D2에서 4개 워크스트림(W1 활성화 넛지·W2 hot-lead 알림·W3 인텐트 드립·W6 브리프 발송)의 **라스트마일을 동시에 블록.**
- **C(채널톡 적재)** 는 W4 콘텐츠·원장언어 플라이휠 **전체의 유일한 입력.** 입력이 0이면 이미 완성된 마이닝·어드민 패널·크론이 전부 공회전.

즉 이 셋은 "고치면 편해지는 개선"이 아니라 **"안 고치면 그 위의 모든 자동화가 멈추거나 잘못된 숫자 위에 굳는" 구조적 게이트**다.

### 0.3 권고 결정 순서 — 무엇을 먼저

가역성(되돌리기 난이도)과 언블록 폭을 기준으로 다음 순서를 권고한다.

| 순위 | 결정 | 이번 주 착수 이유 |
|------|------|-------------------|
| **1번째** | **B(발송)** — 이번 주 스텝1만 | 반나절 작업(환경변수 2개 + WeCom URL)으로 **4개 워크스트림 라스트마일이 즉시 simulation→live**. 되돌리기 매우 쉬움(키 제거). 가장 큰 즉효. |
| **2번째** | **A(매출 정본)** — 과도기 정본 선언 + 커버리지 게이트 | 가장 **비가역적**이므로 "가장 가역적인 형태"로 지금 못 박아야 각자 분모 고착을 막는다. 코드 변경 거의 0. |
| **3번째** | **C(채널톡)** — 키 발급 + 로컬 검증 | 대표 5분 키 발급이 병목. W1/W2가 P0인 8명 팀에서 **W4는 착수는 하되 우선순위는 낮게.** |

> **핵심 메시지: A는 "가장 가역적인 형태로 지금 선언", B는 "이번 주 반나절에 켠다", C는 "5분 키 발급으로 검증만 시작".** 셋 다 큰 신규 엔지니어링을 지금 요구하지 않는다.

**질문: 8명이 매일 보고, 6개 자동화 지표가 formula를 얹을 "매출의 단일 진실"을 무엇으로 선언할 것인가.**

### 1.1 실측 현황 (대표 검증용)

- **`crm_orders` 코드 전무** — Grep 결과 `.ts/.tsx` 파일 0건(직접 확인). insert/upsert/create migration 0건. 4개 docs에만 등장.

### 1.3 권고

**옵션1을 즉시 '과도기 정본'으로 확정**하되, **옵션3을 정본의 '구현 형태'로 로드맵에 얹고**, **옵션4(crm_orders)는 '고객360 매출 축'으로 분리 유예**한다.

즉 **"지표 정본 = `branch_rev_deals`(+source_links 커버리지)"** 라벨을 지금 못 박고, 물리 저장을 시트 미러→DB-native(옵션3)로 단계 승격한다.

**이유:**
1. 자동화 설계 §2.5·§6이 이미 "crm_orders write 미구현 → branch_rev_deals+source_links 과도기 정본"으로 판정했고, 실측(crm_orders 0건, pipeline route가 listBranchRevDeals 직결)이 이를 확증.
2. **되돌리기가 핵심 제약**인데 옵션1이 가장 가역적(라벨만 이동), 옵션4가 가장 비가역(status 매핑 오류 시 6지표 소급 오염). "잘못 정하면 각자 분모로 굳는다"에 정확히 대응하는 것은 **"가장 가역적인 것 먼저"**.
3. 8명 팀·즉시 가시성 우선 가치에 정합 — 옵션1은 **오늘 켤 수 있다.**

**권고 순서:**
- ① D1을 "과도기 정본 = branch_rev_deals, 커버리지 게이트 동반"으로 확정 선언(문서·metric_definitions 라벨).
- ② `source_link_coverage_pct` 뷰 + 데이터-헬스 배지(퀵윈, 마이그레이션 무) — 미달 시 편중/매출 `NOT_TRUSTED`.
- ③ 옵션3(워크트리 DB-native) 머지를 2.292 경유로 정식화해 write 경로 확보.
- ④ 옵션4 crm_orders는 고객360 고객매출 전용으로 분리 착수(성과분석 정본과 이원화 금지, reconcile 대사만).

**리스크:**
- (a) 옵션1을 '과도기'로 **명시 안 하면** 시트 정본이 관성으로 영구화 → 자체소유 0% 고착. **"커버리지 X% 도달 시 옵션3 승격" 트리거를 문서화 필수.**
- (b) 통화 함정 — 성과/편중 CNY, 오더 USD. currency CHECK(P4) 동반해 grand-total 혼합 차단.
- (c) 옵션3 머지 시 챗봇 `classification.ts` 드라이브바이 회귀 **(가정)** — git checkout으로 2.292 유지.

### 1.4 이번 주 첫 스텝

**`source_link_coverage_pct` 측정 뷰 1개 + `/admin/crm` 데이터-헬스 배지 노출**(마이그레이션 무, `crm_source_links` confirmed 기준).

핵심: **정본을 고르기 전에 "정본이 얼마나 믿을 만한가"를 숫자로 먼저 본다.** 이것 없이는 어떤 정본을 골라도 "매출 절반 무음 누락"(ERP 키스톤 리스크)을 볼 수 없다. **정본 선택보다 '정본 신뢰도 측정'이 선행.**

### 1.5 반대편 steelman — 옵션4(crm_orders 즉시 구축)

> '과도기 정본'은 **정치적 미루기**이고, 진짜 회사 매출은 시트가 아니라 NEO(2.1억+ 위안, 공식 고객매출)에 있다. 지사 REV 시트는 지사 영업팀의 **파이프라인 관점 숫자**이지 회사 손익의 book-of-record가 아니다. 옵션1을 굳히면 "8명이 매일 보는 매출"과 "회사가 실제 인식하는 매출"이 **영구히 갈라지고**, 편중(top10 70~77%)·LTV·리뉴얼 방어 같은 전략 지표가 전부 지사 시트라는 **대리변수** 위에 선다.
>
> 되돌리기가 어렵다는 건 옵션4를 미룰 이유가 아니라 **지금 제대로 하라는 이유**다 — 나중에 시트 위에 쌓은 6개 지표를 NEO로 옮기는 재작업이 지금 crm_orders를 한 번 제대로 만드는 것보다 크다. `owner-names.ts`·`getNeoCrmCustomers` 정제 자산이 이미 있어 PRD가 말하는 만큼 순신규도 아니다. status 매핑 리스크는 reconcile 게이트(기존 NEO 고객총액 대사)로 관리 가능하고, 통과 못 하면 어차피 지금 시트 숫자도 못 믿는 것이다.
>
> 즉 '가역성 우선'은 결정을 **데이터 없는 상태로 동결**시키는 함정일 수 있으며, 회사 매출의 단일 진실을 NEO로 잡는 것이 "8명이 같은 숫자를 본다"는 전제에 더 부합한다.

**참모 판단:** 이 반론의 핵심(시트=파이프라인 대리변수, NEO=진짜 손익)은 강력하며 **부분 채택**한다 — 그래서 권고 ④에서 crm_orders를 폐기하지 않고 '고객360 매출 축'으로 **분리 착수**시킨다. 다만 status 매핑이 검증되지 않은 지금 crm_orders를 **성과분석 정본으로까지** 굳히면 6지표가 동시에 오염될 수 있어, "정본으로 승격"과 "축 구축 착수"를 분리하는 것이 안전하다.

### 1.6 열린 하위질문 (대표 결정 필요)

- 커버리지 **몇 %를 '정본 신뢰 임계'**로 볼 것인가 (설계 ≥90% 제안이나 **계측 없는 목표라 표본 축적 후 확정 — 가정**).
- 옵션1→옵션3 **승격 트리거**를 커버리지 도달로 할지, 워크트리 머지 준비도로 할지.
- crm_orders(옵션4)를 성과분석 정본으로도 쓸지 vs 고객360 매출 축으로만 분리할지 — **이원화 허용 범위.**
- NEO status 매핑(续费→renewal / 新签→new_sign) 전수 코드와 payload stage 필드 조사가 **언제 가능한지**(PRD §8.2 미해결).
- 통화 표시: **CNY 유지 vs KRW 환산** — 환산 시 환율 소스·시점 고정 정책(PRD §8.1 미해결).

## 2. 결정 B — 발송 서비스(이메일/메시지)

**질문: 라스트마일 발송 채널을 무엇으로 표준화하고, 지금 무엇을 켤 것인가.**

### 2.1 실측 현황 — 결정 범위가 생각보다 좁다

설계서 §D2는 이 1개 결정이 4개 워크스트림 라스트마일을 동시에 블록한다고 명시했으나, **코드 실측 결과 이 4개는 이미 상당수 배선돼 있고 실제로 막힌 건 '환경변수 + 채널정책 확정'뿐이다.**

- **W1 넛지·W3 드립·W6 초안발송**은 전부 `lib/email.ts`의 `sendBatchEmail`/`sendInternalNotification` 위에 이미 올라가 있어 **`RESEND_API_KEY`+`RESEND_FROM` 두 값만 채우면 즉시 동작**(현재 simulation 모드). Grep 확인: `lib/email.ts`, `lib/automation-engine.ts`, `app/api/admin/email/send/route.ts` 모두 존재.
- **W2 hot-lead/미응대 알림**은 `lib/server/lead-response-alerts.ts`에서 이미 `channels:["wecom_webhook"]`로 발송 배선됨(Grep 확인) — **이 결정을 안 기다리고 settings에 WeCom webhook URL만 넣으면 켜진다.**

따라서 이 결정의 **실질 범위**는 "고객 대면 외부 발송(W1 넛지·W3 드립)을 이메일 단일로 갈지, 카카오를 섞을지"로 좁혀진다.

### 2.3 권고

**옵션5(하이브리드)를 '단계적 단일 진입'으로 채택.**

**이유:**
1. 코드 실측상 이 결정은 "무엇을 새로 만들까"가 아니라 **"이미 배선된 멀티채널 중 무엇을 언제 켤까"** — `lib/email.ts`(Resend 3-tier)·`emit-event.ts`(wecom/kakao/email 라우팅)·`lead-response-alerts.ts`(W2가 이미 wecom_webhook 발송)가 완성돼 있고 막힌 건 환경변수와 채널정책뿐.
2. **채널 단일화는 각 용도에서 최악의 채널을 강제한다** — 이메일 통일 시 거래적 알림 도달률이 죽고, 알림톡 통일 시 마케팅 드립(광고성)을 아예 못 보냄. `notification-architecture-plan.md`가 이미 "내부=WeCom, 마케팅=이메일, 외부거래적=Kakao"로 정책을 못박아 뒀다.

**단계 순서 (하이브리드 명시):**

| 단계 | 채널 | 용도 | 상태 | 시점 |
|------|------|------|------|------|
| **1단계** | WeCom webhook | 내부 ops 알림(W2 hot-lead/미응대) | 이미 배선 — settings URL 입력만 | **이번 주** |
| **1단계** | Resend 이메일 | 마케팅 드립·넛지·초안발송(W1·W3·W6) | 이미 배선 — env 2개만 | **이번 주** |
| **2단계** | 카카오 알림톡 | 고객 대면 거래적(일정확정·계약리마인더·영수증) | payload 빌더 신규 필요 **(가정: emit-event는 generic만)** | 1~2주 병렬 |
| **3단계** | Resend 웹훅 | email_sent/open/click 물화 + subscribers/campaigns JSON→Supabase | W3 attribution 선행 | 이후 |

**리스크:**
- (a) 발신도메인 SPF/DKIM 미인증 시 첫 배치 스팸 처리 — **도메인 인증 먼저.**
- (b) 자동발송 금지 원칙(P2) — 드립도 **사람 승인 세그먼트만.**
- (c) D7 미결(자동구독→명시 옵트인) — 법무 확인 전 마케팅 모수를 **옵트인 명시 리드로 제한.**
- (d) W3 attribution을 **정보성 알림톡에 걸지 말 것.**

### 2.4 이번 주 첫 스텝

**반나절 작업:** Vercel에 `RESEND_API_KEY` + `RESEND_FROM` 입력(발신도메인 SPF/DKIM 인증 포함) 후 `/admin/marketing` 발송탭에서 `mode:"test"`로 본인 주소에 1통 실발송 → provider가 `resend`로 찍히고 열람추적·수신거부 링크가 동작하는지 확인. 동시에 `/admin/settings`에서 `wecomOpsWebhookUrl` 입력 → W2 미응대 알림 cron이 WeCom 룸으로 실제 발송되는지 검증.

**이 둘로 W1·W2·W3·W6 라스트마일이 simulation→live로 전환된다.**

### 2.5 반대편 steelman — 옵션2(카카오 알림톡 단일)

> 한국 학원 원장은 이메일을 거의 안 연다. B2B라도 실질 커뮤니케이션은 **100% 카카오톡**이다. 이메일 드립을 이번 주에 켜봤자 오픈율 한 자릿수로 W3 attribution 표본이 **노이즈**가 되고, P5(계측 선행) 명분으로 죽은 채널을 계측하는 **자기기만**이 된다. 어차피 카카오 심사 1~2주가 병목이면 그 1~2주를 지금 시작해 8월부터 진짜 도달되는 채널로 실측하는 게 낫다.
>
> 하이브리드는 채널 3개 동의/법규 매트릭스를 8명 팀이 이고 가야 하는데, **소규모 팀의 진짜 제약은 코드가 아니라 운영 주의력**이다 — 채널을 늘리면 어느 메시지가 어느 동의 근거로 나가는지 추적이 무너지고, 정보성/광고성 경계 위반(알림톡에 광고 문구)으로 **계정정지 리스크**가 커진다. 알림톡 하나로 거래적부터 확실히 도달시키고 마케팅 드립은 도달 채널 검증 후 붙여라.

**참모 판단:** 이 반론의 핵심(이메일 도달률·팀 주의력·계측 진정성)은 타당하다. **대표는 스텝1 test 발송에서 실제 오픈율을 2주 관측한 뒤 이메일 드립 확대를 결정하는 게 안전하다.** 다만 알림톡은 광고성 드립을 **구조적으로 못 보내므로** '단일'이 될 수 없다는 점이 옵션2를 단일화의 결정적 한계로 남긴다 — 그래서 하이브리드가 여전히 우세하되, 이메일 드립의 **확대 속도**를 오픈율 관측에 연동하라는 것이 반론의 정당한 요구다.

### 2.6 열린 하위질문 (대표 결정 필요)

- **D7:** 자동구독(옵트아웃)→명시적 옵트인 전환 여부 — 법무 확인 필요. 미결 시 마케팅 모수를 '동의 명시 리드'로 한정.
- **발신도메인 확정:** `RESEND_FROM`을 `noreply@classin.co.kr` / `classin.ai.kr` / `classin.com` 중 무엇으로? (email.ts 기본값 classin.ai.kr, 캠페인 푸터 classin.co.kr, userEmail classin.com) — 도메인 인증 대상이 이 결정에 물림.
- **카카오 게이트웨이:** Solapi vs NHN(Toast) vs 기타 — emit-event의 kakao_alimtalk가 릴레이 URL 방식이라 **게이트웨이별 payload 빌더 신규 구현 범위가 갈림.**
- **JSON→Supabase 이관 시점:** W3 attribution·다중인스턴스 발송의 선행(현재 파일락 미구현 NOTE-5). 이메일 라이브와 동시에 갈지 이후로 미룰지.
- **(가정) 카카오 payload 빌더 미구현 확인:** emit-event는 kakao_alimtalk에 generic notification payload만 전송 — 알림톡 템플릿 변수 매핑 빌더가 별도로 있는지, 없으면 **스텝2 신규 엔지니어링 범위 확정 필요.**

### 3.3 권고

**옵션1(Open API 크론 sync)을 켠다 + 즉시 후속으로 저장소를 Supabase `channel_conversations` 테이블로 승격.** 옵션3 웹훅은 **이미 배선된 실시간 알림 보완재로 병행 유지**(신규 로직 추가 없이 현 상태 그대로).

**이유:**
1. 옵션1은 신규 개발이 아니라 **'이미 지어진 것 켜기'** — API 클라이언트·sync 엔진·크론·어드민 트리거·마이닝이 전부 존재·배선. 잔여 작업은 환경변수 + 실키 1회 검증 + 영속 저장 승격뿐.
2. **권한 장벽이 낮다** — 채널톡 설정>보안에서 키 발급은 대표 1회 5분.
3. rate limit 안전(버킷 100·초당 10 vs run당 25~50건).
4. 개인정보 방어(redactSensitiveText)가 마이닝 전 이미 적용.

**단계 순서:**

| 주차 | 작업 |
|------|------|
| **1주차** | 채널톡 Open API 키 발급 → `.env`에 `CHANNEL_TALK_ACCESS/SECRET` → 로컬 수동 sync 1회로 **실제 필드 매핑 검증**(코드 주석이 '실키로 한 번 검증 후 매핑 확정' 명시) → mineFaqSuggestions 결과 육안 확인 |
| **2주차** | `channel_conversations` Supabase 마이그레이션 + repository readAll/writeAll을 Supabase로 교체(인터페이스 유지) → 크론이 프로덕션에서 영속 적재 |
| **3주차** | question_clusters 영속화 → chatbot_recommended_questions **초안 자동생성(어드민 검토 후 게시, 자동게시 금지** — 캐논·메모리 일관 원칙) |

**리스크:**
- (a) 실키 응답 필드가 방어적 파싱 가정과 다를 수 있음 → 첫 검증에서 잡힘, 코드가 이미 방어적.
- (b) JSON 폴백을 프로덕션에서 켜면 미영속 → **2주차 Supabase 승격 전까지 프로덕션 크론은 신뢰 금지**, 검증은 로컬/단일서버에서.
- (c) 개인정보: transcript 원문에 연락처가 남으므로 **DB 적재 시점에도 redact 적용 여부를 승격 시 재확인**(현재 redact는 마이닝 단계 적용, 저장 단계는 raw).

### 3.4 이번 주 첫 스텝

대표가 채널톡 관리자 콘솔 **'설정 > 보안 > API'에서 Open API 액세스 키 페어**(위젯 플러그인 키와 별개)를 발급 → 로컬 `.env.local`에 `CHANNEL_TALK_ACCESS`/`CHANNEL_TALK_ACCESS_SECRET` 설정 → 개발서버에서 `/admin/channel-talk` 수동 sync 버튼 1회로 **실제 대화가 로컬 JSON에 적재되는지·방어적 필드 매핑이 실제 응답과 맞는지 검증**(비파괴, 로컬만).

### 3.5 반대편 steelman — 옵션4(동결)

> 8명 팀에서 지금 진짜 P0는 매출에 직결되는 W1(SW 활성화·LTV)과 W2(리드·세일즈 파이프라인)이지 챗봇 콘텐츠 플라이휠(W4)이 아니다. W4를 켜도 산출물은 'chatbot_recommended_questions 초안'과 '콘텐츠 갭 후보'인데, 이건 어차피 어드민이 검토·게시하는 **사람-루프**가 걸려 있어 자동화 레버리지가 낮다(캐논이 '자동게시 금지' 못박음). 즉 대화 적재를 자동화한들 병목은 **발행 측 사람 시간**으로 옮겨갈 뿐이다.
>
> 게다가 옵션1을 제대로 하려면 JSON→Supabase 승격이라는 실제 엔지니어링(0.5~1일)이 딸리고, 그동안 프로덕션 크론은 미영속이라 신뢰 못 한다. 대화량이 적은 초기라면 mineFaqSuggestions의 **minCount≥2 임계를 넘는 군집 자체가 거의 안 나올 수 있어**, 적재를 켜도 '유의미 제안 0'으로 여전히 공회전할 위험이 남는다. 따라서 W1/W2가 안정 궤도에 오르고 채널톡 누적량이 임계(**가정: 주 수십 건 이상**)를 넘길 때까지 옵션4로 두고, W4는 그때 켜는 게 8명 팀의 집중 관점에서 합리적이다.

**참모 판단:** 이 반론은 **우선순위 관점에서 정당**하며, 그래서 §0.3에서 C를 **3순위**로 두었다. 다만 옵션1의 이번 주 실제 부담은 '대표 5분 키 발급 + 로컬 sync 1회'뿐이고, 이 첫 sync가 **"대화량이 minCount 임계를 넘길 만큼인가"를 실측**해 주는 진단이기도 하다 — 즉 동결 vs 착수를 지금 데이터로 판정하려면 **키 발급 후 첫 sync로 raw 건수를 세는 것 자체가 옵션4 반론의 검증**이 된다. 따라서 "3순위로 두되, 진단용 첫 sync는 이번 주에" 가 두 입장을 모두 만족시킨다.

### 3.6 열린 하위질문 (대표 결정 필요)

- **영속 저장을 언제 Supabase로 승격할지** — 로컬 검증(1주차)과 프로덕션 적재(2주차) 사이 게이트를 어디에 둘지.
- **DB 적재 시점 개인정보 처리** — 현재 redact는 마이닝 단계에만. 원문 저장 시 redact를 저장 전에도 적용할지(감사/재분석 vs 최소수집 원칙 trade-off).
- **적재 임계 검증** — 실제 대화량이 minCount≥2 군집을 유의미하게 만들 만큼인지. 키 발급 후 첫 sync에서 raw 건수를 먼저 세어보고 W4 우선순위 재확인.
- **크론 주기**(현재 매일 1회 00:15 UTC)가 적절한지 — 실시간성은 웹훅 알림 보완이나, 대화량 늘면 주기 상향 검토.
- **(가정)** 웹훅 route의 알림 전용 설계를 verbatim 적재까지 확장할 필요가 있는지 — 현재는 크론/수동 sync가 본문을 채우므로 불필요하나, 실시간 적재 요구 시 재검토.

## 4. 한 페이지 결정 시트 — 대표 결정 대기

| 결정 | 권고안 | 되돌리기 난이도 | 이번 주 첫 스텝 | 상호 의존성 |
|------|--------|----------------|-----------------|-------------|
| **A. 매출 정본** | **옵션1(branch_rev_deals)을 '과도기 정본'으로 즉시 선언** + 옵션3(DB-native)을 로드맵 + 옵션4(crm_orders)는 고객360 축으로 분리 | **낮음(어렵다)** — 6지표가 이 분모 위에 굳음. 그래서 "가장 가역적 형태"로 선언 | `source_link_coverage_pct` 뷰 1개 + `/admin/crm` 데이터-헬스 배지(마이그레이션 무) | **B·C와 독립.** W3 채널 LTV가 A의 분모 + B의 email attribution **둘 다** 필요 → A·B 함께 있어야 W3 완성 |
| **B. 발송 서비스** | **옵션5(하이브리드) 단계적 채택** — 1단계 WeCom+Resend 즉시, 2단계 카카오 병렬 | **높음(쉽다)** — emit-event 멀티채널이라 채널 붙였다 뗌 자유 | Vercel `RESEND_API_KEY`+`RESEND_FROM` + `wecomOpsWebhookUrl` → test 1통 실발송 검증 | **가장 독립적, 가장 즉효.** W1/W2/W6가 B에 직접 물림. W3는 A(분모)+B(발송) 동시 필요 |
| **C. 채널톡 적재** | **옵션1(Open API 크론) 켜기** + Supabase 승격 후속 + 옵션3 웹훅 보완 유지 | **매우 높음(가장 쉽다)** — 키 제거하면 즉시 무해 정지 | 대표가 채널톡 Open API 키 페어 발급 → 로컬 `.env.local` → 수동 sync 1회 검증 | **A·B와 독립.** W4만 담당. 첫 sync가 '대화량 임계' 진단 겸함 |

> **읽는 법:** 되돌리기 난이도가 **A가 가장 어렵고 C가 가장 쉽다.** 그래서 A는 "가장 가역적인 형태(라벨 선언)"로 지금 못 박고, B/C는 마음 편히 켜도 된다. 유일한 강한 커플링은 **W3(인텐트 사다리 LTV)** 로, A의 매출 분모와 B의 email attribution을 **둘 다** 요구한다 — A·B를 같은 주에 처리하면 W3가 열린다.
