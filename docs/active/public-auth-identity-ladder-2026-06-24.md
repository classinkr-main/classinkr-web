# 공개 사용자 로그인 — 점진적 정체성 계단(Identity Ladder) 설계 & 객관적 평가

- 작성일: 2026-06-24
- 범위: **공개/일반 사용자 로그인만** (관리자/admin 인증 제외, 파트너 포털 V2 제외)
- 담당 파트: 플랫폼&데이터(인증/스티칭) · 마케팅/그로스/CRM(동의·퍼널·프로모션·구독) · 컨텐츠 발행(프리미엄 게이팅)
- 관련 가이드: [06-platform-data](playbook/06-platform-data.md), [04-growth-crm](playbook/04-growth-crm.md), [03-content-pub](playbook/03-content-pub.md)

## 1. 목적과 스탠스

로그인을 **순수 리드 수집기**로 키우려는 게 아니다. 깨지지 않는 **하나의 고객 ID**를 확보하되, 특정 제품에 미리 못 박지 않는다. 그 ID에 **사용자가 받는 구체적 혜택**을 붙여 "로그인할 이유"를 만들고, 그 멤버 명단·행동을 **리드·퍼널 자산**으로 활용한다.

확정된 의도(우선순위):
1. **리드 캡처 / CRM 강화** — 검증된·지속되는 고품질 신원
2. **통합 ID 전초** — 미래 제품/포털 계정으로 승격 가능한 durable identity (대상 제품은 **미정**)

로그인에 붙일 구체적 혜택(향후, 순차):
- **프리미엄 컨텐츠 받기·열람·재열람** ← 1차 쐐기(wedge)
- **프로모션 코드 받기** ← 2차
- **정기 구독 / 행사 알림** ← 3차

## 2. 객관적 평가 (먼저)

### 2.1 핵심 진단: 두 목적은 부분적으로 충돌한다

- **리드 캡처 관점에서 로그인은 마이너스다.** OAuth 동의·계정 생성은 email 한 줄보다 마찰이 크고, 상단 퍼널에서 강제하면 리드 **수(volume)**가 줄어든다. 현재 운영이 email 게이트 중심인 것은 **올바른 선택**이었다.
- **통합 ID 전초 관점에서는 로그인만 할 수 있는 일이 있다.** email 게이트가 만드는 리드는 *email 문자열* 기반이라 오타·복수 이메일·인증 없음으로 **깨지기 쉽다**. 로그인은 검증·중복제거·재방문 추적되는 **durable `auth.users` 신원**을 만든다.

> **설계 철칙: email 게이트를 로그인으로 "대체"하지 않는다. 로그인을 그 위에 "선택적 승격 계단"으로 얹는다.**
> 이렇게 해야 리드 볼륨(email 게이트)과 통합 ID(로그인 승격)를 동시에 얻는다.

### 2.2 현재 구현 현황 (솔직한 진단)

기술적으로 약 70% 구현돼 있으나 **사실상 끊겨 있다.**

| 영역 | 상태 | 평가 |
|------|------|------|
| Google OAuth (Supabase) | 작동 | 표준 구현 |
| Naver OAuth (커스텀) | 코드만 완성 | `NAVER_CLIENT_ID/SECRET` 미설정 → 실작동 불가 |
| `user_profiles` + RLS | 완성 | service_role only, 인프라 견고 |
| `stitchIdentity` (익명→유저→리드) | 완성하나 취약 | `findLatestLeadIdByEmail`("최근 1개")는 오결합 위험 |
| 자료 다운로드 게이트 | 이중화 | 코드엔 `email`/`login` 둘 다, 운영은 email 중심 |
| 로그인 후 UX | **끊김** | 로그인 성공 후 자동 재다운로드 없음 → `/resources`로 튕김 |
| 마이페이지/회원 영역 | 없음 | 로그인의 사용자 가치 사실상 0 |
| Kakao | 없음 | 국내 원장 ICP 최대 공백 |

### 2.3 제안 설계 스코어카드 (0–10)

| 차원 | 점수 | 근거(약점 포함) |
|------|:---:|------|
| 두 목적 동시 충족(볼륨+통합ID) | 9 | email 게이트 보존 + 로그인 승격 → 거의 이상적 |
| 사용자 가치(로그인 이유) | 8 | 프리미엄 컨텐츠로 이유 확보. **콘텐츠가 진짜 프리미엄일 때만 성립** |
| 구현 리프트(쐐기) | 7 | 인프라 70% 존재. Kakao 커스텀 OAuth는 신규 작업 |
| 보안(탈취·오결합) | 8 | 검증 이메일 앵커가 방어. **Kakao/Naver `email_verified` 오처리 시 8→4** |
| 신원 분열 방지 | 7 | `leads.user_id` 1:N 개선. 소셜-without-email은 여전히 분열(머지 미구현) |
| 미래 확장성(전초) | 8 | `account_ref` 예약 + durable `auth.users`. 과투자 없이 문 열어둠 |
| 운영/법적 부담 | 6 | 마케팅 동의·발송은 정보통신망법상 의무(동의·철회 처리 실재) |
| **종합** | **~7.5** | 방향 견고. 리스크는 "콘텐츠 실질 가치"·"소셜 `email_verified` 정확도"에 집중 |

### 2.4 솔직한 리스크 5

1. **프리미엄이 진짜 프리미엄이어야 한다** — 게이트만 치고 내용이 평범하면 마찰만 늘고 전환↓. 콘텐츠 품질 의존.
2. **`email_verified` 오처리 = 계정 탈취/오결합** — Phase 1의 보안 게이트.
3. **마케팅 동의는 법적 의무** — 미동의 발송 금지, 수신거부(철회) 처리 필수.
4. **게이트 과용 금지** — 무료 자료까지 로그인 막으면 볼륨 붕괴. `tier` 운영 규율 필요.
5. **머지 부재** — 소셜·이메일 불일치 사용자는 당분간 중복 신원. 수용하고 미래 머지로 미룸.

### 2.5 정직한 대안(채택 안 함)

- **B. 로그인-우선 게이트**: 고가치 자료를 로그인 강제. 신원 정확도 최고지만 리드 볼륨 감소 → "질 ≫ 양"일 때만 정당.
- **C. 보류/최소화**: 지금 로그인 안 키움, 죽은 Naver 경로만 정리. 구체 제품 계정이 생길 때 투자.
- 채택: **A. 점진적 정체성 계단** (볼륨·통합ID 동시 충족, 사용자 가치를 프리미엄 컨텐츠로 확보).

## 3. 정체성 모델 (Identity Ladder)

```
L0 익명      cln_aid (쿠키)                              [있음]  → client_events
L1 리드      leads (email 게이트)                         [있음, 볼륨 주력]
L2 혜택 멤버  auth.users + user_profiles                  ← "로그인할 이유"가 사는 곳
             ├─ 프리미엄 컨텐츠 열람·재열람 (1차 쐐기)
             ├─ 프로모션 코드 (2차)
             └─ 구독 / 행사 알림 (3차)
L3 제품 계정  account_ref (예약, 미사용)                   [미정]
```

한 사람 = 한 `auth.users` = N leads + N events. 로그인 전엔 email-lead가 대리 신원, 로그인 시 `auth.users`가 표준이 되어 이전 조각을 흡수·승격한다.

### 3.1 결정 1 — 표준 스파인은 `auth.users`, `leads`는 1:N로 매단다

- 새 `persons`/`contacts` 테이블은 **만들지 않는다** (YAGNI — "통합 ID만 확보" 스탠스에 과함).
- `leads`에 `user_id` (nullable FK → `auth.users`) 추가 → **1 user → N leads** 관계를 lead 쪽에 기록.
- `user_profiles.lead_id`는 "대표 리드" 편의 포인터로만 유지(폐기 아님).

### 3.2 결정 2 — 신뢰 앵커는 "검증된 이메일"만 (보안 필수)

- 리드/행동을 user에 자동 결합하는 것은 **provider가 `email_verified=true`로 준 이메일일 때만**.
- 미검증 소셜로 타인 이메일을 주장해 피해자의 리드·활동을 가로채는 공격을 차단.
- Google은 검증 보장. **Kakao/Naver는 `email_verified` 클레임을 반드시 확인**(없거나 false면 자동 결합 금지).

### 3.3 결정 3 — L3(제품 계정)는 "예약만"

- `user_profiles.account_ref` (nullable) 컬럼 1개만 추가, **지금은 쓰지 않는다**. 주석으로 "미래 제품/포털 승격 예약"이라 명시. 테이블·로직은 만들지 않는다.

## 4. 로그인 & 게이트 UX (프리미엄 컨텐츠 쐐기)

### 4.1 끊긴 곳 복구 — 의도 보존(intent preservation)

현재 로그인 성공 후 원래 자료로 안 돌아오고 `/resources`로 튕긴다.

```
프리미엄 자료 클릭
  ├─ 로그인됨?  예 → 즉시 열람/다운로드 (+ material_downloads에 user_id·lead_id 기록)
  └─           아니오 → PublicLoginDialog (intent=premium, asset=slug 보존)
                       → 소셜/이메일 로그인 → /auth/callback (next 복귀)
                       → upsertPublicUserProfile + stitchIdentity
                       → 보존된 intent 자동 실행 (자료 자동 열림)
```

- `next`와 함께 의도(자료 slug/액션)를 안전하게 보존(same-origin 검증 기존 유지).
- 콜백 완료 후 보존된 intent를 자동 실행 → "로그인했더니 그냥 자료가 열림" 경험.

### 4.2 프로바이더 세트 (국내 ICP 반영)

- **Google**: 유지(작동).
- **Kakao**: **추가**. Supabase 기본 미지원 → 기존 Naver 패턴을 재사용한 커스텀 라우트(`/api/auth/kakao/start|callback`). `email_verified` 확인 포함.
- **Naver**: 환경변수 설정 + `email_verified` 확인으로 **살린다**. 미설정이면 **버튼을 숨긴다**(죽은 버튼 노출 금지).
- **이메일 매직링크/OTP**: 2차로 미룸(YAGNI). 1차는 소셜만.

### 4.3 게이트 공존 (평가 철칙의 구현)

- 자료 메타에 `tier: free | premium` (기존 `gate` 필드 확장/정렬).
  - `free` = **email 게이트** (볼륨 유지)
  - `premium` = **login 게이트** (고품질 신원)
- 운영자가 자료별로 `tier` 지정 → email 게이트와 login 게이트가 **공존**.
- 무료 자료를 로그인으로 막지 않는다(볼륨 보호).

## 5. 스티칭 · 동의 · 재열람

### 5.1 스티칭 결정론화 (추측 → 확정)

- `findLatestLeadIdByEmail`("최근 1개") 폐기 방향.
- 로그인 시: **검증 이메일과 일치하는 모든 leads를 user에 연결**(`leads.user_id` set), 익명 events를 user_id/lead_id로 역채움(기존 stitch 활용).
- 충돌(검증 이메일 없음/불일치) → **자동 결합하지 않음**, 새 신원으로 두고 관리자 머지 여지만 남김(머지 UI는 미래).
- 스티칭 결과를 **감사 로그**로 남김(누가 어떤 lead에 언제 결합).

### 5.2 동의(consent) 캡처 — 발송의 법적 근거

- 첫 로그인 시 **마케팅 수신 동의를 명시적으로 수집**(`user_profiles.marketing_consent`). 이게 향후 구독·행사 알림/프로모션 발송의 근거.
- 분석 동의(`cln_consent`)는 기존 정책대로.
- 수신거부(철회) 경로를 함께 설계(법적 의무).

### 5.3 재열람 표면 (최소 멤버 영역)

- `/account` 단일 페이지:
  - **내 프리미엄 자료** 목록(`material_downloads` 기반) + 재열람 링크
  - 알림/마케팅 동의 설정(opt-in/철회)
- 풀스펙 마이페이지/대시보드는 **만들지 않는다**(YAGNI). "다시 보기 + 설정" 딱 그만큼.

### 5.4 퍼널 연결

- L2 멤버 = 어드민 CRM에서 "검증 이메일 + 프리미엄 열람 = 고의향" 세그먼트로 활용. 기존 leads/CRM 파이프 재사용.

## 6. 데이터/마이그레이션 영향

> 마이그레이션 규율: 타입/코드에 컬럼을 추가하면 반드시 `supabase/migrations/YYYYMMDD_*.sql` 동반 (누락 시 무음 INSERT 실패).

Phase 1에서 필요한 스키마 변경(예상):
- `leads.user_id` (nullable FK → `auth.users(id)`, 인덱스) — user↔lead 1:N
- `user_profiles.account_ref` (nullable) — L3 승격 예약(미사용)
- 자료 메타 `tier` (free/premium) — 기존 `gate`와 정렬
- 스티칭 감사 로그 저장소(기존 테이블 재사용 가능성 우선 검토)

`user_profiles.marketing_consent`는 이미 존재 → 첫 로그인 동의 캡처에 활용.

RLS: `user_profiles`, `leads` 등은 기존대로 service_role 경로(서버 라우트)로만 쓰기. 어드민 경로는 admin 클라이언트 사용 철칙 유지.

## 7. 롤아웃 단계

| Phase | 내용 | 비고 |
|-------|------|------|
| **0. 정리** | intent 보존 버그픽스 · Naver 미설정 버튼 숨김 · 죽은 경로 정리 | 저비용, 즉시 효과 |
| **1. 쐐기(핵심)** | 프리미엄 `tier` 게이트 + Kakao OAuth + 검증이메일 스티칭 + 동의 캡처 + `/account` 최소 + 마이그레이션(`leads.user_id`, `account_ref`) | 본 설계의 본체 |
| **2. 프로모션 코드** | 코드 발급·검증·소진 시스템 | growth-crm |
| **3. 구독·행사 알림** | 알림 발송 + 선호센터 + 행사 연동 | growth-crm |
| **(미정) L3 제품계정** | `account_ref` 활성화 + 승격 흐름 | 구체 제품 결정 시 |

각 Phase 검증 게이트: `npx eslint app components lib --max-warnings=0` + `npm run build`.

## 8. 성공지표

- **L1→L2 전환율** — 프리미엄 게이트 노출 대비 로그인 완료율
- **프리미엄 자료당 검증 리드 수**
- **재열람율** — `/account` 재방문 / 프리미엄 자료 재열람
- **마케팅 동의율** — 첫 로그인 시 opt-in %
- **오결합/중복 신원 비율** — 목표치 이하 유지
- **(역지표) 무료 email 게이트 볼륨** — 로그인이 볼륨을 잠식하지 않는지 감시

## 9. 테스트 전략

- **단위**: 스티칭 결정론(검증/미검증 이메일, 다중 lead 매칭), `email_verified` 분기
- **통합**: provider별(Google/Kakao/Naver) 로그인 → intent 자동 실행 → `material_downloads` 기록
- **보안**: 미검증 이메일로 타인 lead 결합 시도 **차단**, RLS(service_role only) 확인, same-origin 유지
- **회귀**: 무료 email 게이트 흐름 무영향
- **게이트**: `npx eslint app components lib --max-warnings=0` + `npm run build`

## 10. 안 만들 것 (YAGNI 명시)

- 풀스펙 마이페이지/대시보드
- `persons`/`contacts` 새 스파인 테이블
- L3 제품 계정 실제 구현
- 이메일 매직링크(1차)
- 관리자 신원 머지 UI(1차)
- 프로모션/구독 시스템(Phase 2–3로 분리)
