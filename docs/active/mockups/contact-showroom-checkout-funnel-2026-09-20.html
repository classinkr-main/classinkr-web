1차 기획(2026-08-29)은 백엔드를 거의 다 만들었다. 쇼룸은 슬롯·가용성·접수·알림·캘린더 어댑터까지, 구매는 서버 단가 핀·상태 기계·중복 방지까지 동작한다. 공개 쇼룸 화면도 월 캘린더와 슬롯 선택, 409 충돌 리커버리까지 완성돼 있다. 이번 실측에서 드러난 것은 그 위에 얹힐 세 개의 끊긴 고리다.

세 개의 끊긴 고리

만들어졌지만 닿지 않고, 접수되지만 처리되지 않는다

01 · 도달

쇼룸 예약에 도달할 방법이 없다

/showroom을 가리키는 링크가 제품 전체에 2개뿐이다. 헤더·푸터·홈·모바일 CTA는 전부 /contact로 간다. 전략 문서가 "가장 강한 CTA"로 지목한 경로다.

02 · 처리

접수를 확정할 화면이 두 개 다 없다

showroom_bookings·checkout_requests 모두 GET/PATCH API는 있는데 호출하는 어드민 UI가 0건이다. 접수가 requested/new에 머문다.

03 · 측정

퍼널 뒤쪽 두 단계가 데이터에서 사라진다

쇼룸·구매 리드가 source: "contact_page"를 빌려 쓴다. 리드 랭킹의 showroom: 14 가중치는 한 번도 실행되지 않는 죽은 코드다.

그림 1 · 진입 경로 지도

사이트 전역 진입점 5개 중 쇼룸으로 가는 것은 0개다

헤더·푸터·모바일 CTA는 문의로, 홈의 두 CTA는 리드마그넷 다운로드로 간다. 쇼룸으로 들어오는 링크는 문의 화면 사이드바의 작은 텍스트 링크와 실험용 랜딩뿐이다.

원천이 조용히 비면 연휴가 예약 가능일로 열린다

구글 서비스 계정 자격이 없으면 공휴일 조회가 빈 배열을 반환한다. 설날·추석이 예약 가능일로 표시되고, 화면에 어떤 저하 신호도 없다. "덜 막는" 방침 자체는 타당하지만, 그 방침이 자격 미설정이라는 상시 상태에도 똑같이 적용되면 연휴에 예약을 받는다.

막힌 날짜의 이유가 캘린더에 없다

P0

장바구니 합계가 설치비를 빼고 계산된다

설치 유형 라디오가 신청 모달 안에만 있어, 좌측 합계는 설치비를 모른다. 1차 기획이 "설치를 가격에 반영했다"고 기록한 범위가 모달까지였고, 그 앞 단계는 그대로다.

P1

자유서술이 필수이고, 자동완성이 꺼져 있다

필수 6개 중 하나가 textarea다. "전화 주세요"만 하려는 사람도 작문해야 한다. autoComplete 속성은 페이지 전체에 2개뿐이라 모바일 타이핑 비용이 그대로 든다. 필수 해제는 서버 변경 없이 가능하다 — 클라이언트가 문의 유형 접두를 조합하므로 본문이 비어도 서버 필수 검사를 통과한다.

P2

디자인 시스템 위반이 이 화면에만 남아 있다

블루-그레이 slate-* 55회. 신규 화면(/showroom·/checkout)은 0회인데 문의 화면만 구 스타일이다. 자동 가드는 어드민 한 폴더만 스캔하고 검사 패턴에 slate-가 없어 공개 화면은 무검사다.

scripts/check-design-tokens.mjs:20

실행 순서

유입을 늘리기 전에 처리할 화면이 서 있어야 한다

같은 배포에 싣는다
PHASE A

도달과 신뢰

쇼룸 진입 경로 신설, 설치비를 장바구니 합계에 반영, 희망일 주말·공휴일 차단, 폼 마찰 3건.

PHASE B

운영 루프 닫기

접수 큐 어드민 화면, 마이그레이션 적용 확인 수단, 고객 확인 경로, 저하 신호.

PHASE C

데이터 정합

리드 source 확장, 직책·규모·honeypot 추가, UTM·익명 ID 배선, 계측 allowlist 확장.

PHASE D

UX 심화

캘린더 상태 표시와 접근성, 문의 화면 재구성, 공개 화면 디자인 가드, 폼 계약 테스트.

A와 B를 붙이는 이유: 유입만 늘리고 처리 화면이 없으면 "1영업일 내 연락" 약속이 구조적으로 깨진다. C를 D보다 먼저 두는 이유: A·B의 효과를 재려면 계측이 먼저 서 있어야 하는데, 지금은 구매 화면 진입조차 데이터에 없어 개선 전후 비교가 불가능하다.

판단 대기

이번 라운드에서 새로 열린 결정

1차 문서의 D1~D8은 그대로 유효하다. 아래는 각각 제안을 붙여 문서에 기록했다.

#결정제안
D9 접수 큐 어드민 화면의 위치 CRM 리드 큐 안의 "접수" 탭에 쇼룸·구매를 함께. 알림 링크가 이미 리드 큐를 가리킨다. 캘린더는 확정된 일정을 보는 곳이고 접수는 처리할 큐다
D10 고객 확인 발송 범위 이메일로 시작. 이메일이 선택 필드라 전원 발송은 불가능하고, 필수화는 마찰을 늘린다. 알림톡은 외부 발송 요건이 따라붙는다
D11 구매 화면 계측 복구 여부 복구한다. 다만 동의 배너를 띄우면 터널 UX가 바뀌므로, 동의 없는 방문자의 내부 적재를 함께 정해야 한다
D12 희망일에 오전/오후 선호를 받을지 받는다. 지금은 시간대 정보가 없어 설치 조율에 통화가 한 번 더 든다. 슬롯 확정은 하지 않는다
D13 문의 폼 직책을 선택지로 올릴지 올린다. 자유 입력이라 집계 키로 못 쓴다. 다만 직책은 리드 스코어에 0점이라 집계·검색에 한정된 이득이다
D14 쇼룸을 헤더에 넣는 방식 운영 합의 필요. 헤더는 모든 화면에 걸리고 모바일 폭 제약이 있다. 플레이북이 "시안 먼저 합의"를 요구하는 영역

즉시 확인

결정이 아니라 운영 점검 항목

환경 변수 점검

구글 서비스 계정 자격이 운영 환경에 설정돼 있는지 확인이 필요하다. 미설정이면 공휴일 조회가 조용히 빈 배열을 반환해 설날·추석이 예약 가능일로 열린다. 화면에 아무 신호도 없어 그럴듯하게 보인다.

설정돼 있다면 화면 저하 신호만 추가하면 된다. 아니라면 — 이미 연휴 예약을 받고 있었다는 뜻이므로 즉시 조치 대상이다.
