## 1. 한 줄 원칙

문서센터는 제품 기능을 나열하는 곳이 아니라, 학원이 ClassIn을 도입하고 운영하면서 같은 실수를 반복하지 않도록 돕는 공개 운영 지식 베이스다.

## 2. 정보 구조 — 카테고리 8개와 의도 카드 4장

공개 경로는 `/docs` 하나다. 옛 경로 `/guides`와 옛 분류(빠른 시작 / 운영 가이드 / 기능 매뉴얼 / 도움말 / 문제 해결)는 더 쓰지 않는다. 문서는 아래 8개 카테고리 중 하나에만 둔다(원천: `lib/docs.ts`의 `docsCategories`).

| 카테고리 (id) | 독자 | 쓰는 내용 | 쓰지 않는 내용 |
| --- | --- | --- | --- |
| 클래스인 시작하기 (`start`) | 처음 쓰는 사람, 도입 검토자 | 설치, 회원 가입, 로그인·접속 문제, 도입 전 FAQ | 긴 기능 설명, 가격 단정 |
| 소프트웨어 가이드 (`software`) | 기능이 궁금한 사람 | 교실·판서, 학습 활동, AI 기능, 통계, 요금제 개요 | 역할별 따라 하기 순서(관리자·교사 가이드로) |
| 관리자 가이드 (`admin`) | 원장·실장·운영팀 | 유료 전환, 기관 설정, 교사·학생 추가, 코스 개설, 스토리지, 모니터링, 통계 | 수업 진행 요령 |
| 교사 가이드 (`teacher`) | 수업을 맡은 강사 | 코스·구성원, 학습 활동, 교실 설정, 자료, 웹 라이브, 녹화 문제 | 결제·계약 |
| 학생 가이드 (`student`) | 학생·학부모 | 코스 참여, 수업·다시보기, 숙제 제출, 학습 보고서 | 관리자 화면 |
| 하드웨어 가이드 (`hardware`) | ClassIn Board 사용·검토자 | 판서·기본 조작, AI 카메라·마이크, 모델 사양, 안전 수칙 | 확인되지 않은 사양 |
| 전자칠판 배송·설치 (`board`) | IT 담당자, 설치 엔지니어 | 배송 뒤 설치, 카메라 연결 | 판매 조건 |
| 업데이트 (`updates`) | 운영팀 | 무엇이 바뀌었고 무엇을 확인할지 | 검증되지 않은 릴리즈 약속 |

홈의 의도 카드 4장은 카테고리와 다른 축(독자의 상황)이다. 카드는 카테고리로 연결되지만, 글을 쓸 때는 "이 글이 어느 카드 독자의 첫 3편이 될 수 있는가"를 함께 본다.

| 의도 카드 | 연결 카테고리 | 카드 독자가 찾는 것 |
| --- | --- | --- |
| 도입을 검토하고 있어요 | `start` | 우리 학원에 맞는지, 무엇이 필요한지 |
| 학원을 운영하고 있어요 | `admin` | 계정·코스·권한 같은 운영 설정 |
| 수업을 맡고 있어요 | `teacher` | 수업 전 준비부터 판서, 녹화, 과제까지 |
| 수업을 듣고 있어요 | `student` | 참여 방법, 수업 중 알아둘 점, 다시보기 |

### 수업 한 바퀴 안의 자리

모든 글은 수업 한 바퀴(설치 → 준비 → 교실 점검 → 판서·녹화 → 다시보기 → 과제·관리자 데이터) 중 어디에 있는지 첫 문단에서 알 수 있어야 한다. `/docs/first-week`는 이 여정을 DAY 1 / 2–3 / 4–5 / 6–7 네 단계로 묶어 보여 준다. 새 글이 이 여정의 한 단계를 대표하면 first-week 링크 후보로 올린다.

### 편집 원칙

- 독자가 지금 하려는 일에서 출발한다(기능 이름이 아니라 행동).
- 하지 말 것: 내부 표현 공개, 확인하지 않은 화면명·버튼 위치·가격, 같은 주제 중복 공개, 옛 경로 `/guides`.

## 3. 따라 하기 글 작성 틀

관리자·교사 가이드처럼 순서를 따라 하는 글은 아래 순서로 쓴다.

1. 대상: 원장, 운영팀, 교사, 상담팀 중 누가 읽는지 명시한다.
2. 언제 쓰는가: 첫 수업 전, 도입 첫 주, 월말, 상담 전처럼 사용 순간을 적는다.
3. 목표: 이 가이드로 줄이려는 운영 사고를 한 문장으로 쓴다.
4. 권장 순서: 사용자가 그대로 따라 할 3-7단계를 쓴다.
5. 체크리스트: 완료 여부를 확인할 수 있는 문장으로 쓴다.
6. 복사 문구: 학부모, 교사, 내부 담당자에게 보낼 수 있는 짧은 안내문을 넣는다.
7. 흔한 실수: 실제 운영에서 놓치기 쉬운 항목을 예방 문장으로 쓴다.
8. 관련 문서: 매뉴얼, 도움말, 문제 해결 문서로 다음 경로를 연결한다.
9. 챗봇 요약: 상담 답변에 바로 쓸 수 있도록 단정한 한 문장으로 정리한다.

## 4. 미완성 콘텐츠 처리 규칙

공개 문서에는 `TBD`, `placeholder`, `준비 중`, `확인 필요` 같은 내부 메모를 남기지 않는다.

사실 확인이 끝나지 않은 내용은 세 가지 중 하나로 처리한다.

- 공개하지 않는다: DB 전환 후에는 `status = draft` 또는 `review`로 둔다.
- 더 일반적으로 쓴다: 수치, 일정, 가격, 지원 시간을 확정하지 않고 확인해야 할 항목만 안내한다.
- 내부 문서에 둔다: 운영팀 지침, 상담 스크립트, 장애/환불/계약처럼 민감한 내용은 공개 문서와 분리한다.

공개 전에 반드시 확인해야 하는 항목:

- 요금, 할인, 환불, 세금계산서 기준
- 지원 시간, 응답 SLA, 장애 대응 약속
- 하드웨어 사양, 설치 조건, A/S 범위
- 특정 기능의 실제 화면명과 권한명
- 릴리즈 날짜와 변경 범위
- 개인정보, 보안, 계약 관련 문구

세 원천이 같은 주제를 겹쳐 다룰 수 있다. 같은 주제는 대표 문서 하나에 모으고, 나머지는 대표 문서로 연결하거나 공개 목록에서 뺀다.

### 공개 전 게이트

공개(또는 생성 digest를 공개 목록에 남기기) 전에 아래를 통과해야 한다. 규칙 초안은 `lib/docs-gate/digest-publish-gate.ts`, 현재 후보 목록은 [docs-digest-publish-gate-draft.md](./docs-digest-publish-gate-draft.md).

문서 단위 — 하나라도 걸리면 공개하지 않는다:

- 테스트·임시·샘플·제목 없음 같은 제목
- 빈 캡처(내용 없음)
- 특정 날짜에 묶인 공지성 제목(`~4/23`, `6/16 (화)`)
- 질문·지시문이 제목(`Q :`, `따라와 주세요!`, `1.`로 시작)
- 단계 없이 화면 설명만 있는 글
- 번역 툴, CS 진단 화면, 데이터 로그처럼 고객용이 아닌 화면
- 같은 제목의 앞선 문서가 이미 있음 → 대표 문서로 통합

섹션 단위 — 문서는 남기되 공개 전에 고친다:

- "CS 주의사항과 원본 캡처" 섹션: 원본 파일명과 캡처 주석은 공개하지 않는다. 고객에게 유효한 주의/팁만 본문으로 옮긴다.
- "빨간 박스", "스텝 N:", "강조됨" 같은 캡처 판독 문장: "○○을 누릅니다"처럼 행동 문장으로 다시 쓴다.
- 생성 오타(예: "주세요요합니다", "설졍").

게이트는 현재 초안이며 공개 목록에 자동 적용하지 않는다. 제외 후보는 사람이 검토하고, 승인된 것만 `INTERNAL_ONLY_CS_FIGMA_DOC_SLUGS` 또는 생성기에 반영한다. 대량 삭제는 승인 후다.

## 6. 먼저 채울 글

먼저 채울 공개 글은 아래 순서다(카테고리는 관리자·교사·학생 가이드).

1. 도입 첫 주 운영 플레이북
2. 교사 온보딩 운영 가이드
3. 학생·학부모 사전 안내 가이드
4. 수업 전 10분 운영 루틴
5. 출결·보강 운영 기준 가이드
6. 월말 운영 리포트 확인 가이드
7. 재등록 리스크 상담 대응 가이드

이 중 1-4는 첫 수업 사고를 줄이는 문서이고, 5-7은 운영 리듬과 상담 품질을 높이는 문서다.

현재 문서 보강 우선순위에서는 ClassIn 수업 생성 옵션(수업 녹화·현장 녹화·온스테이지·하이브리드 수업·개인 칠판) 오개념 정비를 채널톡 연동 문서와 채널톡 상담 가이드보다 소폭 앞에 둔다.

## 7. 문장 톤

- 고객에게 불안감을 주는 표현보다 행동을 안내하는 표현을 쓴다.
- "문제가 발생하면"보다 "수업 중에는 먼저 빠르게 복구합니다"처럼 쓴다.
- "반드시"는 법적/계약적 기준이 확실할 때만 쓴다.
- 제품 기능이 아직 확정되지 않았으면 기능명보다 운영 행위 중심으로 쓴다.
- 내부 메모, 개발 상태, 임시 구현 상태는 공개 문서에 넣지 않는다.

## 8. 게시 전 체크리스트

- 대상 독자가 첫 문단에서 바로 보이는가?
- 사용 순간과 운영 목표가 분명한가?
- 체크리스트가 실제 완료 여부를 판단할 수 있는 문장인가?
- 안내 문구가 그대로 복사해도 어색하지 않은가?
- 관련 문서 slug가 실제로 존재하는가?
- 챗봇 요약이 원문보다 과장하지 않는가?
- 가격, 지원 시간, 기능명, 날짜가 검증된 값인가?
- 공개하면 안 되는 내부 정책이나 민감 정보가 없는가?
- 8개 카테고리 중 하나에 맞게 두었고, 수업 한 바퀴 안의 자리가 첫 문단에서 보이는가?
- 같은 주제의 대표 문서가 이미 있지 않은가?
- 공개 전 게이트(5장)에 걸리는 제목·섹션·오타가 없는가?

### 정식 발표 배포 체크리스트

- [ ] 로컬 관리자(`/admin/docs`)에서 상단 상태가 `Supabase live`인지 확인한다.
- [ ] 발표 문서는 검수 중 `draft` 또는 `review` 상태로 두고, 공개 전에는 필요하면 `unlisted`로 링크 검수한다.
- [ ] 공개 문서 화면 검수 시 로컬과 운영 환경의 `USE_SUPABASE_DOCS=true` 설정 여부를 확인한다.
- [ ] 최종 승인 후 문서 상태를 `published`, 공개 범위를 `public`으로 바꾼다.
- [ ] 저장 후 문서 검색 인덱스를 재생성하고, 공개 `/docs/...` URL에서 제목, 본문, SEO, 관련 문서를 확인한다.
- [ ] 운영 DB에서 관리자 수정본을 원본으로 삼는 문서는 `scripts/seed-docs.ts` 재실행이나 upsert migration으로 덮어쓰지 않도록 배포 전 확인한다.

### 정적 시드 상태 규칙

`lib/docs.ts`의 문서는 정적 폴백 원천이면서 `scripts/seed-docs.ts`의 Supabase 시드 원천이다. 정식 공개 전 검수용 문서는 정적 원천에서도 아래 메타데이터를 명시한다.

- `status: "review"` 또는 `status: "draft"`로 둔다.
- `visibility: "unlisted"`와 `noindex: true`를 함께 둔다.
- 챗봇에 공개 답변으로 쓰면 안 되는 검수 문서는 `published`로 바꾸기 전까지 `noindex: true`를 유지한다.

현재 검수용으로 시드되는 체크리스트 문서:

- `admin/academy-system-checklist`
- `hardware/electronic-whiteboard-classroom-checklist`

`scripts/seed-docs.ts`는 위 상태/공개범위/색인 제외 값을 그대로 upsert한다. 따라서 시드를 실행해도 두 문서는 관리자 문서 탭에서 편집 가능하지만, 공개 목록·공개 검색·챗봇 답변에는 승인 전 노출되지 않는다.

## 9. DB 전환 후 운영 방식

v0에서는 [lib/docs.ts](../../lib/docs.ts)를 공개 원천으로 사용한다.

DB 전환 후에는 `docs_articles.status`로 작성 단계를 관리한다.

- `draft`: 내부 초안
- `review`: 사실 확인과 톤 검수 중
- `published`: 공개 가능
- `archived`: 더 이상 현재 기준이 아님

`visibility`는 공개 전략을 관리한다.

- `public`: 목록과 검색에 노출
- `unlisted`: 직접 링크, 관련 문서, 챗봇 검색에는 사용하되 대표 목록에서는 덜 강조
- `internal`: 운영팀/상담팀 내부용

문서 수정은 원문, 챗봇 요약, 관련 문서, 검색 키워드를 함께 갱신해야 한다.
