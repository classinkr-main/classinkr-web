## 0. 한 줄 결론

**에이전트를 많이 만들지 않는다. 지침(헌법·플레이북·스킬)을 두껍게 만들고, 오케스트레이터 1 + 운영 에이전트 7 + 빌더 에이전트 6이 그 지침을 공유하며 돈다.** 사람 8명은 판단·승인·통화·방문에만 시간을 쓰고, 수집·정렬·초안·집계·대조는 전부 기계가 한다.

"에이전트를 잔뜩 만들어 팀을 꾸리는 것보다, 팀 같은 지침을 많이 깔고 유기적으로 돌리는 게 결과가 좋다"는 말은 빅테크 가이드와 이 저장소의 7월 설계 원칙 양쪽이 같은 결론으로 수렴한 사실이다(부록 A §A.7). 그래서 이 기획의 "팀"은 **에이전트 수**가 아니라 **지침 계층 × 승인 게이트 × 운영 리듬**이다. 에이전트는 그 지침을 실행하는 얇은 진입점일 뿐이다 — 이미 `.claude/agents/*.md`가 플레이북으로 라우팅하는 얇은 진입점으로 설계된 것과 같은 철학을 사업 운영 전체로 확장한다.

### 4.2 L1 — 오케스트레이터 "지사 참모" (1개)

- **역할**: 사람이 말하는 모든 요청과 스케줄 트리거의 **단일 진입점**. 요청을 기능군(§2)으로 분류 → 해당 운영 에이전트에 위임 → 산출물을 헌법 기준으로 검수 → 승인 큐에 올리거나 사람에게 질문.
- **직접 하는 일**: 아침 브리프(북극성 3숫자 + 오늘 액션 큐 + 승인 대기 초안), 주간 브리프(금요일 6숫자), 에이전트 간 충돌 판정(예: 같은 고객을 세일즈와 고객성공이 동시에 건드릴 때), 비용·실패 집계.
- **하지 않는 일**: 도메인 산출물을 직접 쓰지 않는다. 외부 시스템에 쓰기를 하지 않는다.
- **북극성**: 사람 1명이 하루에 승인·편집하는 데 쓰는 시간 ≤ 30분, 초안 채택률 ≥ 60%.
- **왜 1개인가**: 빅테크 가이드 전부가 "매니저 1 + 워커"를 기본형으로 두고, 워커끼리 직접 대화하는 구조는 컨텍스트 분열로 실패한다고 경고한다(부록 A §A.5).

**빌더 6 ↔ 운영 7의 관계**: 운영 에이전트가 "이 화면·이 API가 있으면 사람 시간이 준다"를 발견하면 **작업 요청서**(`docs/active/ai-team/requests/`)를 남기고, 사람이 승인하면 빌더 에이전트가 플레이북대로 구현한다. 운영 에이전트가 코드를 직접 고치지 않는다.

**왜 7개인가**: 기능군 10개를 사람 오너 기준으로 묶으면 7이 된다. 오너가 같은 기능군은 한 에이전트가 맡아야 컨텍스트가 끊기지 않는다(원칙 4). 8번째 이상은 스킬로 흡수한다. 나중에 CSM #2·RevOps가 채용되면 C·D의 사람 오너만 바뀐다.

### 4.4 L3 — 스킬·플레이북 (팀의 대부분은 여기)

스킬 1개 = 반복되는 업무 절차 1개. Anthropic Agent Skills(`SKILL.md`)·`.codex/skills/classin-kr-team` 형식을 따른다. **에이전트를 늘리는 대신 스킬을 늘린다.**

```
docs/active/ai-team/skills/<skill-name>.md
---
name: weekly-report-fill
owner_agent: F
human_owner: MKT 팀장
gate: 2 (초안 → 사람 원클릭)
schedule: 금 14:00 KST (ledger-weekly-close 크론 뒤)
inputs: REV 시트 주차 수금, Compass 과정 KPI, 광고 insights, Notion KA 단계표(지난주)
outputs: Notion "팀주간/월간보고서" 신규 주차 페이지 초안(표 10개 채움 + 결론 4문단 초안 + "확인 필요" 카드)
sources_rule: 모든 숫자에 (출처·기준시각) 병기, 통화 혼합 금지
forbidden: 제출, 원장 수정, 없는 숫자 추정
eval: 사람이 수정한 셀 수 / 전체 셀 수 (목표 ≤ 10%)
---
절차 1. … 2. … (사람이 읽어도 그대로 수행 가능한 수준)
```

Phase별 스킬 목록은 §7. 첫 10개: 주간보고 채우기 · 월간 VP 보고 초안 · 광고 누수 감시 · 광고 예산 사용표 갱신 · 리드 트리아지 · 데모 F/U 시퀀스 · 30일 활성화 리스트 · 리뉴얼 D-day 큐 · 입출고 대조 · 데이터 헬스 점검.

## 5. 승인 게이트 — 4등급

모든 스킬은 등급 하나를 갖는다. 등급이 없는 스킬은 가동하지 않는다.

| 등급 | 의미 | 예 |
|---|---|---|
| **G1 자동 실행** | 되돌릴 수 있고 외부에 나가지 않는 읽기·집계·대조·내부 알림 | 데이터 헬스 배지, 광고 CPL 이상 탐지 카드, 입출고 불일치 리포트, 아침 브리프 |
| **G2 초안 → 사람 원클릭** | 산출물은 완성형이지만 실행은 사람 | 주간보고 초안, 견적 패키지 초안, 드립 이메일 초안, 콜 스크립트, 온보딩 콜 예약, 제안서 초안, 작업 요청서 |
| **G3 사람 작성 → AI 검토** | 판단이 사람 것, AI는 린트·대조·누락 지적 | KA 협상 메모, 파트너 조건, 평가 코멘트, 본사 지원 요청, 가격 정책 |
| **G4 AI 금지** | 법·돈·관계가 걸린 최종 행위 | 고객 발송 실행, 콘텐츠 게시, 광고 집행 변경, 출고 확정·재고 조정, 원장 수정, 서명·계약, 세금계산서, 평가 판정, 보고 제출 |

승인 큐는 자동화 설계의 `crm_tasks` 스파인 + `agent_drafts`를 그대로 쓴다(새 테이블을 만들지 않는다, P6). 초안 카드는 "출처·기준시각·확인 필요 항목·채택/수정/폐기" 4요소를 갖는다. 폐기 사유는 에이전트 원장에 자동 적재된다.

## 7. 로드맵 — 켜는 순서

자동화 설계가 못박은 "척추 먼저, 병렬 착수 금지"를 따른다. 각 Phase는 **사람이 체감하는 시간 절감 1개**를 기준으로 닫는다.

### Phase 0 — 헌법과 참모 (2주)

- [ ] `docs/active/ai-team/constitution.md` 작성(4등급 게이트·산출물 형식·금지어·통화·PII·에스컬레이션). L0 기존 문서 링크만, 복제 금지.
- [ ] 오케스트레이터 정의 1개(`.claude/agents/chief-of-staff.md`) — 라우팅 표는 §2 기능군, 위임 대상은 운영 에이전트 파일.
- [ ] 운영 에이전트 7개의 **얇은 진입점 파일**(각 30줄 이내: 소유 기능군·오너·북극성·먼저 읽을 문서·금지).
- [ ] 스킬 2개 가동: **주간보고 채우기**(F) · **아침 브리프**(L1). 둘 다 읽기 전용.
- [ ] 에이전트용 읽기 전용 어드민 계정·capability, Notion 초안 전용 권한.
- [ ] 원장 파일 7개 생성, 채택률·비용 기록 시작.
- 닫는 기준: 금요일 주간보고 작성 시간이 사람 기준 절반 이하. 숫자 수정 셀 ≤ 10%.

### Phase 1 — 돈이 새는 곳 (1개월)

- [ ] G: 광고 누수 감시 · 광고 예산 사용표 갱신 · 설명회 F/U 시퀀스.
- [ ] S: 리드 트리아지 · 데모 F/U 시퀀스 · 견적 패키지 초안 · KA 단계표 갱신.
- [ ] F: 월간 VP 보고 초안 · 수금 예정 vs 실제 대조 · 미수금 알림.
- [ ] 선행 과제(빌더 트랙): Hot Lead 5분 알림 켜기, `leads.first_response_at` 스탬프 UI, `crm_tasks` 스파인 물리화.
- 닫는 기준: 핫리드 5분 응대율이 측정되고, CPL 이상이 24시간 안에 카드로 뜬다.

### Phase 2 — 반복매출과 재고 (1개월)

- [ ] C: 30일 활성화 리스트 · D+1/7/14 콜 예약·스크립트 · 리뉴얼 D-day 큐 · 상위 10사 이상신호 · 성공사례 초안.
- [ ] H: 입출고 대조 · 배송예정·샘플 추적 · 설치팀 일정 초안 · 수입 서류 체크리스트.
- [ ] 선행 과제: 채널톡 원문 적재(P0), HW 시트↔어드민 이관 결정(하드웨어 프로세스 정의서 §2 질문 10개), 활성화 배럴 사람 지정.
- 닫는 기준: 설치 후 30일 미사용 계정이 매일 아침 큐 상단에 있고, 시트↔어드민 불일치가 0.

### Phase 3 — 행정·조직·학습 루프 (지속)

- [ ] F: 인증·조달 요건 체크리스트·기한 추적, 본사 지원 요청 정리, AI 비용 리포트.
- [ ] P: 과정 KPI 집계, 온보딩 커리큘럼, 채용 JD(CSM #2·RevOps).
- [ ] D: 정본 불일치 리포트 상시화, 작업 요청서 → 빌더 트랙 파이프.
- [ ] L1: 분기 캐논 갱신 제안, 스킬 채택률 기반 폐기·개선.
- 닫는 기준: 신규 입사자가 플레이북+에이전트만으로 D+30에 독립 수행.

**하지 말 것**: 7개 넘는 운영 에이전트, 에이전트 간 직접 메시지, 외부 쓰기 API 연결(광고·발송·결제), 정본 복제 테이블, 평가·급여 데이터 접근, "AI가 알아서"라는 말로 게이트 등급을 비우는 것.

사고 대응: 에이전트가 잘못된 숫자·문구를 낸 경우 (1) 해당 스킬 즉시 비활성 (2) 원장에 실패 패턴 기록 (3) 골든셋에 케이스 추가 (4) 지침 수정 후 재가동. 사람 실수와 같은 절차다.

### A.1 Anthropic

- **Building effective agents** (anthropic.com/engineering/building-effective-agents): 워크플로(코드가 정한 경로) vs 에이전트(LLM이 스스로 경로 결정). 패턴 5개 — 프롬프트 체이닝·라우팅·병렬화·**오케스트레이터-워커**·평가자-최적화. "가장 단순한 해법을 찾고, 필요할 때만 복잡도를 올려라." 자율성은 "비용과 오류 누적 위험"을 키운다. 도구 문서는 사람 신입에게 설명하듯.
- **How we built our multi-agent research system** (…/multi-agent-research-system): 리드 에이전트가 계획·분배·종합. 내부 평가에서 단일 에이전트 대비 90.2% 향상했지만 토큰은 **채팅의 약 15배**. 적합: 병렬화 큰 조사, 컨텍스트 초과, 도구 다수. 부적합: 공유 컨텍스트·강한 상호의존(대부분의 코딩). 위임 프롬프트에는 "목표·출력 형식·도구 지침·경계"가 반드시 들어가야 한다. 평가는 약 20개 현실 케이스 + LLM 판정 + 사람 수동 확인. 체크포인트·재시도·전체 추적 필수.
- **Building multi-agent systems: when and how** (claude.com/blog, 2026-01): 기본은 **단일 에이전트**. 분할 이유는 셋뿐 — 컨텍스트 오염, 병렬화, 도구 선택을 돕는 특화. 그 밖에는 "조정 비용이 이익을 넘는다", "단일 에이전트 프롬프트 개선으로 동등한 결과". 멀티는 토큰 3~10배. "서브에이전트를 줄이고 **점진적으로 공개되는 컨텍스트와 도구**를 써라."
- **Effective context engineering** (…/effective-context-engineering-for-ai-agents): 컨텍스트는 유한한 "주의 예산". 시스템 프롬프트는 "적절한 고도"(if/else도 모호함도 아님). 도구는 최소·명확 — "사람 엔지니어가 어느 도구를 쓸지 단정 못 하면 에이전트도 못 한다." 장기 작업은 압축·구조화된 메모(파일)·적시 검색·요약만 돌려주는 서브에이전트.
- **Writing tools for agents** (…/writing-tools-for-agents): 도구가 많다고 좋지 않다. 연쇄 단계를 하나로 합치고, 서비스별 네임스페이스, 고신호 필드만 반환, 설명은 신입 온보딩처럼.
- **Agent Skills** (…/equipping-agents-for-the-real-world-with-agent-skills): `SKILL.md` 디렉터리. "점진적 공개가 핵심 설계 원칙" — 메타데이터는 항상, 본문은 트리거 시, 연결 파일은 필요 시. 스킬은 **절차 지식의 재사용 단위**. 평가에서 출발.
- **Claude Code subagents / agent teams** (code.claude.com/docs): 같은 지시의 워커를 반복 생성할 때만 서브에이전트. 반복 왕복·공유 컨텍스트 큰 단계·빠른 수정에는 쓰지 말 것. 팀은 "먼저 더 가벼운 방법이 되는지 확인", **3~5명**, "집중된 3명이 흩어진 5명보다 낫다", 일반 세션 대비 약 7배 토큰.
- **Managed Agents·하네스 설계** (claude.com/blog, …/effective-harnesses-for-long-running-agents, …/harness-design-long-running-apps): 서브에이전트는 1단계 깊이·상한. 자기 평가는 편향되므로 **평가자를 분리**("독립 평가자를 회의적으로 튜닝하는 편이 훨씬 다루기 쉽다"). 하네스 구성요소는 "모델이 혼자 못 하는 것에 대한 가정"이라 모델이 좋아지면 제거한다. 세션 로그가 진실의 원천, 자격증명은 하네스에 두지 않는다.

### A.2 OpenAI

- **A practical guide to building agents** (cdn.openai.com, PDF): "단일 에이전트의 역량을 먼저 최대화하라… 종종 도구를 가진 단일 에이전트로 충분하다." 분할 신호는 복잡한 지시 미준수·잘못된 도구 선택 반복. 도구 수보다 **유사·중복**이 문제. 두 형태 — **매니저 패턴**(에이전트를 도구로, 한 에이전트만 사용자 접점) vs 분산 핸드오프. 가드레일은 층층이(분류기·정규식·도구 위험등급). 사람 개입 트리거 둘 — 실패 임계 초과, 고위험(되돌릴 수 없음·결제) 행동.
- **Agents SDK handoffs** (openai.github.io/openai-agents-python/handoffs): 핸드오프는 LLM에게 도구로 보인다. `as_tool`은 호출자가 통제 유지, handoff는 대화 소유권 이전.
- **AgentKit/Agent Builder**: 노코드 빌더는 2026-11-30 종료. 코드는 Agents SDK, 자연어 업무는 ChatGPT Workspace Agents로. **Frontier**(2026-02)는 에이전트를 "AI 동료"로 — 신원·권한 범위·온보딩·피드백·성과 리뷰, 즉 오케스트레이션보다 **에이전트 운영 거버넌스**.

### A.3 Google

- **ADK 멀티에이전트 패턴** (developers.googleblog.com, adk.dev): Sequential(결정적, 디버그 쉬움)·Parallel(각자 고유 상태 키)·Loop(생성-비평, 반복 상한)·LLM 위임 코디네이터·AgentTool·**사람 승인 도구**(되돌릴 수 없는 행동). "session.state가 화이트보드", 서브에이전트 설명이 "LLM용 API 문서", "첫날부터 중첩 루프를 만들지 말고 순차 체인부터".
- **A2A** (a2a-protocol.org): MCP는 에이전트↔도구, A2A는 에이전트↔에이전트. Agent Card로 발견. Linux Foundation 산하.
- **Google Cloud 멀티에이전트 참조 아키텍처 / Gemini Enterprise**: 코디네이터가 라우팅, 반복 상한, 사람이 "감시·override·일시정지". 에이전트별 신원·최소권한·기본 거부 egress·레지스트리·전체 추적, 사용 사례마다 측정 가능한 결과.
- **Towards a Science of Scaling Agent Systems** (arxiv 2512.08296): 멀티에이전트 효과는 "+80.8%(분해 가능한 재무 추론)에서 −70.0%(순차 계획)까지". 단일 기준이 높아지면 수익 체감. **중앙 검증 없는 구조는 오류를 더 전파**.

### A.4 Microsoft

- **Agent Framework orchestrations** (learn.microsoft.com): Sequential·Concurrent·Handoff(메시 — 수신 에이전트가 완전 소유)·Group Chat(매니저가 발화자 지정, 턴 상한)·Magentic(작업 원장+진행 원장, 정체 감지 시 재계획). Magentic은 "원 설계 밖에서는 검증 안 됨 — 단순하면 Group Chat". 승인 필요 도구·체크포인트로 며칠짜리 대기.
- **Copilot Studio multi-agent guidance** (2026-05): "하위 작업마다 에이전트를 만들지 마라." 분할 조건: 고유 도구·지식 도메인, 다른 거버넌스·접근, 서비스로 재사용. **"부모 에이전트만 최종 응답. 서브에이전트는 응답자가 아니라 조사자."** MUST/NEVER 언어, 서브에이전트마다 겹치지 않는 지식 소스 1개, 연결된 에이전트 호출을 "강력한 행동"처럼 취급.

### A.5 논쟁: 소수 강한 에이전트 vs 다수 전문 에이전트

- **Cognition, "Don't build multi-agents"** (2025-06): "컨텍스트를 공유하라, 메시지가 아니라 전체 추적을", "행동은 암묵적 결정을 담고, 충돌하는 결정은 나쁜 결과를 낳는다". 가장 단순한 준수법은 단일 스레드 선형 에이전트 + 압축.
- **Cognition, "Multi-agents: what's actually working"** (2026-04): 되는 것 — 깨끗한 컨텍스트의 검증자 루프, 더 강한 모델로의 에스컬레이션, 구조화된 매니저→자식 map-reduce, **읽기 전용 서브에이전트(사실상 도구 호출)**. 비구조화 스웜은 "대부분 산만". 규칙: **쓰기는 단일 스레드, 추가 에이전트는 행동이 아니라 지능을 더하는 데**.
- **LangChain, "How and when to build multi-agent systems"**: Cognition과 Anthropic은 동의하는 바가 더 많다 — 컨텍스트 엔지니어링이 핵심, 읽기는 병렬·쓰기는 아님, 최종 산출물은 한 에이전트가, 작은 평가(약 20건).
- **벤치마크**: Tran & Kiela(Stanford, 2026-04, arxiv 2604.02460) — 같은 사고 토큰 예산에서 "단일 에이전트가 일관되게 멀티를 따라잡거나 능가". Google 스케일링 연구 — 팀 크기가 아니라 **작업 구조**가 결정, 순차 작업은 39~70% 손실.

### A.6 실무자·유튜브 (SMB 운영)

- Nate Herk: AI를 "채팅 도구가 아니라 신입 직원"으로. "일이 밀리고 돈이 새는 곳"에서 시작. 2025년 n8n "궁극의 에이전트 팀" 템플릿은 오케스트레이터 1 + 도메인 서브에이전트 4(이메일·캘린더·연락처·콘텐츠). 2026-11 인터뷰에서 **"에이전트 하나가 마케팅팀 전체를 돌린다"는 과장**이라 했고, 오래된·모순된 데이터 위에서 "정확히" 행동하는 실패 모드를 경고.
- Nick Saraev: 대량·저위험 → 에이전트, 고가치 → 결정적 워크플로. "에이전틱 워크플로"는 LLM을 라우터로만 두고 실행은 코드로.
- Cole Medin(2026 Principled Agentic Engineer): 린한 컨텍스트의 주 오케스트레이터 1 + 10만 토큰을 태우고 **짧은 요약만** 돌려주는 조사 서브에이전트. 컨텍스트 엔지니어링(PRP) > 바이브 코딩.
- Andrej Karpathy(2026-04 AI Ascent): 에이전트는 "오류 가능·확률적". 체크포인트마다 사람 승인으로 "목줄"을 잡고, 검증기가 신뢰를 증명한 곳에서만 자율성을 올린다. 지표가 명확하면(AutoResearch) 완전 자율 루프도 가능.
- Liam Ottley: 엔터프라이즈 실패 vs SMB 성공, 결과를 팔아라, 테스트·최적화에 투자. 단순 챗봇은 범용화됨.
- 공통 실패 모드: 에이전트가 사용자에게 직접·중복 응답, 오래된 지식, 조정 비용이 일보다 큰 과분할, **에이전트 오너 부재**, 사람 감독 계획 없음(2026 설문: 36%가 없음).

### A.7 모든 출처가 동의하는 12개 규칙

1. 강한 에이전트 하나로 시작, 증거가 있을 때만 추가.
2. 분할 이유는 셋뿐 — 컨텍스트 오염·진짜 병렬·도구/지시 과부하. "부서마다 하나"는 아니다.
3. 오케스트레이터 하나가 작업을 소유하고 사용자에게 말하는 유일한 목소리. 워커는 조사자.
4. 읽기는 병렬, 쓰기는 직렬. 최종 산출물은 한 에이전트가 쓴다.
5. 위임 프롬프트에 목표·출력 형식·도구 지침·경계.
6. 생성자와 평가자 분리. 검증자는 깨끗한 컨텍스트 + 루브릭.
7. 도구는 최소·명확. 에이전트를 늘리는 대신 **점진적 공개(스킬)**.
8. 컨텍스트는 예산 — 압축·파일 메모·적시 검색·요약 반환.
9. 되돌릴 수 없는·고가치 행동과 실패 임계 초과에 사람 개입. 승인 필요 도구, 며칠 기다릴 수 있는 체크포인트.
10. 예산·상한 — 토큰, 반복·라운드·정체 횟수, 팀 3~5, 위임 깊이 1.
11. 관측·내구성 필수 — 전체 추적, 에이전트별 신원·최소권한, 재개 가능한 체크포인트.
12. 일찍·작게 평가(약 20건 + 사람 검토). 모델이 바뀔 때마다 하네스를 재검토해 죽은 부품을 뺀다.

### A.8 출처가 갈리는 곳

- 동료 간 자율성: OpenAI(핸드오프)·Microsoft(Handoff/Group Chat)는 분산 패턴을 제공, Anthropic·Cognition은 리드 1 + 1단계 위임을 선호.
- 멀티에이전트의 가치: Anthropic은 조사에서 90% 향상, Stanford·Google은 같은 연산량에서 이득 없음·순차 작업 큰 손실. 조정: 이득은 **추가 연산과 넓이 우선 작업 형태**에서 온다.
- 토큰 배수: 15배(조사)·3~10배(2026-01)·7배(팀). Cognition은 비용을 스웜 회피 이유로, Google은 작업 적합도 다음으로.
- 컨텍스트 공유: Cognition은 전체 추적 공유, 2026년 Anthropic·Cognition은 검증자만 깨끗한 컨텍스트.
- 노코드 vs 코드: OpenAI는 시각 빌더를 접고 SDK로, Google·Microsoft는 거버넌스 붙인 노코드 유지.
- "AI 직원" 은유: 크리에이터는 조직도(오케스트레이터 + 부서 에이전트)를 팔고, 랩은 "부서별 특화는 보통 잘 지시된 에이전트 하나 + 스킬에 진다"고 말한다. **이 기획은 둘을 절충한다** — 사람 오너 단위로 7개를 두되, 업무 확장은 스킬로만.

### B.3 AI 팀 설계에 직접 영향을 주는 저장소 규칙 14개

1. AI 초안은 자동 게시·자동 발송하지 않는다(플레이북 03·05, 캐논 §7).
2. AI 권한 범위: 허용 = 지시를 오더 티켓으로, 조회·요약, 생성 보조. 금지 = 자동 의사결정, 우선순위 추천·재정렬, 사람 확인 없는 쓰기, AI 제안→실행 연결(`admin-ai-widget-remote-order-plan-2026-09-28.md` §2).
3. 외부 발송 크론은 dry-run·실행당 상한·멱등 키 필수. 계기는 2026-09-02 262건 과발송(AGENTS.md, 운영 장애 지침 §2).
4. Solapi 키가 있으면 고객에게 실발송된다. 새 환경은 `MESSAGING_DRY_RUN=1` 먼저.
5. NEO·REV·Compass 금액은 합산하지 않는다. 중복 제거는 `confirmed` 연결로만. Compass 산식을 복제하지 않는다.
6. 외부 쓰기는 초안→dryRun→승인→실행. 사람이 고른 담당자는 덮지 않는다.
7. 통화 혼합 금지(오더 USD·매출/수금 CNY·딜 KRW).
8. 표시광고법: 회사 수치 캡션, 가격·기관 수·스펙 단정 금지, "$30B" 금지.
9. 정직한 한계·금지 표현: 결제·출석·ERP 대체 주장 금지, 경쟁사 브랜드명 비노출, 한자·"준비 중" 금지.
10. 미승인 목표(`0. DSH_NEW_TEMP`, 노션 원문)는 확인 전 반영 금지.
11. 회계 증빙은 지우지 않는다(취소·역분개). 매출 초안은 금액 0, 설치 완료는 자동 감지하지 않는다.
12. 실패를 0건·성공으로 가장하지 않는다. 운영에서 JSON 폴백 금지.
13. 개인정보: 동의 전 픽셀 금지, raw IP·PII 저장 금지. 공개 캡처 PII 노출 사고 있었음.
14. 운영 DB 쓰기·배포는 사람이 실행. 노션 캘린더는 읽기 전용. 오너 없는 수기 테이블 금지.
