## 2. 확인한 결함과 수정

### 2.1 [안정성·기능] 홈 새로고침이 작업대에 닿지 않았다

`app/admin/crm/page.tsx`의 `refreshAll()`은 `neoCrmRefreshKey`를 올리고,
`CrmPriorityQueuePanel`은 그 키가 바뀌면 `load()`를 다시 부른다. 그런데 `load()`는
`force` 없이 호출돼 90초 TTL 메모리 캐시를 그대로 되돌려줬다. 결과적으로 "새로고침"을
눌러도 우선순위 큐는 한 글자도 바뀌지 않는다. `CrmWeekAheadPanel`은 아예 `refreshKey`
연결조차 없었다.

- `refreshKey` 변화를 감지해 `load({ force: true })`로 보낸다.
- `CrmWeekAheadPanel`에 `refreshKey` prop을 추가하고 홈에서 배선했다.

### 2.2 [안정성] 필터 연타 시 이전 응답이 최신 화면을 덮어썼다

`CrmPriorityQueuePanel.load()` / `CrmWeekAheadPanel.load()`는 진행 중인 요청을 취소하거나
무시하지 않았다. 레인(신규·연장·고객관리)을 빠르게 바꾸면 먼저 보낸 요청이 나중에 끝나
**제목은 새 레인, 목록은 직전 레인**인 상태로 굳는다. 화면에는 오류가 없으므로 운영자는
잘못된 목록을 정상으로 읽는다.

- 요청 세대(sequence) 가드를 넣어 마지막 요청만 상태에 반영한다.
- `loading`/`refreshing` 해제도 최신 요청에서만 한다.

### 2.3 [DB 설계·안정성] 리드 전량 조회가 조용히 잘렸다

`lib/repositories/leads.ts`의 `getLeads()` / `getDashboardLeads()` / `getCampaignLeads()`는
`range` 없이 `select`만 했다. PostgREST는 서버의 `max-rows`를 넘는 행을 **오류 없이 잘라서**
돌려준다. 이 세 함수는 리드 보드, 우선순위 큐, 캠페인 귀속의 입력이므로, 절단은
"그 리드는 없다"로 화면에 나타난다. 조용한 데이터 손실이고, 리드가 늘수록 확률이 올라간다.

- 페이지네이션 루프(`fetchAllLeadRows`)로 전량 수집을 보장한다.
- 첫 페이지에서만 `count: "exact"`로 총량을 잡아 불필요한 재조회를 없앴다.
- 페이지 전진은 **요청 크기가 아니라 실제 수신 행 수**만큼 한다. 서버 상한이 요청 크기보다
  작아도 행을 건너뛰지 않는다.
- `created_at` 단독 정렬은 전순서가 아니다 — 동시각 리드가 페이지 경계에 걸리면 중복·누락이
  생기므로 `id`를 타이브레이커로 함께 정렬한다.
- 컬럼 누락 폴백(`confirmed_at`)은 `LeadQueryError`로 원본 오류 모양을 보존해 그대로 유지했다.

회귀 테스트: `tests/repositories/leads-pagination.test.ts` (5 케이스 — 단일 페이지,
max-rows 초과, 서버 상한 < 요청 크기, 빈 테이블, 경량 컬럼 경로).

### 2.4 [입력-출력] 부분 실패를 전체 실패로 보고했다

우선순위 큐의 "연락 결과" 저장은 두 요청이다: ① 연락 로그 POST ② 리드 상태·팔로업 PATCH.
②만 실패해도 "연락 결과 저장에 실패했습니다"라고만 떴다. 운영자는 다시 입력하고, 그러면
①이 한 번 더 실행돼 **연락 기록이 중복**된다.

- 어디까지 성공했는지 상태로 추적해, 로그가 남은 경우에는 폼을 닫고 "기록은 저장됨 ·
  상태 반영 실패"로 구분해 알린다. 실패 원인 문자열도 함께 노출한다.
- 로그 자체가 실패한 경우에는 입력을 그대로 두어 재시도가 가능하게 한다.

### 2.5 [사용성] 리포트 탭이 탭이 아니었다

홈 하단 "리포트 · 분석"의 5개 탭(매출 상세·성과·리드·팀 KPI·수납/로그)은 `aria-pressed`가
붙은 버튼 묶음이었다. 스크린 리더에 탭으로 읽히지 않고, 화살표 키 이동이 없어 5번 탭까지
Tab을 다섯 번 눌러야 했다.

- `role="tablist"` / `role="tab"` / `role="tabpanel"`, `aria-selected`, `aria-controls`,
  roving `tabIndex`를 붙였다.
- ←/→ 로 탭 이동, Home/End 로 양 끝 이동을 추가했다.

### 2.6 [정보성·편의성·경로] 빈 목록이 막다른 길이었다

우선순위 큐가 비면 `"{레인} 레인에 표시할 우선순위가 없습니다."` 한 줄이 전부였다. 원인이
셋(시점 필터 / 담당자 필터 / 정말 없음)인데 구분이 없어, 운영자가 필터를 하나씩 되돌리며
알아내야 했다. 또한 조회 실패로 `data`가 없는 경우에도 같은 "없습니다" 문구가 떠서,
**못 불러온 것을 없는 것으로** 말하고 있었다.

- 실패와 빈 목록을 다른 문구로 분리했다.
- 원인을 판정해 문구를 바꾸고, 되돌릴 버튼(시점 필터 해제 / 담당 전체 / 다른 레인 N건 /
  리드 보드 열기)을 함께 준다.

### 2.7 [연결·정보성] 계산해 놓고 아무 데도 안 쓰던 값들

- `summary.sourceTotals.task`: 서버가 계산해 내려보내지만 화면에서 한 번도 렌더되지 않았다.
  할 일은 매출 기회와 경쟁시키지 않으려고 이 큐에서 의도적으로 뺀 것인데, 건수를 안 보여주니
  "할 일이 없다"로 읽힌다. 목록 아래에 활성 할 일 건수 + `/admin/crm/activity` 경로를 남겼다.
- `generatedAt`: 캐시로 뜨는 목록인데 기준 시각이 어디에도 없었다. 부제에 표시한다.

### 2.8 [기능] 월 키가 모듈 로드 시점에 굳어 있었다

`CRM_BRANCH_KPI_MONTH = getKstMonthKey(new Date())`가 모듈 최상단 상수였다. 탭을 켜 둔 채
달이 바뀐 세션은 지난달 KPI를 **이번 달 라벨로** 계속 본다.

- 조회 시점마다 KST 월을 다시 계산하고, 화면 라벨도 같은 값을 쓰도록 prop으로 내렸다.

### 2.9 [안정성] 토스트 타이머 누수

`app/admin/crm/page.tsx`와 `LeadsBoardClient.tsx`의 `showToast`가 `setTimeout` 핸들을
버렸다. 언마운트 후 `setState` 경고가 나고, 토스트가 연달아 뜨면 **이전 타이머가 새 토스트를
3초보다 빨리 지운다**.

- 타이머 핸들을 ref로 잡아 재호출 시 취소하고, 언마운트에서 정리한다.

### 2.10 [안정성] 요약 필드 방어적 접근

`summary.laneTotals[lane]` / `summary.bucketCounts.today`를 직접 인덱싱하고 있었다. 응답
스키마가 바뀌거나 이전 payload가 섞이면 렌더 중 TypeError로 패널 전체가 죽는다. 캐시 버전
키(`v:2`)가 있어 현재는 나지 않지만, 죽는 방식이 나쁘므로 `?? 0`으로 낮췄다.

## 2-B. 2차 감사에서 나온 결함과 수정

### 2B.1 [데이터 정확성] 통화가 다른 금액을 빼서 "미수" 배지를 만들고 있었다

`Customer360Drawer`가 `orderTotal($) - collectionTotal(¥)`로 `outstanding`을 만들고, 그 값을
`deriveCustomerFlags`에 넣어 "미수" 배지를 켰다. 통화가 다른 수의 뺄셈이라 결과에 의미가 없다 —
수금이 크면 미수 없음으로, 반대면 허위 미수로 나온다. 저장소는 이 혼용을 명시적으로 금지한다
(`Customer360DetailShared`: "NEO orders($)/잔액·수금·성과(¥)와 절대 섞지 않는다").

같은 통화의 미수 원천이 360 페이로드에 없으므로, 틀린 신호를 계속 만드는 대신 배지를 껐다.
통화별 금액은 '수금·성과 요약'과 상세 화면에서 이미 분리해 보여준다.

LTV도 같은 문제였다 — `collectionTotal(¥) ?? orderTotal($) ?? quoteTotal(₩)` 중 아무거나 골라
한 숫자로 쓰고 표기는 **항상 `₩`**를 붙였으며, VIP 기준선 `30,000,000`을 통화 구분 없이 적용했다.
₩3천5백만 견적 한 건이면 VIP가 되고, ¥ 고객은 ¥3천만(≈₩57억)이 필요해 사실상 도달 불가능했다.
금액에 통화를 붙여 다니는 `CrmMoney`를 도입하고 기준선을 통화별로 나눴다(어림 환산임을 명시).

회귀 테스트: `tests/crm/money-format.test.ts`(표기·통화별 기준선 8케이스).

### 2B.2 [권한] REV 시트만 읽기 롤이 넓었다

`/api/admin/crm/revenue-sheet`만 인자 없는 `verifyAdmin(req)`을 써서 GET 기본값
`BRANCH_READ_ADMIN_API_ROLES`(**VIEWER 포함**)가 적용됐다. 형제 CRM 라우트는 전부
`CRM_STAFF_ADMIN_API_ROLES`(VIEWER 없음)를 명시한다. 결과적으로 `/admin/crm/deals`에서 막히는
VIEWER가 같은 매출 원천인 REV 시트(확정 금액·고객명·팀별 분해)는 그대로 열람할 수 있었다.

### 2B.3 [사용자 경로] 통합 고객 라우트에 Suspense 경계가 없었다

`useSearchParams`를 쓰는 클라이언트 컴포넌트는 Suspense 경계가 필요하다. 형제 라우트
(`leads`, `accounts`)는 이미 `<Suspense fallback={null}>`로 감싸는데 **가장 중심 화면인
`customers/unified`만** 빠져 있었다.

### 2B.4 [안정성] 경쟁 응답 · 공용 잠금 · 이중 제출

- 요청 세대 가드 누락: `NeoCrmTeamPanel`(기간 이동), `app/admin/crm/deals`(6/12개월 전환).
  연타하면 이전 기간 응답이 최신 화면을 덮어써 **헤더는 새 기간, 숫자는 옛 기간**이 된다.
- 공용 스칼라 잠금: 매칭 인박스(`pendingLinkId`)와 지도 원천(`linkingExternalId`)이 진행 중
  상태를 값 하나로 잡았다. 다른 행을 누르는 순간 이전 행 버튼이 요청 중인데도 다시 활성화돼
  같은 대상에 중복 요청이 나갈 수 있었다. 행별 `Set`으로 바꿨다.
- 수집 '명단 분석' 이중 클릭: `busy`는 리렌더 커밋 뒤에야 버튼을 막는다. 빠르게 두 번 누르면
  둘 다 `batch?.id`를 `undefined`로 읽어 **빈 배치가 두 개** 생기고 하나는 고아로 남는다.
  동기 ref로 잠근다.
- `Customer360Drawer.loadMoreEvents`가 요청 **전에** 펼침 플래그를 켜고 실패를 삼켰다.
  실패하면 목록은 잘린 채인데 "전체 활동 보기" 버튼(`!eventsExpanded` 조건)만 사라져
  재시도 수단 없이 갇혔다.

### 2B.5 [정보성] 실패를 "없음"으로 단언하던 자리들

- `CrmCustomerPicker`: 검색 실패를 "일치하는 고객이 없습니다 · 직접 입력으로 저장됩니다"로
  그렸다. 실제로는 있는 고객을 자유 텍스트로 새로 만들게 유도하는 문구라, 중복·미연결
  레코드를 만든다. 실패 상태를 분리했다.
- `NeoCrmCustomersClient`: 첫 조회 실패 시 큰 빈 상태 패널이 "동기화된 고객이 아직 없습니다"라고
  단언했다. 장애를 데이터 없음으로 오인시킨다. 실패 전용 상태 + 재시도 버튼으로 분리했다.
- 일괄 확정·제외가 200건 상한을 **조용히** 잘라, `updated + failed`가 선택 건수와 맞지 않았다.
  `skipped`를 반환해 밝히고, 실패는 개수 대신 행 이름으로 알린다. 필터 변경 시 선택도 비운다.
- 수집 적용 실패가 "3건은 적용에 실패했습니다"뿐이었다. 서버는 행별 사유를 남기는데 클라이언트
  타입이 `errorMessage`를 버리고 있었다. 행 번호·이름·사유를 보여준다.

### 2B.6 [DB 설계] 페이지 집계를 총계처럼 보여줬다

`listCrmDeals`의 `summary.total`은 DB 전체 건수(`count: "exact"`)인데
`open/won/lost/openAmount`는 **이번 페이지만** 센 값이다. 360은 딜을 20건으로 고정 조회했으므로,
딜이 20건을 넘는 고객은 "딜 25건"이라고 표시하면서 예상금액은 20건 합계만 보여줬다.

- `aggregateTruncated` 플래그를 추가해 집계가 전체를 덮지 못하면 화면이 그 사실을 밝힌다.
- `getCrmCustomer360`에 `dealsLimit`을 추가하고 상세 페이지는 200으로 올렸다.
- 회귀 테스트: `tests/crm/deals-summary-truncation.test.ts`.

REV 시트(`admin-crm-revenue-sheet`)도 `.limit(1200)`을 걸면서 절단 경고가 없었다. 형제 모듈
(`admin-crm-revenue`)은 같은 위험을 `getQueryLimitWarning`으로 알리는데 여기만 조용히 잘려,
요약·팀별 집계가 소리 없이 과소 집계될 수 있었다. 경고를 추가했다.

### 2B.7 [입력-출력] 검사 없이 통과하던 값들

- 녹음 50MB 상한이 서버에만 있어, 300MB 파일도 **전부 업로드한 뒤에야** 거절됐다(느린 회선에서
  수 분). 상한 상수를 계약 파일로 공유해 고르는 즉시 막는다.
- 리드 등록에 전화·이메일 형식 검사가 없어 `asdf` 같은 값이 그대로 저장됐다. 벌크 파서가 이미
  쓰던 기준을 단건 폼에도 적용했다.
- `/api/admin/crm/revenue?months=abc`가 `NaN`을 통과시켜, 하위 clamp도 `NaN`을 그대로 흘려
  월 목록이 빈 배열이 됐다 — 오류 없이 **텅 빈 차트**가 나갔다.
- `account-master`·`reconcile/hw-rev` 라우트에 try/catch가 없어 본문에 `{ error }`가 없는
  프레임워크 기본 500이 나갔다(클라이언트가 사유를 못 읽음).

### 2B.8 [사용성] 다이얼로그 접근성

`LeadRegisterModal`에 Escape 닫기·포커스 트랩·포커스 복귀·`role="dialog"`가 전부 없었다.
`Customer360Drawer`는 `aria-modal="true"`를 선언하고도 트랩이 없어 Tab이 배경 페이지로
새어 나갔다. 저장소에 이미 있는 공용 훅 `useDialogFocus`(Escape + Tab 트랩 + 포커스 복귀)로
둘을 통일하고, 드로어에는 배경 스크롤 잠금과 토스트/오류 live region을 더했다.

### 2B.9 [기능] 새로고침이 닿지 않던 두 번째 자리

`CrmInsightsClient`의 전환 퍼널·채널별 전환율은 빈 의존성 배열 effect로 1회만 조회하고
새로고침 버튼(`load({force:true})`)과 연결돼 있지 않았다. 리드를 등록하고 새로고침해도 두 블록은
세션 내내 첫 로드 값 그대로였다.

### 2B.10 [속도] 활성 리드 수의 제곱으로 늘던 파생 집계

리드 보드의 `pipelineRiskLeads`가 활성 리드마다 `stalledLeads`·`overdueFollowUps` 두 배열을
선형 탐색했다. 이 memo는 60초 틱과 모든 필터 변경마다 다시 도므로, 활성 리드 3천 건이면 매번
수백만 번 비교한다. id `Set` 색인으로 바꿨다. `NeoCrmCustomersClient`의 검색도 지연값이 없어
키 입력마다 최대 1만 행을 다시 걸러 정렬했다(통합 목록은 이미 `useDeferredValue`를 쓴다).

## 3. 감점 없이 통과한 부분

가혹 채점에서도 이미 기준을 넘긴 항목은 손대지 않았다. 근거를 남긴다.

- **레이아웃 위계**: 홈은 리드 요약 → 행동 큐 → 결과 지표 → 참조(리포트, 기본 접힘) 순서로
  이미 정리돼 있다. 참조 표면은 베이지(`#fafaf8`)로 한 단 가라앉혀 행동 표면과 구분한다.
- **속도**: Recharts·360 드로어·리드 등록 모달·팀 패널이 모두 `next/dynamic`으로 분리돼 첫
  페인트에서 빠진다. 팀 KPI는 해당 탭을 열 때까지 요청 자체를 지연한다. `adminFetchJsonCached`가
  TTL + stale-while-revalidate를 제공하고, 서브탭 링크는 hover/focus에서 프리워밍한다.
- **콜드 로드 표시**: `...` 텍스트 대신 값 자리 크기의 스켈레톤을 쓴다. 실패 시 0으로 대체하지
  않고 `—` + "확인 불가" 문구로 구분한다(의사결정 수치를 0으로 위장하지 않는다).
- **통화 혼동 방지**: ₩(자체집계) / $(오더) / ¥(동기화)가 인접하는 자리마다 통화 칩과 산정
  기준 캡션을 강제한다.
- **DB 스키마**: `crm_tasks`는 CHECK 제약, 5개 목적별 인덱스(담당자 롤업·홈 큐·360·스누즈
  재부상·소스 이벤트), `updated_at` 트리거, RLS 정책을 모두 갖췄다. 스키마 설계 자체는 양호했다 —
  §2.3의 감점은 **읽기 경로**의 문제였다.
- **매칭 불가 노출**: 쇼룸 캘린더 데모 중 고객을 못 붙인 건수를 숨기지 않고 화면에 드러낸다.

## 4. 90선에 못 미친 채 남긴 항목

정직하게 남긴다. 이번 범위에서 고치지 않았다.

### 4.1 속도 (88)

- `getCrmPriorityQueue()`가 매 요청마다 리드 전량 + Neo 계정 전량 + 할 일 200건 + 활동 요약 +
  쇼룸 캘린더를 모두 가져와 **메모리에서** 점수 계산·정렬·필터한다. 리드가 수천 건 규모로
  커지면 §2.3의 페이지네이션이 왕복을 늘리는 만큼 응답 시간도 함께 늘어난다.
- 근본 해법은 점수 계산을 소재별 스냅샷 테이블(또는 머티리얼라이즈드 뷰)로 내리고 큐 API는
  정렬된 상위 N건만 읽는 것이다. 스키마 변경이 필요해 별도 작업으로 둔다.

### 4.2 편의성 (89)

- 우선순위 큐의 필터(소스·레인·시점·담당자)가 URL에 남지 않는다. 새로고침하면 기본값으로
  돌아가고 링크로 공유할 수 없다. 리드 보드는 `lens`/`sort`를 URL에 유지하므로 화면 간 규칙이
  어긋나 있다.
- 이 패널은 홈·사이드바(compact)·임베드 3곳에서 쓰인다. URL을 쓰는 주체를 정하지 않고
  동기화를 넣으면 서로 덮어쓴다. 소유권 결정이 먼저라 이번에 넣지 않았다.

### 4.3 남은 구조적 위험(고치지 않음, 기록만)

- **수집(capture) 열 매핑**: 헤더 없는 붙여넣기는 `DEFAULT_POSITIONAL_MAP`
  `[기관명, 담당자, 전화, 이메일]` 순서를 가정한다. 다른 순서로 붙여넣으면 전화번호가 기관명
  칸에 들어가고, 그 상태로 매칭이 돌아 기존 고객을 못 찾고 신규 리드를 새로 만든다.
  파서·API는 `mapping`/`hasHeader`를 이미 받지만 UI에 열 매핑 확인 단계가 없다.
  화면 신규 설계가 필요해 이번 범위에서 제외했다.
- **매칭 '제외' 되돌리기**: 리드·Neo CRM 소스 행을 "제외"하면 되돌릴 액션이 렌더되지 않고,
  수동 재연결은 `branch_rev_sheet` 소스로만 제한돼 있다. 후보 재생성은 상태와 무관하게 기존
  쌍을 제외하므로 오클릭이 사실상 영구 고정된다. 되돌리기 UX 결정이 선행돼야 한다.
- **통합 목록 offset 페이지네이션**: 60초 TTL로 재생성되는 메모리 배열을 우선순위 기준으로
  정렬한 뒤 offset으로 자른다. 페이지 이동 사이에 스냅샷이 갱신되면 경계 행이 중복되거나
  건너뛸 수 있다. 커서 기반 전환이 필요하다.
- `LeadsBoardClient.tsx`가 2,601줄이다. 동작 결함은 찾지 못했지만 이 크기 자체가 변경 위험이다.
- `CrmPriorityQueuePanel`에 `handleTaskAction`과 task 액션 버튼이 남아 있으나, 소스 필터가
  `customer`/`lead`/`neo_account`뿐이라 task 항목이 이 목록에 들어올 경로가 없다. 죽은 분기다.
- `customers-neo`는 한 번에 최대 1만 행을 내려주고 이후 페이지네이션 수단이 없다. 활성 계정이
  1만을 넘으면 KPI 총계와 목록이 갈라진다. 현재 규모에서는 미도달로 판단해 남긴다.
