# Admin OS 운영 결정 (2026-07-11)

상태: 현재 기준 문서  
범위: Admin OS의 인증·권한·데이터 정본·CRM 정보구조·상태·삭제·공개 기준

이 문서는 아래 항목에서 과거 설계 문서보다 우선한다. 실제 구현이 아직 이 결정과 다르면 “현재 동작”이 아니라 마이그레이션 대상으로 기록한다.

## 1. 계정과 권한

- 관리자 계정 정본은 Supabase `admin_profiles`다.
- 운영 정본 역할은 `SUPER_ADMIN`(슈퍼 어드민) / `BRANCH`(지사장) / `ADMIN`(어드민) 3종이다.
  `EDITOR`·`VIEWER`·`PARTNER`는 기존 세션·프로필을 깨지 않기 위한 레거시 호환 값이며, 신규 계정의
  운영 역할로 확장하지 않는다.
- 최종 슈퍼 어드민은 한 명이다.
- 역할만으로 모든 권한을 결정하지 않는다. 슈퍼 어드민이 사용자별 기능 권한을 부여한다. 예: 하드웨어 최종 승인 권한.
- 모든 활성 지사장·어드민은 하드웨어 재고와 일반 원장을 편집할 수 있다. 출고 확정·원장 취소 같은
  최종 실행은 지정 운영자에게 부여한 `hardware.finalize` 기능 권한으로 제한한다.
  `SUPER_ADMIN`의 권한은 비상 복구용으로 유지한다.
- 관리자는 전체 지점 데이터를 볼 수 있다. 데이터 격리 대신 담당자 매핑으로 `내 리드`, `내 할 일`, `내 고객` 보기를 제공한다.
- 기본 API 정책은 안전한 읽기(`GET/HEAD/OPTIONS`)에 지사장을 포함하고, 생성·수정·삭제는 관리자 역할만 허용한다. 계정·설정·개발 내부 정보는 읽기도 관리자 전용으로 명시한다.
- 사이드바·모바일 메뉴·커맨드 팔레트가 `roles`·`nav_preset`·`nav_overrides`를 사용해 항목을
  숨기더라도 이는 업무 표면을 정리하는 UX 규칙이지 보안 경계가 아니다. 실제 데이터·동작 권한은
  각 API의 관리자 가드와 필요한 `capabilities` 검사에서 강제한다.
- 레거시 공유 비밀번호와 환경변수 사용자 목록은 종료 대상이다. 전환 중에도 신규 운영 기능은 이를 정본으로 삼지 않는다.

## 2. 거래와 CRM 데이터

- 고객·딜·견적·계약·결제 흐름의 목표 정본은 Portal V2 모델이다.
- V1→V2 마이그레이션이 끝날 때까지 자동 추정 매핑이나 양쪽 동시 쓰기를 새로 추가하지 않는다.
- 자체 CRM DB가 작업 정본이다. REV 시트, 기존 매출 시트, 외부 CRM은 연결된 원천으로 표시하며 출처·갱신 시점·매칭 상태를 숨기지 않는다.
- 외부 CRM 수정 권한이 준비되기 전에는 읽기와 변경 요청을 분리한다. 승인되지 않은 직접 write-back은 추가하지 않는다.
- 위험·지연·건강도는 사용자가 고르는 딜 단계가 아니라 원천 데이터에서 계산한 신호다.

## 3. CRM 정보구조와 입력

최상위 CRM 작업면은 다음 다섯 개를 기준으로 한다.

1. 현황
2. 고객DB
3. 기록
4. 입력함
5. 검수

- 행사 참석자 입력은 독립 CRM 정본을 만들지 않는다. 행사 입력 결과를 CRM 기록·고객·리드에 연결한다.
- 마케팅팀의 반복 사용성을 위해 행사 화면의 빠른 진입은 유지하되, 저장 결과는 공용 입력·검수 흐름을 따른다.
- 파트너 전용 제품 표면은 현재 운영 범위에서 제외한다. 기존 파트너 기능은 내부 Admin OS로 통합하고, 견적 외부 공유 링크만 고객 접점으로 유지한다.
- 다음 액션 실행 상태는 `crm_tasks`가 담당한다. 외부 CRM 변경 요청과 REV/매출 데이터 연결은 별도 검수 흐름으로 유지한다.
- `snoozed`의 UI 용어는 **미루기**이며 재개일을 가진다. 재개일을 생략한 빠른 미루기는 다음 날 오전 9시(KST)를 사용한다.

## 4. 상태와 삭제

- 상태는 허용 enum과 명시적 액션(`complete`, `snooze`, `cancel`, `reopen` 등)으로만 전이한다. 임의 문자열 상태 PATCH를 허용하지 않는다.
- 잘못 입력한 일반 기록·견적·할 일은 삭제할 수 있어야 한다. 가능한 경우 즉시 물리 삭제 대신 취소·보관 상태로 전환하고 복구 액션을 제공한다.
- 고객처럼 하위 데이터가 많은 엔티티의 연쇄 삭제는 일반 삭제와 분리한다. 영향 범위 표시, 대상명 재입력 수준의 강한 확인, 감사 기록, 복구 수단 없이는 제공하지 않는다.
- 매출·재고·계약처럼 회계·운영 증빙이 되는 데이터는 취소·무효·역분개를 우선한다.

## 5. UI와 공개 기준

- 공식 UI 언어는 한국어다. `리드`, `Account`, `Opportunity`, `Bill`, `Revenue`처럼 팀이 고유 용어로 합의한 단어는 유지할 수 있다.
- 모바일 핵심 진입점은 [2026-07-29 어드민 탭 재구성](admin-tab-restructure-2026-07-29.md)의
  `캘린더 / 견적·문서 / CRM / More` 결정을 따른다. 이 결정은 이 문서의 과거
  `Overview / CRM / 견적 / 캘린더·입력함` 우선순위를 대체한다.
- Dev Mode는 로드맵·버그·데이터 품질·패치노트와 함께 공개 기준을 관리하는 내부 프로젝트 작업면이다.
- `Alpha / Beta / MVP / New` 표시는 공개 조건과 종료일이 없는 경우 사용하지 않는다.
- 공개 전 최소 근거는 책임자·목표일·완료 조건, 관련 테스트, 데이터 원천, 서버 권한 검사, 모바일 확인, 복구 또는 롤백 방법이다.

## 6. 감사와 운영 상태 표시

- 감사로그는 로그인 실패, 권한 변경, 개인정보 열람·내보내기, 승인·실행, 취소·삭제, 설정 변경처럼 책임 추적이 필요한 이벤트에 한정한다.
- 보존기간·열람자·마스킹 세부 정책과 퇴사·휴직 세션 회수 SLA는 후속 결정으로 둔다.
- 블로그, CRM 입력, 외부 연동처럼 저장 성공 여부가 중요한 화면은 `저장됨 / 실패 / 읽기 전용 / 미설정`을 구분한다. 모든 화면에 동일한 상태 배지를 강제하지 않는다.
- 로컬 JSON 쓰기는 개발·테스트에서만 허용한다. 운영/Vercel에서는 DB 미구성을 파일 저장 성공으로 폴백하지 않고 오류로 노출한다.

## 7. 문서 우선순위와 경계

- 이 문서의 CRM 5작업면 결정은 [2026-06-27 CRM 통합 마스터 설계](../superpowers/specs/2026-06-27-crm-unified-master-design.md)의 “정확히 6탭” 선언을 대체한다.
- 사이드바 배치·모바일 진입점은 [2026-07-29 어드민 탭 재구성](admin-tab-restructure-2026-07-29.md)이
  이 문서의 초기 UI 우선순위를 대체한다. 계정 정본·역할 3종·서버 권한 경계는 이 문서를 계속 따른다.
- 파트너 표면 결정은 과거 파트너 포털 구축 계획을 대체한다. V2 도메인 모델 자체는 유지한다.
- V1→V2 실제 데이터 마이그레이션은 별도 병행 트랙이다. 이 문서는 목표 정본과 새 결합 금지 경계만 확정한다.
- 구현 현황과 잔여 작업은 [Admin OS 통합 재구성 마스터플랜](admin-os-unification-master-plan-2026-07-03.md)에서 추적한다.
