## 0. 한 줄 요약

지금 어드민의 AI는 CS 상담 초안을 만드는 한 화면(`/admin/cs-chatbot`)에 갇혀 있고, ⌘K는 화면 이동만 한다. 이 기획은 ① 어느 화면에서나 뜨는 **AI 위젯**, ② 흩어진 AI 기능과 오더 이력을 모으는 **AI 올인원 탭**, ③ 화면에 직접 가지 않고 말로 작업을 시키는 **원격 오더**를 하나의 구조로 묶는다. 원칙은 하나다 — **AI는 오더 티켓을 "작성"만 하고, 실행은 사람이 확인 버튼을 눌러야 일어난다.**

갈매봇이 하는 일은 두 갈래다. **묻기**(조회·R0)와 **오더**(R1 이상). 사용자가 기대한 기능은 네 가지다.

| 기호 | 기능 | 등급 | 상태 |
|---|---|---|---|
| A | **클래스인 정보 답** — 제품·정책·절차를 묻는다. 답에 근거 문서·확정 여부(확정 · 확인 필요)·고객에게 그대로 전해도 되는지를 함께 보인다. 고객에게 나갈 문안은 계속 CS 코파일럿에서 만든다 | R0 | 기획 없음 → **이 개정에서 추가**(R12) |
| B | **원격 오더** — 말로 시키면 오더 카드를 만들고 사람이 확인해 실행한다 | R1~R3 | 기획·시안 있음 |
| C | **링크 안내** — 어드민 화면 바로가기와, 고객에게 보여 줘도 되는 공개 페이지 링크를 구분해 준다. 고객용 링크는 허용 목록(`link_id`)에 있는 것만 | R0 | 기획 없음 → **추가** |
| D | **담당자 안내** — "이 건은 누구에게 물어보나"에 답한다. 고객·딜 담당 → 본사(HQ) 담당표 → 한국 팀 담당표 순으로 결정형으로 찾고, 없으면 모른다고 답한다 | R0 | 기획 없음(리드 담당 *변경* 오더만 있었다) → **추가** |

묻기(A·C·D)는 모델 없이도 먼저 낼 수 있다 — 결정형 함수가 근거와 표를 읽어 카드를 만든다(§11.9, 결정 13). 질문과 오더를 가르는 판정은 코드가 한다. "누구야·링크 알려줘·되나·초안·예정" 같은 질문형 문장은 실행 키워드("결제"·"출고"·"견적")가 들어 있어도 오더 카드로 보내지 않는다.

## 3. 제품 구성 — 세 개의 면

### 3.1 갈매봇 위젯 (전역 플로팅)

- **위치**: 어드민 전 화면 우하단. 마운트 지점은 `components/admin/AdminShell.tsx`의 `AdminCommandPaletteLauncher` 옆(로그인 세션이 있을 때만).
- **열기**: 플로팅 버튼, 단축키(후보 `⌘/Ctrl + J` — 브라우저 기본 단축키 충돌 확인 필요), ⌘K에서 매칭되는 화면이 없을 때 나오는 "AI에게 오더" 항목.
- **역할 분담**: ⌘K = 어디로 **갈지**, AI 위젯 = 무엇을 **할지**. 팔레트는 없애지 않는다.
- **화면 맥락**: 지금 보고 있는 경로와 열려 있는 대상(고객·리드·견적 ID)을 칩으로 보여 주고(화면이 `useAdminAiEntity` 훅으로 직접 알린다 — §11.6), "이 고객"·"이 견적" 같은 지시어를 그 대상으로 해석한다. 칩을 지우면 맥락 없이 묻는다.
- **추천 칩**: 화면별로 자주 쓰는 질문·오더 3개. 정적 목록으로 시작한다(AI가 우선순위를 추천하는 것이 아님 — §2).
- **모드 구분 없음**: 묻기와 오더를 탭으로 나누지 않는다. 답이 조회면 답변이, 쓰기면 오더 카드가 나온다. 어느 쪽인지는 **질문형 판정이 먼저**다(§0) — 묻기만 했는데 실행 카드가 나오면 안 된다.
- **공통 추천 칩**: 화면별 3개 아래에 어느 화면에서나 같은 묻기 칩 "담당자 찾기 · 링크 찾기 · 정책 묻기"를 둔다(R28).
- **모바일**: 하단 시트. 어드민 모바일 하단 내비와 겹치지 않게 버튼 위치를 올린다.
- 화면 구성·상태·배치 규칙의 상세는 §11.

### 3.2 AI 올인원 탭 (`/admin/ai`)

| 하위 탭 | 내용 |
|---|---|
| 대화 | 위젯과 같은 대화를 넓게. 좌측 최근 대화, 우측 오더함 요약 |
| 오더함 | 확인 대기·유예 중·완료·실패·되돌림 전체 이력. 필터(내 오더/전체, 도메인, 등급). 되돌리기·재시도 |
| AI 도구 | 흩어진 기존 AI 기능의 **바로가기 모음**. 기능을 이 탭으로 옮기지 않는다 — 각 화면이 계속 정본 |
| 오더 카탈로그 | 지금 내릴 수 있는 오더 전체 목록, 등급, 필요한 역할. "무엇을 시킬 수 있나"의 단일 기준 |

- **내비 배치**: `ADMIN_NAV`에 1항목 추가. 범주는 "홈", Overview 바로 아래를 제안한다(§9 결정 D3). 배열 선언 순서와 `DEFAULT_PRIMARY_HREFS`의 경계를 함께 고쳐야 한다.
- **CS 코파일럿과의 관계**: `/admin/cs-chatbot`은 상담 검토 대기 흐름을 가진 CS 전용 작업면이라 그대로 둔다. 위젯은 그 지식 검색을 **읽기 소스로만** 재사용한다. 고객에게 나가는 답변 초안은 계속 CS 코파일럿에서 만든다.

**지식 재사용 단위 — 부품.** 코파일럿의 출력(초안 문장)을 가져오지 않고, 그 안의 **근거 부품**만 꺼내 쓴다. 지금 코파일럿 맥락은 문자열로 합쳐져 나온다. `lib/internal-cs-chat/context.ts`에서 `buildInternalEvidence()`를 별도로 export해(큐레이션 지식 · 사고 이력 · 공개 문서 · 내부 문서 근거를 구조화한 목록) 갈매봇이 근거와 확정 여부를 직접 보이게 한다. 기존 코파일럿 출력은 바꾸지 않는다(B2). 챗봇 답 색인(`data/answer-index`)은 참고 칸이다 — 정본이 아니라 후보 찾기용이다. 상담 사례(채널톡 벡터 검색)는 **수만 보여 준다**(건수·유형). 상담 본문 원문은 갈매봇 답에 싣지 않는다.

**정보 질문 경로(신설).** 사용자 발화 → ① 질문형 판정(코드) → ② 담당자 질문이면 `contact.who`, 링크 질문이면 `link.find`, 그 밖이면 `knowledge.ask` → ③ 근거 부품 검색(결정형) → ④ 답 카드(§11.9). 모델은 ③의 근거를 문장으로 다듬는 데만 쓰고(결정 11), 모델이 없거나 죽어도 근거 카드는 나온다. 근거가 없으면 지어내지 않고 "확인된 근거가 없습니다 + CS 코파일럿 열기"를 보인다.

### 3.3 원격 오더 엔진

채팅 한 줄이 실행으로 이어지는 경로. 상세는 §4~§6.

## 4. 오더 등급

모든 오더는 다섯 등급 중 하나로 등록된다. 등급은 코드에 고정하며 LLM이 바꾸지 못한다.

| 등급 | 뜻 | 확인 방식 | 되돌리기 |
|---|---|---|---|
| R0 조회 | 읽기 전용 | 없음 — 바로 답변 | 해당 없음 |
| R1 등록 | 새 행 추가(할 일·기록·일정) | 카드에서 1클릭 | 실행 후 10분 |
| R2 변경 | 기존 데이터 수정. 돈·재고가 움직이는 **민감 변경**(결제 확정·입출고 확정·금액 변경) 포함 — §4.2 | 전/후 비교 미리보기 + 확인 | 일반 변경은 실행 후 10분(이전 값 복원). 민감 변경은 오더마다 다름(§4.2) |
| R3 발송 | 외부로 나가는 것(문자·메일·공유 링크·발행) | 수신자·본문 미리보기 + 확인 + **30초 취소 유예** | 유예 중 취소만. 나간 뒤에는 불가 |
| R4 금지 | 위젯에서 실행하지 않음 | 거절 안내 + 해당 화면 딥링크 | — |

### 4.1 오더 카탈로그 v1 (제안)

### 4.2 R2 민감 변경 — 결제 확정 · 입출고 확정 · 금액 변경

2026-09-28 결정으로 세 오더를 R4(금지)에서 R2로 옮겼다. 확인 방식은 일반 R2와 같다(전/후 비교 + 확인 버튼). 다만 돈과 재고가 움직이므로 아래 조건을 덧붙인다.

| 오더 | 카드에 반드시 보여 줄 것 | 권한 | 되돌리기 |
|---|---|---|---|
| 결제(수납) 확정 | 거래건, 회차, **통화를 붙인 금액**, 입금일, 상태 전/후 | 스태프 + `payment.confirm`(신설 제안) | 수납 취소 경로가 현재 API에 없다 — 만들기 전까지는 되돌리기 없음으로 표시 |
| 입출고 확정 | 품목, 예정 수량 → 확정 수량, 처리일, 가용 재고 전/후 | 하드웨어 편집 + `hardware.finalize`(기존) | 오더 되돌리기 없음. 취소(void)는 R4로 남겨 하드웨어 화면에서 한다 |
| 금액·단가 변경 | 견적 번호와 버전, 합계 금액 전/후, 변동률, 통화 | 스태프 + `amount.edit`(신설 제안) | 새 버전을 만드는 방식이라 이전 버전이 그대로 남는다 — 되돌리기 = 이전 버전으로 복귀 |

공통 규칙:

- **한 번에 1건.** 여러 건을 묶어 확정·변경하지 않는다.
- **capability는 티켓 작성 시와 확인 시 두 번 검사한다.** capability가 없는 사람에게는 카드 대신 "권한 없음 + 해당 화면 열기"를 보여 준다.
- **금액은 AI가 계산한 값을 그대로 쓰지 않는다.** "10% 할인" 같은 지시는 서버가 원본 금액에서 다시 계산하고, 카드에는 서버 계산 결과만 표시한다.
- **금액 변경은 발송과 분리한다.** 새 버전을 만들어도 고객에게 자동으로 나가지 않는다. 보내려면 별도의 R3 오더가 필요하다.
- **이미 수락된 견적·체결된 계약의 금액은 바꾸지 않는다.** 이 경우는 거절하고 해당 화면을 안내한다.
- **실행·실패 모두 `logAdminAudit`에 남긴다.** 입출고 확정은 기존 액션명 `hardware.movement.finalize`를 그대로 쓴다.
- 파트너 포털 선행 기획([partner-portal-future-features.md](partner-portal-future-features.md) §D)은 금액 변경을 금지로 분류했다. 그 표는 파트너(외부 사용자)용이고, 이 결정은 내부 어드민 스태프에 한한다.

**견적 초안의 단가 지정(결정 8 — 결정 대기, 추천 c).** `quote.draft.create`는 단가를 입력으로 받지 않고 "전 품목 10% 할인" 같은 **할인 지시**만 받아 서버가 템플릿 단가에서 계산한다. 사람이 단가를 직접 정하겠다고 하면(예외) R1로 두되 카드에 템플릿 단가와의 차이와 경고를 표시한다. 단가 직접 지정을 `amount.edit` capability로 막는 안(a)은 초안이 R1이라는 분류와 맞지 않아 추천하지 않는다.

확인이 필요한 것: "결제 확정"이 가리키는 대상. 현재 코드에서 수납을 기록하는 경로는 거래건 수납 등록(`app/api/portal/payments/route.ts`, `paid_at` 기록)이고, 도입 신청(`checkout-requests`)은 `new|contacted|scheduled|done|canceled` 상태 전이만 있어 결제 확정 단계가 없다. 기획은 전자를 기준으로 썼다(§9 D8).

## 5. 오더 수명주기

```
발화 → 의도 해석(LLM, 제안만) → 서버 검증 → 오더 티켓(draft) → 미리보기 카드
     → 사람 확인 → [R3: 30초 유예] → 실행 → 감사 로그 → 되돌리기 창(10분)
```

| 상태 | 뜻 | 다음 |
|---|---|---|
| `draft` | 티켓 작성됨, 확인 대기 | `confirmed` · `cancelled` · `expired`(15분) |
| `confirmed` | 사람이 확인 | R3면 `grace`, 아니면 `executing` |
| `grace` | 30초 유예 | `executing` · `cancelled` |
| `executing` | 실행 중 | `succeeded` · `failed` |
| `succeeded` | 완료 | `undone`(10분 안) |
| `failed` | 실패 — 사유 표시 | 재시도는 새 티켓으로 |

**코드의 상태 이름(`OrderState`)과 맞춘다.** 화면·서버 공용 타입(`lib/admin-ai/types.ts`)의 이름은 `draft`·`editing`·`grace`·`done`·`sent`·`aborted`·`undone`·`cancelled`·`expired`·`failed`다. 위 표의 `confirmed`·`succeeded`는 설계 단계의 이름이며 구현은 코드 이름을 따른다(`succeeded` = `done`/`sent`, `cancel` = `cancelled`/`aborted`). 서버에는 화면에 없는 `executing`(실행 중)을 **서버 전용**으로 추가한다.

- `editing`은 화면 전용이다 — DB에 두지 않는다. 수정은 브라우저 안의 일이고, 서버 티켓은 `draft` 그대로다.
- `redraft`(다시 작성)는 **새 id**의 티켓을 만든다. 만료·취소·되돌림·실패한 티켓을 되살리지 않는다.
- 수정 중에는 만료 시계를 멈추되, **절대 만료**를 둔다(수정을 열어 두고 자리를 비워도 무한정 남지 않게). 화면은 패널이 닫히거나 새 대화가 시작되면 수정을 취소로 되돌리고 시계를 다시 돌린다(§11.10).

서버 검증 단계에서 확인하는 것: 입력 스키마, 요청자 역할·capability, 대상 존재 여부, 건수 상한, 같은 오더 중복(멱등 키).

## 6. 구조

### 6.1 오더 레지스트리

오더 하나 = 선언 하나. 위치 제안 `lib/admin-ai/orders/`.

```ts
interface AdminOrderDefinition<Input> {
  id: string                       // "crm.task.create"
  domain: "crm" | "hardware" | "calendar" | "messaging" | "quotes" | ...
  risk: "R0" | "R1" | "R2" | "R3"  // R4는 레지스트리에 없고 거절 목록에만 있다
  roles: readonly AdminApiRole[]
  capability?: AdminCapability
  input: Schema<Input>             // LLM에 넘기는 도구 선언도 여기서 생성
  preview(input, admin): Promise<OrderPreview>   // 쓰기 없음
  execute(input, admin): Promise<OrderResult>
  undo?(result, admin): Promise<void>
}
```

- `execute`는 **도메인 lib 함수를 직접 호출**한다. 기존 `app/api/admin/*` 라우트를 서버에서 HTTP로 다시 부르지 않는다 — `requireVerifiedAdminContext` 안의 same-origin 검사에 막히고, 인증 주체가 흐려진다. 비즈니스 로직이 라우트 파일 안에 있는 도메인은 먼저 lib으로 뽑아야 한다(오더마다 선행 작업 여부 확인 필요).
- 오더 핸들러의 소유권은 해당 도메인 파트에 있다. 어드민 코어는 레지스트리 규약만 갖는다.

### 6.4 LLM

- **모델 어댑터는 전송을 새로 만들지 않는다.** 전송은 `gemini-transport`(Vertex)와 Claude 제공자 설정(`claude/config`, 예산·상한 패턴)을 재사용한다. 도구 선언은 **JSON Schema 한 벌**을 정본으로 두고 Gemini용 형식은 변환해서 쓴다 — 레지스트리가 도구 선언을 생성하므로 모델 교체는 어댑터 한 곳에서 끝난다(§9 D5). `lib/internal-cs-chat/gemini.ts`는 CS 코파일럿 전용으로 남긴다(갈매봇이 import하지 않는다).
- **1순위 모델은 결정 대기**(결정 11, 추천: Claude 1순위, Vertex Gemini 폴백). 도구 호출 안정성이 중요하고 내부 사용량이 적어서다. 어느 쪽이든 결정형 폴백이 있어 모델 없이도 S1′(묻기·조회)는 출시할 수 있다.
- 타임아웃은 라우트 상한보다 짧게, 연속 호출의 최악 합을 `maxDuration` 안에 둔다. 유료 호출은 클라이언트 연타와 서버 중복을 모두 막는다.
- LLM이 죽어도 위젯은 죽지 않는다 — 폴백으로 "화면 이동 추천 + 오더 카탈로그 링크"를 보여 준다.

### 6.5 홈 MCP와 공용 도구 레지스트리 (2026-11 점검에서 추가)

홈 MCP(`app/api/mcp/route.ts`, `lib/mcp/server.ts`, `lib/mcp/tools.ts`)는 직원 개인의 AI 클라이언트가 어드민 업무 함수를 도구로 부르는 **또 하나의 입구**다. 지금 읽기 8·쓰기 2(`quote_create_draft`·`hw_plan_movement`)가 있고, 쓰기는 클라이언트의 승인 창에만 맡긴다. 갈매봇과 MCP가 같은 업무를 따로 구현하면 등급·권한·마스킹이 두 벌이 된다.

| 원칙 | 내용 |
|---|---|
| 정본 | `lib/ops-tools/`(신설 — `registry.ts`·`actor.ts`·`guard.ts`·`redact.ts`·`defs/*`). 도구 정의 한 벌을 두고 **어댑터 두 개**(MCP·갈매봇)가 읽는다. `lib/mcp/tools.ts`는 어댑터가 된다 |
| 신원 | `ToolActor` — 누가 부르는지(어드민 계정·토큰 scope·입구). 모든 도구가 actor를 받는다 |
| 등급 | R0는 `run` 하나. **R1 이상은 `preview`·`execute`로 나누고 `run`을 두지 않는다.** 레지스트리 시험이 R1 이상 정의에 `run`이 있으면 실패한다 |
| 갈매봇과 MCP 쓰기 | **갈매봇은 MCP 쓰기 `run`을 부르지 않는다.** 같은 업무 함수를 `preview`·`execute`로 거치고 사람 확인 카드를 요구한다 |
| MCP의 위치 | **MCP = 오더 엔진의 또 다른 입구.** 지금 MCP 쓰기는 클라이언트 승인에 의존하므로 신뢰 모델이 다르다. S2(오더 저장소) 뒤에 MCP 쓰기도 **서버 티켓 + 어드민 확인**으로 통일한다(결정 1: 지금은 쓰기 scope 기본 꺼짐(c), S2 때 티켓화(b)) |
| 토큰 | scope·만료·어드민 이메일을 줄 형식으로 둔다(1단계, 결정 2). `internal` 플래그는 scope로만 켠다. DB 해시 저장은 B5 뒤 |
| 가림 | 응답 직렬화 직전에 공통 가림(연락처·이메일). 직원 개인 Claude 계정으로 고객 연락처가 나가지 않는다(결정 7, 추천: 안 된다 — 원문은 서버 실행 단계에서만) |
| 메타 시험 | 도구 id 집합 = MCP ∪ 갈매봇 집합이 레지스트리와 같다 |

운영 `HOME_MCP_TOKENS` 형식을 바꾸는 일은 운영 환경변수를 사용자가 직접 바꿔야 하므로 코드와 따로 알린다.

## 7. 안전 설계

| 위험 | 방어 |
|---|---|
| AI가 멋대로 실행 | 쓰기는 전부 사람 확인. 확인 API는 LLM 도구 목록에 없음 |
| 프롬프트 주입(리드 메모·채널톡 본문·문서에 지시문이 섞여 들어옴) | 조회 결과는 데이터로만 취급. 도구 호출은 **사용자 발화 턴에서만** 허용한다. 조회 뒤 쓰기 제안은 일률로 막지 않는다 — `deals_list → quote_create_draft` 같은 정상 흐름이 막히기 때문이다. 대신 규칙은 이렇다: **대상 id는 이번 턴에 서버가 돌려준 것만 쓴다. 값은 확인 시점에 서버가 다시 읽는다. 카드에 근거가 된 사용자 발화를 보인다.** 모델이 조회 결과 속 문장을 지시로 따른 흔적(발화에 없는 대상·값)은 서버가 버린다 |
| 권한 우회 | 셸·위젯은 보안 경계가 아니다. 티켓 작성 시와 확인 시 두 번 서버에서 역할·capability 검사 |
| 잘못된 대상 | 동명 고객이 여럿이면 실행하지 않고 후보를 되묻는다. 카드에 대상 ID·지역을 함께 표시 |
| 돈·재고가 잘못 움직임 | R2 민감 변경은 capability 필수, 1건 단위, 금액은 서버 재계산, 통화 표기, 수락·체결 건 변경 거절(§4.2) |
| 오발송 | R3는 1건 단위, 30초 유예, `MESSAGING_DRY_RUN` 존중, 수신 동의 확인 |
| 이중 실행 | 멱등 키 + 확인 버튼 1회성 |
| 개인정보 | LLM에 보내는 연락처는 마스킹. 원문은 실행 단계에서 서버가 DB로 다시 읽는다 |
| 링크 오안내 | 링크는 **허용 목록(`link_id`)**에서만 낸다 — 모델이 주소 문자열을 만들지 않는다. 어드민 링크와 고객용 링크를 구분해 표시하고, 고객용은 `SITE_URL` 한 도메인으로 고정한다(결정 9) |
| 담당자·내부 지식 노출 | 담당표와 내부 근거는 **server-only**다. 클라이언트 번들에 담당자 이름·내부 문서가 들어가지 않는다(번들 검사). 서버는 요청한 도메인의 한 줄만 돌려준다(결정 6) |
| MCP 쓰기 | 토큰 scope로 쓰기를 기본 끈다. 갈매봇은 MCP 쓰기를 부르지 않는다(§6.5) |
| 시안이 실제로 보임 | 샘플 데이터 카드가 실제 실행처럼 보이지 않게 한다 — 운영(`VERCEL_ENV=production`)에서는 스위치를 무시하고, 카드에 "시안 — 실제로 실행되지 않습니다" 띠를 둔다(§13.4) |
| 장애 | 저장 실패를 성공으로 응답하지 않는다. 실패 사유를 카드에 그대로 표시 |

### 11.1 이름과 아이콘

- 이름은 **갈매봇**. 위젯 머리말, 플로팅 버튼, 답변 아바타, ⌘K 항목, AI 올인원 탭 머리말에 쓴다. 사이드바 탭 이름은 "AI 올인원"을 유지한다.
- 아이콘은 두 가지로 자른다.

| 크롭 | 쓰는 곳 | 크기 |
|---|---|---|
| 전신 | 위젯 첫 화면 인사, AI 올인원 탭 머리말 | 52~104px |
| 얼굴(원형) | 플로팅 버튼, 답변 아바타, 사이드바, ⌘K | 22~52px |

- 22px에서는 전신이 뭉개진다. 작은 자리는 반드시 얼굴 크롭을 쓴다.
- 받은 원본은 회색 배경의 2000px 래스터다. 배경과 바닥 그림자를 걷어낸 투명본을 `docs/active/mockups/assets/`에 두었다. 실제 적용 때는 `public/`으로 옮긴다.
- **갈매봇 그림만 파랑·노랑이고 화면 크롬은 Classin Green과 웜 뉴트럴만 쓴다.** 버튼·선·강조에 갈매봇의 파랑을 가져오지 않는다. `DESIGN.md`의 파랑 금지와 부딪히므로 예외 등재가 필요하다(§12-4).
- 장애 상태에서는 아바타를 흑백·반투명으로 낮춘다. 표정 변형 그림은 아직 없다.

### 11.5 배치 규칙 — 우하단이 이미 쓰이고 있다

코드 조사 결과 우하단과 오른쪽 가장자리를 이미 쓰는 화면이 많다.

| 기존 요소 | 위치 | 파일 |
|---|---|---|
| 하드웨어 재고 빠른 기록 버튼 | 우하단 고정 | `components/admin/hardware/HardwareInventoryClient.tsx` |
| 매출 장부 떠 있는 버튼과 패널 | 우하단 고정 | `components/admin/branch/SalesLedgerWorkbench.tsx` |
| 저장 알림 | 우하단 | `components/admin/marketing/MarketingHub.tsx`, `components/admin/crm/leads/shared.tsx` |
| 리드 보드 작은 패널 | 우하단 | `components/admin/crm/leads/LeadsBoardClient.tsx` |
| 오른쪽 서랍(440~680px) | 오른쪽 전체 높이 | `LeadDrawer.tsx`, `TemplateEditorDrawer.tsx`, `AutomationRuleSlideOver.tsx` |
| 모바일 하단 내비 | 하단 전체 폭 | `components/admin/AdminSidebar.tsx` |

규칙(시안 04):

1. 화면의 자체 버튼이 자리를 지키고 갈매봇이 그 위로 올라간다.
2. 오른쪽 서랍이 열리면 서랍 왼쪽으로 비켜난다.
3. 알림이 떠 있는 동안 위로 비켜났다가 돌아온다.
4. 모바일에서는 하단 내비 위.
5. 쌓임 순서는 서랍·알림보다 아래. 갈매봇이 저장 버튼이나 오류 알림을 덮지 않는다.

구현 방식 제안: 화면이 "우하단을 얼마만큼 쓰는지"를 셸에 알리는 작은 훅을 두고, 런처가 그 값만큼 비켜난다. 화면마다 위치를 하드코딩하지 않는다. 이 방식이 맞는지는 §12-7.

### 11.6 화면 맥락 계약

```ts
interface AdminAiPageContext {
  path: string                    // "/admin/crm/customers/unified"
  label: string                   // "CRM › 고객DB"
  entity?: {
    type: "lead" | "customer" | "deal" | "quote" | "hardware_item" | "hardware_movement"
    id: string
    label: string                 // "한빛수학학원"
  }
}
```

- 화면은 `useAdminAiEntity({ type, id, label })`(`components/admin/ai/use-admin-ai.ts`)로 알린다. 훅 골격과 등록부(`lib/admin-ai/page-entity.ts`)는 있고 **화면 연결은 각 화면 소유 파트의 일이다**(2026-11 B1은 골격까지만). 화면이 닫히면 자동으로 거둔다.
- 화면이 훅으로 직접 알린 것만 맥락이 된다. 알리지 않은 화면은 경로만 넘어간다. 화면의 글자를 긁어 추측하지 않는다.
- 맥락은 힌트다. 서버는 `entity.id`를 DB에서 다시 읽고 요청자의 조회 권한을 확인한다.
- v1에서 맥락을 알리는 화면: CRM 고객 상세·리드 서랍, 견적 상세, 하드웨어 품목 상세. 나머지는 경로만.
- 「맥락 끄기」는 그 대화에만 적용된다.

### 11.7 키보드와 접근성

| 동작 | 키 |
|---|---|
| 여닫기 | `⌘/Ctrl + J` (후보 — 브라우저 기본 단축키와 충돌 확인 필요) |
| 닫기 | `Esc`. 카드 수정 중이면 수정 취소가 먼저(패널은 열려 있다), 한 번 더 누르면 닫힌다. 패널 밖에 포커스가 있어도 받되, 넓은 화면에서 페이지의 다른 입력란에 포커스가 있으면 건드리지 않는다 |
| 탭 이동 | 탭 목록에서 `←` `→`(`Home` `End`). 선택된 탭만 Tab 순서에 들어간다(roving tabindex) |
| 보내기 / 줄바꿈 | `Enter` / `Shift + Enter`. 한글 조합 중에는 보내지 않는다 |

- 떠 있는 위젯은 포커스를 가두지 않는다(본문을 계속 쓸 수 있어야 한다). 모바일 하단 시트(lg 미만)는 `aria-modal`과 `inert`(뒤 화면)로 가두고 Tab이 시트 가장자리에서 맞은편으로 돈다. 닫으면 포커스가 갈매봇 버튼으로 돌아온다.
- **확인 버튼에 자동으로 포커스를 주지 않는다.** Enter 연타로 오더가 실행되는 것을 막는다.
- 대화 전체를 `aria-live`로 두지 않는다(카드 시계가 매초 읽힌다). 화면 낭독기용 상태 줄 둘만 둔다 — "새 답변 한 줄"과 "만료 1분 전 한 번". 카드의 남은 시간은 알림 영역 밖이다. 등급은 색만이 아니라 글자(R1 등록)로도 표시한다.
- 움직임 줄이기 설정을 따른다.

### 11.8 말투

- 합니다체, 짧게. 감탄·이모지 없음.
- 실행 전: "~할 준비가 됐습니다. 내용이 맞으면 실행해 주세요."
- 실패: 무엇이 나갔고 무엇이 안 나갔는지를 먼저 말한다.
- 모르면 추측하지 않고 되묻는다. 요약은 기록 원문에서 뽑은 것만 쓴다.
- 다음 할 일을 먼저 만들어 내밀지 않는다. "필요하면 말씀해 주세요"까지만 한다(§2).

### 11.9 오더 카드

시안 03 구역. 카드는 위젯·AI 올인원 탭·확인 대기 목록·모바일 시트에서 같은 컴포넌트 하나를 쓴다.

**구조** (위에서 아래로)

| # | 부분 | 규칙 |
|---|---|---|
| 1 | 머리 — 오더 이름과 대상 | 대상을 이름 바로 아래에 굵게 둔다. 대상이 첫눈에 보여야 엉뚱한 고객에 실행하는 실수가 준다 |
| 2 | 등급 | 글자(R2 변경)와 머리 옆 짧은 세로 막대. 색만으로 구분하지 않는다. 카드 모서리를 따라 휘는 선은 쓰지 않는다 |
| 3 | 값 | 바뀌는 값은 「이전 → 이후」 한 줄. 이전은 흐리게, 이후는 굵게. 취소선은 한글에서 읽기 어려워 쓰지 않는다 |
| 4 | 금액 | 금액이 있는 오더는 값 위에 금액 블록을 따로 둔다. 통화 코드를 항상 붙이고, 변동이 있으면 이전 금액과 차액을 함께 보인다 |
| 5 | 건드리지 않는 것 | 이 오더가 바꾸지 않는 항목을 한 줄로 적는다 |
| 6 | 상태와 남은 시간 | 확인 대기는 만료까지, 완료는 되돌리기 마감까지, 발송 유예는 발송까지 남은 시간이 흐른다 |
| 7 | 행동 | 실행이 맨 앞, 취소가 맨 뒤. 채움 버튼은 하나만. 발송(R3)만 경고색 채움 |
| 8 | 안내 | 필요한 권한과 되돌리기 가능 여부. 되돌릴 수 없는 오더는 이 줄이 경고색 |

**상태별 모습**

| 상태 | 머리 막대 | 값 | 하단 |
|---|---|---|---|
| 확인 대기 | 등급색 | 보통 | 남은 시간 + 실행 · 수정 · 취소 + 안내 |
| 수정 중 | 등급색 | 고칠 수 있는 값만 입력칸. 대상에는 자물쇠 | 수정 완료 · 수정 취소 |
| 발송 유예 | 경고색 | 보통 | 줄어드는 막대 + 남은 초 + 발송 취소 |
| 완료 | 등급색 | 보통 | 결과 + 열기 + 되돌리기(남은 시간) |
| 취소 · 되돌림 · 만료 | 회색 | 강조만 뺀다. 카드를 통째로 흐리게 하지 않는다 | 사유 + 다시 작성 |
| 실패 | 위험색 | 보통 + 사유 상자 | 무엇이 나갔고 안 나갔는지 + 열기 · 다시 작성 |

- 수정으로 바뀐 값에는 「수정됨」을 붙인다. 갈매봇이 채운 값과 사람이 고친 값이 구분된다.
- 닫힌 카드도 값은 읽을 수 있어야 한다. 나중에 대화를 다시 볼 때 무엇을 하려던 것인지 알 수 있어야 하기 때문이다.
- 폭이 300px보다 좁은 자리에서는 아이콘을 빼고 이름표를 값 위로 올린다.
- 조회(R0)·거절(R4)·되묻기 카드도 같은 머리 구조를 쓰되 하단에는 화면 열기만 둔다.

**오더함에서는 확인하지 않는다(R5).** 오더함 표의 행에는 확인·취소 버튼을 두지 않는다. 확인 대기·수정 중 행에는 **"카드 열기"**만 있고, 같은 `OrderCard`가 행 아래에 펼쳐진다. 확인은 금액·전/후 값이 보이는 카드에서만 한다. 행에서 1클릭으로 결제 확정을 누를 수 있으면 서버가 붙은 뒤 그대로 실제 실행 경로가 된다. 줄이는 방향의 버튼(발송 취소·되돌리기)은 표에 남는다. 시험이 이 계약을 고정한다.

**시안 표시(R16).** 시안 모드에서 카드 맨 위에 "시안 — 실제로 실행되지 않습니다" 띠를 둔다. 확인 버튼은 "시안 확인", 완료 문구는 "시안 완료 · 실제로는 실행되지 않았습니다"다. "권한 확인 ✓"처럼 서버가 확인한 것처럼 보이는 문구와 샘플의 "수신 동의 확인됨"은 쓰지 않는다. 카드의 "권한 · 결제 확정"은 "필요 권한 · 결제 확정"으로 바꿔 요구 사항임을 분명히 한다. live 모드가 되면 이 띠와 문구는 자동으로 사라진다.

**묻기 카드 3종(B4가 만든다).** 답은 글이 아니라 카드로 낸다. 같은 머리 구조(대상·등급 R0)를 쓴다.

| 카드 | 보이는 것 | 하단 |
|---|---|---|
| `answer` | 답 문장, **근거**(문서 이름·위치), 확정 여부(확정 · 확인 필요), "고객에게 그대로 전해도 되는지" 배지 | CS 코파일럿 열기(고객 문안은 거기서) |
| `links` | 링크 목록. 어드민 바로가기와 고객용 공개 링크를 구분 표시, 고객용은 허용 목록의 `link_id`만 | 열기 · 복사 |
| `contact` | 담당 한 줄(역할·이름·채널), 확인일, 90일이 넘으면 "확인 오래됨", 담당표에 없으면 "모릅니다 + 기본 안내" | 담당표 열기 |

B1(이번 묶음)은 시나리오 id를 `who`·`knowledge`·`link`로 나눠 두고 **글 블록**으로만 답한다. B4가 시나리오별로 이 카드로 바꿔 끼운다.

### 11.10 새 대화 설계 (점검 N1~N8)

공개 위젯의 원칙(버튼 한 번 · 되돌리기 · 맥락 초기화 · 확인 대기 오더 유지)을 갈매봇에 옮긴 것이다. 점검 전에는 새 대화가 messages를 지우기만 했고, 발송 유예 중이던 오더(30초 뒤 그대로 나간다)에 위젯에서 다시 닿을 수 없었다.

| # | 항목 | 설계 | 상태 |
|---|---|---|---|
| N1 | 버튼 | 머리에 "+ 새 대화" 글자(패널이 좁으면 아이콘만). **확인창 없이 한 번.** 메시지가 0개면 비활성 | B1 구현 |
| N2 | 되돌리기 | 6초 토스트 "새 대화를 시작했습니다 · 되돌리기". 스토어에 직전 대화 **1칸** 스냅샷(`restore-conversation`). 진행 중이던 답은 멈춘 채 복구된다. 새 질문을 하면 칸이 닫힌다 | B1 구현 |
| N3 | **지우지 않는 것** | 확인 대기·수정 중·발송 유예·되돌릴 수 있는 완료 오더와 화면 맥락. 위젯 "확인 대기" 탭을 **"오더" 탭**으로 넓혀 유예 중을 맨 위에 둔다. 안내 한 줄 "오더는 새 대화에도 남습니다" | B1 구현 |

### 13.3 서버를 붙일 때 바꿀 곳

1. `lib/admin-ai/client.ts`의 `adminAiClient`를 실제 구현으로 교체한다. 화면 코드는 바뀌지 않는다.
2. 오더 확인·취소·되돌리기는 지금 스토어 안에서만 상태가 바뀐다. `store.ts`의 `actOnOrder`가 확인 API(§6.2)를 부르고 그 응답으로 전이하도록 바꾼다. 상태 전이 규칙(`order-state.ts`)은 서버도 같은 것을 써야 한다.
3. 시안 표시는 `adminAiStore.mode`를 따른다. 실제 구현으로 바꾸면 자동으로 사라진다.

### 13.4 배포 전 조건

- 스위치 `NEXT_PUBLIC_ADMIN_AI_PREVIEW="1"` 로 켜고 배포하면 전원의 사이드바에 "AI 올인원(시안)"이 보이고 샘플 데이터가 나온다. 서버 1단계(조회)가 붙기 전에는 운영에서 켜지 않는다. **2026-11부터는 운영(`VERCEL_ENV=production`)에서 스위치가 "1" 이어도 무시된다**(preview·development 환경에서만 켜진다). 운영에서 시안을 의도적으로 보려는 경우는 없다 — 서버 1단계가 붙으면 이 차단을 live 모드 판정으로 바꾼다.
- 시안 카드는 "시안 — 실제로 실행되지 않습니다" 띠를 단다(§11.9).
- 이번 점검의 선행 조건: B1(위 안전 수정) → B2(담당자·지식 근거의 서버 전용화, 번들 노출 검사) → B3(공용 도구 레지스트리·MCP 보강)이다. 담당표·내부 근거가 클라이언트 번들에 들어 있는 동안에는 C·D를 실제 모드로 켜지 않는다.
- 정책 문서 개정(D1)은 끝났다. 시점은 D13을 따른다 — 코드는 2026-10-19 통합 병합으로 들어갔고(D13 이행, 스위치 꺼짐), 운영에서 켜는 것은 서버 1단계 뒤다.
