# 하드웨어 재고관리 프로세스 정의서 ↔ 현재 구현 차이와 이어서 할 작업

작성: 2026-10-28
상태: 기본 결정 적용(§6) · 순서 2~9 구현 중(§7 계약) · 시트 끄기(10~12)는 보류

기준 문서: 운영자가 작성한 "하드웨어 재고관리 프로세스 정의서"(2026-10-27, Claude Docs). 구글 시트 행렬 관리를 어드민 기록 기반 관리로 옮기는 목표 모델이다 — 사람은 입고·출고 기록 2종만 입력하고, 재고현황·판매대시보드는 기록에서만 계산한다.

관련: [하드웨어 SCM 탭 기준](./hardware-scm-tab-reference.md) · [하드웨어·오더·매출 연결 로직](./hardware-order-revenue-link-plan-2026-10-22.md)(T0~T4 편입 순서) · [DB 마이그레이션 런북](./db-migration-runbook.md)

## 1. 요약

원장(`hardware_movements`)·재고 계산·물류번호(로트) 해석기는 이미 있다. 목표 모델에 필요한 아래 항목은 코드에 없다.

- 출고 **유형**(세일즈·프로모션·A/S·샘플), 입고 **무상 여부**, 고정 **진행 상태** 3종(배송 예정·설치 완료·회수)
- **회수 → 원 출고 건** 연결, 출고 **CRM 고객 id**, 담당자 **사용자 id**(본인 건 수정)
- **입고관리 권한자** 권한, 매니저가 **물류번호를 직접 고르고 잔여 초과면 저장 차단**
- 사유 필수 **재고 조정** 화면, FY **품목 × 월 판매대시보드**(설치 완료 / +배송 예정)

지금 동작과 정면으로 부딪히는 것 5가지:

| 지금 | 정의서 |
| --- | --- |
| 로트가 모자라도 FIFO 로 자동 배정하고 출고를 막지 않는다(2026-09-14 운영자 결정, `20260914_hardware_confirm_planned_v3.sql`) | 매니저가 물류번호를 직접 고르고, 잔여를 넘으면 저장 차단 |
| 창고 재고 = '창고' 위치 잔액(사무실·고객사 입고는 창고에 안 잡힘, 샘플 배정·수리는 창고에서 빠짐) | 창고 재고 = 입고 − 설치 완료 + 회수 ± 조정(위치 무관) |
| 샘플은 사무실 샘플 풀(창고→사무실 배정, 사무실↔샘플 대여·반납)과 샘플 유닛 표가 기준 | 샘플 = 유형 '샘플' 출고 − 샘플 회수 |
| 가져오기 때 시트가 이긴다(앱 확정·오더번호 같은 앱 기록을 취소) | 어드민 기록이 원본 |
| `hardware.finalize` 1명(DB 유니크 인덱스로 1명 제한) + 슈퍼 어드민만 확정·실현 기록 수정·취소 | 입고관리 권한자는 전체, 매니저는 본인 출고 건 등록·수정 |

## 2. 먼저 정해야 할 것 (구현을 막는 질문)

1. **입고관리 권한자는 누구인가.** 이왕찬 한 명(지금 `hardware.finalize`)인가, 여러 명인가. 새 권한을 만드나, finalize 를 넓히나. 지사장(슈퍼 어드민)은 자동 포함인가.
2. **배송 예정 → 설치 완료는 누가 바꾸나.** 정의서는 담당 매니저, 지금은 이왕찬만. 같은 기록의 상태를 바꾸나(정의서), 지금처럼 새 기록 + 예정 취소인가. 부분 확정이 계속 필요한가.
3. **보관 장소.** 인천 더조은(FPL)을 없애나, 네 번째 장소로 두나. 클래스인 사무실·고객사 보관분도 창고·가용 재고에 넣나(정의서 공식은 위치를 보지 않는다).
4. **샘플.** 창고에서 나갔다 회수로 돌아오는 모델(정의서)로 바꾸나, 사무실 샘플 풀을 유지하나. 샘플 유닛 추적 표(`hardware_sample_units`)는 남기나.
5. **승인된 오더의 배송 예정.** 하드웨어 승인 때 배송 예정을 자동으로 만드는 것을 유지하나. 유지하면 담당(딜 담당·요청자?)·물류번호·예정일은 누가 채우나 — 지금은 셋 다 비어 있다.
6. **물류번호.** 다음 신규 번호는 C3 부터(시트에 C2 가 이미 있다). 기존 번호에 나중 날짜 입고를 덧붙이게 하나. FIFO 자동 배정을 모든 곳에서 없애나(물류번호 없는 기존 배송 예정 확정 포함). 배송 예정 등록 때부터 물류번호 필수인가. "잔여"는 창고 기준인가 가용 기준인가.
7. **기존 데이터 이관.** 시트 이관 행을 수정 가능한 어드민 행으로 바꾸나. 지금 음수 재고(예: STD1(promoted) −16, STD1 H8 초과)는 조정 기록으로 정리하나. 이상한 번호(H7(과사람), Sample, FY24-25 표시 H0)는 어떻게 두나.
8. **품목 목록 확정.** D2T·카메라 브라켓·전원 케이블(3m/1m)의 정식 이름, 65"·110" IFP 와 S1 의 물류번호 관리 여부, 목록에 없는 품목(STDM1, DT1)의 처리.
9. **알림·샘플.** 배송 예정 30일 경과는 예정일 기준인가 등록일 기준인가, 어느 채널로 누구에게 보내나. 샘플 반납 예정일은 메모(정의서)인가 별도 칸인가.
10. **판매대시보드 세부.** 회수를 판매에서 빼나. 날짜 없는 배송 예정은 어느 달에 넣나. 행은 품목(SKU) 단위인가 묶음 단위인가. 금액도 보이나.

| 정의서 | 상태 | 지금 |

## 4. 연결 로직(S1~S4)과의 관계

- **오더 승인 → 배송 예정 자동 생성**(S3): 정의서에서는 매니저가 출고를 등록한다. 자동 생성을 유지하면 담당자·물류번호·예정일을 채워야 하고, 없애면 승인은 오더번호만 발급한다(§2-5).
- **매시간 시트 가져오기**(S1): 지금 교체 가져오기는 시트 이관 행 전체를 지우고 다시 싣는다 — 탭(입고/출고/재고현황)별로 끌 수 없다. T1(입고만 끄기)을 하려면 가져오기를 `source_table` 단위로 나눠야 하고, 재고현황 "현재고 보정" 행도 멈춰야 어드민 기록과 싸우지 않는다.
- **시트가 이긴다 · 시트 오더번호 열 · 시트 확인 칸**(S4): T2(출고를 어드민으로) 때 모두 끈다. 그때부터 오더번호는 어드민 출고 기록에 직접 붙는다.

## 5. 만드는 순서 (각각 따로 배포 가능)

1. **결정**: §2 의 1~6 번. 스키마와 재고 공식이 갈린다.
2. **스키마 추가(동작 변화 없음)**: `hardware_movements` 에 출고 유형·진행 상태(고정값)·무상 여부·회수 원 출고 연결·CRM 고객 id·담당자/작성자 사용자 id, `hardware_items` 에 물류번호 관리 여부·보고 묶음·정렬. 유형(시트 유형/메모)·진행 상태(정규식)·물류번호(`reference_no`) 백필.
3. **권한**: 입고관리 권한 신설 + 소유 판정. 입고·조정은 입고관리 권한자, 출고 수정·취소는 본인 또는 입고관리 권한자.
4. **출고 등록 v2**: 출고일·유형·진행 상태 필수, CRM 고객 선택, 담당자 자동. 잔여 1대 이상 물류번호 선택 + 서버 초과 차단(배송 예정 포함). 신규 기록의 FIFO 자동 배정 제거, 작업건 출고도 물류번호 지원.
5. **회수 등록**: 원 출고 건 선택 → 물류번호·품목·고객 자동, 남은 수량까지만.
6. **입고 v2**: 무상 여부, 물류번호 순번 검증, 수량만 관리하는 품목은 물류번호 생략, 메모, 보관 장소 정리, 고객사 직배송 흐름.
7. **재고 조정 화면 + 재고 공식 정리**: ± 수량·사유 필수·입고관리 권한자만. §2-3 결정대로 공식 정리, 가용 음수 알림, 최소재고 편집 화면.
8. **판매대시보드**: 서버 집계 FY 품목 × 월("설치 완료 / +배송 예정"), 세일즈 + 프로모션, 고정 행. 클라이언트 2,000건 집계와 개요 타일 정리.
9. **알림·오더 정렬**: 배송 예정 30일 경과 알림(크론, 담당자별), 샘플 반납 예정일 필수, 오더 승인이 담당자·예정일을 채우거나 자동 생성을 멈춤.
10. **T1 전환(입고)**: 가져오기를 표 단위로 나누고, 기존 입고 행을 물류번호가 채워진 어드민 행으로 이관, 액세서리 기초 재고 입고, 현재고 보정 중단, 입고 가져오기 끄기.
11. **T2 전환(출고)**: 기존 출고 행 이관, 출고 가져오기·시트가 이긴다·오더번호 열 대사 끄기.
12. **T4**: `branch_hw_*` 미러 읽기 전용, `branch_hw_sales_monthly` 정리.

## 6. 적용한 기본 결정 (2026-10-28)

운영자 지시: "시트 끄기 제외하고 전부 적용" — §5 의 2~9 를 만들고 10~12(T1·T2·T4)는 하지 않는다. §2 질문에는 답이 없어 아래 기본값으로 진행했다. 시트 가져오기가 계속 도는 동안 어드민 기록과 싸우지 않는 쪽을 골랐다. 바꾸려면 이 표만 고치고 해당 코드를 따라 고친다.

| # | 질문 | 기본값 |
| --- | --- | --- |
| D1 | 입고관리 권한자 | 새 권한 `hardware.inbound`(여러 명 가능, 설정 > 팀원에서 부여). `hardware.finalize` 보유자(이왕찬)와 슈퍼 어드민은 자동 포함. 오더 승인은 계속 finalize |
| D2 | 배송 예정 → 설치 완료 | 본인 건(담당자·작성자 계정) 또는 입고관리 권한자가 확정. 지금처럼 새 기록 + 예정 차감(부분 확정 유지). 확정 행 상태는 `설치 완료` |
| D3 | 보관 장소·창고 공식 | 그대로(위치 기준 '창고' 잔액, 인천 더조은 = 창고). 공식 변경은 시트 현재고 보정이 멈추는 T1·T2 때 한다. 고객사 직배송은 입고·출고를 같은 '고객사 직송' 위치로 한 번에 기록해 창고에 영향이 없게 한다 |
| D4 | 샘플 | 사무실 샘플 풀·샘플 유닛 표 유지. 원장 출고에 유형 '샘플'을 더하고 샘플 출고는 반납 예정일 필수 |
| D5 | 오더 승인 배송 예정 | 자동 생성 유지. 유형 세일즈, 고객 = 오더 고객, 담당 = 딜 담당자(없으면 승인 요청자), 예정일·물류번호는 비워 두고 담당 매니저가 채운다(확정 때 물류번호 필수) |
| D6 | 물류번호 | 신규는 C3 부터(`nextLotNo`). 물류번호 관리 품목의 새 출고(배송 예정 포함)·확정은 물류번호 필수 + 잔여 초과 차단, FIFO 자동 배정은 새 기록에서 없앤다. 잔여 = 배송 예정까지 뺀 잔여(가용 기준). 오더 승인이 자동으로 만든 배송 예정만 물류번호 없이 둔다 |
| D7 | 기존 데이터 이관 | 하지 않는다(T1·T2 범위). 음수 재고는 입고관리 권한자가 재고 조정으로 정리 |
| D8 | 품목 목록 | 정의서 18개 이름으로 시드(없는 이름만 생성). 65"·110" IFP·S1 은 물류번호 관리, 액세서리·터치펜은 수량만. STDM1·DT1 은 건드리지 않는다 |
| D9 | 알림 | 배송 예정 30일 경과 = 예정일(없으면 등록일) 기준, 매일 담당자별 묶어 WeCom. 샘플 반납 예정일은 별도 칸(`expected_return_at`), 지나면 같은 알림에 싣는다 |
| D10 | 판매대시보드 | 서버 집계, 세일즈 + 프로모션(유형 모르는 시트 행은 세일즈로 센다), 회수는 빼지 않고 따로 보인다. 날짜 없는 배송 예정은 "날짜 미정" 칸. 행은 품목 단위, 묶음 소계. 수량만(금액 없음) |

## 7. 구현 계약 (병렬 작업 기준)

정본 규칙은 [`lib/hardware/inventory-process.ts`](../../lib/hardware/inventory-process.ts) 한 곳이다 — 서버 검증·화면·대시보드·알림이 이 함수들을 같이 쓴다. 스키마는 `supabase/migrations/20261028_hardware_inventory_process.sql`(칸 추가 + 품목 시드 + 확정 v4, 재실행 무해).

### 7-1. 원장 칸 (`hardware_movements`)

| 칸 | 값 | 쓰는 곳 |
| --- | --- | --- |
| `outbound_type` | `sales`·`promotion`·`as`·`sample` | 출고·회수. 시트 행은 비어 있다 → 응답의 `outbound_type_resolved`(시트 유형·메모 추정) |
| `is_free` | boolean | 입고 무상 여부(필수) |
| `return_of_movement_id` | 원 출고 id | 회수만(CHECK) |
| `customer_id` | `customers.id` | 출고 클라이언트. `to_location` 에는 계속 표시 이름 |
| `owner_user_id` · `created_by_user_id` | 계정 id | 본인 건 판정(`isOwnMovement`). 이전 어드민 행은 이름으로 판정 |
| `expected_return_at` | 날짜 | 샘플 출고 필수 |

진행 상태(`status`) 새 값: `배송 예정` · `설치 완료` · `회수`(`HARDWARE_PROGRESS_STATUS`). 예정 판정 정규식은 시트 행 때문에 그대로 둔다.

품목(`hardware_items`): `lot_tracked`(기본 true) · `report_group`(`board`·`camera`·`stand`·`accessory`·`pen`) · `sort_order`.

### 7-2. 권한 (`toHardwareActor` · `canActOnMovement`)

| 동작 | 누가 |
| --- | --- |
| 입고·재고 조정 등록, 실현 기록(설치 완료·회수·입고·조정) 수정·취소, 품목 설정 | 입고관리 권한자(`requireHardwareInventoryManager`) |
| 출고·회수 등록 | 편집 역할 전원(담당 = 본인. 다른 담당 지정은 입고관리 권한자만) |
| 배송 예정 수정·확정·취소 | 본인 건 또는 입고관리 권한자 |
| 오더 승인·반려·취소, 스냅샷 복원 | `hardware.finalize`(그대로) |

화면 viewer(`/api/admin/hardware` 응답, `lib/hardware/hardware-viewer.ts`): `canFinalize` · `canWrite` · `canManageInventory` · `userId` · `name`. 버튼은 표시만 막고 강제는 서버가 한다.

### 7-3. API

| 경로 | 바뀌는 것 |
| --- | --- |
| `POST /api/admin/hardware/movements` (단건·`movements[]`) | 새 필드 `outboundType` · `customerId` · `isFree` · `returnOfMovementId` · `expectedReturnAt` · `ownerUserId` · `adjustDirection`(`increase`·`decrease`). 규칙: 입고·조정 = 입고관리 권한자, 조정은 메모(사유) 필수, 입고는 `isFree` 필수. 고객사로 가는 출고는 `occurredAt`·`outboundType` 필수, 샘플은 `expectedReturnAt` 필수, 진행 상태는 `배송 예정`/`설치 완료` 로 맞춘다. 물류번호 관리 품목의 출고는 `lotNo` 필수 + 잔여 초과 422. 회수는 `returnOfMovementId` 필수 — 품목·물류번호·고객·유형은 원 출고에서 채우고 남은 수량까지만 |

### 7-4. 작업 나눔

W1 구현 메모(2026-10-28):
- 규칙은 요청자가 있는 쓰기에만 적용된다. 오더 승인처럼 시스템이 만드는 기록은 검사 없이 새 칸만 싣는다.
- 사무실·샘플 풀·수리로 가는 이동과 거기서 돌아오는 반납은 예전 흐름 그대로다(유형·고객·물류번호 선택 없음, 실제 출고는 FIFO).
- 마이그레이션 전 DB에서는 품목 `lot_tracked` 칸이 없다. 이때는 물류번호 규칙을 건너뛰고, 새 칸은 빼고 저장한다. 앱을 먼저 배포해도 지금 동작이 깨지지 않는다.
