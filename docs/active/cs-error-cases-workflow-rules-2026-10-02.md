- 작성일: 2026-10-02
- 대상: 이 업무를 처음 맡는 AI 또는 팀원
- 함께 쓰는 문서: `20261002_오류케이스_인덱스.md`(선례 76건의 목록과 요약), `20261002_오류케이스_보충기록.md`(문서가 없던 건의 상세)
- 근거: HQ 보고 템플릿 v2, 프로젝트 업무 원칙 메모, 케이스 문서의 재사용 체크리스트. 규칙과 흐름 옆의 (D-xx), (S-xx)는 그 내용이 나온 선례 ID다.

## 0. 이 문서로 하는 일

ClassIn Korea 지사는 한국 고객사(학원·교육기관)가 ClassIn 제품을 쓰다 생긴 문제를 접수하고, 지사 권한으로 확인할 수 있는 것은 직접 확인하고, 나머지는 중국 본사(HQ)에 넘긴다. 이 문서는 그 일을 도울 때 **어떤 순서로 확인하고, 무엇을 단정하지 않고, 고객과 HQ에 어떻게 전달하는지**를 적은 것이다.

새 문의가 들어오면 아래 순서로 판단한다.

1. **현상을 다시 정의한다.** 고객이 쓴 말("업로드 오류", "인터넷 끊김", "녹음이 안 됨")은 현상의 이름이 아니다. 실제로 무엇이 일어났는지 로그와 화면으로 확인한다(4장).
2. **인덱스에서 선례를 찾는다.** 오류 코드나 문구는 인덱스 부록 B, 고객사 이력은 부록 A, 증상 유형은 1~12장.
3. **5장의 증상별 흐름**을 따라 지금 가진 자료로 어디까지 갈라졌는지 보고, 다음에 받아야 할 자료를 정한다.
4. **확인된 사실과 추정을 나눠서** 답한다. 선례의 원인이 지금 건의 원인이라는 보장은 없다. 같은 증상이 다른 원인에서 나온 선례가 여럿 있다.
5. 고객 안내문이나 HQ 문의를 쓸 때는 2장의 규칙과 3장의 형식을 따른다.

인덱스와 보충기록은 길다. 인덱스의 부록 A~E(고객사별 식별정보, 오류 코드, HQ 담당자, 원본 정리 메모)는 문서 끝에 있으니 끝까지 읽는다. 증상별 확인 순서는 인덱스 부록 D에도 요약돼 있는데, 이 문서 5장과 다르면 5장을 따른다.

이 문서와 인덱스로 **판단할 수 없는 것**도 있다. 아래는 사람에게 넘긴다.

- 선례의 현재 상태: 인덱스의 상태는 2026년 9월 말 이전 기록이다.
- 보증, 교체, 환불, 가격, 보상 여부: 내부 합의 전에는 고객에게 먼저 꺼내지 않는다.
- HQ 서버·코드·DB 내부에서 일어난 일: 지사는 볼 수 없다. 추정으로만 적고 HQ에 확인을 넘긴다.
- 고객사 네트워크 장비 설정: 지사는 바꾸지 않는다. 근거를 붙여 고객사 담당자에게 요청한다.

## 1. 업무 상황

| 구분 | 내용 |
|---|---|
| 고객 | 한국 학원·교육기관. 채널은 카카오톡, 채널톡, 전화, 이메일 |

## 2. 지킬 규칙

### 2-1. 사실과 추정

- 직접 재현했거나 로그·측정으로 확인한 것만 단정형으로 쓴다. 증상에서 미루어 본 것은 "추정됩니다", "~로 보입니다"로 쓴다.
- 원인이 확정되기 전에 고객에게 말할 때는 확인된 사실과 미확인 항목을 나눠서 적는다.
- HQ 답변에 `应该`(아마), `按理说`(이론상), `正常来说`(정상적으로는)가 붙어 있으면 추정이나 일반론이다. 고객에게 옮기기 전에 확답을 다시 받는다(D-16, D-05).
- HQ가 말한 수치를 고객에게 단독으로 인용하지 않는다. "10cm면 정상"이라는 HQ 발언을 권장 이격 거리처럼 안내하면, 이미 그 거리에서 문제가 난 현장에서는 바로 반박당한다(D-05).
- 증상이 비슷하다고 HQ 내부 구조를 단정하지 않는다. 숙제 렌더링 건에서 지사가 "`<ol>`이 분해된다"고 단정했다가 HQ 조회로 기각됐다(D-01).
- HQ 1차 답변이 "네트워크 문제"여도 그대로 받지 않고 콘솔 지표와 시각을 대조한다. HQ가 다른 수업을 보고 답한 선례(S-03), 시각이 맞지 않은 선례(S-10), 답하지 않고 넘어간 질문이 남은 선례(D-19)가 있다.
- API와 기능 사양에 관한 HQ 답변은 공식 문서(docs.eeo.cn)와 교차 확인한 뒤 고객에게 전달한다.

### 2-2. 고객 안내

**전달하는 것**: 확인된 원인, 시스템 이상 여부, 복구 가능 여부, 남아 있는 자료, 다음에 할 일.

**전달하지 않는 것**

- 설정을 누가, 언제 그렇게 해 두었는지. "선택하지 않으셔서"가 아니라 "지정되지 않은 상태였습니다"처럼 상태만 적는다(D-04, D-21).
- 오류 코드, 서버명, Client IP, Account ID 같은 내부 정보(D-21).
- 확정되지 않은 원인, HQ가 확답하지 않은 기본값·사양.
- 하드웨어 결함·불량이라는 말. 원인 확정 전에는 "확인 중"까지만 한다(D-03, D-05).
- 파손 건의 원인 판단. 귀책 문제가 걸려 있어 고객에게 먼저 말하지 않는다(S-18).
- 의미를 모르는 로그 필드(S-22).
- 고객 파일에 문제가 있을 가능성. 확인 전에는 언급하지 않는다(S-25).

**쓰는 방법**

- 고객이 쓴 현상 이름이 틀리면 첫 회신에서 바로잡는다. "업로드 오류"를 그대로 받으면 재업로드 요청처럼 엉뚱한 방향으로 간다(D-04).
- 복구 불가는 원인 설명과 함께 전한다. 단독 통보는 반발을 부른다(D-04).
- 원인 회신에 "앞으로 이렇게 하라"는 점검 지시를 같이 싣지 않는다. 책임 전가로 읽힐 수 있어, 고객이 재발 방지를 물을 때 따로 안내한다(D-04). 다만 다음 수업에 바로 필요한 조작 절차는 같이 준다(D-21). 원인을 가르기 위한 확인 요청(핫스팟으로 한 번 수업해 보기, 기기 1대만 로그인하기, 공유기 전원 재인가)은 점검 지시나 우회책 안내가 아니다. 무엇을 확인하려는 것인지 밝히고 요청한다(D-19, D-20).
- 우회책을 근본 해결 전에 먼저 안내하면 그 우회가 표준 운영으로 굳는다. 미러링의 핫스팟 우회가 그런 예다(D-07).
- 고객사 설정을 "잘못됐다"고 하지 않는다. 의도된 보안 설정일 수 있으므로 "해제가 필요합니다"로 쓴다(D-07).
- 스펙 기대와 달랐던 건은 "안 된다"보다 "사양은 이렇고 그 안에서 이렇게 맞췄다"로 쓴다(D-16).
- "학원 네트워크 전체가 끊긴 것이냐" 같은 질문에는 확인한 범위(그 기기 한 대)까지만 답한다(D-20).
- 재현 영상을 첨부할 때는 "연결을 일부러 끊어 재현한 것"이라고 적는다(D-20).
- 재부팅(restart)과 초기화(reset)를 구분해 적는다(S-31).
- 지연, 손실률, 어느 구간이 불안정했는지는 풀어서 전달한 선례가 있다(D-18, D-20). 코드 번호, 서버명, IP, 계정 ID는 뺀다.
- 톤은 채널에 맞춘다. 카카오톡 고객 안내는 친근하고 실무적인 한국어로, 짧게 쓴다.
- 내부 승인이 필요한 것은 결제, 환불, 고객 중대 클레임 등에 한정된다. 그 밖의 회신은 승인 없이 보낸다.

**캡처를 보낼 때**

- 필요한 영역만 잘라 보낸다. 지사 백오피스 경로, Media Server 이름, Port는 가린다(D-04).
- HQ가 준 중국어 UI 캡처는 그대로 보내지 않고, 한국어 화면으로 다시 찍어 주석을 단다(D-21).
- WeCom 자동 번역 결과를 그대로 옮기지 않는다. `红外`(적외선)가 "red"로, `特写`(트래킹)가 "특필"로 나온 선례가 있다(D-05, D-16).

고객 안내문 뼈대(카카오톡):

```
안녕하세요, ○○님. ○/○ ○○ 수업 건 확인 결과입니다.

▪ 원인
(확인된 사실. 추정이면 "~로 추정됩니다")

▪ 영향 / 복구
(복구 가능 여부와 남아 있는 자료)

▪ 다음 수업부터 / 다시 발생하면
(바로 할 조작, 또는 재발 시 알려 달라는 정보: 수업명, 발생 시각)
```

위 뼈대는 확인을 마친 뒤의 결과 회신용이다. 접수 직후 콘솔을 보기 전에는 원인이나 복구 가능 여부를 말하지 않고 조회에 필요한 값만 묻는다. 현상 이름을 바로잡는 것은 확인을 마친 결과 회신에서 한다.

```
안녕하세요, ○○님. 클래스인입니다.
말씀하신 ○/○ 수업 건 바로 확인해 보겠습니다.

정확한 수업을 찾기 위해 아래 내용 부탁드립니다.
▪ 수업명
▪ 선생님(또는 학생) 로그인 계정
▪ 수업 시작 날짜와 시각

기록을 확인한 뒤 원인과 함께 다시 안내드리겠습니다.
```

### 2-3. HQ 에스컬레이션

- **넘기기 전에 지사에서 할 수 있는 확인을 끝낸다.** 콘솔 지표, 정상 대조군, 사내 재현. 설정 문제로 판명되면 넘기지 않는다(D-04, D-13, D-14).
- **세 언어로 쓴다.** 중국어(WeCom 발송용), 영어, 한국어(내부 참조) 순서이고 각각 별도 코드 블록에 넣는다. 중국어만 요청받아도 한국어판을 같이 낸다.
- **구조는 네 부분이다.** 인사와 한 줄 요청, 식별자 불릿, `Error info :` 블록(증상, 수치, 콘솔 상태, 관련 설정), 추정 원인 한 줄과 확인 요청. 확인 요청이 여럿이면 번호를 붙인다. 긴 서술 문단을 넣지 않는다. 불릿은 마크다운 기호 대신 `-`를 쓰고 이메일·계정은 링크 없이 원문 그대로 둔다.
- **분류를 적는다.** 버그는 `缺陷`, 기능 요청은 `需求`. 표시가 없거나 HQ가 `建议`(제안)로 받으면 백로그로 밀린다. 버그와 기능 문의를 한 메시지에 섞지 않는다(D-01, S-11, S-28). 원인이 확정되지 않은 결함 의심 건은 `疑似缺陷`로 적은 선례가 있다(S-36).
- **단말 건은 기기, OS 버전, 클라이언트 버전, 최신 여부를 같이 적는다.** HQ가 가장 먼저 되묻는 항목이다.
- **기재하지 않는 값**: Device ID, Client IP, Server(미디어·접속 서버명), Owner(영업 담당), 숙제 ID. 숙제 ID처럼 조회 키가 없을 때는 기관명, 담당자 UID, 대상 이름, 기간으로 대신한다.
- **예외**: 그 값이 증상의 직접 근거면 적는다. IP 충돌이 원인일 때의 Client IP, 서버·경로가 의심 지점일 때의 Media Server와 Port가 그렇다. 기준은 "그 값을 빼면 증상 설명이 성립하는가"다(D-02, D-19). 게이트웨이 구간은 정상인데 서버 연결만 나쁜 끊김 건은 서버와 경로가 의심 지점이므로 Media Server, Port, Client IP를 적는다(D-19).
- **지사 콘솔의 시각은 항상 KST다. HQ에 보낼 때는 중국 시각(UTC+8)으로 바꿔 적는다.** 중국 시각 = KST − 1시간(KST 18:00 → 17:00)이고 시간대를 같이 적는다. HQ가 보내는 캡처의 시각도 UTC+8이므로, 받은 시각은 1시간을 더해 KST로 읽는다(D-19, D-21). 케이스 문서에 실린 과거 발송문은 KST로 적은 것이 많으니 형식만 참고한다.
- **API 건은 콘솔 API 로그 번호로 요청을 지목한다.** 일부러 넣은 비정상 요청(프로브)은 미리 알리거나 빼고 낸다. 프로브 로그 때문에 오진이 난 선례가 있다(S-19).
- **계정, 수업명, 시각을 맨 위에 둔다.** HQ가 다른 수업을 보고 답한 선례가 있다(S-03).
- **선임 담당자에게는 완충 표현을 쓴다.** `百忙之中打扰您`, `冒昧`, `请教`. 기술팀에 처음 문의할 때 쓴 선례가 있다(D-18).
- **재문의는 앞선 회신을 한 줄로 인용하고, 그 회신이 설명하지 못하는 지표와 답받지 못한 항목을 번호로 다시 묻는다.** 小助手가 답한 건은 그 대화에 이어서 묻고, 小助手가 담당자를 안내했으면 그 담당자에게 직접 묻는다(D-05, D-19).
- **같은 담당자와 여러 건이 동시에 진행되면 건명을 적는다**(D-03과 D-05가 같은 대화창).
- **담당자가 바뀌면 첨부를 처음부터 다시 보낸다**(S-11).
- **An Vu(EEO 베트남 소속)의 답은 HQ 공식 입장이 아니다.** 확정이 필요한 것은 HQ 제품·개발 담당에게 따로 확인한다.
- **파일 전달은 WeDrive로 한다.** 화질 비교용 영상은 다시 인코딩하지 않는다. 학생 얼굴·음성이 있을 수 있어 링크는 지정 공유로 한다(D-16).
- **HQ 원격 지원(AweSun)의 식별 코드와 인증 코드는 담당자에게 1:1로만 전달한다.** 단체방에 올리지 않는다(D-16).

### 2-4. 문서화

- 케이스 문서 파일명은 `날짜_고객사_주제_케이스.md`. 개정하면 `_v2`를 붙이고 구버전은 지운다.
- 들어가는 내용: 식별 정보, 고객 문의, 확인 결과, 확정 사항과 추정, 배제한 원인과 근거, HQ 문의·회신, 고객 발송문 전문, 미해결 항목, 재사용 포인트, 업데이트 로그.

| 용어 | 뜻 |
|---|---|
| 전자칠판 (ClassIn Board) | S65 / S75 / S86 / S110. 2세대는 IR(적외선) 터치. 안드로이드 본체에 OPS가 꽂힌 구조 |
| OPS | 전자칠판에 들어가는 Windows PC 모듈. ClassIn X가 여기서 돈다 |
| ClassIn Cam T1 (CS11A) | 카메라. 화면이 두 개다: 트래킹(特写, 1080p 고정)과 파노라마(全景) |

| 메인 NIC | 인터넷용. 규격은 **자동 IP·자동 DNS**. 표준 구성은 ASIX USB 기가비트 |
| 카메라 NIC | 카메라 전용망. 규격은 **`192.168.1.222` / `255.255.255.0`, 게이트웨이·DNS 공란** |

배선 선례(D-02): 메인 랜선은 벽단자에서 전자칠판 하단 LAN 포트로 들어가 ASIX USB 랜카드로 잡힌다. 카메라는 PoE 스위치를 거쳐 OPS 본체 LAN(내장 Realtek)에 물린다. T1의 IP는 선례에서 `192.168.1.180`이었다(D-15, T-05). 다만 어느 NIC가 메인인지는 배선에 따라 기기마다 달랐고 고정 IP가 엉뚱한 NIC에 들어간 경우도 있었으므로, 어댑터 이름이나 설정값만으로 역할을 단정하지 않는다.

## 4. 접수하면 먼저 하는 일

1. **조회에 필요한 값을 받는다.** 수업명, 사용자 계정, 수업 시작 시각(월·일·시). 계정이 없으면 콘솔에서 수업을 찾을 수 없으므로 계정은 반드시 받는다. 하드웨어면 SN, 시스템 버전, 설치일.
2. **받은 계정이 맞는지 본다.** 고객이 준 번호와 콘솔에서 잡힌 계정이 다른 선례가 있다(S-13). 같은 기관에 여러 건이 동시에 진행 중이면 계정과 강의실이 섞이기 쉬우니 Client IP와 deviceName으로 강의실을 확인한다(D-21). Identity 칸으로 교사 계정인지 학생 계정인지 확정한다(S-32).
3. **현상을 다시 정의한다.** 고객 표현과 실제 현상이 달랐던 선례:
   - "영상 업로드 오류" → 녹화가 아예 시작되지 않음(D-04)
   - "인터넷 끊김" → 앱 강제 종료(D-02b)
   - "녹화 시작 메시지는 있는데 파일이 없다" → 시작 직후 오류로 중단(D-21)
   - "업로드가 느리다" → 실제로는 불러오기(다운로드) 구간(S-25)
   - "수업이 갑자기 종료됐다" → 예정 종료 시각에 정상 종료(S-13)
4. **정상 대조군을 붙인다.** 같은 계정·같은 기기의 정상 수업, 같은 학원의 정상 교실, 사내 테스트 계정 재현. 대조군이 있어야 "원래 이런 것인지"를 가를 수 있다(D-04, D-09, S-10, S-32).
5. **변수를 하나씩만 바꾼다.** 1대 전원 차단(D-05), 휴대폰 모드 토글(D-01), 핫스팟 연결(D-19, D-20), 어댑터 하나 비활성화(D-15)처럼 결과가 둘 중 하나로 갈리는 실험을 고른다.
6. **조치하기 전에 증거를 남긴다.** 재부팅·재설정·케이블 재체결·파일 재업로드는 원인을 지운다. 먼저 `ipconfig /all`, 로그, 설정 화면을 캡처한다(D-07, D-09, S-21, S-25, S-40).
7. **한 고객의 두 건을 하나로 묶지 않는다.** 정율사관의 7/30 건과 8/8 건은 네트워크와 메모리로 원인이 달랐다(D-02).

### 5-2. 녹화

**가. 녹화본이 없다**

1. `Recording Settings`를 본다.
   - **Disable이고 `Start Lesson-recording` 이벤트가 없음** → 그 회차를 만들 때 녹화 옵션이 꺼져 있었다. 시스템 결함이 아니고 복구할 수 없다. 녹화 설정은 회차 단위로 생성 시점에 정해지므로, 같은 반이어도 생성 배치(课节ID 대역)가 다르면 값이 다를 수 있다. 아직 진행하지 않은 회차의 설정은 지사 조회 화면이 아니라 기관 콘솔의 코스 관리에서만 보인다(D-04).
   - **Enable이고 Start가 있고 `Lesson-recording Error`가 있음** → 시작 단계에서 실패. `Camera Name`이 빈 값이고 error code 4001이면 카메라 녹화를 시작할 때 카메라가 지정되지 않은 것이다. 카메라 녹화 패널은 카운트다운 뒤 자동으로 시작하므로, 톱니바퀴에서 카메라를 고르지 않으면 조용히 실패한다(D-21). error code 2001도 같은 문구(카메라 영상 녹화 중 예외)로 나온 선례가 있다(S-10).
   - **Enable이고 Start도 있고 `Pushflow Quality Upload`도 정상인데 재생본이 없음** → HQ로 넘긴다(S-09).
2. Reason 문자열로 구성을 확인한다. **교실 녹화 OFF + 카메라 녹화만 ON**인 기관은 카메라 녹화가 실패하면 대신할 녹화가 없다. KJ영재센터가 이 구성이다.
3. 코스 목록의 녹색 "현장 녹화가 시작되었습니다"는 시작 이벤트만 반영한다. 그 뒤의 중단은 표시되지 않는다(D-21).
4. 수업 스크린샷은 녹화와 따로 저장된다. 기관 콘솔의 [수업 스크린샷]에서 볼 수 있어, 녹화가 없을 때 판서 확인 수단으로 안내한다(D-21).
5. 호스트가 Android 기기였는지 본다. 네트워크가 끊겼을 때 로컬 녹화로 넘어가지 못한다는 HQ 1차 회신이 있다(S-03, 재확인 전).
6. **복구 가능 여부**: 녹화본의 복구나 재처리는 실질적으로 불가능하다. 녹화가 시작되지 않았거나 시작 직후 실패한 경우는 데이터 자체가 없고(D-04, D-21), 끊겨서 나뉜 녹화나 품질이 이상한 녹화본도 되살리거나 다시 처리할 수 없다. 고객에게 복구를 기대하게 하는 표현을 쓰지 않는다. AI 요약의 재요약 신청은 이와 별개로 가능했다(D-11).
7. 예전 녹화가 사라졌다는 문의라면 장애가 아니라 보관 설정일 수 있다. 기관에 자동 삭제가 설정돼 있는지 확인하되 설정 상태를 단정하지 않는다. 보관과 요금 정책은 `20260929_KJ영재센터_녹화보관_스토리지요금_케이스.md`에 있다(문의 건이라 인덱스에는 넣지 않았다).

1. Status History의 입·퇴장 시각과 `Start Lesson-recording` 횟수를 대조한다. 교사가 교실을 나갔다 들어오거나 기기를 바꾸면 그만큼 비고 파일이 나뉜다(S-14).

4. 공사나 정전 뒤라면 전자칠판의 유선 NIC 상태와 유·무선 이중 연결을 본다(S-10).

전송 구간이 아니라 녹화 인코딩, 믹싱, 트랜스코딩 쪽이다. 지사 콘솔로는 확인할 수 없어 HQ에 서버 원본 스트림 상태를 묻는다.

- 음성 잡음·싱크 밀림 → 같은 모델 단말끼리 클라이언트 버전을 대조한다. 6.0.9.1671에서만 난 선례(S-39, 추정).
- 하울링 → 교실 장치가 정상이고 장치 변경이 없으면 믹싱 단계 추정(S-16).

**라. 녹화 화질 불만**

고객이 보는 것이 실시간 화면인지 녹화 파일인지, 트래킹인지 파노라마인지부터 묻는다. ClassIn X의 녹화는 카메라와 무관하게 최대 1080p이고 T1 트래킹은 1080p 고정이다. 흰 바탕과 글자가 날아가면 과노출이고 카메라 쪽 파라미터 조정으로 해결되며 설정은 카메라에 저장된다. OBS 경유는 두 화면 중 하나만 되고 매 수업 수동으로 켜야 하므로, T1 직결과 먼저 비교한다(D-16).

### 5-3. 카메라가 안 잡힌다

1. **최근에 자리를 옮겼거나 공사를 했는지** 묻는다. 그렇다면 배선부터 본다(D-09, S-10).
2. **고객 담당자에게 자료를 부탁할 때는 `ncpa.cpl` 창 사진과 `ipconfig` 결과 사진**으로 받는다(`ncpa.cpl` 창에 어댑터의 장치명이 보인다). 실패 교실 전부, 정상 교실 한 곳, 복구된 교실을 같이 받는다. 이때 TCP/IPv4 속성 창은 열게 하지 않는다. DHCP면 실제 IP가 안 보이고, 담당자가 설정을 건드릴 위험이 있다(D-09). 지사가 원격(RustDesk)이나 방문으로 직접 볼 때는 `ipconfig /all` 원문을 본다. IP 설정을 바꾸는 조치도 선례에서는 지사가 직접 했다(D-02, D-15).
3. 카메라 NIC 상태로 가른다.

   | 보이는 것 | 읽는 법 | 선례 |
   |---|---|---|
   | "네트워크 케이블 언플러그됨" | PoE 급전 실패. 인젝터·스위치의 AC 전원, 포트 방향(LAN/Data In과 PoE Out), 케이블 순. "USB를 꽂으면 되고 빼면 안 됨"도 같은 신호 | S-34 |
   | 링크는 있는데 `169.254.x.x`이고, 다른 어댑터에도 `192.168.1.222`가 없음 | 카메라 NIC에 고정 IP가 적용되지 않음. `192.168.1.222`를 넣고 어댑터를 껐다 켠다. CameraCMS에서는 검색은 되는데 `Connection failed`로 보인다 | T-05 |
   | 한 어댑터는 `192.168.1.222`, 다른 어댑터는 `169.254.x.x`이고 CameraCMS에서 검색은 되는데 `Connection failed` | 고정 IP가 카메라가 물리지 않은 NIC에 들어가 있을 수 있다. 4번으로 카메라가 어느 쪽에 있는지 확정한 뒤 5번 순서로 옮긴다 | D-15 |
   | 어댑터가 목록에 없음 | OPS 모듈 안착, USB 랜카드 탈락 | D-09 |

4. **어느 NIC에 카메라가 물렸는지**는 어댑터 이름으로 판단하지 않는다. IP 설정값은 참고가 되지만 설정이 엉뚱한 NIC에 들어가 있을 수 있어, 확정은 응답 여부로 한다. 어댑터 A를 "사용 안 함"으로 두고 CameraCMS에서 다시 검색했을 때 `Search:0`이면 카메라는 방금 끈 A에 물려 있고, 켜져 있는 다른 어댑터에는 카메라가 없다(D-15).
5. **IP를 다른 어댑터로 옮길 때**는 기존 어댑터에서 먼저 지우고 새 어댑터에 넣는다. "사용 안 함" 상태의 어댑터도 IP 설정을 갖고 있어 중복 경고가 난다. 옮긴 뒤 CameraCMS에서 기존 항목을 Delete하고 Start Search → Add to client로 다시 등록한다(D-15, T-05). 자리 이동으로 랜선이 서로 바뀐 것이 확인되면 랜선을 원래 포트로 되돌리는 방법도 있으나, 선례는 IP 설정을 옮기는 쪽이었고 둘 중 무엇을 택할지 정해진 기준은 없다.
6. NIC와 배선이 정상이면 **ping → 554 포트 → CameraCMS의 fps** 순으로 본다. ping과 554가 되는데 CMS에서도 `0*0 0.0fps 0Kbps`면 카메라가 영상 송출만 멈춘 것이므로, 로그와 설정을 캡처한 뒤 CMS에서 Reboot한다(Reset이 아니다). 재등록보다 재부팅을 먼저 해야 어느 조치가 효과였는지 구분된다(S-40).
7. **타사 네트워크 카메라(RTSP)**: 주소를 `rtsp://계정:비밀번호@IP:554/stream1` 표준형으로 넣는다. OBS에서는 되는데 ClassIn X 직결이 안 되면 주소 표기부터 본다. OBS는 `//`가 빠진 주소도 받아들이지만 ClassIn X는 오류 안내 없이 거부한다. 비밀번호에 `@`가 있으면 `%40`으로 바꾸고, 카메라 IP는 고정한다(D-06).
8. 카메라 NIC에 게이트웨이와 DNS를 비워 두면 Wi-Fi 인터넷과 유선 카메라를 같이 쓸 수 있다(D-15).
9. HQ: 문의는 朱晨阳, 원격 디버깅은 张冰(AweSun).

### 5-4. 전자칠판 네트워크

1. **규격부터 대조한다.** 메인 NIC는 자동 IP, 카메라 NIC는 `192.168.1.222` 고정. 규격에서 벗어난 설정이 보이면 값이 그럴듯해 보여도 1순위로 의심한다(D-02).
2. **`ipconfig /all` 원문**을 본다. Windows 네트워크 문제 해결사는 링크가 있고 고정 IP가 들어 있으면 "이상 없음"을 내므로 근거가 되지 않는다(D-02).
3. **`Duplicate`**는 같은 망의 다른 기기가 그 IP를 쓰고 있다는 뜻이다. 동시에 케이블과 배선은 살아 있다는 반증이다(D-02).
4. **유선이 죽으면 Wi-Fi로 자동으로 넘어가** 수업이 "되긴 되는" 상태가 되고 문제가 가려진다. Wi-Fi가 인터넷을 대신하고 있는지 본다(D-02, D-07, D-15).
5. 링크는 있는데 수신이 0패킷이면 배선·스위치·어댑터 쪽이다. 같은 자리에 노트북 USB-LAN을 직결해 IP를 받는지로 기기 쪽과 배선 쪽을 가른다(D-15b).
6. **수업 중에는 ping 같은 연결 테스트를 못 돌린다.** 그런 확인이 필요한 건은 수업이 없는 시간에 방문한다(D-02).
7. ISP의 "장비 쪽 문제"는 그들이 점검한 범위(회선~공유기)가 정상이라는 뜻이지 전자칠판 결함 확정이 아니다(D-02).
8. 고객사 장비를 건드리지 않고 쓸 수 있는 **조회 전용 명령**:

   ```
   ipconfig /all
   arp -a
   route print
   netsh wlan show interfaces
   netstat -ano | findstr LISTENING
   w32tm /query /status
   ```

   `ipconfig /release`, `/renew`, `w32tm /resync`, `netsh int ip set`은 쓰지 않는다. 조회처럼 보이지만 상태를 바꾸고 `Duplicate` 같은 증거를 없앤다(D-07).
9. Windows 시계가 계속 밀리는 교실은 NTP가 막힌 망일 수 있다. 로그 시각을 대조할 때 주의한다(S-29, D-07).

### 5-5. 미러링

1. **오류 문구**를 받는다. "장치가 동일한 LAN에 연결되어 있지 않습니다"면 아래 순서로 간다.
2. **판별 순서**(D-07):
   1. 양쪽의 게이트웨이 주소 대조 → 다르면 서브넷이 나뉜 것
   2. `arp -a`로 게이트웨이 MAC 대조 → 다르면 공유기 2대가 같은 대역을 쓰는 중복 서브넷. 양쪽 IP가 `192.168.0.x`로 같아 보여도 별개 망일 수 있다
   3. PC와 전자칠판 사이 양방향 ping

      | 게이트웨이 통신 | 단말 간 ping | 결론 |
      |---|---|---|
      | 정상 | 양방향 성공 | 망은 정상. 포트·앱 쪽 |
      | 정상 | 양방향 실패 | 공유기의 AP 클라이언트 격리 |
      | 정상 | 한 방향만 성공 | 호스트 방화벽 |

   4. 유선 단말로도 ping → 무선에만 걸린 제한인지
   5. 미러링 코드 직접 입력 → 탐색 단계만의 문제인지
3. PC 한쪽에서만 보면 이 판정이 나오지 않는다. 전자칠판 OPS에서도 조회 명령을 돌려야 한다.
4. 전자칠판 핫스팟(`ClassInX-…`)으로 연결되면 망 문제이고 기기·앱은 정상이다(S-33).
5. "갑자기 안 된다"면 설정이 아니라 바뀐 상태를 찾는다. 고객의 "같은 네트워크고 바꾼 적 없다"는 말은 실제로 서로 닿는지와 별개다(S-33).
6. **격리 해제는 고객사 네트워크 담당자가 한다.** 지사는 측정 근거를 붙인 요청서를 만든다. 핫스팟 우회는 먼저 안내하지 않는다(D-07).
7. **검은 여백**: 소스와 화면의 화면비(16:10과 16:9)를 대조한다. 배율(%)은 송출 해상도를 바꾸지 않는다. 해상도를 바꾼 뒤에는 미러링을 다시 연결한다. 16:9로 맞춰도 여백이 남으면 사용법이 아니라 결함 후보로 HQ에 올린다(S-36).

### 5-6. 후면 TV·보조 화면·화면 지연

- **보조 화면이 안 잡힌다**: Win+P와 디스플레이 "감지"로 Windows가 그 화면을 보는지 먼저 확인한다. Windows가 못 보면 ClassIn 문제가 아니다. 케이블이 전자칠판 패널의 HDMI IN이 아니라 **OPS의 HDMI 출력**에 꽂혀 있는지 본다. 노트북을 TV에 꽂아 보는 테스트는 TV 입력단만 검증한다(S-24, S-40).
- **보조 화면에 검은 띠**: 「설정 > 시스템 > 디스플레이 > 고급 디스플레이」의 디스플레이 1, 2 캡처를 받아 데스크톱 모드와 활성 신호 모드의 화면비를 대조한다(D-13).
- **화면 지연**: 밀리초 스톱워치를 모든 화면에 띄워 동시에 찍고 구간별로 나눈다. 조건은 한 번에 하나만 바꾼다. 무선 환경의 화면공유 구간 지연은 1.0~1.5초가 실측 기준이고, HDMI 구간은 0.1~0.2초다. S86 2세대는 루프아웃을 지원하지 않는다(D-08).

1. **SN, 시스템·펌웨어 버전, 설치일**을 먼저 받는다. 설치 후 기간으로 보증 범위 안인지 적는다.

4. 선례별 첫 확인:

### 5-8. 앱이 안 열린다·로그인 후 멈춘다·소리가 안 난다

1. 입실 전에 죽은 것은 콘솔 수업 기록에 없다. 로그인 이력에서 버전, 접속 노드, IP가 바뀐 시점을 찾는다(S-35).
2. **같은 기기에 다른 계정, 같은 계정으로 다른 기기**를 교차로 시험해 기기 쪽인지 계정·서버 쪽인지 가른다(S-30, S-35).
3. 모바일은 되고 PC만 무반응이면 인강용 DRM·보안 플레이어(Kollus Player, NSD 등)가 깔려 있는지 묻는다(S-08, 추정).
4. 실행하자마자 꺼지면 화면 녹화로 어느 단계(스플래시, 로그인, 홈)에서 꺼지는지 먼저 특정한다(S-30).
5. 소리가 아예 안 들리면 네트워크가 아니라 출력 경로다. 블루투스 이어폰, 앱 권한을 보고 같은 수업의 다른 학생은 들렸는지 묻는다(S-15).
6. 오류창 글자가 `????`나 ◆로 깨지면 Windows의 "Beta: 세계 언어 지원을 위해 Unicode UTF-8 사용" 옵션과 시스템 로캘을 본다(S-26, S-27).

### 5-10. API

1. **errno 102**는 순서대로 본다: 호출한 API가 실제로 있는지 → safeKey와 timeStamp 생성 → 쓰기 권한 활성화. 고객이 AI가 만든 코드로 없는 엔드포인트를 부른 선례가 있다(W-04). 조회 API가 성공했다는 것은 서명이 맞다는 근거가 되지 않는다(S-19).
2. HQ에는 콘솔 API 로그 번호로 요청을 지목한다.
3. **datasub 활성화, 콜백 URL 변경, VA 발급**은 WeCom이 아니라 `gpc.request@classin.com`으로 메일을 보낸다. @classin.com 계정에서 보낸 메일만 수신된다. 필수 정보는 SID, 콜백 URL, 알림 이메일, 구독 항목.
4. 웹훅 수신 실패는 응답 포맷부터 본다(W-03). 콜백 URL은 등록 전에 본사 쪽에서 DNS가 풀리는지 확인한다(W-05).
5. `addCourseClass` 등 v1 인터페이스는 2025-05-26부로 deprecated다. LMS 인터페이스로 안내한다.
6. AI 기능(요약, 스크립트)은 API로 제공되지 않는다.
7. 공식 문서는 docs.eeo.cn. 콘솔의 API 메뉴는 중국어 전용이라 영문 문서(docs.eeo.cn/api/en/)를 안내한다(T-04).
8. 확정이 필요한 API 사안은 张雅茹(제품)와 郑婉勤(API 총괄)에게 확인한다. An Vu의 답만으로 고객에게 안내하지 않는다.

## 6. 되풀이된 패턴

- **고객 표현은 현상이 아니다.** 첫 회신에서 현상을 다시 정의한다(4장 3번).

- **자동으로 넘어가는 동작이 문제를 가린다.** Wi-Fi 폴백(D-02), 카운트다운 뒤 자동 시작하는 카메라 녹화(D-21), 미러링 실패 시 안내되는 핫스팟(D-07).
- **화면의 "시작됨", "정상" 표시는 그 뒤의 실패를 반영하지 않을 수 있다**(D-21, D-02의 문제 해결사).
- **자리 이동, 공사, 정전 뒤의 장애는 배선과 NIC 상태부터 본다**(D-09, S-10, S-34).
- **실시간은 정상이고 녹화본만 이상하면 지사 콘솔로는 원인을 볼 수 없다.** 버전 대조까지 하고 HQ로 넘긴다(S-16, S-22, S-39).
- **HQ의 첫 답은 "네트워크 문제"인 경우가 많다.** 구간별 지표, 시각, 답하지 않은 질문을 들고 다시 묻는다(D-19, S-10, S-35).
- **HQ의 "정상 범위" 진술을 받아 두면** "더 띄우세요" 같은 반복 안내로 끝나는 것을 막을 수 있다(D-05).
- **값을 물을 때 산정 기준을 같이 묻는다.** "12,288MB 써도 되나"가 아니라 "물리 RAM의 몇 배인가"를 받으면 다음 기기에 스스로 적용할 수 있다(D-02).
- **재체결·재부팅으로 나은 건은 원인이 특정된 것이 아니다.** 원인 미확정으로 적고 재발 시 볼 지점을 남긴다(D-09, S-40).
- **신버전이 나온 직후의 이상은 버전을 대조한다.** 같은 현장의 다른 기기가 어느 버전인지 본다(S-39, T-01).
