# Partner Portal Customers / Calendar Deep Plan

기준일: 2026-04-14

## 1. 문서 목적

`/partner` 안의 `고객`, `캘린더` 탭을 단순 조회 화면이 아니라 실제 운영 판단과 후속 액션이 이어지는 허브로 재정의한다.

이 문서는 아래 두 질문에 답하는 데 집중한다.

1. 고객 탭은 무엇을 기준으로 묶고 어떤 액션으로 이어져야 하는가
2. 캘린더 탭은 단순 달력이 아니라 어떤 운영 예외와 우선순위를 보여줘야 하는가

## 2. 한 줄 결론

- `고객 탭`은 고객 정보 관리 화면이 아니라 `거래 탐색 + 관계 상태 판단 허브`여야 한다
- `캘린더 탭`은 날짜 보기 화면이 아니라 `설치/미팅/문서 기한 예외 처리 허브`여야 한다
- 두 탭은 분리된 메뉴이지만, 실제 사용 흐름은 `고객 -> 거래 -> 일정`, `캘린더 -> 거래/고객 복귀`로 순환해야 한다

## 3. 현재 상태 요약

현재 구현 기준:

- [app/partner/(portal)/customers/page.tsx](../../app/partner/(portal)/customers/page.tsx)
  - 고객 카드 목록, 검색, 고객 추가
  - 카드에는 기관명, 담당자, 지역, 진행 건수, 계약/미수금 정도만 노출
- [components/partner-portal/CustomerDetailSlideOver.tsx](../../components/partner-portal/CustomerDetailSlideOver.tsx)
  - 연락처, 재무 요약, 거래 이력, 최근 활동, 메모를 슬라이드오버로 제공
  - API payload 에 포함된 `recent_calendar_events` 는 아직 표시되지 않음
- [app/partner/(portal)/calendar/page.tsx](../../app/partner/(portal)/calendar/page.tsx)
  - 월간 캘린더, 날짜별 상세, 일정 리스트, 타입 필터, 일정 추가
  - 설치/미팅/문서 기한/내부 일정은 보이지만 `충돌`, `지연`, `확정 필요`, `비어 있는 일정` 같은 운영 큐는 없음

현재 구조의 장점:

- 고객과 캘린더가 이미 1차 메뉴로 분리되어 있어 접근이 쉽다
- V2 도메인 기준으로 고객/거래/캘린더가 연결될 수 있는 기반은 갖춰져 있다
- 고객 상세와 캘린더 화면 모두 `조회용 기반 컴포넌트` 는 이미 존재한다

현재 구조의 갭:

- 고객 탭이 아직 `기관 카드 모음` 수준이라 어떤 고객을 먼저 봐야 하는지 판단하기 어렵다
- 캘린더 탭이 아직 `일정 열람` 중심이라 어떤 일정이 위험한지, 누가 바로 움직여야 하는지 드러나지 않는다
- 두 탭 모두 `거래건 상세` 와의 왕복 액션이 약하다
- 고객 탭에서 `다음 일정`, 캘린더 탭에서 `고객 상태/거래 단계` 가 충분히 보이지 않아 문맥 전환 비용이 크다

## 4. 역할 재정의

### A. 고객 탭의 역할

고객 탭은 아래 상황에서 가장 먼저 열어야 하는 화면이어야 한다.

- 특정 기관의 전체 거래 이력을 보고 싶을 때
- 어느 고객이 지금 위험 상태인지 빠르게 분류하고 싶을 때
- 새 컨택, 새 거래, 후속 미팅을 고객 문맥에서 시작하고 싶을 때

즉 고객 탭은 `관계 중심 탐색기` 다.

### B. 캘린더 탭의 역할

캘린더 탭은 아래 상황에서 가장 먼저 열어야 하는 화면이어야 한다.

- 오늘/이번 주에 무슨 일정이 실제로 움직이는지 보고 싶을 때
- 확정은 됐는데 일정이 비어 있는 거래, 일정 충돌, 문서 마감 임박 건을 잡아내고 싶을 때
- 날짜 기준으로 바로 재조정, 확정, 완료 처리하고 싶을 때

즉 캘린더 탭은 `시간축 운영 관제판` 이다.

## 5. 공통 설계 원칙

- 고객을 중심 엔티티로 보되, 실제 운영 단위는 항상 `거래건` 이라는 사실을 숨기지 않는다
- 탭은 조회 단위이고, 상태 전환은 가능한 한 거래/일정 액션으로 연결한다
- 표보다 `우선순위`, `다음 액션`, `예외` 를 먼저 보여준다
- 고객 탭은 `누구를 먼저 볼지`, 캘린더 탭은 `언제를 먼저 처리할지`를 답해야 한다
- 두 탭 모두 `홈` 과 `workspace` 를 대체하지 않고 보조 진입점 역할을 수행한다

## 6. 고객 탭 심화 기획

### A. 핵심 JTBD

- 오늘 바로 대응이 필요한 고객이 누구인지 알고 싶다
- 한 고객에 묶인 여러 거래를 빠르게 비교하고 싶다
- 고객 정보, 최근 문서, 최근 일정, 미수 리스크를 한 묶음으로 보고 싶다
- 이 고객 문맥에서 바로 신규 컨택/미팅/일정 액션으로 이어지고 싶다

### B. 탭의 기본 정보 구조

권장 구조:

1. 상단 요약 스트립
2. 우선순위 필터/세그먼트
3. 고객 목록 또는 보드
4. 고객 상세 패널

핵심은 `목록 -> 상세 -> 액션` 흐름이 한 화면 안에서 이어지는 것이다.

### C. 상단 요약 스트립

고객 탭 상단에는 단순 총 고객 수보다 `리스크 중심 요약` 이 먼저 보여야 한다.

권장 KPI:

- 활성 고객 수
- 진행 거래가 있는 고객 수
- 미수금 있는 고객 수
- 이번 주 일정 있는 고객 수
- 후속 액션 없는 고객 수

`후속 액션 없는 고객 수` 는 아래 같은 케이스를 뜻한다.

- 컨택 단계인데 다음 미팅이 없음
- 확정 단계인데 설치 일정이 없음
- 문서 기한이 지났는데 후속 로그가 없음

### D. 기본 세그먼트

고객 탭의 1차 세그먼트는 이름 검색보다 먼저 와야 한다.

권장 기본 칩:

- `전체`
- `오늘 확인 필요`
- `진행 중 거래 있음`
- `미수 있음`
- `일정 임박`
- `휴면`

판단 기준 초안:

- `오늘 확인 필요`
  - 오늘 일정이 있거나
  - 문서 기한이 오늘/내일이거나
  - 일정/문서 후속이 비어 있는 고객
- `휴면`
  - 14일 이상 활동 로그 없음
  - 진행 거래는 없고 최근 액션도 없음

### E. 목록 레이아웃

현재의 카드 그리드는 유지 가능하지만, 카드 안 정보 밀도를 조금 더 높여야 한다.

고객 카드에 반드시 보여야 하는 것:

- 고객명, 담당자, 지역/캠퍼스
- 활성 거래 수
- 대표 거래 단계
- 다음 일정 시각
- 미수 여부
- 최근 액션 시각

추가로 카드 하단에 `거래 스택 미리보기` 가 필요하다.

예시:

- `본관 전자칠판 교체 / 계약`
- `별관 추가 설치 / 확정`

노출 규칙:

- 최대 2건까지만 바로 보여주고
- 초과분은 `+2 more` 같은 접기형 표시

### F. 고객 우선순위 점수

정렬 기본값은 이름순이 아니라 `attention_score desc` 여야 한다.

점수 요소 예시:

- 오늘 일정 존재
- 미수금 존재
- 확정 상태인데 설치 일정 없음
- 최근 활동 없음
- 문서 기한 임박

이 점수는 화면에 직접 점수 숫자로 보여주기보다 아래 형태로 번역한다.

- `즉시 확인`
- `이번 주 추적`
- `안정`

### G. 고객 상세 패널 재구성

현재 슬라이드오버는 좋은 출발점이지만, `거래 탐색기` 역할을 강화해야 한다.

권장 상세 패널 탭:

- `개요`
- `거래`
- `활동`

#### 개요

- 고객 기본 정보
- 계약/실수납/미수금
- 최근 일정 3건
- 최근 문서/활동 3건
- 바로 실행 CTA

바로 실행 CTA:

- `신규 컨택`
- `미팅 일정 추가`
- `정보 수정`

여기서 중요한 점:

- `recent_calendar_events` 는 현재 payload 에 이미 있으므로 바로 노출 가능하다
- 고객 상세의 첫 화면에서 `다음 일정 없음` 상태를 보이게 해야 한다

#### 거래

- 활성 거래 리스트
- 완료 거래 아카이브
- 각 거래 카드의 현재 단계, 금액, 다음 일정, 최근 문서 상태

이 탭의 목적은 고객 아래 여러 거래를 `비교` 하는 것이다.

각 거래 카드 빠른 액션:

- `상세 열기`
- `문서 보기`
- `일정 추가`

#### 활동

- 고객 단위 활동 타임라인
- 거래 활동과 고객 활동을 섞되, 어떤 거래에서 발생했는지 라벨링
- `일정 생성/변경`, `문서 공유`, `단계 변경`, `수정 로그` 를 한 축으로 보여준다

### H. 고객 탭에서 반드시 보여야 하는 예외

- 진행 거래는 있는데 다음 일정이 없는 고객
- 미수금이 있는데 최근 수납/후속 로그가 없는 고객
- 고객 1곳에 활성 거래가 2건 이상이라 혼선 가능성이 큰 경우
- 문서가 공유되었지만 최근 응답/후속 액션이 없는 경우

이 예외들은 단순 배지보다 `우측 미니 액션 레일` 또는 카드 상단 경고칩으로 보이는 것이 좋다.

### I. 고객 탭 액션 원칙

고객 탭에서는 아래 액션까지만 직접 처리하고, 나머지는 거래/캘린더로 넘긴다.

- 고객 생성/수정
- 신규 컨택 생성
- 미팅 일정 생성

아래 액션은 링크 아웃 우선:

- 계약 단계 진행
- 설치 상세 편집
- 수납 등록

즉 고객 탭은 `관계 시작점`, 거래 상세는 `실행 중심점` 으로 역할을 나눈다.

### J. 고객 탭 모바일 원칙

- 카드 목록은 유지
- 상세는 전체 화면 시트로 확장
- 요약 수치보다 `오늘 확인 필요`, `다음 일정`, `미수금` 세 요소를 우선 배치

## 7. 캘린더 탭 심화 기획

### A. 핵심 JTBD

- 오늘과 이번 주의 실행 일정을 한 번에 보고 싶다
- 일정 충돌, 비어 있는 일정, 문서 기한 위험을 빠르게 잡고 싶다
- 날짜를 보고 바로 확정/변경/완료 같은 후속 액션을 하고 싶다
- 일정 하나를 열었을 때 고객/거래 문맥까지 함께 보고 싶다

### B. 캘린더 탭의 기본 구조

권장 구조:

1. 상단 운영 요약
2. 보기 전환
3. 메인 캘린더
4. 선택 날짜 상세
5. 예외 큐
6. 전체 일정 리스트

현재 화면은 `월간 캘린더 + 날짜 상세 + 리스트` 구조가 있으므로, 여기에 `예외 큐` 와 `문맥 정보` 를 보강하는 방향이 적절하다.

### C. 상단 운영 요약

캘린더 상단에는 아래 네 수치가 가장 중요하다.

- 오늘 일정
- 이번 주 설치
- 일정 충돌
- 일정 미배정 건

`일정 미배정` 예시:

- 확정 거래인데 설치 일정 없음
- 설치 일정인데 장소 없음
- 설치 일정인데 팀/담당 정보 없음

### D. 보기 전환

캘린더 탭은 장기적으로 3가지 보기 전환을 갖는 것이 좋다.

- `월간`
- `주간/아젠다`
- `예외 큐`

도입 우선순위:

- 1차: `월간 + 리스트` 유지
- 2차: `예외 큐` 추가
- 3차: `주간/아젠다` 추가

이유:

- 현재 사용자는 달력 자체보다 `이번 주 처리 대상` 을 더 자주 확인할 가능성이 높다
- 설치/미팅 운영은 월간보다 주간/예외 큐 효율이 높다

### E. 필터 체계

현재 타입 필터는 유지하되, 운영 필터를 한 층 더 추가해야 한다.

1차 필터:

- `전체`
- `설치`
- `미팅`
- `문서 기한`
- `내부 일정`

2차 운영 필터:

- `오늘`
- `이번 주`
- `지연`
- `충돌`
- `미확정`

### F. 날짜 셀 표현 강화

현재 날짜 셀은 일정 수와 제목 2건 정도만 보여준다.
운영 관점에서는 아래 신호가 더 중요하다.

- 설치 여부
- 위험 일정 여부
- 문서 기한 여부
- 다일 일정 여부

권장 표현:

- 설치: amber 점
- 미팅: green 점
- 문서 기한: gray 점
- 위험/충돌: red corner chip

### G. 선택 날짜 상세 패널

선택 날짜 패널은 단순 일정 목록이 아니라 `그날 바로 처리할 액션` 이 보여야 한다.

이 패널에서 각 이벤트에 보여야 하는 것:

- 일정 타입
- 시간
- 고객명
- 거래명
- 장소
- 현재 상태
- 다음 액션

다음 액션 예시:

- `거래 열기`
- `고객 보기`
- `일정 변경`
- `완료 처리`

### H. 이벤트 카드 정보 강화

현재 이벤트 카드는 `title`, `description`, `timezone`, `deal_id` 수준이다.
실사용 관점에서는 아래 정보가 필요하다.

- 고객명
- 거래 단계
- 설치/미팅 상태
- 관련 문서 위험 여부
- 미수금 위험 여부

즉 캘린더 이벤트는 단순 이벤트가 아니라 `거래 문맥이 입혀진 projection` 이어야 한다.

### I. 예외 큐

캘린더 탭의 핵심 차별 포인트는 `예외 큐` 다.

권장 섹션:

- `오늘 놓치면 안 되는 일정`
- `충돌/겹침`
- `확정됐지만 일정 없음`
- `문서 기한 임박`
- `완료 처리 안 된 지난 일정`

예외 큐에서는 날짜 정렬보다 `행동 우선순위` 정렬이 중요하다.

### J. 일정 생성/수정 원칙

캘린더 탭에서 가능한 직접 액션:

- 미팅 일정 생성
- 설치 일정 생성
- 일정 변경
- 일정 상태 변경

권장 규칙:

- 생성 시 반드시 고객 또는 거래 중 하나의 문맥을 잡아준다
- 설치 일정은 거래 연결이 없으면 생성하지 않는다
- 문서 기한은 직접 생성보다 문서 상태에서 projection 되는 구조가 안전하다

### K. 캘린더 탭에서 고객/거래로 돌아가는 흐름

캘린더 탭에서는 항상 아래 두 점프가 쉬워야 한다.

- 이벤트 -> 고객 상세
- 이벤트 -> 거래 상세

그 이유:

- 같은 날짜 안에서도 사용자가 진짜 확인하고 싶은 것은 일정 그 자체보다 `이 일정이 어느 거래 문맥에서 왜 중요한가` 이기 때문이다

### L. 캘린더 탭 모바일 원칙

- 월간 보기보다 `오늘/이번 주 아젠다` 우선
- 선택 날짜 패널은 하단 시트
- 예외 큐는 접힌 아코디언이 아니라 위쪽에 먼저 노출

## 8. 고객 탭과 캘린더 탭의 연결 흐름

### 흐름 1. 고객 기준 후속 미팅 생성

`고객 탭 -> 고객 상세 -> 미팅 일정 추가 -> 캘린더 반영`

### 흐름 2. 고객 기준 설치 누락 발견

`고객 탭 -> 확정 거래 확인 -> 일정 없음 배지 -> 설치 일정 추가 -> 캘린더 반영`

### 흐름 3. 캘린더 기준 고객 문맥 확인

`캘린더 탭 -> 일정 선택 -> 고객 보기 -> 고객 아래 다른 거래/미수/최근 활동 확인`

### 흐름 4. 캘린더 기준 거래 액션 수행

`캘린더 탭 -> 이벤트 선택 -> 거래 상세 이동 -> 설치 완료/문서/수납 후속 처리`

### 흐름 5. 홈과의 역할 분리

- 홈: 전체 운영 요약과 오늘 할 일
- 고객: 기관/관계 관점 탐색
- 캘린더: 시간축/예외 관점 탐색

## 9. 데이터 / API 보강 포인트

### A. 고객 탭에 필요한 추가 집계

고객 목록 응답에는 장기적으로 아래 파생값이 필요하다.

- `next_event_at`
- `next_event_type`
- `attention_level`
- `has_unscheduled_confirmed_deal`
- `inactive_days`

### B. 고객 상세에 필요한 즉시 반영 포인트

현재 payload 에 이미 있는 값 중 바로 활용 가능한 것:

- `recent_calendar_events`

즉시 개선 포인트:

- 상세 패널 개요 탭에 `최근 일정` 추가
- 거래별 `next_installation_at` 노출

### C. 캘린더 탭에 필요한 projection

캘린더 응답에는 아래 필드가 함께 붙는 것이 좋다.

- `customer_name`
- `deal_title`
- `deal_stage`
- `event_health`
- `is_overdue`
- `is_conflict`
- `requires_follow_up`

### D. 원칙

- 원본은 계속 `calendar_events`
- 고객/거래 문맥을 얹는 것은 BFF projection
- 설치/문서 due/내부 일정은 같은 시간축 위에 올리되, 액션 권한은 source type 에 따라 다르게 가져간다

## 10. 구현 우선순위

### Phase 1. 빠른 체감 개선

- 고객 상세에 `최근 일정` 노출
- 고객 카드에 `다음 일정`, `최근 액션`, `대표 거래 단계` 추가
- 캘린더 리스트/상세 카드에 `고객명`, `거래명` 추가

### Phase 2. 운영 판단 강화

- 고객 세그먼트 `오늘 확인 필요 / 미수 있음 / 일정 임박`
- 고객 정렬 기본값을 attention 기준으로 변경
- 캘린더에 `예외 큐` 추가

### Phase 3. 실행 연결 강화

- 고객 상세에서 `신규 컨택`, `미팅 일정 추가` 고정 CTA
- 캘린더 이벤트에서 `고객 보기`, `거래 열기`, `일정 변경` 액션 강화
- 확정 거래의 `일정 없음` 경고를 고객/캘린더 양쪽에서 동시 노출

### Phase 4. 고급 운영 기능

- 주간/아젠다 뷰
- 일정 충돌 자동 감지
- 문서 기한과 수납 리스크를 캘린더 예외 큐에 결합

## 11. 최종 방향

`고객` 탭은 "누구를 먼저 볼 것인가" 를 결정하는 화면이어야 하고,
`캘린더` 탭은 "언제를 먼저 처리할 것인가" 를 결정하는 화면이어야 한다.

이 둘이 서로 연결되면 `/partner` 는 단순 탭 모음이 아니라,
`관계 축` 과 `시간 축` 두 개의 운영 진입점을 가진 포털로 작동하게 된다.
