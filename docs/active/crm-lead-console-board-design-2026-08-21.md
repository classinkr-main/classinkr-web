# CRM 리드 — 콘솔 기본 + 보드/시트 전환 설계 (2026-08-21)

대상 화면: `/admin/crm/customers/leads` (구현체 [components/admin/crm/leads/LeadsBoardClient.tsx](../../components/admin/crm/leads/LeadsBoardClient.tsx))

지금 화면은 목록에 닿기 전에 패널 6개(렌즈·단계·담당자·미확인 인박스·리스크·카운트 카드 10개)를
지나고, 숫자로 들어가는 창구가 세 군데로 갈라져 있으며, 기록 1건에 `행 → 드로어 → 연락 추가 → 폼 → 저장`
5단계가 든다. 이 문서는 그 구조를 **콘솔(기본) + 보드(대안 뷰) + 시트(대안 입력)** 로 재편하기로 한
결정과 그 근거를 남긴다. 구현은 미착수이며, 이 라운드에서는 아래 §5의 안정화 항목만 선반영했다.

---

## 1. 폭 예산 — 모든 결정의 상한

콘텐츠 폭은 뷰포트가 아니라 **1616px에서 하드캡**된다.

```
W = min(뷰포트 − 사이드바 240, 1680) − 64
```

- `max-w-[1680px]` — [app/admin/layout.tsx](../../app/admin/layout.tsx)
- `lg:px-8` (64px) — [app/admin/crm/layout.tsx](../../app/admin/crm/layout.tsx)

| 뷰포트 | W | 콘솔 레일 | 독 |
| --- | --- | --- | --- |
| 2560 · 1920 | 1616 | 260px 세로 | 400px in-flow |
| 1512 | 1208 | 260px 세로 | 400px in-flow |
| 1440 | 1136 | 56px 아이콘 | 400px in-flow |
| 1280 | 976 | 56px 아이콘 | 400px in-flow (목록 488px) |

임계는 목록 하한 480px에서 역산한다 — 세로 레일 유지 `260+16+480+16+400 = 1172`,
독 in-flow 유지 `56+16+480+16+400 = 968`. 즉 **W < 968에서만 독이 오버레이**가 된다.

W는 뷰포트만이 아니라 사이드바 접힘(±176px)에도 좌우되므로 미디어쿼리로는 원리적으로 맞출 수 없다 —
컨테이너 폭을 ResizeObserver로 실측한다. 다만 **보드의 독만은 뷰포트 단독**으로 판정한다(≥1920 in-flow).
W 기준으로 하면 사이드바를 접었을 때 컬럼이 300→252px로 *좁아지는* 역전이 생긴다.

## 2. 뷰 축

`?view=console|board` 단일 파라미터. `console`이 기본값이라 URL에서 생략된다.

- **전환은 어떤 상태도 리셋하지 않는다** — `filter · lens · sort · q · group · source · lead` 전부 보존.
- 대신 같은 `filter`를 뷰마다 다르게 해석한다.
  - **상태 동일선상 6키**(`all · unconfirmed · new · contacted · converted · closed`)는 보드에서
    행 술어가 아니라 **컬럼 포커스**로 강등 — 해당 컬럼 강조 + 나머지 `opacity 0.6`, 카드는 전부 표시.
  - **직교 키**(`unresponded*` · `unassigned` 등)와 `group` · `q`는 컬럼을 가로질러 AND.
- 컬럼 헤더는 필터가 걸려 있을 때만 `필터 n / 전체 N` 두 숫자를 쓴다.
- 뷰 선호는 사람별로 기억하되, 착지 URL에 `view · lead · focus · filter` 중 하나라도 있으면 **링크가 이긴다**.

대가: 같은 URL이 두 뷰에서 다른 결과 집합을 낸다. "링크 공유 = 같은 화면"은 `view`까지 같을 때만 성립한다.

### 기존 딥링크

`?focus=risk`는 정상 동작한다 — `#pipeline-risk` 밴드로 스크롤되고, 리스크 리드가 0건일 때만
밴드 자체가 렌더되지 않아 아무 일도 일어나지 않는다. 보드에서는 레일 '48시간+ 방치' 선택으로 리매핑한다.
(깨진 것을 고치는 게 아니라 의미를 옮기는 것이다.)

## 3. 보드 컬럼은 4개가 아니라 5개

`미확인 / 신규 / 연락중 / 전환 / 종료`. 종료는 기본 64px 세로 스트립으로 접는다.

**전환·종료를 병합하지 않는 이유**: 전환은 `POST /api/admin/leads/{id}/convert-v2`가 고객사와 딜을
실제로 만드는 비가역 액션이고, 종료는 단순 status PATCH다. 병합하면 드롭 한 번의 의미가 결정 불가가 되고,
잘못 고르면 CRM 고객 없는 `status=converted`가 쌓여 캠페인 전환율이 조용히 부풀며 되돌릴 UI가 없다.

큐는 콘솔에서 세로 레일 260px, 보드에서 **상단 가로 스트립**으로 같은 데이터를 눕힌다. 세로 260px은
컬럼 하나와 정확히 맞바꾸는 값인 반면, 가로 스트립의 세로 비용은 78px(컬럼당 카드 5.6→5장)뿐이다.

모집단: **활성 214 = 신규 + 연락중**. 미확인은 확인 게이트 밖이라 활성에 포함되지 않고,
전환·종료는 활성 밖이다. 세 축을 한 숫자에 섞지 않는다.

### 상태 변경 경로 — 드래그는 보조 입력

1차 경로는 (a) 카드 포커스 + 숫자키 1~5, (b) 카드 오버플로 메뉴, (c) 독의 상태 버튼 그리드.
드래그는 라이브러리 없이 HTML5 DnD로 얹되 유일 경로가 되면 안 된다 — `draggable`은 터치 이벤트를
발생시키지 않아 터치 노트북·태블릿에서 통째로 죽고, 키보드 사용자에게는 이동 수단이 0개가 된다.

W < 968이 아니어도 **1920 미만에서는 독이 오버레이**라 전환·종료 컬럼이 가려진다. 그 폭에서
두 단계로 가는 경로는 숫자키 4/5다. 오버레이에 scrim을 깔면 포인터를 전부 삼켜 드래그가 조용히
죽으므로 scrim 제거는 선택이 아니라 필수다.

## 4. 입력 — 컴포저(기본) + 시트(대안)

- **컴포저**는 독 하단에 상시 고정. 콘솔 독과 보드 독이 **같은 단일 인스턴스**를 쓴다.
  보드에 별도 하단 바를 만들지 않는다 — 보드는 '선택된 리드 없음'이 정상 상태라 대상이 모호하고,
  두 벌이 되면 채널↔결과 규칙이 두 곳에서 갈라진다.
- **시트**는 뷰가 아니라 모달이다(`?sheet=create` / `?sheet=wrapup&lead=<id>`).
  `view=sheet`로 두면 뒤에 목록이 없는 뷰가 되어 닫기 동선이 사라진다.
  두 모드가 3그룹(누구 / 어디서 / 다음 행동)을 공유하고, wrapup에서는 '누구'가 읽기 전용으로 접힌다.
- 컴포저 ↔ 시트 확장 시 입력 중이던 내용·선택한 칩이 캐럿 위치까지 이관된다.

### 높이는 3단만

칩 28 / 컨트롤 36 / 시트 필드 44. **40px을 새로 들이지 않는다** — 36px이 이 저장소의 사실상 표준이다.
시트의 '큼직함'은 높이 8px이 아니라 그룹 간 여백 24px과 핵심 필드 1열 배치로 번다.

### 저장 트리거 한 줄 규약

> 이산값(칩·드롭다운·프리셋)은 **선택 즉시** 저장하고 실패 시 낙관값을 되돌린다.
> 자유 텍스트(메모·직접 날짜)는 `⌘↵` 또는 저장 버튼으로만 커밋한다.
> **blur는 어떤 경우에도 저장하지 않는다.**

'다음 행동'은 `POST /logs → PATCH follow_up_at → PATCH status` 최대 3회 순차 호출이며
트랜잭션이 없다. 중간 실패는 '로그는 저장, 팔로업 실패'처럼 조각 단위로 알리고 실패한 조각만 재시도한다.
저장 실패 시 폼을 닫지 않는다.

## 5. 이 라운드에 선반영한 안정화

설계와 별개로, 위 구조가 전제하는 계약이 이미 깨져 있던 지점을 먼저 고쳤다.

| 증상 | 원인 | 수리 |
| --- | --- | --- |
| 드로어를 연 채 다른 행을 누르면 앞 리드의 메모·담당자·팔로업이 남고, 닫을 때 그 값이 새 리드에 저장됨 | `LeadDrawer`에 `key` 없음 + 상태를 `useState` 초기값으로만 시드 | 리드 id를 `key`로 걸어 인스턴스 격리 |
| 팔로업 날짜를 부분 입력하고 벗어나면 기존 팔로업이 무음 삭제 | native date가 미완성 상태에서 `""`를 반환 → `follow_up_at: null` PATCH. 닫기 경로의 강제 blur로 매번 재현 | `validity.badInput` 가드 + 값이 그대로면 쓰기 생략 |
| 카카오·이메일 기록에 통화 결과가 붙어 응대 통계 오염 | 결과 칩이 숨겨져도 직전 선택값이 state에 남아 전송 | [lib/crm/contact-log.ts](../../lib/crm/contact-log.ts) SSOT 신설, 클라이언트·서버가 같은 표를 봄 |
| 등록 시 담당자·첫 팔로업이 저장되지 않음 | 라우트가 파싱하지 않고, `saveLead`가 두 컬럼을 `null`로 하드코딩 | 두 지점 모두 통과시킴. 날짜만 온 값은 정오(12:00 UTC) 고정 |
| 검색 타이핑 중 매 키 입력마다 `replaceState` | URL 되쓰기 effect가 `searchQuery`에 직접 의존 | 검색어만 300ms 디바운스 |

## 6. 아직 정해지지 않은 것 (운영 정책)

기술로 답이 나오지 않아 남겨 둔다.

1. 보드에서 **전환 컬럼으로의 드롭**을 허용할지 — `convert-v2`는 비가역이다. 확인 다이얼로그 후 허용 / 아예 금지.
2. 담당자를 사용자 디렉터리 드롭다운으로 바꿀 때 **디렉터리 밖 이름**(외부 파트너·퇴사자)을 백필로 정리할지, '직접 입력' 탈출구로 살려둘지.
3. 보드 미확인 컬럼이 게이트 밖까지 보여주면 **콘솔 목록 건수와 숫자가 달라진다** — 배지로 설명하고 허용할지, 콘솔 기본 목록에도 미확인을 포함해 하나로 만들지.
4. 작성 중인 기록 초안을 **새로고침 후에도** 살릴지 — 살리려면 브라우저 저장소가 필요하고 리드 메모(개인정보 가능)가 평문으로 남는다.

## 7. 구현 시 분해 방향

`LeadsBoardClient.tsx`(3,000줄 초과)를 그대로 두고 뷰를 얹지 않는다. 순수 규칙(URL 코덱·컬럼 분배·큐 정의)을
`lib/crm/`로 먼저 빼고, 워크벤치 셸 / 큐 레일 / 목록 / 상세 독 / 컴포저 / 보드 뷰 / 시트로 나눈다.

주의: 현재 `tests/crm`의 어떤 파일도 `LeadsBoardClient`를 import하지 않는다 — 분해하는 동안
타입체크만 통과하면 통과처럼 보인다. 렌더 테스트(콘솔 3-pane · 보드 5컬럼 · 필터 해석 전환 · 독 key 격리)가
분해의 전제다. 이 저장소의 컴포넌트 테스트는 `renderToStaticMarkup` 기반이다
([tests/crm/action-rail.test.tsx](../../tests/crm/action-rail.test.tsx) 참고).
