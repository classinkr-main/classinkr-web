## 0. 한 줄 요약

CRM에서 홈페이지 문의가 안 보이는 이유는 셋이다. ① 새 문의를 거르는 범위·확인 게이트, ② 리드에 '특이사항'이라는 개념이 없음(코드의 '특이사항'은 고객 360 안 '위험' 기록 피드 하나), ③ 문의 원문이 상세 패널 7번째 블록에 있고 확인·배정·팔로업이 패널 안에서만 된다는 것.
①은 PR #65가 대부분 고쳤다. 이 문서는 ②·③을 다루는 화면 시안 4개(A 현황 띠 · B 리드 수신함 2단 · C 시트형 표 · D 어디서나 여는 패널)와, 어느 시안을 고르든 먼저 깔아야 할 공통 바닥(특이사항 규칙 하나, 재문의 내용 연결 등)을 정리한다.
**권장은 B(리드 화면을 수신함으로) + A 축소판(현황 맨 위 요약 → B로 착지)** 이다.

## 1. 요청과 해석

요청(운영자, 2026-11-05): "CRM 탭 디벨롭 — ① 홈페이지 문의, 빠른 리드들 보기 쉽지 않다 ② 특이사항 있는 데이터들 먼저 접근 가능하게 ③ 타고 들어가는 게 많다. 목업 4개 시안."

- **홈페이지 문의** = 응대 대상 소스(`DIRECT_INBOUND_LEAD_SOURCES`) 중 홈페이지 폼: 문의(`contact_page`)·데모 신청(`demo_modal`)·쇼룸 예약(`showroom_booking`)·도입 신청(`checkout_request`).
- **빠른 리드** — 코드에 같은 이름의 개념이 없다. 이 문서는 "바로 응대해야 하는 리드" = 응대 대상 소스 전체(위 4개 + Meta 리드폼 `meta_lead_ads`)로 읽었다. Meta 즉석 양식만 뜻했다면 시안의 '광고' 칩이 그 자리다. 카카오 FAST TRACK 배너(`components/contact/ContactFastTrack.tsx`)는 리드 행을 만들지 않으므로 이 화면에 나올 수 없다(D2에서 확인).
- **특이사항** = "사람이 먼저 봐야 할 이유가 있는 건"으로 넓혀 읽었다. 지금 코드의 위험 기록(`sentiment = 'risk'`)을 포함하고, 리드·고객 양쪽의 규칙 기반 사유를 더한다(§3 F1).

### 2.2 특이사항이 먼저 오지 않는다

- 코드의 '특이사항'은 `crm_customer_events.sentiment = 'risk'` 하나다. 사람이 손으로만 고른다(컴포저 `+ 상세` 안 '분위기', `불만 접수` 템플릿). 자동 경로(연락 기록·결과 기록·채널톡)는 위험을 쓰지 않는다(`lib/crm/lead-contact-event.ts:47-50`).
- 그 값을 쓰는 곳은 고객 360 **드로어**의 `타임라인 | 특이사항 피드` 토글 하나다(`Customer360Drawer.tsx:1153`, 로드한 20건만). 드로어는 고객DB 행의 '빠른 보기'에서만 열린다. 다른 모든 고객 링크가 가는 360 **전체 페이지**에는 위험 필터가 없다.
- 현황 '오늘 연락', 우선순위 엔진(`lib/crm/priority.ts`), 고객DB 플래그·보기, 세그먼트, 건강도 도넛, 전체 분석 '리스크' 목록 — 어디도 위험 기록을 읽지 않는다.
- **재문의**는 새 행을 만들지 않고 `last_inflow_at` + `crm_customer_events`(`site_inflow`, "재문의(재유입)")로만 남는다(`lib/server/lead-capture.ts:443-492`). 리드 상세는 그 이벤트를 읽지 않아(`lib/repositories/lead-activity.ts`) **리드 보드·상세에 재문의 표시도, 새 문의 내용도 없다.** 보드의 미응답 시간도 재문의 시각이 아니라 처음 들어온 시각으로 센다.
- 고객 플래그(VIP·만료임박·미수…)는 리드에 쓰이지 않고, 고객 쪽에서도 미수·VIP는 사실상 안 나온다(드로어가 `outstanding = null`을 넘김, `Customer360Drawer.tsx:1120`; 고객DB 행은 `vip`·`outstanding`을 안 넘김).
- 라벨·색이 제각각이다: '리스크'/'위험'/'특이사항(위험)'/'리스크 {등급}', `#B85C33`(토큰 밖)과 `#B43E3E`.

### 2.3 타고 들어가는 게 많다

오늘 들어온 홈페이지 문의 원문을 읽기까지(main 기준):

| # | 동작 |

- PR #65 뒤에도 CRM 쪽 경로는 4번 클릭 + 긴 스크롤이다(Overview 띠·토스트의 '보기 →'는 1번).

- 확인·담당·팔로업·상태·메모는 상세 패널 안에서만 바꾼다(묶음 작업 제외). 미확인 리드는 확인 전에 배정할 수 없다.

- 특이사항(위험) 하나 읽기: CRM → 고객DB → 검색 → 빠른 보기 → 활동 → 특이사항 피드(5번 + 입력).

## 3. 시안과 무관하게 먼저 할 것 (공통 바닥)

네 시안 모두 아래 위에 선다. 스키마 변경 없이 된다(F2의 이벤트 읽기 포함).

### F1. 특이사항 규칙 하나 — `lib/crm/notables.ts`(새 순수 모듈)

리드·고객 한 건을 받아 `{ kind, tone, label, reason, evidence }[]`를 돌려준다. 화면은 **가장 급한 사유 하나**만 행에 쓰고(어드민 라벨 단순화 — 한 행에 배지 하나), 나머지는 상세에 근거와 함께 둔다. 사유마다 "왜 이렇게 판정했는지"(근거)를 같이 싣는다.

| 사유 | 톤 | 판정 | 데이터 | 지금 가능 |
| --- | --- | --- | --- | --- |
| 24h+ / 48h+ 미응답 | 손실(Danger) | 응대 대상 소스 · 신규 · 테스트 제외, 시계 = max(처음 유입, 마지막 재유입) | `lib/crm/lead-response-status.ts` | 가능 — 보드 시계를 서버 요약과 통일 |
| 재문의 N회째 | 확인(Warning) | `hasInflowStamp` + `site_inflow` 이벤트 수, 직전 문의 뒤 연락 기록 유무 | `leads.last_inflow_at`, `crm_customer_events` | 가능(F2) |
| 방문·데모 일정 임박 | 확인 | 쇼룸 예약 일시 D-3 이내, 데모 '희망 시점' | 쇼룸 예약 테이블, `message` | 쇼룸 가능 · 데모 희망 시점은 자유 글이라 날짜를 못 읽으면 표시하지 않음 |
| 부재 반복 | 확인 | 연락 기록 결과 '부재중' 연속 2회+ | `lead_contact_logs` | 가능 |
| 팔로업 지남 | 확인 | `follow_up_at` < 오늘(KST) | `leads` | 가능 |
| 구매 신호 | 구매(Green) | 도입 신청 · 문의 유형 '도입 상담' 중 견적/방문 요청 · 원생 300명+ | `source`, `source_detail`, `size` | 가능(견적·방문 문구는 F1 2단계) |
| 지원 문의 → CS | 이관(중립) | 문의 유형 그룹 `support`(수업 운영·결제/계약·계정/기술·하드웨어/AS) | `lib/contact/topics.ts` `ContactTopicGroup` — 지금 미사용 | 가능 |
| 위험 기록 (고객) | 손실 | `sentiment = 'risk'`, 최근 30일(해결 상태가 없어 기간으로 자름) | `crm_customer_events` | 가능 |
| 만료 임박 · 미수 (고객) | 확인 · 손실 | `lib/crm/customer-flags.ts`, `lib/crm/service-risk.ts` | NEO 스냅샷, 딜 미수 | 가능 — F6 버그 수정 동반 |
| 경쟁 제품 · 해지 언급 | 손실 | 문의·기록 본문 키워드 | `message`, 기록 본문 | **D4 결정 후** — 오탐 위험, 근거 문장 표시 필수 |

### F2. 재문의 내용을 리드 화면에 연결

`lib/repositories/lead-activity.ts`가 그 리드의 `site_inflow` 이벤트를 함께 읽어 '문의 이력'으로 내준다(첫 문의 → 재문의 순, 사이 연락 기록 유무). 보드 미응답 시간도 `inflowClockMs`로 맞춘다.

### F3. 쇼룸·도입 신청 라벨

`SOURCE_LABEL`에 `showroom_booking: "쇼룸 예약"`, `checkout_request: "도입 신청"`을 넣는다(원시 키 노출 제거).

### F4. 문의 원문을 위로

리드 행·카드에 문의 내용 한 줄 미리보기. 상세는 `특이사항 → 문의 내용 → 빠른 조치 → 연락 기록 → 문의 이력` 순으로 바꾸고 연락처·활동·광고 귀속은 접는다. 쇼룸·도입 신청 문의는 `message` 안의 칸(희망 일시·인원·품목·합계·메모)을 칸으로 풀어 보여 준다(`lib/crm/lead-message.ts` 확장).

### F5. 확인과 배정을 한 번에

'확인하고 나에게 배정' 한 동작을 허용한다(지금은 확인 전 배정 차단 — D6). 딥링크 `?lead=`는 범위 밖 리드도 연다.

### F6. 위험 표기 통일

라벨은 '위험 기록' 하나, 색은 Danger 토큰(`#B85C33` 신규 사용 금지 — `lib/crm/status-tone.ts`). 드로어 `outstanding = null`·고객DB 행의 `vip`/`outstanding` 누락을 고쳐 미수·VIP가 실제로 보이게 한다.

## 4. 시안 4개

네 시안은 같은 샘플 데이터(2026-11-05 14:32, 오늘 문의 7 · 특이사항 11 · 늦어진 응대 4 · 응대 전 8)를 쓴다.

### 시안 A — 현황 맨 위 '먼저 볼 것' 3단

- **바꾸는 곳**: CRM 현황(업무 현황) 맨 위 한 블록. 기존 패널(리드 요약 · 오늘 연락 · 고객 찾기 · 매출·수금)은 그대로 아래로 내려간다.
- **구성**: 세 칸 — **새 문의**(오늘 · 최근순 · 내용 두 줄 미리보기 · 어제 이 시각 대비), **특이사항**(사유 한 줄 · 리드+고객), **늦어진 응대**(24h+ · 부재 반복 · 팔로업 지남). 행을 누르면 그 자리에서 펼쳐 전문 + 학원 규모·직책·담당 + `확인하고 나에게 배정 · 전화 · 담당 지정 · 내일 팔로업`. 머리에 유입 토글(전체 · 홈페이지 · 광고 · 접수). 이 블록만 전사 기준이라고 머리에 밝힌다.
- **클릭**: 원문 0(미리보기)~1(펼침), 조치 1.
- **재사용**: PR #65의 오늘 유입 피드(`lib/marketing/intake-feed.ts`)·리드 요약 전사 묶음·1분 갱신 훅. 새 것: F1 규칙, 펼침 행.
- **장점**: 변경 범위가 가장 작다. PR #65 CRM 배지가 그대로 이 블록에 착지한다.
- **단점**: 현황이 더 길어진다. 하루 문의가 20건을 넘으면 띠가 목록 노릇을 못 해 결국 리드 화면으로 가야 한다. 현황의 나머지(내 담당)와 범위가 섞여 보인다.
- **소유**: 그로스·CRM(`components/admin/crm/home/**`).

### 시안 B — 리드 화면을 수신함으로(목록 + 오른쪽 상세 고정)

- **바꾸는 곳**: 고객DB › 리드에 '수신함' 보기를 추가하고 기본값으로 둔다. 콘솔·보드는 그대로 남는다.
- **구성**:
  - 왼쪽 목록: `특이사항 있음 · 먼저 → 오늘 · 그 밖 → 어제` 묶음. 행 = 미확인 점 · 이름 · 기관 · 시각 / 사유 하나 + 문의 내용 한 줄. 위에 유입 칩(응대 대상 전체 · 홈페이지 · 광고 · 쇼룸·도입 신청), 문의 내용까지 찾는 검색, 범위.
  - 오른쪽 상세(드로어 대신 고정 칸): 머리(유입·소재·시각·미확인·연락처 + Compass ↗ · 고객 360 ↗) → **빠른 조치 한 줄**(확인 · 담당 · 팔로업 · 상태 · 전화 · 문자) → **특이사항**(사유 + 근거) → **이번 문의 내용**(칸으로) → **문의 이력**(첫 문의 → 재문의, 사이 연락 유무) → 연락 기록 한 줄 입력 → 접힌 연락처·사이트 활동·광고 귀속.
  - 키보드: J/K 이동 · E 확인 · A 나에게 배정 · F 내일 팔로업.
  - 휴대폰: 목록 → 상세가 위아래로 쌓인다.
- **클릭**: CRM 배지(착지를 리드 수신함으로, D5) → 행 = 2.
- **재사용**: 리드 목록 조회·필터 상태(`lib/crm/leads-board-state.ts`), 상세 패널의 각 섹션 컴포넌트(배치만 바꿈), `LeadMessageCard`. 새 것: 수신함 레이아웃, 묶음 정렬, 빠른 조치 줄, 문의 이력(F2).
- **장점**: '타고 들어가는' 구조(목록 → 드로어 → 스크롤)를 없앤다. 다음 문의로 바로 넘어가 연달아 처리하기 좋다. 재문의 맥락이 처음으로 리드 화면에 보인다.
- **단점**: 작업량이 가장 크다. `LeadsBoardClient.tsx`(2,631줄)·`LeadDrawer.tsx`(1,481줄)는 [CRM 탭 디벨롭 기획](crm-tab-develop-plan-2026-09-12.md) W2 원칙대로 분할부터 해야 한다.
- **소유**: 그로스·CRM(`components/admin/crm/leads/**`).

### 시안 C — 시트형 표 + 특이사항 열

- **바꾸는 곳**: 리드 콘솔 목록의 열과 기본 보기.
- **구성**: 저장된 보기 탭(특이사항 먼저 · 오늘 문의 · 응대 지연 · 재문의 · 쇼룸·데모 일정 · 미배정 · 진행 중 전체 · + 보기 저장). 열 = `들어온 시각 · 유입 · 이름·기관 · 문의 내용(한 줄) · 특이사항(사유 + 근거 한 줄) · 담당 · 응대 · 다음 할 일(버튼)`. 기본 정렬 '특이사항 급한 순'. 행을 누르면 표 안에서 펼쳐 전문·조치·문의 칸. 선택하면 묶음 줄(확인 · 담당 지정 · 내일 팔로업 · 종료).
- **클릭**: 보기 탭 1 → 펼침 1 = 2~3.
- **재사용**: 콘솔 목록·묶음 바(`LeadsConsoleList.tsx`, `LeadsBulkBar.tsx`). 새 것: 문의 내용·특이사항 열, 행 펼침, 저장된 보기.
- **장점**: 시트에 익숙한 팀이 한 화면에서 가장 많이 본다. 묶음 처리에 강하다.
- **단점**: 열이 많아 휴대폰에서는 카드로 바뀐다(표는 가로 스크롤 상자). 깊은 이력은 결국 펼침 밖으로 가야 한다.
- **소유**: 그로스·CRM.

### 시안 D — 어디서나 여는 문의 패널

- **바꾸는 곳**: 어드민 셸 전체. 사이드바 CRM 배지 · ⌘K '문의' · 새 문의 알림의 '보기'가 오른쪽 패널을 연다. 하던 화면(예: 견적)은 그대로 둔다.
- **구성**: 탭 `새 문의 · 특이사항 · 늦어진 응대 · 내 할 일`, 유입 칩 + 미확인만. 카드마다 문의 전문 · 사유 · `확인하고 나에게 배정 · 전화 · 내일 팔로업 · 전체 기록 ↗ / Compass ↗`. 휴대폰에서는 전체 화면 시트.
- **클릭**: 1.
- **재사용**: PR #65의 배지 카운트(`useAdminNavCounts.ts`)·토스트(`AdminNewInquiryToast.tsx`)·오늘 유입 피드. 새 것: 셸 패널, 패널용 조치 API 호출.
- **장점**: 다른 일을 하다가도 바로 응대한다.
- **단점**: 어드민 셸(공통) 변경이라 어드민 코어와 조율해야 한다. 패널 안에서 할 수 있는 일이 얕아, 이력·기록은 결국 리드 화면으로 간다. 리드 화면 자체가 그대로면 근본 문제는 남는다.
- **소유**: 어드민 코어(셸·배지·⌘K) + 그로스·CRM(패널 내용).

## 6. 권장

**B를 본체로, A를 축소해 현황 입구로 쓴다.**

- 세 불편 중 근본은 ③(목록 → 드로어 → 7번째 블록)이다. 이걸 없애는 건 B뿐이다. A·D는 입구를 늘리지만 깊은 내용은 여전히 리드 화면에 있다.
- A 축소판 = 현황 맨 위에 세 칸 숫자 + 칸마다 상위 3줄(사유 한 줄). 행을 누르면 B 수신함이 그 문의를 선택한 채 열린다. 현황에 목록을 하나 더 만들지 않는다.
- C의 '특이사항 열 · 저장된 보기 탭'은 B 안의 '콘솔(표)' 보기에 흡수한다(같은 F1 규칙을 쓰므로 비용이 작다).
- D는 B가 자리 잡은 뒤 실사용(배지 클릭 수·토스트 '보기' 수)을 보고 판단한다. PR #65 토스트의 '보기 →'가 B로 착지하면 D의 이득 대부분을 먼저 얻는다.

- 내부 값은 화면에 내보내지 않는다. 사전에 없는 값은 '기타 (원래 값)'으로 감싸 보이고 테스트가 잡는다.
