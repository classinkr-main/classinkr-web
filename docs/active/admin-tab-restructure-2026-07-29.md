## 1. 문제 진술

어드민은 지금까지 **한 사람(문준혁)의 실험대**로 자랐다. 회의 발언 그대로:

> "지금 기능을 다 넣은 거는 일단 되는 것들, 저도 제 실험용, 그리고 필요할지 몰라 —
> 뭐가 필요할지 모르고 뭐가 유용할지 모르니까. 저희가 거의 한 매달마다 업무 프로세스가 바뀌고 있어서."

그 결과 사이드바 항목이 21개가 됐고, 팀원들은 쓰지 않는다. 회의에서 나온 진단은 두 줄이다.

> "접어놓는 이게, 왜냐하면 진짜 많을수록 안 써요." (신희성)
> "회사 입장에서는 시간이랑 돈만 써서 [만들어놓고 안 쓰는] 그런 상황." (정규성)

**이 작업의 목적은 기능 삭제가 아니라 표면 정리다.** 팀원 각자가 자기 사이드바를 열었을 때
"내가 오늘 쓸 것"만 5개 안팎으로 보이게 하고, 나머지는 접되 라우트·딥링크·⌘K 검색은 전부 살린다.

### 1.1 회의가 명시적으로 구분해달라고 한 것

> "만약에 디자인이나 우리가 보기가 안 좋아서 무시할 수도 있는 그런 파트가 있어요.
> 그러니까 그 부분은 좀 구분을 했으면 좋겠다." (문준혁)

즉 **① 안 쓰니까 접는 것**과 **② 만듦새가 나빠서 안 쓰는 것**은 다른 처방이 필요하다.
①은 §4 처분표, ②는 §6 사용성 개선으로 나눠 다룬다.

## 3. 현행 진단

### 3.1 "숨김"이라는 말이 가리킨 두 가지

회의에서 "숨기자"가 서로 다른 두 뜻으로 쓰였다.

| 발언 | 실제 의도 |
|---|---|
| "저 밑에는 그냥 접어놓고" / "이거 숨기고" (캠페인 관리·마케팅 프로젝트) | **접기** — 문은 계속 쓰지만 팀원 눈에서 치움 |
| "얘 숨김. 근데 나중에 저는 보고 싶어요. 권한을 좀 줘야 될 것 같긴 해요" (Analytics) | **접근 제한** — 특정인만 |

그래서 축을 둘로 나눈다.

- **배치(placement)**: `primary`(상시 노출) / `folded`(하단 "기타" 접힘)
- **접근(access)**: `allow` / `deny` — deny면 사이드바·⌘K에서 사라짐

## 4. 목표 IA

### 4.1 사이드바 구조

섹션 헤더 4개를 **제거**한다. 상시 항목이 4~6개인데 헤더가 4개면 헤더가 더 많다.

```
📅 캘린더                    ← 첫 화면
📄 견적·문서
📦 하드웨어 재고
📣 캠페인
📝 콘텐츠
📖 가이드 문서               ← 전원 상시라 cs 전용인 내부 CS보다 위
🎧 내부 CS
──────────────────────────
▸ 기타 12                    ← 기본 접힘. 펼치면 3범주 소제목
    고객·매출
       CRM
       KR Team
       매출 장부  〔다듬는 중〕
    마케팅·분석
       자료 퍼널
       Analytics
       캠페인 관리
       마케팅 프로젝트
    시스템
       Overview
       CS 콘솔
       운영 상태
       설정
       개발 도구
```

- 상시 항목은 사람마다 다르다(§5.2). 위 그림은 `super`(문준혁) 기준.
- "기타" 펼침 상태는 `localStorage`에 기억한다.
- 기타 안의 3범주 소제목은 **해당 범주에 항목이 1개 이상 있을 때만** 렌더한다.
- **이 순서는 `ADMIN_NAV` 배열의 선언 순서로만 표현된다** — 렌더 단계에서 재정렬하지 않는다.
  가이드 문서가 내부 CS보다 위인 것은 임의 선택이 아니다: `tests/admin/sidebar-docs-gaps.test.ts`가
  cs 섹션 선언 순서를 `[docs, chatbot, cs-chatbot]`로 고정하고 있어 `docs < cs-chatbot`이 강제된다.
  두 계약이 같은 배열을 `filter`로 읽으므로 반대 순서는 표현 자체가 불가능하다.

### 4.3 병합에 대한 판정 근거

병합은 **회의가 명시적으로 지시한 2건만** 수행한다.

- ✅ **Analytics ← 방문자/트래픽**: "아예 그냥 합쳐주세요"(정규성). 트래픽 화면은 삭제하지 않고
  Analytics의 탭으로 들어간다. `/admin/traffic`은 `/admin/analytics?tab=traffic`으로 redirect.
- ✅ **캘린더 ← 공개 행사**: "공개 행사라는 말 빼고 캘린더 아래에". 이미 캘린더에 `event` 소스로
  붙어 있으므로 nav 항목만 내리고, `/admin/events` 관리 화면은 캘린더 안의 링크로 도달 가능하게 둔다.
- ❌ **KR Team + 매출 장부 병합은 하지 않는다**. 두 화면이 겹치지만 회의 지시가 없었고,
  "탭과 기능 자체는 남겨져 있는 상황"으로 간다. 둘 다 기타 › 고객·매출에 나란히 둔다.

## 5. 권한 모델

### 5.1 데이터 모델

```sql
-- supabase/migrations/20260729_admin_nav_access.sql
ALTER TABLE public.admin_profiles
  ADD COLUMN IF NOT EXISTS nav_preset TEXT,
  ADD COLUMN IF NOT EXISTS nav_overrides JSONB NOT NULL DEFAULT '{}'::jsonb;

COMMENT ON COLUMN public.admin_profiles.nav_preset IS
  '어드민 사이드바 프리셋 키(staff|sales|marketing|cs|lead|branch|super). NULL이면 기존 role 기반 동작(무변화).';
COMMENT ON COLUMN public.admin_profiles.nav_overrides IS
  '프리셋 대비 사람별 예외. {"/admin/crm":"primary","/admin/analytics":"deny"} 형태. 키=nav href, 값=primary|folded|deny.';
```

**기존 `capabilities` 컬럼과 섞지 않는다.** `capabilities`는 `hardware.finalize` 같은 *동작* 권한이고,
`nav_*`는 *표면 배치* 축이다. 한 배열에 넣으면 둘 다 읽기 어려워진다.

### 5.2 프리셋 정의

코드 SSOT: `components/admin/admin-nav-access.ts` (신규, `admin-nav.ts` 옆).

먼저 19개 항목(21 − 흡수 2)을 접근 성격에 따라 세 묶음으로 나눈다. **프리셋은 이 위에서 배치만 고른다.**

| 묶음 | 항목 | 접근 규칙 |
|---|---|---|
| `MOON_ONLY` (7) | Overview · CS 콘솔 · 운영 상태 · 설정 · 개발 도구 · 캠페인 관리 · 마케팅 프로젝트 | `super` 외 전원 **차단** |
| `RESTRICTED` (2) | 매출 장부 → `lead`·`branch`·`super`만 / Analytics → `lead`·`super`만 | 그 외 **차단** |
| `OPEN` (10) | 캘린더 · 견적·문서 · 하드웨어 재고 · 캠페인 · 콘텐츠 · 내부 CS · 가이드 문서 · CRM · KR Team · 자료 퍼널 | 전 프리셋 **접근 가능**. 프리셋은 배치(상시/기타)만 정한다 |

그래서 프리셋은 **"무엇을 상시로 올릴지"만 선언**하면 된다. 선언하지 않은 접근 가능 항목은 자동으로 기타로 간다.

| 키 | 표시명 | 상시(primary) 세트 | 개수 |
|---|---|---|---|
| `staff` | 기본 | 캘린더 · 가이드 문서 | 2 |
| `sales` | 영업 | `staff` + 견적·문서 · 하드웨어 재고 | 4 |
| `marketing` | 마케팅 | `staff` + 캠페인 · 콘텐츠 | 4 |
| `cs` | 고객 지원 | `staff` + 내부 CS · 견적·문서 | 4 |
| `lead` | 총괄 | `staff` + 캠페인 · 콘텐츠 · 견적·문서 · 하드웨어 재고 | 6 |
| `branch` | 지사장 | `staff` + KR Team · 매출 장부 · 견적·문서 | 5 |
| `super` | 최고 관리자 | 상시 7 전부 (§4.1) | 7 |

`staff`가 최소 바닥이다. 캘린더는 첫 화면이라 전원 필수, 가이드 문서는 "전원 상시" 결정에 따른다.

**배정 제안** (문준혁이 UI에서 최종 결정):
정규성 `lead` · 신희성 `marketing` · 황찬우 `marketing` · 김민재 `cs` ·
이왕찬 `sales` · 박한 `sales` · 진소망 `sales` · 김정무 `branch` · 문준혁 `super`

회의에서 언급되지 않은 5명(박한·진소망·이왕찬·황찬우·김정무)은 **추정**이므로, 배포 시점에는
배정하지 않고 문준혁이 UI에서 켠다(§8).

### 5.3 해석 순서

```
1. nav_preset이 NULL   →  기존 ADMIN_NAV[].roles 기반 동작 (= 오늘과 완전히 동일)
2. nav_preset 있음      →  프리셋의 상시 세트 적용, 나머지 접근 가능 항목은 folded
3. nav_overrides 있음   →  해당 href만 프리셋 위에 덮어씀 (primary | folded | deny)
4. role === SUPER_ADMIN →  항상 전체 접근 (프리셋·오버라이드 무시)
```

**오버라이드는 부여도 회수도 한다.** `MOON_ONLY`·`RESTRICTED` 항목에 `folded`/`primary`를 지정하면
프리셋 기본 차단을 뚫고 접근이 열린다. 예: 신희성(`marketing`)에게 매출 장부를 열어주려면
`nav_overrides = {"/admin/branch/ledger": "folded"}`. 반대로 `deny`를 지정하면 회수한다.
이 부여는 슈퍼 관리자만 할 수 있다(§5.4 API 가드).

4번은 자기 발등 찍기 방지다. 슈퍼 관리자가 실수로 자기 설정 화면을 deny하면 복구 경로가 없다.

위치: `/admin/settings?tab=members`. 현재 읽기 전용 계정 디렉터리(`MembersPanel`)를 편집 가능하게 확장.

위 예시: `cs` 프리셋의 상시 4개 + 오버라이드로 하드웨어 재고 1개 승격 = 상시 5.
접근 가능한 `OPEN` 10개 중 나머지 5개가 기타로 간다. `MOON_ONLY` 7개와 `RESTRICTED` 2개는 목록에
회색 잠금 상태로 보이되 켤 수 없다(슈퍼 관리자가 `RESTRICTED`는 명시 부여 가능 — 아래).

- 프리셋 변경 시 오버라이드는 **유지**하고 "예외 N개" 뱃지로 알린다. "프리셋만 적용(예외 지우기)" 버튼 별도.
- 프리셋 기본값과 다른 행에는 `예외` 뱃지.
- SUPER_ADMIN 대상 행은 전부 잠금(🔒) — §5.3 4번.
- 우측 미리보기는 실제 `AdminSidebar` 렌더 로직을 공유한다(별도 구현 금지 — 어긋나면 신뢰를 잃는다).

**API**: `PATCH /api/admin/users/[userId]/nav-access` — `requireVerifiedAdminContext(req, ["SUPER_ADMIN"])`.

### 5.5 보안 경계 — 이 설정이 하는 일과 하지 않는 일

**정직하게 적어둔다.** `app/admin/layout.tsx`는 클라이언트 컴포넌트이고 이 저장소에 `middleware.ts`가 없다.

| 레이어 | 이번 작업 | 실제 강제력 |
|---|---|---|
| 사이드바 · ⌘K 팔레트 | ✅ nav access로 필터 | 표면 정리 |
| 페이지 직접 진입(URL 입력) | ⚠️ 클라이언트 가드만 추가 | 우회 가능 |
| 데이터 접근 | ❌ 이번 작업 범위 밖 | **API `verifyAdmin` 롤 체크가 담당** (기존) |

즉 **이 기능은 업무 표면을 정리하는 UX 장치이지 보안 경계가 아니다.**
민감 데이터를 특정인에게서 실제로 차단해야 한다면 해당 API의 `requireVerifiedAdminContext` 롤 목록을
좁히는 별도 작업이 필요하다. 스펙 승인 시 이 한계를 함께 승인하는 것으로 본다.

## 7. 첫 화면 전환

`app/admin/page.tsx`의 `redirect("/admin/overview")` → `redirect("/admin/calendar")`.

전원 캘린더가 첫 화면이다. 문준혁도 마찬가지이며, Overview는 기타 › 시스템에서 접근한다.
사람별 첫 화면 분기는 하지 않는다 — 이 파일은 세션을 모르는 서버 컴포넌트이고,
분기를 넣으려면 리다이렉트 전에 세션 조회가 들어가 첫 진입이 느려진다.

## 8. 롤아웃

```
1. 배포          nav_preset 전원 NULL → 모든 팀원 화면 오늘과 동일 (§5.3-1)
2. 문준혁 검증   자기 계정에 preset='super' 부여, 새 사이드바·기타 그룹·권한 UI 확인
3. 문준혁 배정   /admin/settings?tab=members 에서 8명에게 프리셋 부여
4. 공지          변경 안내 (탭이 사라진 게 아니라 "기타"에 있다는 점 명시)
```

되돌리기: 해당 사용자의 `nav_preset`을 NULL로 되돌리면 즉시 기존 동작. 배포 롤백 불필요.

다음 주 VP 방문 일정이 있으므로 3단계는 방문 전에 마친다.

## 11. 미결 사항

1. **하드웨어 재고를 상시로 두는 것** — 회의에서 "이거 왕찬 님과 이야기해 보셔야 되고"로 남았다.
   이왕찬 확인 전까지는 `sales`·`lead` 프리셋에만 상시로 둔다.
2. **자료 퍼널 승격 시점** — VP 방문 후 쓸 만해지면 `marketing` 프리셋의 상시로 올린다.
3. **매출 장부 접근 범위** — 회의는 "희성 님하고 저랑"이었으나 `branch`(김정무)도 성과 화면이 필요하다.
   현재 설계는 `lead`·`branch`·`super`에 접근 부여 + 신희성은 오버라이드로 부여. 배정 시 확인.
