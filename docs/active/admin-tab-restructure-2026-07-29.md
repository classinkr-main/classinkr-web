# 어드민 탭 재구성 — 설계 스펙 (2026-07-29)

> 근거: 2026-07-29 홈페이지 피드백 회의에서 확정한 탭 축소·개인화 결정.
> 현재 구현 기준: `components/admin/admin-nav.ts`와 `components/admin/admin-nav-access.ts`.
> 선행 IA 역사 기록: [admin-ia-redesign-2026-06-29.md](../archive/admin-ia-redesign-2026-06-29.md),
> [cs-admin-console-ia-2026-07-27.md](cs-admin-console-ia-2026-07-27.md).

## 1. 문제 진술

어드민은 빠르게 기능을 늘리는 과정에서 실험용 표면과 일상 운영 표면이 한 사이드바에 섞였다.
회의에서 확인한 핵심 문제는 기능 부족이 아니라 탐색 밀도였다.

> "지금 기능을 다 넣은 거는 일단 되는 것들, 저도 제 실험용, 그리고 필요할지 몰라 —
> 뭐가 필요할지 모르고 뭐가 유용할지 모르니까. 저희가 거의 한 매달마다 업무 프로세스가 바뀌고 있어서."

그 결과 사이드바 항목이 21개가 됐고, 팀원들은 쓰지 않는다. 회의에서 나온 진단은 두 줄이다.

> "접어놓는 이게, 왜냐하면 진짜 많을수록 안 써요."
> "회사 입장에서는 시간이랑 돈만 써서 [만들어놓고 안 쓰는] 그런 상황."

**이 작업의 목적은 기능 삭제가 아니라 표면 정리다.** 팀원 각자가 자기 사이드바를 열었을 때
"내가 오늘 쓸 것"만 5개 안팎으로 보이게 하고, 나머지는 접되 라우트·딥링크·⌘K 검색은 전부 살린다.

### 1.1 회의가 명시적으로 구분해달라고 한 것

> "만약에 디자인이나 우리가 보기가 안 좋아서 무시할 수도 있는 그런 파트가 있어요.
> 그러니까 그 부분은 좀 구분을 했으면 좋겠다."

즉 **① 안 쓰니까 접는 것**과 **② 만듦새가 나빠서 안 쓰는 것**은 다른 처방이 필요하다.
①은 §4 처분표, ②는 §6 사용성 개선으로 나눠 다룬다.

## 2. 설계 원칙

| # | 원칙 | 근거 |
|---|---|---|
| P1 | **삭제하지 않는다. 접는다.** 라우트·기능·⌘K는 전부 보존 | "탭과 기능 자체는 남겨져 있는 상황" |
| P2 | **'당장 쓸 5개'는 사람마다 다른 5개** | 영업·마케팅·CS 담당자의 일상 작업면이 서로 다르다 |
| P3 | **가시성과 접근권한을 분리한다** | 회의의 "숨김"이 두 뜻으로 쓰였다 (§3.1) |
| P4 | **프리셋 미배정 기본값은 기존 role 기반 표시를 유지한다** | 설정이 없는 계정의 화면을 임의로 바꾸지 않는다 |

## 3. 현행 진단

### 3.1 "숨김"이라는 말이 가리킨 두 가지

회의에서 "숨기자"가 서로 다른 두 뜻으로 쓰였다.

| 발언 | 실제 의도 |
|---|---|
| "저 밑에는 그냥 접어놓고" / "이거 숨기고" (캠페인 관리·마케팅 프로젝트) | **접기** — 문은 계속 쓰지만 팀원 눈에서 치움 |
| "얘 숨김. 근데 나중에 저는 보고 싶어요. 권한을 좀 줘야 될 것 같긴 해요" (Analytics) | **접근 제한** — 특정인만 |

그래서 축을 둘로 나눈다.

- **배치(placement)**: `primary`(상시 노출) / `folded`(하단 "기타" 접힘)
- **접근(access)**: `allow` / `deny` — deny면 사이드바·⌘K에서 사라짐

### 3.2 코드로 검증한 사실

회의 발언 중 코드로 확인이 필요했던 것들. **회의에서 가정한 것과 실제가 다른 항목이 있다.**

| 회의 발언 | 코드 실측 | 판정 |
|---|---|---|
| "구글 캘린더에서 땡겨올 수 있어요?" → "이미 넣어놨어요" | [lib/team-member-calendars.ts](../../lib/team-member-calendars.ts) — 서비스 계정으로 등록 팀원 캘린더 읽기, **assignee = 캘린더 주인**으로 매핑 | ✅ 사실. 회의에서 제기된 "누구 건지 안 나옴"은 이미 해결된 구조 |
| "휴일 반영, 공휴일 같은 거 반영되고 하면 얘도 쓸 만할 것 같아요" | `EventType`에 `holiday`는 있으나 **수동 입력 타입**. 한국 공휴일 자동 주입 없음 | ❌ **실제 갭** → U1 |
| "공개 행사는 캘린더에 붙이면 돼" | 캘린더 `SOURCE_OPTIONS`에 `event`(공개 행사) **이미 포함** | ✅ 이미 붙어 있음. 남은 건 nav 항목 이동뿐 |
| "본문 다듬기 초안 생성 먼저 아니에요?" | [BlogPostEditor.tsx:2084](../../components/admin/BlogPostEditor.tsx) — "본문 다듬기"가 "초안 생성"보다 **위** | ✅ 지적이 맞음 → U6 |
| "요거 흰색이 있으면 좋겠어요. 바탕 화면이 흰색으로" | AI 패널 자체는 `bg-white`. 다만 에디터 본문이 `#fcfcfb`(미세 회색) | ⚠️ 패널은 이미 흰색 — 어둡게 보인 건 에디터 본문 → U7 |
| "메타 광고 실시간 동기화되는 거예요?" → "메일(스케줄)로 하루 두세 번" | 캠페인 warm-up에 `/api/admin/meta/campaigns` 존재, 수동 동기화 버튼 있음 | ✅ 사실 |

### 3.3 재구성 전 21탭

재구성 전 `ADMIN_NAV` 배열은 5섹션 21항목이었다. 현재 배열은 공개 행사와 트래픽의 최상위
nav 항목을 내린 19항목이며, 두 독립 라우트 자체는 계속 유지된다.

```
home       Overview
sales      KR Team · 매출 장부(MVP) · CRM · 견적·문서 · 하드웨어 재고 · 캘린더
marketing  캠페인 · 캠페인 관리 · 마케팅 프로젝트 · 콘텐츠 · 자료 퍼널 · 공개 행사 · Analytics · 방문자/트래픽
cs         가이드 문서 · CS 콘솔 · 내부 CS
system     운영 상태 · 설정 · 개발 도구
```

문제: 상시 노출 21개 + 섹션 헤더 4개. 팀원 관점에서 자기 것은 3~5개뿐인데 나머지 16~18개가 섞여 있다.

## 4. 목표 IA

### 4.1 사이드바 구조

섹션 헤더 4개를 **제거**한다. 상시 항목이 4~6개인데 헤더가 4개면 헤더가 더 많다.

```
📅 캘린더                    ← 첫 화면
📄 견적·문서
📦 하드웨어 재고
📣 캠페인
📝 콘텐츠
📖 가이드 문서               ← 전원 상시라 cs 전용인 내부 CS보다 위
🎧 내부 CS
──────────────────────────
▸ 기타 12                    ← 기본 접힘. 펼치면 3범주 소제목
    고객·매출
       KR Team
       매출 장부  〔다듬는 중〕
       CRM
    마케팅·분석
       자료 퍼널
       Analytics
       캠페인 관리
       마케팅 프로젝트
    시스템
       Overview
       CS 콘솔
       운영 상태
       설정
       개발 도구
```

- 상시 항목은 사람마다 다르다(§5.2). 위 그림은 `super` 프리셋 기준이다.
- "기타" 펼침 상태는 `localStorage`에 기억한다.
- 기타 안의 3범주 소제목은 **해당 범주에 항목이 1개 이상 있을 때만** 렌더한다.
- **이 순서는 `ADMIN_NAV` 배열의 선언 순서로만 표현된다** — 렌더 단계에서 재정렬하지 않는다.
  가이드 문서가 내부 CS보다 위인 것은 임의 선택이 아니다: `tests/admin/sidebar-docs-gaps.test.ts`가
  cs 섹션 선언 순서를 `[docs, chatbot, cs-chatbot]`로 고정하고 있어 `docs < cs-chatbot`이 강제된다.
  두 계약이 같은 배열을 `filter`로 읽으므로 반대 순서는 표현 자체가 불가능하다.

공개 행사와 방문자/트래픽은 최상위 nav에서만 내렸으며, `/admin/events`와 `/admin/traffic`
독립 라우트는 유지한다.

기타 12의 3범주 배분:

| 범주 | 항목 |
|---|---|
| 고객·매출 (3) | CRM · KR Team · 매출 장부 |
| 마케팅·분석 (4) | 자료 퍼널 · Analytics · 캠페인 관리 · 마케팅 프로젝트 |
| 시스템 (5) | Overview · CS 콘솔 · 운영 상태 · 설정 · 개발 도구 |

### 4.3 병합에 대한 판정 근거

최상위 nav 정리는 **회의가 명시적으로 지시한 2건만** 수행한다.

- ✅ **Analytics ↔ 방문자/트래픽 연결**: 트래픽은 최상위 nav에서 내렸지만 `/admin/traffic` 독립 화면을
  유지한다. Analytics는 리드·소스·콘텐츠 분석을 담당하고, 홈페이지 흐름·방문·전환 진단이 필요할 때
  트래픽 화면으로 링크한다. `/admin/traffic`을 Analytics 탭으로 리다이렉트하지 않는다.
- ✅ **캘린더 ← 공개 행사**: "공개 행사라는 말 빼고 캘린더 아래에". 이미 캘린더에 `event` 소스로
  붙어 있으므로 nav 항목만 내리고, `/admin/events` 관리 화면은 캘린더 안의 링크로 도달 가능하게 둔다.
- ❌ **KR Team + 매출 장부 병합은 하지 않는다**. 두 화면이 겹치지만 회의 지시가 없었고,
  "탭과 기능 자체는 남겨져 있는 상황"으로 간다. 둘 다 기타 › 고객·매출에 나란히 둔다.

## 5. 권한 모델

운영 정본 역할은 `SUPER_ADMIN`·`ADMIN`·`BRANCH` 3종이다. `EDITOR`·`VIEWER`·`PARTNER`는
기존 프로필·세션과 nav 표시를 깨지 않기 위한 레거시 호환 값이며, 새 역할 단계로 확장하지 않는다.
프리셋은 역할을 대체하지 않고 사이드바 배치만 개인화한다.

### 5.1 데이터 모델

```sql
-- supabase/migrations/20260729_admin_nav_access.sql
ALTER TABLE public.admin_profiles
  ADD COLUMN IF NOT EXISTS nav_preset TEXT,
  ADD COLUMN IF NOT EXISTS nav_overrides JSONB NOT NULL DEFAULT '{}'::jsonb;

COMMENT ON COLUMN public.admin_profiles.nav_preset IS
  '어드민 사이드바 프리셋 키(staff|sales|marketing|cs|lead|branch|super). NULL이면 기존 role 기반 동작(무변화).';
COMMENT ON COLUMN public.admin_profiles.nav_overrides IS
  '프리셋 대비 사람별 예외. {"/admin/crm":"primary","/admin/analytics":"deny"} 형태. 키=nav href, 값=primary|folded|deny.';
```

**기존 `capabilities` 컬럼과 섞지 않는다.** `capabilities`는 `hardware.finalize` 같은 *동작* 권한이고,
`nav_*`는 *표면 배치* 축이다. 한 배열에 넣으면 둘 다 읽기 어려워진다.

### 5.2 프리셋 정의

코드 SSOT: `components/admin/admin-nav-access.ts` (`admin-nav.ts` 옆).

먼저 19개 nav 항목(재구성 전 21 − nav에서 내린 2)을 접근 성격에 따라 세 묶음으로 나눈다.
**프리셋은 이 위에서 배치만 고른다.**

| 묶음 | 항목 | 접근 규칙 |
|---|---|---|
| 최고 관리자 전용 (7) | Overview · CS 콘솔 · 운영 상태 · 설정 · 개발 도구 · 캠페인 관리 · 마케팅 프로젝트 | `super` 외 전원 **차단** |
| `RESTRICTED` (2) | 매출 장부 → `lead`·`branch`·`super`만 / Analytics → `lead`·`super`만 | 그 외 **차단** |
| `OPEN` (10) | 캘린더 · 견적·문서 · 하드웨어 재고 · 캠페인 · 콘텐츠 · 내부 CS · 가이드 문서 · CRM · KR Team · 자료 퍼널 | 전 프리셋 **접근 가능**. 프리셋은 배치(상시/기타)만 정한다 |

그래서 프리셋은 **"무엇을 상시로 올릴지"만 선언**하면 된다. 선언하지 않은 접근 가능 항목은 자동으로 기타로 간다.

| 키 | 표시명 | 상시(primary) 세트 | 개수 |
|---|---|---|---|
| `staff` | 기본 | 캘린더 · 가이드 문서 | 2 |
| `sales` | 영업 | `staff` + 견적·문서 · 하드웨어 재고 | 4 |
| `marketing` | 마케팅 | `staff` + 캠페인 · 콘텐츠 | 4 |
| `cs` | 고객 지원 | `staff` + 내부 CS · 견적·문서 | 4 |
| `lead` | 총괄 | `staff` + 캠페인 · 콘텐츠 · 견적·문서 · 하드웨어 재고 | 6 |
| `branch` | 지사장 | `staff` + KR Team · 매출 장부 · 견적·문서 | 5 |
| `super` | 최고 관리자 | 상시 7 전부 (§4.1) | 7 |

`staff`가 최소 바닥이다. 캘린더는 첫 화면이라 전원 필수, 가이드 문서는 "전원 상시" 결정에 따른다.

실제 사용자별 프리셋·예외 배정은 `admin_profiles`의 현재 값과 설정 UI에서 관리한다.
실명 계정 매핑을 이 기준 문서에 복제하지 않는다.

### 5.3 해석 순서

```
1. nav_preset이 NULL   →  기존 ADMIN_NAV[].roles 기반 동작 (= 오늘과 완전히 동일)
2. nav_preset 있음      →  프리셋의 상시 세트 적용, 나머지 접근 가능 항목은 folded
3. nav_overrides 있음   →  해당 href만 프리셋 위에 덮어씀 (primary | folded | deny)
4. role === SUPER_ADMIN →  접근 차단 불가. 프리셋 배치는 적용하고 오버라이드는 무시
```

**오버라이드는 부여도 회수도 한다.** 기본 차단·제한 항목에 `folded`/`primary`를 지정하면
프리셋 기본 차단을 뚫고 접근이 열린다. 예: `marketing` 프리셋 사용자에게 매출 장부를 열어주려면
`nav_overrides = {"/admin/branch/ledger": "folded"}`. 반대로 `deny`를 지정하면 회수한다.
이 부여는 슈퍼 관리자만 할 수 있다(§5.4 API 가드).

4번은 자기 발등 찍기 방지다. 슈퍼 관리자가 실수로 자기 설정 화면을 deny하면 복구 경로가 없다.

### 5.4 권한 설정 UI

위치: `/admin/settings?tab=members`. `MembersPanel`에서 프리셋과 예외를 편집한다.

**행 클릭 → 우측 드로어**

```
┌─ CS 담당자  staff@example.invalid  ────────────────┐
│                                                     │
│  프리셋   [ 고객 지원 ▾ ]        예외 1개           │
│  ─────────────────────────────────────────────      │
│                                                     │
│  캘린더            [ 상시 | 기타 | 차단 ]           │
│  견적·문서         [ 상시 | 기타 | 차단 ]           │
│  내부 CS           [ 상시 | 기타 | 차단 ]           │
│  가이드 문서       [ 상시 | 기타 | 차단 ]           │
│  하드웨어 재고     [ 상시 | 기타 | 차단 ] 예외      │
│  CRM               [ 상시 | 기타 | 차단 ]           │
│  ...                                                │
│  설정              [ 상시 | 기타 | 차단 ] 🔒        │
│                                                     │
│  ─────── 이 사용자가 보게 될 사이드바 ───────       │
│  📅 캘린더                                          │
│  📄 견적·문서                                       │
│  📦 하드웨어 재고        ← 예외로 올린 항목         │
│  🎧 내부 CS                                         │
│  📖 가이드 문서                                     │
│  ▸ 기타 5                                           │
│                                                     │
│              [ 되돌리기 ]  [ 저장 ]                 │
└─────────────────────────────────────────────────────┘
```

위 예시: `cs` 프리셋의 상시 4개 + 오버라이드로 하드웨어 재고 1개 승격 = 상시 5.
접근 가능한 `OPEN` 10개 중 나머지 5개가 기타로 간다.

기본 차단·제한 항목도 **행은 잠기지 않는다** — §5.3대로 오버라이드가 차단 묶음을 뚫기
때문이다. 이 드로어를 여는 사람은 이미 슈퍼 관리자이므로, 필요하면 그 자리에서 열어줄 수 있어야 한다.
잠기는 것은 **대상이 SUPER_ADMIN일 때 드로어 전체**뿐이다(자기 발등 찍기 방지).

- 프리셋 변경 시 오버라이드는 **유지**하고 "예외 N개" 뱃지로 알린다. "프리셋만 적용(예외 지우기)" 버튼 별도.
- 프리셋 기본값과 다른 행에는 `예외` 뱃지.
- SUPER_ADMIN 대상 행은 전부 잠금(🔒) — §5.3 4번.
- 우측 미리보기는 실제 `AdminSidebar` 렌더 로직을 공유한다(별도 구현 금지 — 어긋나면 신뢰를 잃는다).

**API**: `PATCH /api/admin/users` — 기존 capabilities 엔드포인트에 body 판별자로 nav 분기를 얹는다
(`navPreset`/`navOverrides` 키가 있으면 nav 경로). 별도 라우트를 새로 파지 않는 이유는 가드
(`requireVerifiedAdminContext(req, ["SUPER_ADMIN"])`)와 감사 로그 배선이 이미 거기 있기 때문이다.
감사 action만 `admin.nav_access.update`로 분리해 capabilities 변경과 구분한다.

**주의**: nav 분기는 두 컬럼을 함께 덮어쓴다(완전 상태 전송 — capabilities 경로와 같은 관례).
호출하는 쪽은 `navPreset`과 `navOverrides`를 **항상 같이** 보내야 한다.

### 5.5 보안 경계 — 이 설정이 하는 일과 하지 않는 일

`app/admin/layout.tsx`의 nav 필터는 클라이언트 UX 계층이다.

| 레이어 | 이번 작업 | 실제 강제력 |
|---|---|---|
| 사이드바 | ✅ nav access로 필터 | 표면 정리 |
| ⌘K 팔레트 | ⚠️ 현재 `ADMIN_NAV` 정적 목록에서 파생하며 프리셋 미적용 | 접근 제한이 아닌 검색 UX의 알려진 갭 |
| 페이지 직접 진입(URL 입력) | ⚠️ 클라이언트 가드만 추가 | 우회 가능 |
| 데이터 접근·동작 | 별도 서버 경계 | **API 관리자 가드 + 필요한 `capabilities` 검사가 담당** |

즉 **이 기능은 업무 표면을 정리하는 UX 장치이지 보안 경계가 아니다.**
민감 데이터를 특정 역할·사용자에게서 실제로 차단하려면 해당 API의 관리자 가드 롤 목록과
기능별 `capabilities` 검사를 함께 좁혀야 한다.

## 7. 첫 화면 전환

`app/admin/page.tsx`의 `redirect("/admin/overview")` → `redirect("/admin/calendar")`.

전원 캘린더가 첫 화면이다. `SUPER_ADMIN`도 동일하며, Overview는 기타 › 시스템에서 접근한다.
사람별 첫 화면 분기는 하지 않는다 — 이 파일은 세션을 모르는 서버 컴포넌트이고,
분기를 넣으려면 리다이렉트 전에 세션 조회가 들어가 첫 진입이 느려진다.

## 8. 운영 적용 원칙

```
1. `nav_preset`이 NULL인 계정은 기존 role 기반 nav 표시를 유지한다(§5.3-1).
2. 프리셋·예외 변경은 `/admin/settings?tab=members`에서 수행하고 감사 로그를 남긴다.
3. 변경 전 실제 사용자 미리보기를 확인한다.
4. 변경 공지에는 탭이 삭제된 것이 아니라 "기타"로 이동했거나 nav에서만 내려갔음을 명시한다.
```

되돌리기는 대상 사용자의 `nav_preset`을 NULL로, `nav_overrides`를 빈 객체로 복원한다.
실제 사용자별 배정값과 특정 배포 시점의 상태는 이 기준 문서에 기록하지 않는다.

## 11. 미결 사항

1. **하드웨어 재고를 상시로 두는 것** — 운영 담당 확인 전까지 `sales`·`lead` 프리셋에만 상시로 둔다.
2. **자료 퍼널 승격 시점** — VP 방문 후 쓸 만해지면 `marketing` 프리셋의 상시로 올린다.
3. **매출 장부 접근 범위** — 기본 설계는 `lead`·`branch`·`super`에 접근을 부여하고,
   그 외 사용자는 개별 오버라이드로 부여한다. 실제 배정은 설정 UI에서 확인한다.
