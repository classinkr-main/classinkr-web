리드 → 고객 → 견적 → 오더 → 출고 → 매출을 앱 안 데이터로 한 줄에 묶는다. 하드웨어 시트와 매출(REV) 시트는
과도기 동안 입력 창구로만 쓰고, 영역별로 하나씩 어드민 입력으로 옮긴 뒤 끈다.

## 1. 운영자 결정 (2026-10-22)

| 항목 | 결정 |
| --- | --- |
| 최종 방향 | 하드웨어 시트와 매출 시트를 모두 어드민 시스템 안으로 편입한다. 지금의 구글 시트 의존은 과도기다. |
| 과도기 하드웨어 입력 | 지금처럼 시트에 입력한다. 앱이 자동으로 읽는다. |
| 과도기 하드웨어 매출 원본 | REV 시트. 출고는 매출을 새로 만들지 않고 REV 매출 줄과 짝짓는다. |
| 오더 시작점 | 견적 승인. |
| 리드 | 같은 학교·학원이면 기존 고객에 자동 연결한다. 딜은 견적을 만들 때 자동으로 생긴다. |
| 기록 단위 | 입고 1건 = 물량번호 1개(여러 품목이 한 번에). 출고 1건 = 고객 1곳의 물량 = 오더 1건. |
| 하드웨어 승인 | 하드웨어가 들어간 건은 무조건 **이왕찬 또는 지사장**의 승인을 받는다. 고객 승인이나 담당자 처리만으로는 오더가 되지 않는다. |

이 결정은 [입력 가속 기획](./hardware-input-speed-plan-2026-09-20.md)의 "어드민 수기 입력의 범위"에 답한다.
최종은 (c) 출고까지 전부이고, 옮기는 순서는 (a) 입고부터다(§5).

**하드웨어 승인 권한의 현재 상태(2026-10-22 코드 확인).**

- 승인 권한은 기존 기능 권한 `hardware.finalize`로 표현한다. 사람 이름을 코드에 넣지 않는다([Admin OS 운영 결정](./admin-os-operating-decisions-2026-07-11.md) §1: 역할이 아니라 슈퍼 어드민이 사용자별로 부여).
- 지금 이 권한은 이왕찬 계정에만 부여돼 있고(`supabase/migrations/20260711_admin_rbac_actor_audit.sql`), 슈퍼 어드민은 비상용으로 항상 통과한다(`lib/admin-auth.ts`의 `hasAdminCapability`).
- 지사장 역할(`BRANCH`)에는 자동으로 들어가지 않는다.
- 지금 이 권한이 막는 것은 배송 예정 → 실제 출고 확정, 실현된 기록 수정, 원장 취소, 시트 스냅샷 복원이다. 오더 승인은 새로 더한다(§4-3).
- 견적의 `pending_approval` 상태는 파트너 공유만 막고, 실제 승인 절차는 없다(`app/api/portal/quotes/[id]/share/route.ts`).

**후속 결정(2026-10-22).**

- 권한은 지금 그대로 둔다. 이왕찬과 같은 권한을 다른 계정에 더 켜지 않는다.
- 견적은 고객에게 보내기 전에 따로 승인받지 않는다. 승인은 오더로 확정할 때와 출고 확정 때다.
- §4-5(출고 ↔ REV 매출 짝짓기)와 구현 단계 S5는 확장할 때만 한다. 지금은 만들지 않는다.

## 2. 지금 끊긴 곳 (2026-10-22 코드 조사)

- **시트 → 앱은 한 방향, 반만 자동.**
  - 크론이 하루 한 번(08:00 UTC = 17:00 KST) 시트를 `branch_hw_*`로 복사한다(`app/api/cron/sync-branch/route.ts`, `lib/branch/sync/sync-hw.ts`).
  - 재고 원장 `hardware_movements` 반영은 "싱크·백업 후 가져오기" 버튼으로만 된다(`app/api/admin/hardware/import-sheet/route.ts`).
  - 앱이 시트에 쓰는 경로는 없다.
- **리드 → 딜은 버튼 전환뿐.** `lib/crm/lead-conversion.ts`가 고객과 딜을 만들지만 품목·수량은 넘어가지 않고 딜 금액은 0이다. 담당자는 리드 담당이 아니라 버튼을 누른 사람이 된다.
- **딜 모델이 셋.** Portal V2 `deals`(견적·계약이 붙는 곳), `crm_deals`(Deal Lite), NEO 오퍼튜니티 스냅샷이 서로 연결되지 않는다.
- **견적 승인은 할 일 카드만 만든다.** 공유 링크 승인(`app/api/share/quote/[token]/accept/route.ts`)은 견적 상태와 할 일 카드만 바꾸고, 딜 단계·금액·재고 예약은 그대로다. 자동 단계 이동은 견적 → 계약 전환 하나뿐이다(`app/api/portal/quotes/[id]/convert/route.ts`).
- **출고는 CRM 참조만 남긴다.** 확인 모달과 CRM 오더 대사(`components/admin/hardware/inventory/CrmOrderBacklogSection.tsx`, `lib/repositories/hardware-crm-orders.ts`)는 `reference_no`와 `raw.crmLink`만 저장한다. 딜 단계·금액·매출은 바뀌지 않는다. 배송 예정은 전부 사람이 클릭해서 만든다.
- **매출로 가는 자동 경로는 금액 0짜리 초안 하나.** 계약 관리자 서명 시 `lib/admin/handoff/contract-to-ledger-draft.ts`가 CNY 0원 초안을 만든다.
- **고객은 이름 글자로만 맞춘다.** 정규화가 두 벌이다(`lib/branch/account-key.ts`의 `normalizedAccountKey`, `lib/crm-source-linking.ts`의 `normalizeCrmName`). 품목 이름도 다르다(견적 `전자칠판 86"`, 재고 `86" IFP`).
- **통화가 객체마다 다르다.** 견적·딜 KRW, NEO 오퍼튜니티 USD, 매출 CNY. 환산·합산하지 않는다(운영 캐논).
- **버그: 출고↔매출 대사가 배송 예정도 출고로 센다.** `v_hardware_rev_matches`(`supabase/migrations/20260710_hw_rev_reconcile_matches.sql`)는 "배송 예정은 날짜가 없다"고 가정하고 `occurred_at IS NOT NULL`만 본다. 실제로는 예정 등록 때 날짜가 저장된다(`lib/repositories/hardware-inventory.ts`의 `occurred_at: input.occurredAt || null`, 대사 섹션은 오늘 날짜로 등록).

## 3. 설계 원칙

1. **앱 데이터가 뼈대, 시트는 입력 창구.** 연결 로직(오더 연결·재고 예약·매출 짝짓기)은 앱 테이블 위에서만 돈다. 기록 출처(`sheet_import`·`admin_manual`)는 꼬리표일 뿐 로직을 가르는 기준이 아니다. 그래야 시트를 끌 때 로직을 다시 짜지 않는다.
2. **영역마다 원본은 하나.** 같은 영역을 시트와 어드민 두 군데서 동시에 입력하지 않는다. 영역을 옮기는 날 그 영역의 시트 가져오기를 끈다.
3. **시트로 되쓰기는 만들지 않는다.** 없앨 시트에 투자하지 않는다. 서비스 계정은 시트 읽기 권한이면 충분하다.
4. **공통 키는 앱이 발급한다.** 오더번호·고객 ID·품목 SKU를 지금부터 앱이 만들고 시트에는 그 값을 적게 한다. 시트가 없어져도 키는 그대로 이어진다.
5. **오더의 뼈대는 Portal V2 딜.** [Admin OS 운영 결정](./admin-os-operating-decisions-2026-07-11.md)이 고객·딜·견적·계약·결제의 목표 정본을 Portal V2로 정했다. `crm_deals`와 NEO 오퍼튜니티는 여기에 연결만 한다.
6. **통화는 섞지 않는다.** 오더 금액은 견적 통화(KRW) 그대로, 매출은 CNY 그대로 나란히 둔다.
7. **애매하면 자동 확정하지 않는다.** 이름·품목으로 짐작한 연결은 "확인 필요"로 띄우고 사람이 고른다. 오더번호처럼 정확한 키가 있을 때만 자동으로 묶는다.

## 4. 과도기 연결 로직

```
리드 들어옴
 └ 같은 학교·학원(전화·이름)이면 기존 고객에 자동 연결. 애매하면 확인 목록으로

견적 작성
 └ 고객·딜 자동 생성(견적 작성 화면에 이미 있음)

고객이 견적 승인
 └ 하드웨어가 들어 있으면 '하드웨어 승인 대기'로 올리고 이왕찬·지사장에게 알림

이왕찬 또는 지사장이 승인  ← 오더 시작
 └ 오더번호 발급 (예: ORD-2610-014)
 └ 고객 단위 한 묶음으로 배송 예정 자동 등록 → 가용 재고에서 미리 뺀다

시트 '3.출고 현황'에 출고/배송 예정 줄 작성 (오더번호 열에 ORD-… 기입)
 └ 앱이 매시간 자동으로 읽어 원장에 반영 (시트가 안 바뀌었으면 건너뜀)
 └ 오더번호로 오더와 정확히 연결 → 앱이 잡아 둔 예약은 시트 줄로 대체
 └ 출고 완료면 딜 단계를 설치로 옮기고 오더에 출고 대수를 남긴다

매출 (REV 시트가 원본)
 └ 출고 ↔ REV 매출 줄을 고객·월로 자동 짝짓기
 └ "출고됐는데 REV 매출 없음" / "REV에 있는데 출고 없음" 목록

입고 (물량번호 단위)
 └ 시트 '2.입고 현황'을 매시간 자동 반영 → 재고 증가. 리드·오더와는 무관
```

### 4-1. 리드 → 고객 (S2 구현)

- 트리거: 매시간(`/api/cron/link-hourly`의 둘째 잡). 최근 3시간에 들어오거나 재문의한(`last_inflow_at`) 열린 리드, 회차당 최대 200건(`lib/server/lead-customer-autolink.ts`).
  - 공개 리드 저장 경로에는 일을 더하지 않았다. 저장 경로는 부수 효과를 골든 테스트로 묶어 둔 곳이라, 연결 실패가 접수에 영향을 줄 여지를 만들지 않는다.
- 매칭은 기존 엔진을 그대로 쓴다(`lib/repositories/crm-source-links.ts`의 리드 후보 생성, 지정 리드만 보는 `generateLeadLinkCandidatesForLeads`). 지금 비교 키는 기관명(정규화)이다. 전화번호 비교는 아직 엔진에 없다.
- 자동 확정은 고객 대상·신뢰도 0.92 이상·2위와 0.15 이상 차이일 때만(`crm_source_priorities` 정책). lead 는 원래 수동이어서 `20261022_crm_lead_auto_confirm.sql`로 켰다. 애매하면 `/admin/crm/matching` 후보로 남는다. 자동 확정 행은 `metadata.auto_confirmed = true`라 구분·되돌리기가 된다.
- 맞는 고객이 없으면 리드로 둔다. 고객은 견적을 만들 때 생긴다(§4-2).
- 리드 상태·담당·팔로업은 건드리지 않는다(재유입 병합 규칙과 같은 원칙).

### 4-2. 견적 작성 → 딜 (이미 있음)

- 견적 작성 화면(`components/portal/quotes/QuickQuoteComposer.tsx`)이 고객을 고르거나 새로 만들고, 기존 딜을 고르지 않으면 `quote` 단계 딜을 새로 만든다(`resolveDeal`). 그래서 이 단계는 새로 만들지 않았다.
- 견적 품목을 `deal_line_items`로 복사하지 **않는다**. CRM 오더 대사(`lib/repositories/hardware-crm-orders.ts`)가 딜 줄과 견적 줄을 둘 다 읽어서, 복사하면 같은 품목이 두 번 뜬다. 오더의 품목 줄은 승인된 견적 버전에서 바로 가져온다(§4-3).
- 견적 품목 이름(`전자칠판 86"`)과 재고 품목 이름(`86" IFP`)을 잇는 매핑은 오더를 만들 때 필요하므로 S3에서 만든다.
- 남은 차이: 딜 담당은 견적 작성자가 된다(리드 담당을 따르지 않는다).

### 4-3. 견적 승인 → 하드웨어 승인 → 오더 + 배송 예정 (S3 구현)

- 트리거는 둘이다. 고객이 공유 링크(`/share/quote/[token]`)에서 "진행"을 누르거나(`app/api/share/quote/[token]/accept/route.ts`), 담당자가 고객 확답을 받고 견적을 "승인됨"으로 바꾼다(`app/api/portal/quotes/[id]/route.ts` PUT). 둘 다 `ensureSalesOrderForAcceptedQuoteSafely`(`lib/repositories/sales-orders.ts`)를 부르고, 오더 생성이 실패해도 견적 승인 자체는 막지 않는다.
- 한 오더 = 한 고객 = 승인된 견적 1장이다(`sales_orders`). 품목 줄은 승인된 견적 버전에서 떠 와 `lines`에 둔다. 한 견적에 살아 있는 오더(승인 대기·승인됨)는 DB 유니크 인덱스로 하나뿐이라, 고객이 두 번 누르거나 담당자 처리와 겹쳐도 한 건만 남는다. 같은 견적 버전의 오더가 반려·취소됐으면 고객이 다시 눌러도 되살리지 않는다 — 다시 올리려면 견적을 고쳐 새 버전으로 승인받는다.
- 견적 품목 → 재고 품목 매핑은 `lib/orders/order-lines.ts`다. 카탈로그 SKU(`board-86`·`board_86` → `86" IFP`, `camera-t1` → `T1`, `stand` → `STD1`, 86" 패키지 → `86" IFP` + `T1`)를 먼저 보고, SKU가 없으면 품목 이름으로 고른다. 벽걸이 설치는 재고가 아니다. 모호한 하드웨어 줄은 "품목 확인 필요"로 표시되고 배송 예정에는 들어가지 않는다.
- 하드웨어 줄(재고 품목이 있거나 확인 필요인 줄)이 있으면 **하드웨어 승인 대기**로 만든다. 없으면(소프트웨어·서비스만) 바로 승인되고 오더번호가 붙는다(결정자 "자동(하드웨어 없음)").
- 승인 요청 알림: 고객 링크 경로는 견적 진행 알림(`quote.accepted`)에 "하드웨어 승인 대기" 안내 줄이 붙는다. 담당자 경로는 `hardware.order.approval_requested`(승인 필요) 알림이 따로 간다. 둘 다 기존 WeCom 웹훅 경로를 쓴다.
- 하드웨어 탭 홈의 **하드웨어 승인 대기**(`components/admin/hardware/inventory/OrderApprovalSection.tsx`)에서 `hardware.finalize` 권한자(이왕찬, 지사장=슈퍼 어드민)만 승인·반려·취소한다(`app/api/admin/hardware/orders/[id]/route.ts`). 목록은 하드웨어 편집 역할 전원이 본다. 결정은 감사 로그(`hardware.order.approve|reject|cancel`)에 남는다. 반려·취소는 사유가 필수다.
- 승인하면 오더번호 `ORD-YYMM-NNN`(한국 시간 달 기준, 달마다 001부터)을 발급하고, 견적 줄 × 재고 품목마다 배송 예정(창고 → 고객, 상태 "배송 예정")을 만든다. 배송 예정의 `reference_no`는 견적 줄 참조(`portal-quote:<견적>:line:<줄>`)라 CRM 오더 대사 목록에서 그 줄이 빠지고, 오더번호는 `raw.order_no`와 메모에 실린다(시트 '3.출고 현황' 오더번호 열과 같은 자리). 배송 예정을 만들지 못하면 승인을 되돌린다.
- 중복 방지: 승인은 "승인 대기 → 승인됨" 상태 전이로 한 번만 통과한다(동시에 눌러도 한 사람만). 오더번호는 DB 유니크 인덱스로 하나뿐이고, 겹치면 다음 번호로 다시 잡는다.
- 오더번호가 붙으면(승인·자동 승인) 딜을 확정(confirmed)으로 올린다. 전진만 하고, contact·quote·contract 단계일 때만이다. 딜에 오더번호 칸을 따로 두지 않고 오더가 `deal_id`로 딜을 가리킨다.
- 승인된 오더 취소는 아직 배송 예정인 줄만 정리한다. 출고 확정된 줄이 하나라도 있으면 막는다. 취소해도 오더번호는 다시 쓰지 않는다(시트에 적힌 옛 번호가 엉뚱한 오더에 붙지 않게).
- 오더가 잡은 견적의 줄은 **CRM 오더 대사** 목록에 오르지 않는다 — 거기서 따로 예정 등록하면 승인을 건너뛰기 때문이다(`lib/repositories/hardware-crm-orders.ts`).
- 이 단계는 앱 안에서만 일어난다. 시트에는 쓰지 않는다. DB는 `20261022_sales_orders.sql` 적용 전이면 오더 기능만 꺼지고(화면은 "미적용" 안내) 견적 승인은 그대로 된다.

### 4-4. 시트 출고 줄 → 오더

- 하드웨어 시트 '3.출고 현황'에 **오더번호** 열을 추가한다. 앱은 첫 행의 열 이름(`오더번호`)으로 찾는다. 단 기존 열(A~M)은 위치로 읽으므로 그 사이에 끼우면 안 되고 **비고 열 오른쪽(N열 이후)**에 둔다. 사이에 끼우면 값이 밀리기 전에 동기화가 멈추고 오류가 하드웨어 화면에 뜬다.
- 매시간 가져오기에서 오더번호가 있는 시트 줄은 그 오더에 정확히 묶는다. 같은 오더의 앱 예약은 시트 줄로 대체한다(지금의 "가져오기 때는 시트가 이긴다" §8-6 규칙과 같은 방향).
- 오더번호가 빈 시트 줄은 고객 이름 + 품목으로 후보를 찾아 "확인 필요"로 띄운다. 자동으로 묶지 않는다.
- 오더번호는 승인된 오더에만 발급되므로, **오더번호가 없거나 승인되지 않은 번호가 적힌 시트 출고 줄은 "승인 확인 필요"** 목록으로 이왕찬·지사장에게 보인다. 과도기에는 시트에 직접 쓰는 출고가 앱 승인을 우회할 수 있어서, 이 목록이 승인 규칙을 지키는 장치다.
- 시트 줄이 실제 출고(배송 예정 아님)가 되면 딜 단계를 설치(installation)로 옮기고 오더에 출고 대수를 남긴다.

### 4-5. 출고 ↔ REV 매출 (확장할 때만 — 2026-10-22 보류)

- 과도기 원본은 REV 시트다. 앱은 출고로 매출 줄을 만들지 않는다.
- 출고(오더) ↔ REV HW 줄을 고객·월로 짝짓고, 짝 없는 쪽을 목록으로 띄운다. 금액은 통화가 달라 비교하지 않고 존재만 본다.
- REV 시트에도 오더번호 열을 두면 고객·월 짐작 없이 정확히 붙는다(선택).

### 4-6. 입고

- 시트 '2.입고 현황'을 매시간 자동 반영한다. 물량번호 1건에 여러 품목이 한 번에 들어온다.
- 입고는 리드·오더와 연결하지 않는다. 매입 원가(USD·CNY)만 남긴다.

## 5. 시스템 편입 순서 (시트 끄기)

영역 하나를 옮기는 날의 절차는 같다: 그 영역 마지막 시트 가져오기 → 스냅샷 → 그 영역 가져오기 끄기 → 어드민 입력 시작.

| 단계 | 어드민으로 옮기는 것 | 끄는 시트 가져오기 | 바뀌는 로직 |
| --- | --- | --- | --- |
| T0 (지금) | 없음 | 없음 | §4 그대로. 시트 입력 + 매시간 자동 가져오기 |
| T1 | 입고 | '2.입고 현황' | 입고표(`InboundSheet`)가 유일한 입고 입력. 이미 있는 화면이라 가장 쉽다 |
| T2 | 출고 · 배송 예정 | '3.출고 현황', '재고현황' 보정 줄 | 견적 승인 → 예약 → 출고 확정이 앱 안에서 끝난다. 오더번호를 시트에 적는 일이 사라진다 |
| T3 | 매출 | REV 시트 | 매출 원본이 앱 매출 장부가 된다. 이때부터 출고 확정이 매출 초안을 자동으로 만든다(CNY 금액 입력·확인은 사람) |
| T4 | — | 전부 | 시트는 읽기 전용 보관. 내보내기는 앱에서 엑셀로 |

T3에서 "출고가 매출을 만든다"로 바뀌므로, §4-5의 짝짓기 로직은 그대로 두고 방향만 뒤집으면 된다(원칙 1).

## 7. 위험과 대응

- **매시간 전체 교체 가져오기.** 시트를 고치는 도중 상태가 들어올 수 있다. 다음 회차에 바로잡힌다. 시트 체크섬이 같으면 건너뛰어 스냅샷이 쌓이지 않게 한다. 스냅샷 보존 기간 정리가 필요하다.
- **앱 예약과 시트 예정의 이중 계상.** 오더번호가 같으면 시트 줄이 대체한다. 오더번호 없는 시트 예정 줄이 같은 고객·품목이면 "겹침 의심"으로 띄운다.
- **고객 이름 정규화 두 벌.** S2에서 하나로 합친다. 합치면 기존 연결 키가 바뀔 수 있어 재매칭을 한 번 돌린다.
- **견적 공유 뷰어 상태.** 운영 캐논(2026-07)에는 `/share` 뷰어가 준비 중으로 적혀 있었다. S3 구현 때 확인 — `/share/quote/[token]` 화면에 "진행" 버튼이 있고 수락 API가 동작한다. 담당자 "승인됨" 처리도 같은 오더를 만든다.
- **품목 매핑 누락.** 카탈로그에 없는 하드웨어 품목은 "품목 확인 필요"로 승인 화면에 뜨고 배송 예정에 들어가지 않는다. 자주 나오면 `lib/orders/order-lines.ts`의 SKU 표에 더한다.
- **배포·마이그레이션.** 새 마이그레이션은 서울 프로젝트에 먼저 수동 적용한다([DB 마이그레이션 런북](./db-migration-runbook.md)).
