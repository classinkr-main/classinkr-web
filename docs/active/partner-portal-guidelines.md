## 1. 제품 정의

- 파트너 포털은 `파트너사 대표 1인`과 `ClassIn 팀`을 위한 상업 운영 도구다.
- 고객은 포털 로그인 사용자가 아니다.
- 고객은 `링크 기반 열람/서명` 사용자이며, 필요시 `PDF 다운로드`로 문서를 확인한다.
- 이 포털의 목적은 아래 운영 문제를 한 흐름으로 묶는 것이다.
  - 고객 관리 혼선
  - 견적/계약/영수 문서 산재
  - 매출 추적 불명확
  - 설치 일정 펑크
  - 하드웨어 판매 대수 및 상태 파악 어려움

## 2. 핵심 사용자

### A. 파트너사 대표

- 포털의 주 사용자
- 고객, 거래, 문서, 설치 일정, 수납 상태를 직접 관리
- 포털 내부에서는 설치 일정 수정/확정 권한을 강하게 가진다
- 단, 모든 변경은 로그로 남아야 한다

### B. ClassIn 팀

- 파트너 운영을 지원하고 전체 흐름을 관리
- 관리자 기준으로 문서 버전, 수정 이력, 로그를 볼 수 있다
- 파트너와 동일한 운영 데이터를 보되 더 넓은 관리자 맥락에서 사용한다

### C. 고객

- 로그인 사용자 아님
- 링크 또는 PDF로 문서를 열람
- 계약/서명은 발급된 링크 기준으로 처리
- 고객은 항상 `최신 문서`가 아니라 `해당 링크가 가리키는 고정 버전`만 본다
- 견적서와 계약서 모두 `버전 고정 링크` 원칙을 따른다

## 3. 운영 파이프라인

기본 상태 흐름:

`컨택 -> 견적 -> 계약 -> 확정 -> 설치 -> 수납`

설명:

- `컨택`: 파트너가 고객과 접촉 중인 상태
- `견적`: 견적서 작성/발송/수정이 진행되는 상태
- `계약`: 계약서 협의 및 서명 진행 상태
- `확정`: 내부 판단으로 설치 진행 대상으로 확정된 상태
- `설치`: 설치 일정 관리 및 실제 설치 수행 상태
- `수납`: 입금, 분할 입금, 미수금 관리 상태

주의:

- `확정`은 시스템 강제 규칙보다 운영 판단이 우선한다
- 상태 전환은 선형이지만, 문서/설치/수납은 동시에 여러 개가 붙을 수 있다

## 4. 상품 구조

우선 관리 대상 SKU:

- 전자칠판 86
- 전자칠판 75
- AI 카메라 T1
- AI 카메라 S1
- 거치: 스탠드
- 거치: 벽걸이
- 거치: 매립

원칙:

- 설치비나 거치 방식도 판매/설치 통계에 포함한다
- 실제 운영에서는 T1 비중이 높지만, 모델 체계는 열어둔다
- 라인아이템은 표준 SKU 기반으로 두되 단가/설치비 수정 가능해야 한다

기본 단가 가이드:

- 전자칠판 86: `5,800,000원`
- 전자칠판 75: `4,900,000원`
- AI 카메라 T1: `1,200,000원`
- 설치비: `500,000원`

주의:

- 위 단가는 기본값이며, 실제 견적서/계약서에서는 거래별 수정 가능해야 한다
- 설치 완료 금액은 운영상 `돈 기준 금액`으로 본다

## 5. 데이터 모델 원칙

### A. 고객과 거래를 분리한다

`기관(Customer)`과 `거래건(Deal)`은 분리해야 한다.

이유:

- 한 기관이 여러 관/캠퍼스/지역 단위의 거래를 동시에 가질 수 있다
- 기존 계약 이후 다른 지역/관으로 추가 계약이 생길 수 있다
- 고객 단위 1차원 UI로 묶으면 문서/설치/수납 히스토리가 섞여 혼선이 생긴다

권장 구조:

- `기관(Customer)`
  - 기관명
  - 담당자
  - 연락처
  - 주소
  - 사업자 정보
  - 선택 필드: 관/캠퍼스/지역
- `거래건(Deal)`
  - 기관 연결
  - 현재 단계
  - 예상 금액
  - 설치 목표
  - 거래 메모

### B. 문서는 버전 엔티티가 필요하다

특히 견적서는 버전 이력이 필요하다.

원칙:

- 고객에게 발송된 링크는 `문서 버전 고정 링크`여야 한다
- 관리자만 버전 목록과 변경 이력을 본다
- 고객은 해당 링크 버전만 보며, 시스템에서 최신 버전으로 자동 대체하지 않는다
- 견적서와 계약서 모두 버전 관리 가능한 구조가 필요하다

권장 구조:

- `quote_documents`
- `quote_document_versions`
- `contract_documents`
- `contract_document_versions`

또는 최소한:

- 문서 본체 + 버전 테이블 + 외부 공유 토큰 테이블

### C. 설치 일정은 복수 일정이 기본이다

- 거래건 하나에 설치 일정 여러 개를 허용한다
- 설치 일정은 하루짜리만 가정하지 않는다
- 반나절, 시간대 단위, 여러 날짜 분산 설치를 모두 수용할 수 있어야 한다

권장 필드:

- scheduled_start_at
- scheduled_end_at
- timezone
- location
- installer/team
- status
- notes

단일 `DATE`만 두면 곧 막히므로, 최소한 시작/종료 시각 구조를 고려한다.

### D. 수납은 분할 입금을 기본값으로 본다

- 수납은 1회 완납보다 분할 입금이 많다
- 영수증도 여러 건 붙을 수 있다
- 결과적으로 중요한 값은 아래 3개다
  - 계약 기준 금액
  - 실제 수납 누계
  - 미수금

권장 구조:

- `payments`
- `receipts`
- 거래건 기준 계산 필드
  - total_contract_amount
  - paid_amount
  - outstanding_amount
  - payment_status

## 6. 문서 제공 규칙

- 고객 기본 채널은 `링크 공유`
- 보조 채널은 `PDF 다운로드`
- 링크는 버전 고정
- PDF도 발행 시점 버전을 기준으로 생성/보관하는 것이 적절하다
- 계약서 링크도 견적서와 동일하게 `발송 버전 고정`이다
- 관리자는 최신 버전과 예전 버전을 모두 조회 가능해야 한다

## 7. 권한 원칙

- 파트너사 측 사용자는 `대표 1인`만 상정한다
- 파트너 직원용 권한 체계는 현재 범위에서 제외한다
- 파트너 대표는 포털 내부에서 설치 일정 수정/확정 권한을 가진다
- 단, 포털 외부의 전사 관리자 권한과 동일한 개념은 아니다
- 문서, 일정, 수납, 상태값 변경은 모두 로그가 남아야 한다

## 8. 로그 원칙

반드시 남겨야 하는 로그:

- 고객 생성/수정 로그
- 거래건 단계 변경 로그
- 견적서 생성/수정/발송/버전 생성 로그
- 계약서 생성/수정/발송/서명 로그
- 영수증 발행 로그
- 수납 기록 로그
- 설치 일정 생성/수정/확정/완료 로그
- 미팅/메모 로그

로그는 나중에 감사를 위한 부가 기능이 아니라 운영 본체다.

최소 로그 속성:

- actor
- action
- target_type
- target_id
- timestamp
- summary
- payload diff

## 9. 메인 대시보드 KPI 원칙

메인 KPI는 너무 세세한 수치보다 운영 판단에 필요한 거친 지표 위주로 간다.

추천 KPI:

- 문서 건수
  - 진행 중 견적
  - 진행 중 계약
- 컨택 건수
- 설치 관련
  - 설치 예정 건수
  - 설치 진행 중 건수
- 판매 대수
  - 전자칠판 / 카메라 / 거치 포함
- 차이 나는 값
  - 계약 금액 대비 설치 완료 기준 금액
  - 설치 완료 기준 금액 대비 실제 수납액
- 미수금
- 미수 기관 수

메인 화면에서 제외할 것:

- 과도하게 세세한 SKU breakdown
- 버전별 상세 비교
- 세부 회계성 리포트

이런 값은 상세 리포트나 거래 상세에서 본다.

## 10. 가져오기 규칙

- 기존 데이터 이관은 필수 아님
- 대신 고객 정보 CSV/Excel 등록 기능은 제공한다
- 형식이 맞지 않으면 거부한다
- 자동 보정보다 명시적 검증이 우선이다

권장 규칙:

- 템플릿 파일 제공
- 헤더명 고정
- 필수 컬럼 누락 시 전체 거부
- 전화번호/이메일/금액 형식 검증

## 11. UI 구조 원칙

파트너 포털과 관리자 화면 모두 아래 축을 유지한다.

### A. 상위 IA

- 고객사
- 거래건
- 문서
- 설치
- 수납
- 로그

### B. 고객 상세에서 보여야 하는 것

- 기관 기본 정보
- 연결된 거래건 목록
- 거래건별 현재 단계
- 최근 문서
- 최근 설치 일정
- 최근 수납/미수 상태

### C. 거래건 상세에서 보여야 하는 것

- 현재 단계
- 금액 요약
- 문서 타임라인
- 설치 일정 타임라인
- 수납 타임라인
- 활동 로그

즉, `기관`은 껍데기, 실제 운영의 중심은 `거래건`이다.

## 12. 개발 시 주의사항

- 고객 링크는 최신 버전 자동 반영 금지
- 관리자/파트너/고객의 문서 열람 범위 분리
- 설치 일정은 날짜 한 칸으로 끝내지 말고 시간 범위를 고려
- 수납은 단건 영수증 모델로 고정하지 말고 분할 입금 전제
- 고객 1곳에 여러 거래가 붙는 구조를 처음부터 허용
- 포털 내부 강한 편집 권한을 주더라도 수정 로그는 필수

## 13. 현재 남아 있는 결정 포인트

아직 확정이 필요하거나 추후 정리할 것:

- 설치 완료 금액을 거래 총액 기준으로 볼지, 설치된 품목 기준으로 볼지
- 수납 완료 상태의 기준을 완납 기준으로만 둘지, 부분 수납 상태를 별도 둘지
- 관/캠퍼스/지역을 단순 선택 필드로 둘지, 별도 엔티티로 확장할지
- 활동 로그와 미팅 로그를 하나의 timeline으로 통합할지, 별도 탭으로 둘지

현재 권장값:

- 설치 완료 금액은 우선 `돈 기준`으로 집계
- 수납 상태값은 추후 운영하면서 조정
- 관/캠퍼스/지역은 우선 선택 필드 수준으로 시작
- 활동 로그와 미팅 로그는 우선 하나의 timeline에 통합

## 14. 추천 구현 우선순위

1. 고객 / 거래건 분리
2. 문서 버전 고정 링크 구조 도입
3. 설치 일정 복수 + 시간 범위 구조로 변경
4. 수납/미수금 계산 구조 정착
5. 활동 로그 타임라인 도입
6. 대시보드 KPI를 운영형 지표로 재정렬
