# 미러링

## 증상 표현

| 고객 표현 | 실제 현상 | 선례 |
|---|---|---|
| "같은 네트워크인데 미러링이 됐다 안 됐다 한다" | 단말 간 ping 양방향 100% 손실, 게이트웨이 손실 0% — 공유기 AP 클라이언트 격리 유력(간헐성은 미설명) | D-07 |
| "미러링이 갑자기 안 된다(네트워크 같고 바꾼 적 없다)" | 고객의 "같은 네트워크"는 실제로 서로 닿는지와 별개. 오류 문구 미확인 | S-33 |
| "미러링하면 좌우에 검은 여백이 생긴다" | 16:10 노트북 소스. 1920×1080으로 바꾸고 재연결·전체화면 해도 여백 잔존, 사내 16:10 노트북으로 재현 | S-36 |

증상 동의어: 미러링 안 됨, 화면 공유 안 됨, 무선 화면 전송 실패, 미러링 끊김, 미러링 목록에 안 뜸, 동일한 LAN 오류, 같은 와이파이인데 안 됨, 미러링 검은 여백, 화면 양옆 검은 띠, 화면이 꽉 안 참

## 먼저 받을 값

1. **오류 문구** 원문(캡처). "장치가 동일한 LAN에 연결되어 있지 않습니다"인지 확인한다.
2. PC와 전자칠판 양쪽: OS, ClassIn/ClassIn X 버전, 연결한 SSID(Wi-Fi 이름), 유선/무선 여부.
3. 언제부터, 늘 안 되는지 간헐적인지, 최근 바뀐 것(공유기 교체 등).
4. 여백 문제면: 소스 기기 해상도·화면비, 배율, 전자칠판 모델.
5. **조치 전에 증거를 남긴다.** 재부팅 전에 `ipconfig /all` 캡처(S-33).

## 진단 흐름

1. **오류 문구**를 받는다. "장치가 동일한 LAN에 연결되어 있지 않습니다"면 아래 순서로 간다.
2. **판별 순서**(D-07):
   1. 양쪽의 게이트웨이 주소 대조 → 다르면 서브넷이 나뉜 것
   2. `arp -a`로 게이트웨이 MAC 대조 → 다르면 공유기 2대가 같은 대역을 쓰는 중복 서브넷. 양쪽 IP가 `192.168.0.x`로 같아 보여도 별개 망일 수 있다
   3. PC와 전자칠판 사이 양방향 ping

      | 게이트웨이 통신 | 단말 간 ping | 결론 |
      |---|---|---|
      | 정상 | 양방향 성공 | 망은 정상. 포트·앱 쪽 |
      | 정상 | 양방향 실패 | 공유기의 AP 클라이언트 격리 |
      | 정상 | 한 방향만 성공 | 호스트 방화벽 |

   4. 유선 단말로도 ping → 무선에만 걸린 제한인지
   5. 미러링 코드 직접 입력 → 탐색 단계만의 문제인지
3. PC 한쪽에서만 보면 이 판정이 나오지 않는다. 전자칠판 OPS에서도 조회 명령을 돌려야 한다(조회 전용 명령은 `04-board-network.md`).
4. 전자칠판 핫스팟(`ClassInX-…`)으로 연결되면 망 문제이고 기기·앱은 정상이다(S-33).
5. "갑자기 안 된다"면 설정이 아니라 바뀐 상태를 찾는다. 고객의 "같은 네트워크고 바꾼 적 없다"는 말은 실제로 서로 닿는지와 별개다(S-33).
6. **격리 해제는 고객사 네트워크 담당자가 한다.** 지사는 측정 근거를 붙인 요청서를 만든다. 핫스팟 우회는 먼저 안내하지 않는다(D-07).
7. **검은 여백**: 소스와 화면의 화면비(16:10과 16:9)를 대조한다. 배율(%)은 송출 해상도를 바꾸지 않는다. 해상도를 바꾼 뒤에는 미러링을 다시 연결한다("변경한 설정 유지"를 눌렀는지 확인). 16:9로 맞춰도 여백이 남으면 사용법이 아니라 결함 후보로 HQ에 올린다(S-36).

보충

- 미러링 실패 시 안내되는 핫스팟은 자동으로 넘어가는 동작처럼 문제를 가린다. 근본 해결 전에 우회를 먼저 안내하면 그 우회가 표준 운영으로 굳는다(D-07).
- S-36의 고객용 대안(선례): 칠판의 ClassIn에서 자료를 직접 열기(권장), HDMI(사내 미검증).
- 확장 모드 2차 화면의 검은 띠는 `06-rear-display-and-latency.md`(D-13)를 본다.

## 원인 후보와 확신도

- 공유기의 AP 클라이언트 격리(유력 후보, "때때로 성공"이라는 간헐성은 설명되지 않음) — 추정 — D-07
- 미러링 갑자기 안 됨(칠판 네트워크 경로 변화, 장비 변경·AP 격리, PC 방화벽·프로필, 버전 불일치 가설만, 검증 데이터 없음) — 미확정 — S-33
- ClassIn 미러링 송출·수신 처리 쪽 문제(16:10 소스 여백, HQ 미확인) — 추정 — S-36

## 고객 안내 문구

결과 회신 뼈대(카카오톡):

```
안녕하세요, ○○님. 미러링 건 확인 결과입니다.

▪ 원인
(확인된 사실. 추정이면 "~로 추정됩니다")

▪ 필요한 조치
(고객사 네트워크 담당자께 요청드릴 내용과 근거)

▪ 다시 발생하면
(알려 달라는 정보: 오류 문구 캡처, 발생 시각, 사용 기기)
```

쓸 때 지킬 것

- 고객사 설정을 "잘못됐다"고 하지 않는다. AP 격리는 의도된 보안 설정일 수 있으므로 "해제가 필요합니다"로 쓴다(D-07).
- 설정을 누가 해 두었는지 말하지 않는다.
- 핫스팟 우회를 근본 해결 전에 먼저 안내하지 않는다(D-07). 핫스팟 연결 테스트를 원인 가르기로 요청할 때는 무엇을 확인하려는 것인지 밝힌다.
- 고객사 네트워크 장비는 지사가 바꾸지 않는다. 측정 근거를 붙인 요청서를 고객사 담당자에게 준다.
- 여백 건은 "안 된다"보다 "사양은 이렇고 그 안에서 이렇게 맞췄다"로 쓴다. 결함 단정은 하지 않는다.
- 내부 IP·MAC 값, 오류 코드, 서버명은 넣지 않는다.
- 캡처는 필요한 영역만 잘라 보낸다.

## HQ로 넘기는 조건과 적을 것

넘기는 조건

- 판별 순서(게이트웨이 → MAC → 양방향 ping → 유선 ping → 코드 입력)를 마쳤고 망이 정상인데도 안 될 때(포트·앱 쪽).
- 16:9 소스로 맞춰도 여백이 남을 때 → `疑似缺陷`로 올린다(S-36).
- AP 격리처럼 고객사 망 설정으로 판명되면 넘기지 않고 고객사 담당자 요청으로 처리한다. 본사 상급 채널 발송은 내부 승인을 거친 선례가 있다(D-07).

받는 곳(역할명)

- 1차: HQ 서비스 1차 접점(小助手). 1차 답이 "HDMI 유선 사용"처럼 우회면 재문의한다(S-36).
- 네트워크 측면: HQ 네트워크·접속·메모리 담당

적을 것

- 분류: `缺陷` / `疑似缺陷`, 기능 요청과 섞지 않는다.
- 양쪽 단말의 OS·클라이언트 버전, 연결 구성(SSID, 유·무선), 판별 순서별 결과(게이트웨이 통신, 단말 간 ping 방향별 결과, 코드 입력 결과).
- 여백 건: 소스 해상도·화면비, 바꾼 설정, 재연결·전체화면 여부, 사내 재현 결과.
- 시각은 중국 시각(UTC+8 = KST − 1시간).

기재하지 않는 값과 예외

- 기재하지 않는 값: Device ID, Client IP, Server, Owner.
- 예외: 판정 근거가 되는 사설망 값(게이트웨이 대조 등)은 증상 설명에 필요하면 적는다. 그 값은 WeCom 발송문에만 넣고 이 저장소·적재 데이터에는 남기지 않는다.
