# 수업 중 끊김·튕김

## 증상 표현

고객이 쓴 말은 현상의 이름이 아니다. 첫 결과 회신에서 실제 현상으로 바로잡는다.

| 고객 표현 | 실제 현상 | 선례 |
|---|---|---|
| "인터넷 끊김" | 네트워크 끊김이 아니라 앱 강제 종료(闪退) 2회 | D-02b |
| "수업이 갑자기 종료됐다" | 예정 종료 시각 약 27초 뒤 "The customer actively leave the classroom"으로 정상 종료 | S-13 |
| "수업 중 네트워크가 끊긴다" | 메인 NIC 고정 IP가 다른 기기와 충돌해 유선이 마비되고 Wi-Fi로 폴백 | D-02a |
| "최대화한 선생님 화면이 저절로 돌아간다" | 교사 PC가 코드 56으로 끊겨 자동 재입장했고, 재접속 시 최대화가 풀림 | D-20 |
| "학생이 계속 튕긴다" | 41회 재입실, 매번 1~12초 만에 코드 56. 교사는 정상 | D-19 |
| "선생님이 수업 중에 두 번 나갔다" | 두 이탈(코드 57) 직후 모두 신규 "로그인 성공" — 회선 단절이 아니라 프로세스 종료·재실행 | D-18 |
| "Network is malfunctioning 팝업이 뜬다" | 다른 교실은 정상, ClassIn X 재시작으로 복구 — 해당 강의실·기기 요인 추정 | S-31 |
| "특정 학생 수업에서 녹화·카메라·마이크가 끊긴다" | 품질 지표는 정상인데 세션 단절 + 포트 전환·TCP 폴백, 문제 세션에서만 CPU 급등 | S-32 |

증상 동의어: 끊김, 튕김, 튕겨 나감, 접속 끊김, 재입장, 재접속 반복, 퇴장, 이탈, 강제 종료, 앱 꺼짐, 수업 종료, 인터넷 끊김, 네트워크 불안정, 화면이 돌아감, 최대화 풀림, Network is malfunctioning

## 먼저 받을 값

1. **조회 키**: 수업명, 사용자 계정, 수업 시작 시각(월·일·시). 계정이 없으면 콘솔에서 수업을 찾을 수 없으므로 계정은 반드시 받는다.
2. **받은 계정이 맞는지 본다.** 고객이 준 번호와 콘솔에서 잡힌 계정이 다른 선례가 있다(S-13). 같은 기관에 여러 건이 동시에 진행 중이면 Client IP와 deviceName으로 강의실을 확인한다(D-21). Identity 칸으로 교사 계정인지 학생 계정인지 확정한다(S-32).
3. **정상 대조군**: 같은 계정·같은 기기의 정상 수업, 같은 학원의 정상 교실(D-09, S-10, S-32).
4. 상황에 따라 추가로 받는 값
   - 이탈 직후 재로그인 기록이 있으면: 절전 모드 설정, 백신·보안 프로그램, 실제 종료 시각, Windows 이벤트 뷰어(1000/1001, Kernel-Power 41)(D-18)
   - 전자칠판이면: `ipconfig /all` 원문(5-4 흐름, `04-board-network.md`)
   - 단말 정보: 기기, OS 버전, 클라이언트 버전, 최신 여부(HQ가 가장 먼저 되묻는 항목)
5. **조치 전에 증거를 남긴다.** 재부팅·재설정·케이블 재체결은 원인을 지운다. 먼저 `ipconfig /all`, 로그, 설정 화면을 캡처한다.

접수 직후 문구(콘솔을 보기 전에는 원인·복구 여부를 말하지 않는다):

```
안녕하세요, ○○님. 클래스인입니다.
말씀하신 ○/○ 수업 건 바로 확인해 보겠습니다.

정확한 수업을 찾기 위해 아래 내용 부탁드립니다.
▪ 수업명
▪ 선생님(또는 학생) 로그인 계정
▪ 수업 시작 날짜와 시각

기록을 확인한 뒤 원인과 함께 다시 안내드리겠습니다.
```

## 진단 흐름

1. 콘솔에서 **퇴장 시각과 사유 코드**를 본다(`reference-tables.md`의 퇴장 사유와 코드).
   - "The customer actively leave the classroom"이고 예정 종료 시각 근처면 정상 종료일 수 있다(S-13).
2. **이탈 직후 신규 "로그인 성공" 기록이 있는지** 본다(D-18).
   - 있음 → 클라이언트 프로세스가 종료됐다가 다시 실행된 것. 크래시, 프리즈, PC 절전·전원 차단 쪽. 고객에게 절전 모드 설정, 백신·보안 프로그램, Windows 이벤트 뷰어(1000/1001, Kernel-Power 41)를 묻고, HQ에 그 시간대 크래시 업로드 기록을 요청한다.
   - 없음 → 자동 재연결. 회선 단절 쪽.
3. **어느 구간이 나빴는지** 본다.

   | User Gateway | Gateway 2nd | 서버 연결 | 읽는 법 | 선례 |
   |---|---|---|---|---|
   | 나쁨 | — | — | 기기~공유기 구간. Wi-Fi, 유선, IP 설정 | D-02a |
   | 정상 | 지연·General 비율 높음 | 약간 저하 | 공유기 바깥 회선(건물·통신사) | D-20 |
   | 정상 | 정상 | Poor | 통신사→서버 구간, 또는 세션·서버 측 | D-19 |
   | 정상 | 정상 | 정상 | 5분 집계에 안 잡힌 순간 단절이거나, 회선이 아니라 프로세스·CPU 쪽 | D-18, S-32 |

   `Network Duration`이 좋아도 `Gateway 2nd`나 TCP 지연이 나쁘면 재접속이 반복되고 녹화가 끊긴 선례가 있다(S-10).
4. **끊김의 모양**을 본다.
   - 초 단위로 규칙적으로 반복 → 무작위 회선 불량보다 클라이언트·세션·서버 원인을 함께 의심(D-19).
   - 같은 장소의 여러 기기가 같은 시각에, 약 30분 간격으로 → 공유 게이트웨이 쪽 이벤트 추정(S-39 부수 관찰).
   - 특정 세션에서만 → 문제 세션과 정상 세션을 전부 놓고 CPU, 포트 전환, `serviceType`, Device ID의 MAC 변화를 대조(S-32).
5. **전자칠판이면** `ipconfig /all` 원문을 받는다(`04-board-network.md`).
   - 고객이 "끊김"이라 했어도 실제로 강제 종료(闪退)면 메모리를 본다. RAM 8GB OPS는 가상 메모리를 물리 RAM × 1.5(12,288MB, 초기=최대)로 잡는다. HQ 네트워크·접속·메모리 담당 승인 선례(D-02b). 16GB 기기는 기준이 달랐던 이력이 있어 다시 확인한다.
6. **가르는 실험**: 휴대폰 핫스팟(LTE)으로 한 번 수업해 본다. 핫스팟에서도 나면 학생·학원 회선 원인설이 약해지고, 안 나면 회선 쪽으로 확정된다. 기기는 1대만 로그인하게 한다. 이 요청은 원인을 가르려는 확인이지 우회책 안내가 아니다.
7. **끊김에 따라오는 것들**: 재접속하면 최대화한 화면이 기본 배치로 돌아간다(D-20). 카메라 녹화는 끊길 때마다 중단·재시작되어 파일이 나뉜다. 재입실 후 미디어 서버 포트가 바뀐다(10035 → 8000 또는 8080).
8. HQ: 네트워크·접속은 HQ 네트워크·접속·메모리 담당, 1차 접점은 HQ 서비스 1차 접점(小助手). 3번 표의 셋째 줄(게이트웨이 정상, 서버 연결만 Poor)에 해당하면 Media Server, Port, Client IP를 적는다(에스컬레이션 예외 기준).

참고 판단: 한 고객의 두 건을 하나로 묶지 않는다. 정율사관의 7/30 건(D-02a)과 8/8 건(D-02b)은 네트워크와 메모리로 원인이 달랐다.

## 원인 후보와 확신도

- 메인 NIC 고정 IP 충돌로 유선 마비, Wi-Fi 폴백 — 확정 — D-02a
- RAM 8GB OPS 메모리 부족에 따른 강제 종료(HQ 회신, 재발 모니터링 대기) — 추정 — D-02b
- 클라이언트 프로세스 비정상 종료(크래시·프리즈 또는 PC 절전·전원 차단). 회선·성능은 배제했으나 5분 집계라 순간 단절은 남음 — 추정 — D-18
- HQ "학생 네트워크 불안정" vs 지사 "통신사→서버 구간·세션·서버 측 가능성" — 미확정(HQ·지사 견해 충돌) — D-19
- 코드 56 재접속 시 최대화 해제 — 확정(자체 재현) — D-20. 끊김 자체는 공유기 바깥 회선(Gateway 2nd) 불안정 — 추정 — D-20
- 설정된 수업 시간(50분) 종료에 따른 정상 종료 — 추정(계정·기대 길이 미확인) — S-13
- 해당 강의실 기기 측 요인 — 미확정 — S-31
- UDP 세션 간헐 단절(공유기·Wi-Fi 환경 변화) + CPU 급등. 카메라 끊김 근거는 로그에 없음 — 추정 — S-32
- (녹화 실패로 드러난 끊김) 공사 후 유·무선 이중 인터페이스로 시그널링·게이트웨이 반복 단절 — 추정 — S-10

## 고객 안내 문구

결과 회신 뼈대(카카오톡, 확인을 마친 뒤에만):

```
안녕하세요, ○○님. ○/○ ○○ 수업 건 확인 결과입니다.

▪ 원인
(확인된 사실. 추정이면 "~로 추정됩니다")

▪ 영향 / 복구
(복구 가능 여부와 남아 있는 자료)

▪ 다음 수업부터 / 다시 발생하면
(바로 할 조작, 또는 재발 시 알려 달라는 정보: 수업명, 발생 시각)
```

쓸 때 지킬 것

- 오류 코드(54/56/57 등), 서버명, Client IP, Account ID는 넣지 않는다. 지연, 손실률, 어느 구간이 불안정했는지는 풀어서 전달한 선례가 있다(D-18, D-20).
- HQ 1차 답변이 "네트워크 문제"여도 그대로 옮기지 않는다. 콘솔 지표와 시각을 대조한 뒤에 쓴다(S-03, S-10, D-19).
- 확정 전 원인은 확인된 사실과 미확인 항목을 나눠 적는다. 추정은 "추정됩니다", "~로 보입니다".
- "학원 네트워크 전체가 끊긴 것이냐" 같은 질문에는 확인한 범위(그 기기 한 대)까지만 답한다(D-20).
- 재현 영상을 첨부할 때는 "연결을 일부러 끊어 재현한 것"이라고 적는다(D-20).
- 원인을 가르기 위한 확인 요청(핫스팟으로 한 번 수업해 보기, 기기 1대만 로그인하기, 공유기 전원 재인가)은 점검 지시나 우회책이 아니다. 무엇을 확인하려는 것인지 밝히고 요청한다(D-19, D-20).
- 재부팅(restart, 전원 재인가)과 초기화(reset, 공장 초기화)를 구분해 적는다(S-31).
- 원인 회신에 "앞으로 이렇게 하라"는 점검 지시를 같이 싣지 않는다. 고객이 재발 방지를 물을 때 따로 안내한다(D-04).
- 고객사 네트워크 장비 설정은 지사가 바꾸지 않는다. "잘못됐다"가 아니라 "해제가 필요합니다"로 쓰고, 설정을 누가 했는지는 말하지 않는다.

## HQ로 넘기는 조건과 적을 것

넘기는 조건

- 지사에서 할 수 있는 확인(콘솔 지표, 정상 대조군, 사내 재현)을 끝낸 뒤에 넘긴다. 설정 문제로 판명되면 넘기지 않는다.
- 이탈 직후 재로그인이 있으면 그 시간대 크래시 업로드 기록, 코드 57 트리거 조건, 해당 버전 동일 증상 여부, 로컬 로그 수집 경로를 묻는다(D-18).
- 게이트웨이 구간 정상 + 서버 연결만 Poor이면 서버·경로가 의심 지점이므로 넘긴다(D-19).
- 가상 메모리 같은 값을 물을 때는 값이 아니라 산정 기준("물리 RAM의 몇 배인가")을 묻는다(D-02b).

받는 곳(역할명)

- 1차: HQ 서비스 1차 접점(小助手). 小助手가 담당자를 안내했으면 그 담당자에게 직접 묻는다.
- 네트워크·접속·메모리: HQ 네트워크·접속·메모리 담당
- OPS 메모리 산정 기준: HQ 하드웨어 1차·원격 지원 담당(D-02b 선례)

적을 것

- 분류: 버그면 `缺陷`, 원인 미확정 결함 의심이면 `疑似缺陷`. 기능 문의와 섞지 않는다.
- 계정, 수업명, 시각을 맨 위에 둔다(S-03). 시각은 KST에서 1시간을 빼 중국 시각(UTC+8)으로 적고 시간대를 같이 쓴다(KST 18:00 → 17:00).
- 기기, OS 버전, 클라이언트 버전, 최신 여부.
- 콘솔 지표가 일부 비정상이면 구간별 수치를 그대로 적는다(User Gateway, Gateway 2nd, 서버 연결, 지연).
- 확인 요청이 여럿이면 번호를 붙인다. 재문의는 앞선 회신을 한 줄 인용하고, 그 회신이 설명하지 못하는 지표와 답받지 못한 항목을 번호로 다시 묻는다(D-19).

기재하지 않는 값과 예외

- 기재하지 않는 값: Device ID, Client IP, Server(미디어·접속 서버명), Owner(영업 담당).
- 예외: 그 값이 증상의 직접 근거면 적는다. 게이트웨이 정상 + 서버 연결만 나쁜 끊김은 Media Server, Port, Client IP를 적고(D-19), IP 충돌이 원인이면 Client IP를 적는다(D-02). 기준은 "그 값을 빼면 증상 설명이 성립하는가"다.
