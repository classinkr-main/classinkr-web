# 카메라가 안 잡힌다

## 증상 표현

| 고객 표현 | 실제 현상 | 선례 |
|---|---|---|
| "자리를 옮긴 뒤 카메라가 안 된다" | 교실 5곳이 3유형(네트워크 카메라 확인 불가 / 이더넷은 표시되나 카메라 미연결 / 케이블 재정리 직후 복구) — 물리 배선 계층 추정 | D-09 |
| "카메라 프로그램에서 검색은 되는데 연결이 안 된다" | 카메라가 연결된 NIC는 자동 IP라 APIPA로 떨어지고, 카메라용 고정 IP는 다른 NIC에 들어가 있음 | D-15a |
| "카메라 랜선이 계속 '케이블 언플러그됨'으로 나온다" | PoE 급전 실패. 인젝터의 입·출력 케이블이 바뀌어 있음 | S-34 |
| "USB를 꽂으면 되고 빼면 안 된다" | PoE 급전 실패 신호 | S-34 |
| "카메라 화면 두 개가 미리보기가 안 된다" | ping·554 포트는 살아 있고 CMS에서도 `0*0 0.0fps 0Kbps` — 영상 송출만 정지 | S-40 |
| "일부 교실만 네트워크 카메라가 바로 붙는다(나머지는 OBS로 우회)" | ClassIn X가 `//`가 빠진 RTSP 주소를 오류 안내 없이 거부 | D-06 |

증상 동의어: 카메라 안 잡힘, 카메라 인식 안 됨, 카메라 연결 실패, 카메라 화면 안 나옴, 미리보기 실패, 검은 화면, 케이블 언플러그됨, Connection failed, 카메라 프로그램 연결 안 됨, 네트워크 카메라, IP 카메라, 트래킹 화면 안 나옴, 파노라마 안 나옴

## 먼저 받을 값

1. **조회 키**: 수업명, 사용자 계정, 수업 시작 시각(수업 중 발생 시).
2. **하드웨어 값**: 카메라 모델, 전자칠판 SN, 시스템·펌웨어 버전, 설치일. HQ는 하드웨어 건에서 SN을 반드시 요구한다.
3. **최근에 자리를 옮겼거나 공사를 했는지**(D-09, S-10).
4. **자료**: `ncpa.cpl` 창 사진과 `ipconfig` 결과 사진. 실패 교실 전부, 정상 교실 한 곳, 복구된 교실을 같이 받는다(D-09). TCP/IPv4 속성 창은 열게 하지 않는다.
5. **조치 전에 증거를 남긴다.** 재부팅·재설정·케이블 재체결은 원인을 지운다. CMS Streaming/Network 탭, 로그, 설정 화면을 먼저 캡처한다(S-40).

접수 직후 자료 요청 예(문구 뼈대는 2-2 접수용 기준):

```
안녕하세요, ○○님. 클래스인입니다.
말씀하신 ○○ 교실 카메라 건 바로 확인해 보겠습니다.

원인을 찾기 위해 아래 내용 부탁드립니다.
▪ 안 되는 교실 전부와, 잘 되는 교실 한 곳의 사진
  - 키보드 [Windows 키 + R] → ncpa.cpl 입력 후 뜨는 창
  - ipconfig 결과 화면
▪ 최근 자리 이동이나 공사가 있었는지

확인한 뒤 다시 안내드리겠습니다.
```

## 진단 흐름

1. **최근에 자리를 옮겼거나 공사를 했는지** 묻는다. 그렇다면 배선부터 본다(D-09, S-10).
2. **고객 담당자에게 자료를 부탁할 때는 `ncpa.cpl` 창 사진과 `ipconfig` 결과 사진**으로 받는다(`ncpa.cpl` 창에 어댑터의 장치명이 보인다). 실패 교실 전부, 정상 교실 한 곳, 복구된 교실을 같이 받는다. 이때 TCP/IPv4 속성 창은 열게 하지 않는다. DHCP면 실제 IP가 안 보이고, 담당자가 설정을 건드릴 위험이 있다(D-09). 지사가 원격(RustDesk)이나 방문으로 직접 볼 때는 `ipconfig /all` 원문을 본다. IP 설정을 바꾸는 조치도 선례에서는 지사가 직접 했다(D-02, D-15).
3. 카메라 NIC 상태로 가른다.

   | 보이는 것 | 읽는 법 | 선례 |
   |---|---|---|
   | "네트워크 케이블 언플러그됨" | PoE 급전 실패. 인젝터·스위치의 AC 전원, 포트 방향(LAN/Data In과 PoE Out), 케이블 순. "USB를 꽂으면 되고 빼면 안 됨"도 같은 신호 | S-34 |
   | 링크는 있는데 `169.254.x.x`이고, 다른 어댑터에도 `192.168.1.222`가 없음 | 카메라 NIC에 고정 IP가 적용되지 않음. `192.168.1.222`를 넣고 어댑터를 껐다 켠다. CameraCMS에서는 검색은 되는데 `Connection failed`로 보인다 | T-05 |
   | 한 어댑터는 `192.168.1.222`, 다른 어댑터는 `169.254.x.x`이고 CameraCMS에서 검색은 되는데 `Connection failed` | 고정 IP가 카메라가 물리지 않은 NIC에 들어가 있을 수 있다. 4번으로 카메라가 어느 쪽에 있는지 확정한 뒤 5번 순서로 옮긴다 | D-15 |
   | 어댑터가 목록에 없음 | OPS 모듈 안착, USB 랜카드 탈락 | D-09 |

4. **어느 NIC에 카메라가 물렸는지**는 어댑터 이름으로 판단하지 않는다. IP 설정값은 참고가 되지만 설정이 엉뚱한 NIC에 들어가 있을 수 있어, 확정은 응답 여부로 한다. 어댑터 A를 "사용 안 함"으로 두고 CameraCMS에서 다시 검색했을 때 `Search:0`이면 카메라는 방금 끈 A에 물려 있고, 켜져 있는 다른 어댑터에는 카메라가 없다(D-15).
5. **IP를 다른 어댑터로 옮길 때**는 기존 어댑터에서 먼저 지우고 새 어댑터에 넣는다. "사용 안 함" 상태의 어댑터도 IP 설정을 갖고 있어 중복 경고가 난다. 옮긴 뒤 CameraCMS에서 기존 항목을 Delete하고 Start Search → Add to client로 다시 등록한다(D-15, T-05). 자리 이동으로 랜선이 서로 바뀐 것이 확인되면 랜선을 원래 포트로 되돌리는 방법도 있으나, 선례는 IP 설정을 옮기는 쪽이었고 둘 중 무엇을 택할지 정해진 기준은 없다.
6. NIC와 배선이 정상이면 **ping → 554 포트 → CameraCMS의 fps** 순으로 본다. ping과 554가 되는데 CMS에서도 `0*0 0.0fps 0Kbps`면 카메라가 영상 송출만 멈춘 것이므로, 로그와 설정을 캡처한 뒤 CMS에서 Reboot한다(Reset이 아니다). 재등록보다 재부팅을 먼저 해야 어느 조치가 효과였는지 구분된다(S-40).
7. **타사 네트워크 카메라(RTSP)**: 주소를 `rtsp://계정:비밀번호@IP:554/stream1` 표준형으로 넣는다. OBS에서는 되는데 ClassIn X 직결이 안 되면 주소 표기부터 본다. OBS는 `//`가 빠진 주소도 받아들이지만 ClassIn X는 오류 안내 없이 거부한다. 비밀번호에 `@`가 있으면 `%40`으로 바꾸고, 카메라 IP는 고정한다(D-06).
8. 카메라 NIC에 게이트웨이와 DNS를 비워 두면 Wi-Fi 인터넷과 유선 카메라를 같이 쓸 수 있다(D-15).
9. HQ: 문의는 HQ 하드웨어 1차·원격 지원 담당, 원격 디버깅은 HQ 카메라 원격 디버깅 담당(AweSun).

보충(선례에서 확인된 사양·관찰)

- 카메라 랜선은 칠판 하단 LAN이 아니라 OPS 본체 LAN(내장 Realtek)에 꽂는다. 두 칠판이 각자 직결이면 같은 IP(.222/.180)를 써도 충돌하지 않는다(T-05).
- T1의 USB-A 포트와 칠판 USB를 연결하면 PoE 없이 전원이 들어오고 ClassIn X에 USB 카메라로 인식됐다(T-05 실측). USB 연결만으로는 CameraCMS에 나타나지 않는다. USB-A 상시 급전은 하지 않는다(S-34).
- 카메라 전용망의 "식별되지 않은 네트워크"는 정상 표시다(S-34). "선은 원래대로"라는 진술은 포트 방향을 보장하지 않는다(S-34).
- 어느 NIC가 메인인지는 배선에 따라 기기마다 달랐다. 어댑터 이름이나 설정값만으로 역할을 단정하지 않는다(`reference-tables.md` 전자칠판·카메라 절).
- 재체결·재부팅으로 나은 건은 원인이 특정된 것이 아니다. 원인 미확정으로 적고 재발 시 볼 지점을 남긴다(D-09, S-40).

## 원인 후보와 확신도

- 카메라 전용 고정 IP가 카메라가 물리지 않은 다른 NIC에 설정됨 — 확정 — D-15a
- 카메라 NIC 고정 IP 미적용(APIPA) — 확정 — T-05
- PoE 인젝터의 LAN(Data In)과 PoE Out 케이블 역결선 — 확정 — S-34
- RTSP 주소에서 `rtsp://`의 `//` 누락(포트 미기재) — 확정 — D-06
- 물리 배선 계층(포트 뒤바뀜, PoE 미공급, 카메라망 IP 충돌, OPS 모듈·USB 랜카드 탈락 가설). 케이블 재체결로 복구, 원인 미특정 — 추정 — D-09
- 카메라 영상 송출 정지(멈춘 이유 미확인) — 추정 — S-40

## 고객 안내 문구

결과 회신 뼈대(카카오톡):

```
안녕하세요, ○○님. ○○ 교실 카메라 건 확인 결과입니다.

▪ 원인
(확인된 사실. 추정이면 "~로 추정됩니다")

▪ 조치 / 현재 상태
(어떤 조치로 복구됐는지, 남은 확인)

▪ 다시 발생하면
(알려 달라는 정보: 교실, 발생 시각, ncpa.cpl·ipconfig 사진)
```

쓸 때 지킬 것

- 하드웨어 결함·불량이라는 말을 하지 않는다. 원인 확정 전에는 "확인 중"까지만 한다.
- 재체결·재부팅으로 나았으면 원인이 특정됐다고 쓰지 않는다(D-09, S-40).
- 재부팅(restart)과 초기화(reset)를 구분해 적는다. 카메라는 Reboot이지 Reset이 아니다(S-40).
- 고객사 설정을 "잘못됐다"고 하지 않는다. 의도된 설정일 수 있으므로 "해제가 필요합니다", "지정되지 않은 상태였습니다"처럼 상태만 쓰고, 설정 주체를 말하지 않는다.
- 고객사 네트워크 장비 설정은 지사가 바꾸지 않는다. 근거를 붙여 고객사 담당자에게 요청한다.
- 우회(OBS 가상 카메라 등)를 근본 해결 전에 먼저 안내하지 않는다. 우회가 표준 운영으로 굳는다.
- "다른 교실은 되는데 여기만 안 된다"는 수기 설정 편차인 경우가 많다(RTSP 주소 표기, 고정 IP가 들어간 NIC). 고객 탓으로 읽히지 않게 상태만 쓴다.
- 캡처를 보낼 때는 필요한 영역만 잘라 보낸다.

## HQ로 넘기는 조건과 적을 것

넘기는 조건

- NIC·배선·IP 설정·PoE·RTSP 주소를 지사에서 다 확인했는데도 안 될 때. 설정 문제로 판명되면 넘기지 않는다.
- 카메라 자체 동작(송출 정지 반복, 펌웨어, USB 급전 사양 등) 확인이 필요할 때(S-40, T-05).

받는 곳(역할명)

- 문의: HQ 하드웨어 1차·원격 지원 담당(여러 건이 한 대화창에서 진행되므로 건명을 적는다)
- 원격 디버깅: HQ 카메라 원격 디버깅 담당(AweSun). 식별 코드와 인증 코드는 담당자에게 1:1로만 전달하고 단체방에 올리지 않는다.

적을 것

- 분류: `缺陷` / `疑似缺陷` / `需求`를 구분하고 섞지 않는다.
- 하드웨어 건은 식별자를 EEO Account, UID, 제품 SN, 설치일, 세대로 바꾼다.
- 카메라 모델·펌웨어, 배선 구성(PoE 스위치/인젝터, NIC 종류), `ipconfig /all`의 해당 어댑터 상태, CMS 표시값(`Search`, `ConnectStatus`, fps).
- 시각은 중국 시각(UTC+8 = KST − 1시간)으로 적는다.

기재하지 않는 값과 예외

- 기재하지 않는 값: Device ID, Client IP, Server, Owner.
- 예외: IP 충돌이 원인일 때의 IP처럼 그 값을 빼면 증상 설명이 성립하지 않으면 적는다. 카메라망 규격 값(`192.168.1.222`, `192.168.1.180`)은 사양이라 적어도 된다.
- 고객사 실제 IP·SN·MAC 같은 값은 WeCom 발송문에만 넣고 이 저장소·적재 데이터에는 남기지 않는다.
