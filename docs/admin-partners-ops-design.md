# Admin Partners Ops Design

기준 시점: 2026-04-03  
문서 목적: `/admin/partners`를 총판/어드민 담당업무용 운영 허브로 재정의하고, 상위 IA와 탭/섹션/엔티티 구조를 합의한다.

## 1. 한 줄 정의

`/admin/partners`는 파트너 목록이 아니라  
`총판 영업 + 계약 + 설치 이행 + 매출/정산 + 운영 이슈`를 한 워크스페이스에서 처리하는 운영 허브여야 한다.

## 2. 핵심 전제

- 파트너는 외부 포털 사용자가 아니라 내부 운영팀이 관리하는 `총판/협력사`다.
- 특히 하드웨어 총판은 `클래스인 하드웨어 전체 라인업`을 담당할 수 있으므로, 단일 거래가 아니라 반복 거래와 설치 이행을 함께 봐야 한다.
- `견적 -> 계약 -> 설치/납품 -> 매출 -> 정산`은 따로 노는 메뉴가 아니라 자연스럽게 이어지는 하나의 흐름이어야 한다.
- `설치 품목/수량 체크`, `고객 미팅 로그`, `계약 로그`, `애매한 이슈`는 흩어진 메모가 아니라 한곳에서 모아 봐야 한다.
- 계약서는 단순 파일이 아니라 `PDF / 카카오톡 / 링크` 전달 방식과 `만료 / 비밀번호 / 접근 제한` 같은 공개 설정을 가져야 한다.

## 3. 상위 구조 결정

### 라우트

- Phase 1: `/admin/partners`
- Phase 2: 필요 시 외부용 `/partners` 포털 분리

### 관리자 사이드바

- Overview
- CRM / 리드
- 파트너 운영
- 지사 관리
- Analytics
- Calendar
- 콘텐츠
- Settings

### 왜 `/admin/partners`가 맞는가

- 지금 요구는 외부 파트너 조회 포털이 아니라 내부 운영팀의 실행 도구에 가깝다.
- 캘린더, CRM, 설정, 알림과 같이 관리자 문맥 안에서 이어져야 한다.
- 하드웨어 총판 운영은 설정과 계약, 정산, 설치 이행이 함께 움직이므로 독립 포털보다 운영 허브가 먼저다.

## 4. 추천 IA

```text
/admin/partners
  ├─ 파트너 리스트
  ├─ 운영 상태 뷰
  ├─ 위험/대기 큐
  └─ 빠른 생성 액션

/admin/partners/[id]
  ├─ 워크스페이스
  ├─ 거래 흐름
  ├─ 이행 체크
  ├─ 문서/계약
  ├─ 로그/이슈
  └─ 자동화
```

## 5. `/admin/partners` 리스트 페이지 구조

### 역할

이 화면은 “파트너 목록”이 아니라  
`어느 총판/파트너에 지금 손이 가야 하는지`를 보여주는 운영 큐여야 한다.

### 상단 요약

- 활성 파트너 수
- 계약 검토 대기 수
- 설치/납품 진행 중 파트너 수
- 정산 지연 파트너 수
- 해결 안 된 이슈 수

### 기본 뷰

- 전체
- 계약 대기
- 설치 진행중
- 정산 지연
- 이슈 필요
- 휴면/주의

### 리스트 컬럼

- 파트너명
- 유형/채널
- 대표 담당자
- 현재 메인 거래 단계
- 다음 액션
- 미완료 체크리스트 수
- 미팅/계약 최근 로그
- 정산 상태
- 이슈 상태

### 빠른 액션

- 파트너 추가
- 새 거래 시작
- 계약서 생성
- 이행 체크리스트 생성
- 월별 매출 기록

## 6. `/admin/partners/[id]` 상세 워크스페이스

### 헤더

- 파트너명, 유형, 담당자, 연락처
- 메인 거래 단계
- 다음 액션 일시
- 계약 리스크
- 정산 리스크
- 최근 이슈 상태

### 상단 고정 액션

- 새 견적 생성
- 계약서 열기/공유
- 체크리스트 생성
- 미팅 로그 추가
- 이슈 등록

## 7. 상세 탭 설계

### 1. 워크스페이스

가장 먼저 보는 화면이다.  
요약보다 `오늘 처리할 일`과 `지금 막히는 것`이 먼저 보여야 한다.

구성:

- 상태 카드
  - 현재 메인 거래
  - 다음 액션
  - 미완료 체크리스트 수
  - 정산 필요 문서 수
  - 최근 매출 집계
- 통합 타임라인
  - TODO
  - 고객 미팅 로그
  - 계약 로그
  - 이슈/결정 로그
- 우측 큐
  - 오늘 해야 할 일
  - 이번 주 만료 계약
  - 미확인 문서 열람/발송 상태

### 2. 거래 흐름

이 탭이 `견적 -> 계약 -> 매출`을 자연스럽게 연결하는 핵심이다.  
`견적`, `계약`, `영수증`, `매출`을 각각 독립 탭으로 쪼개지 않는다.

구성:

- 거래 카드/파이프라인
  - 발굴
  - 견적 준비
  - 계약 검토/발송
  - 진행중
  - 종료
- 거래 상세 섹션
  - 견적 금액/조건
  - 계약 기간
  - 판매 댓수
  - 결제/정산 조건
  - 담당자
- 다음 단계 액션
  - `견적 저장 후 계약 생성`
  - `계약 체결 후 이행 체크리스트 생성`
  - `이행 완료 후 매출/정산 기록 생성`

핵심 원칙:

- 사용자는 탭을 옮겨 다니며 수작업으로 이어붙이면 안 된다.
- 각 거래는 “다음 단계 생성 버튼”으로 자연스럽게 이어져야 한다.

### 3. 이행 체크

하드웨어 총판 업무 특성상 이 탭은 별도 모듈로 분리하는 게 맞다.

구성:

- 설치/납품 체크리스트
- 품목별 수량 확인
- 준비 상태
- 담당자
- 마감일
- 완료 여부
- 거래 연결

권장 그룹:

- 설치 품목
- 수량 검수
- 출고/납품
- 현장 설치
- 후속 지원

핵심 포인트:

- 단순 TODO가 아니라 `품목 + 수량 + 완료 상태`가 함께 관리돼야 한다.
- 총판이 클래스인 하드웨어 전체를 담당할 수 있으므로 거래마다 체크리스트 템플릿을 재사용할 수 있어야 한다.

### 4. 문서/계약

이 탭은 파일 보관소가 아니라 `문서 운영 센터`다.

다뤄야 할 문서:

- 견적서
- 계약서
- 영수증
- 기타 첨부 문서

계약서/문서별 필수 속성:

- 문서 원본
  - 문서 종류
  - 거래 연결
  - 상태
  - 문서 번호
  - 버전
  - 금액/기간
  - 정산 대상 기간
  - PDF 원본 / 외부 URL / 저장 경로
- 외부 전달본
  - 전달 채널
    - PDF
    - 카카오톡
    - 링크
  - 수신자
    - 이름
    - 연락처
    - 이메일
  - 전달 상태
    - 준비
    - 발송
    - 열람
    - 만료
    - 폐기
- 접근 설정
  - 만료일시
  - 비밀번호 사용 여부
  - 비밀번호 힌트
  - 최대 조회 수
  - 다운로드 허용 여부
  - 출력 허용 여부
  - 워터마크
  - 열람 이력 확인

추가 액션:

- 링크 재발급
- 비밀번호 재설정
- 만료 연장
- 카카오톡 재전송
- PDF 원본 열기

권장 UI 옵션:

- 문서 생성/수정 드로어
  - 기본 정보
  - 파일/링크 정보
  - 기본 보안 정책
- 외부 공유 모달
  - 채널 선택
  - 수신자 선택
  - 만료/비밀번호/다운로드 옵션
  - 재발송 / 링크 복사 / 만료 연장
- 문서 상세 우측 패널
  - 최근 열람 시각
  - 총 조회/다운로드 수
  - 카카오 발송 결과
  - 실패/만료 사유

보안 기본 원칙:

- 원본 파일 URL을 그대로 외부에 공개하지 않는다.
- 비밀번호는 평문이 아니라 해시로 저장한다.
- 만료 연장은 기존 링크를 되살리기보다 새 전달본을 발급하는 편이 안전하다.
- 문서 상태와 전달 상태를 분리해 운영자가 혼동하지 않게 한다.

### 5. 로그/이슈

요구상 가장 중요하게 새로 분리해야 하는 탭이다.  
지금까지는 메모에 묻히기 쉬운 항목들을 `운영 로그`와 `판단 필요 이슈`로 분리해서 봐야 한다.

포함해야 하는 로그:

- 고객 미팅 로그
- 전화/카카오톡/이메일 로그
- 계약 로그
  - 발송
  - 열람
  - 만료
  - 비밀번호 변경
  - 재전송
- 내부 운영 메모
- 결정/승인 로그

이슈 모듈:

- 제목
- 분류
  - 계약
  - 설치
  - 정산
  - 고객 요청
  - 내부 결정 필요
- 심각도
- 담당자
- 마감일
- 상태
  - open
  - waiting
  - blocked
  - resolved

핵심 포인트:

- `애매한 이슈`는 메모로 흩어지면 안 된다.
- 로그는 사실 기록, 이슈는 처리 대상이므로 같은 화면에 두되 구분돼야 한다.

### 6. 자동화

자동화는 별도 탭으로 두되, 실제 트리거는 다른 탭의 데이터에서 온다.

우선 자동화 대상:

- 견적 만료 리마인드
- 계약 만료/갱신 리마인드
- 미완료 체크리스트 알림
- 월말 판매량 취합
- 정산 지연 알림
- 계약 링크 만료 전 알림

표시해야 할 것:

- 자동화 이름
- 상태
- 트리거
- 대상 거래/문서
- 최근 실행
- 다음 실행
- 실패 사유

## 8. 상세 워크스페이스 운영 구조

### 핵심 원칙

상세 워크스페이스는 단순 탭 모음이 아니라 아래 3가지를 동시에 만족해야 한다.

1. 지금 바로 처리해야 하는 Todo를 보여준다.
2. 최근에 무슨 일이 있었는지 타임라인으로 설명한다.
3. 견적에서 매출까지 어디서 막혔는지 한눈에 보이게 한다.

즉, 운영자는 `/admin/partners/[id]` 하나만 열어도
`업무 큐 + 맥락 + 다음 단계`를 같이 볼 수 있어야 한다.

### 추천 화면 골격

#### 1. 상단 요약 스트립

- 현재 메인 거래 단계
- 오늘 처리해야 할 Todo 수
- 설치 체크 진행률
- 계약/정산 리스크 수
- 이번 달 판매량
- 최근 고객 미팅 일시
- 다음 액션 일시

#### 2. 좌측: 실행 큐

이 영역은 "해야 할 일"만 모은다.

- 오늘 할 일
- 이번 주 마감
- 파트너 응답 대기
- 내부 승인 대기
- 설치 품목/수량 체크
- 정산 누락 확인
- 미팅 후속 액션

#### 3. 중앙: 통합 타임라인

이 영역은 "왜 지금 이 상태인지"를 설명한다.

- 고객 미팅 로그
- 견적 로그
- 계약 로그
- 설치 체크 로그
- 영수증 / 입금 로그
- 매출 반영 로그
- 자동화 실행 로그
- 내부 결정 / 메모 / 이슈 로그

#### 4. 우측: 애매한 상황 / 판단 필요

이 영역은 메모가 아니라 관리 대상이다.

- 수량 불일치
- 계약 문구 협의 중
- 고객 요청과 내부 일정 충돌
- 매출 반영은 됐지만 영수증 발행 여부 불명확
- 설치 완료 보고는 왔지만 검수 미확정

핵심은 `애매한 상황`을 notes에 묻지 않고
별도 카드와 상태로 올려서 다음 액션에 연결하는 것이다.

## 9. 필요한 로그 / 타임라인 / Todo 구조

### 로그는 사실 기록, Todo는 실행 항목이다

이 둘은 합쳐서 보이되 모델은 구분하는 편이 맞다.

- 로그
  - 무슨 일이 있었는가
- Todo
  - 지금 무엇을 해야 하는가

### 공통 로그 필드

- `partner_id`
- `deal_id`
- `subject_type`
  - `partner`, `deal`, `document`, `install_item`, `sales_month`, `issue`, `customer`
- `log_type`
- `summary`
- `details`
- `actor`
- `occurred_at`
- `next_action`
- `due_at`
- `status`
- `metadata`

### 필수 로그 유형

#### 1. 고객 접점 로그

- `meeting_logged`
- `call_logged`
- `kakao_logged`
- `email_logged`
- `onsite_visit_logged`

필수 정보:

- 참석자
- 고객/최종 설치 대상
- 논의 주제
- 결정 사항
- 후속 액션

#### 2. 견적 / 상업 로그

- `quote_created`
- `quote_sent`
- `quote_revised`
- `quote_rejected`
- `discount_requested`
- `negotiation_started`

필수 정보:

- 견적 버전
- 금액 변경 전/후
- 수량 변경 전/후
- 고객 피드백
- 다음 단계

#### 3. 계약 로그

- `contract_drafted`
- `contract_sent`
- `contract_revision_requested`
- `contract_revised`
- `contract_signed`
- `contract_on_hold`
- `contract_terminated`

필수 정보:

- 계약 기간
- 수정 요청 포인트
- 보류 사유
- 서명 주체

#### 4. 설치 / 품목 / 수량 로그

- `install_plan_created`
- `install_item_added`
- `install_quantity_updated`
- `install_partially_completed`
- `install_verified`
- `install_issue_reported`

필수 정보:

- 품목명
- 계획 수량
- 확인 수량
- 누락 수량
- 확인자
- 현장 이슈

#### 5. 정산 / 영수증 / 매출 로그

### Todo 유형

- 후속 연락

- 영수증 발행

- 내부 승인
- 애매한 이슈 확인

### 설치 품목 / 수량 체크 Todo는 별도 그룹으로 관리한다

하드웨어 총판 운영에서 가장 자주 열리는 실무 단위는 일반 문장형 Todo가 아니라
`품목 + 수량 + 상태` 조합이다.

권장 필드:

- 체크리스트 그룹명
- 품목
- 계획 수량
- 현재 확인 수량
- 상태
  - `planned`, `ordered`, `delivered`, `installed`, `verified`, `issue`
- 담당자
- 확인 시각
- 누락/이슈 메모

## 10. 상세 운영 플로우

### 견적에서 매출까지 자연스러운 흐름

1. 고객/총판 접점 생성
2. 고객 미팅 로그 기록
3. 견적 초안 생성
4. 견적 발송 / 수정 / 협상
5. 계약 발송 / 수정 요청 / 서명
6. 설치 품목/수량 체크리스트 생성
7. 설치 진행 / 검수 완료
8. 영수증/정산 처리
9. 월별 판매량 / 매출 기록
10. 리뉴얼 또는 추가 기회 생성

### 단계별로 자동 생성되면 좋은 연결

- 견적 생성 후
  - `계약 준비 Todo`
  - `고객 피드백 확인 Todo`
- 계약 서명 후
  - `설치 체크리스트 생성`
  - `출고/납품 일정 생성`
- 설치 완료 후
  - `영수증 발행 Todo`
  - `매출 반영 Todo`
- 매출 반영 후
  - `월말 집계 확인 Todo`
  - `리뉴얼 후보 검토 Todo`

### 애매한 상황 처리 규칙

애매한 상황은 메모가 아니라 `Ops Issue` 로 관리하는 것이 맞다.

필수 필드:

- 제목
- 사실
- 아직 확정되지 않은 부분
- 현재 가정
- 확인해야 할 상대
- 내부 담당자
- 다음 확인 예정일
- 상태
  - `open`, `waiting_confirmation`, `blocked`, `resolved`, `dropped`

예시:

- 설치 요청은 12대인데 계약서는 10대로 기재됨
- 고객 희망 일정은 5월인데 총판 내부 가능 일정은 6월
- 매출은 반영됐지만 영수증 발행 여부가 아직 확인 안 됨

운영자는 이슈를 보고 바로
`누가`, `언제까지`, `무엇을 확인해야 하는지` 알 수 있어야 한다.

## 11. 관리자 캘린더 연동 원칙

### 역할 구분

- `/admin/partners/[id]`는 파트너 일정의 `원본 운영 화면`이다.
- `/admin/calendar`는 파트너 일정이 관리자 전체 일정 속에서 어떻게 보이는지 확인하는 `공용 가시화 레이어`다.
- 즉, 파트너 일정의 상세 수정과 문맥 확인은 파트너 워크스페이스에서 하고, 캘린더는 전체 충돌과 우선순위를 보는 용도로 쓴다.

### 어떤 일정만 캘린더에 올릴 것인가

기본 원칙:

- `sync_to_admin_calendar = true` 인 일정만 올린다.
- 기본 노출은 `planned` 상태만 한다.
- `completed`, `canceled`는 기본 숨김 후 필터로만 본다.

캘린더에 올릴 가치가 있는 일정:

- 고객 미팅
- 후속 연락 마감
- 계약 만료 / 갱신 시점
- 설치/납품 주요 마일스톤
- 정산/영수증 마감

올리지 않아도 되는 것:

- 세부 작업 단위의 내부 Todo
- 품목별 체크리스트 한 줄 한 줄
- 운영 메모성 일정

### 필터 기준

`/admin/calendar`에서 파트너 일정이 헷갈리지 않으려면 최소 아래 필터가 필요하다.

- 소스
  - `전체`
  - `팀 일정`
  - `파트너 일정`
- 파트너
- 담당자
- 거래
- 상태
  - `예정`
  - `완료`
  - `취소`
- 빠른 토글
  - `내 담당만`
  - `이번 주 만료/마감`

기본 추천값:

- 첫 진입은 `전체`
- 단, 상단에서 `파트너 일정만` 1클릭으로 걸러질 수 있어야 한다.

### 배지 기준

파트너 일정은 기존 팀 일정과 같은 색만 쓰면 반드시 헷갈린다.  
색보다 `출처 + 의미 + 위험도`를 분리해서 보여주는 편이 맞다.

권장 배지 순서:

1. 출처 배지
   - `파트너`
2. 유형 배지
   - `미팅`
   - `후속`
   - `마감`
   - `갱신`
3. 위험/상태 배지
   - `오늘`
   - `D-3`
   - `만료임박`
   - `지연`

월간 캘린더 셀과 다가오는 일정 카드에는 최소 아래 정보가 같이 보여야 한다.

- 파트너명
- 거래명
- 일정 유형
- 담당자

즉, `미팅`이라고만 보이면 안 되고  
`[파트너] 분당총판 · HW 패키지 계약 · 미팅`처럼 문맥이 보여야 한다.

### 링크 기준

파트너 일정 카드를 눌렀을 때는 단순 수정 모달보다 `원래 작업 화면`으로 돌아갈 수 있어야 한다.

권장 액션:

- 기본 액션: `파트너 워크스페이스 열기`
- 보조 액션:
  - `거래 흐름 열기`
  - `이행 체크 열기`
  - `문서/계약 열기`

연결 원칙:

- 미팅/후속 일정이면 `로그/이슈` 또는 `거래 흐름`
- 설치/납품 마일스톤이면 `이행 체크`
- 계약 만료/갱신 일정이면 `문서/계약`

### 헷갈리지 않게 하는 UI 원칙

- 파트너 일정은 팀 일정과 같은 목록에 섞여도 `출처 배지`가 항상 먼저 보여야 한다.
- `다가오는 일정` 패널에서는 팀 일정과 파트너 일정을 한 번 더 그룹으로 나누는 편이 안전하다.
- 파트너 일정에서 수정 가능한 것은 시간/담당자 같은 캘린더 속성까지만 두고, 계약 상태나 체크리스트 상태 변경은 파트너 워크스페이스로 보내는 것이 좋다.
- 설치 체크리스트의 세부 항목을 전부 캘린더에 올리지 말고, 마일스톤만 올려야 캘린더가 운영 가능성을 유지한다.

## 12. 권장 엔티티 구조

### 핵심 엔티티

- `Partner`
  - 총판/협력사 기본 정보
- `Deal`
  - 견적부터 매출까지의 상업 흐름 중심
- `OpsChecklistItem`
  - 설치 품목, 수량, 이행 체크
- `Document`
  - 견적서, 계약서, 영수증, 기타 파일
- `DocumentDelivery`
  - PDF/카카오/링크별 외부 전달본
  - 만료, 비밀번호, 다운로드/출력 허용, 수신자, 전송 결과
- `DocumentAccessLog`
  - 열람, 다운로드, 비밀번호 오류, 만료, 재전송 이력
- `ActivityLog`
  - 미팅/전화/카톡/내부 기록
- `Issue`
  - 애매하거나 판단 필요한 운영 이슈
- `SalesRecord`
  - 월별 판매량/금액
- `AutomationRule`
  - 리마인드 및 집계 자동화

### 엔티티 관계 원칙

- `Partner`는 관계의 중심이다.
- `Deal`은 견적, 계약, 판매, 정산의 기준 단위다.
- `OpsChecklistItem`, `Document`, `SalesRecord`, `Issue`는 필요 시 `Deal`에 연결된다.
- `DocumentDelivery`, `DocumentAccessLog`는 `Document`에 귀속되고 필요 시 `Deal`/`Partner`에 함께 연결한다.
- 정산문서는 필요 시 여러 `SalesRecord`와 직접 연결해 근거를 남긴다.

## 13. 왜 이런 구조가 맞는가

- `견적`, `계약`, `영수증`, `매출`을 따로 탭으로 찢으면 사용자가 매번 어디서 다음 작업을 해야 하는지 헷갈린다.
- 하드웨어 총판 운영에서는 계약 체결보다 설치/납품 이행 체크가 실제로 더 자주 열리는 화면이 된다. 그래서 `이행 체크`는 별도 탭이 필요하다.
- `고객 미팅 로그`, `계약 로그`, `애매한 이슈`는 서로 다른 성격이지만 운영 판단은 같이 내려야 하므로 `로그/이슈` 탭에서 함께 보는 편이 효율적이다.
- 계약서 전달 방식과 접근 설정은 단순 파일명 수준이 아니므로 `문서/계약` 탭에서 독립적으로 관리해야 한다.
- 첫 화면은 설정이 아니라 `현재 진행 상황 + 당장 해야 할 일 + 막히는 요소`를 보여줘야 한다.

## 14. MVP 범위

### Phase 1

- `/admin/partners` 리스트와 운영 상태 뷰
- `/admin/partners/[id]` 상세 워크스페이스
- 거래 흐름 탭
- 이행 체크 탭
- 문서/계약 탭
- 로그/이슈 탭

### Phase 2

- 계약 링크/비밀번호/만료 설정
- 카카오톡 전송 이력
- 체크리스트 템플릿
- 이슈 SLA/에스컬레이션
- 월말 판매 취합 자동화

### Phase 3

- 외부 파트너 포털
- 문서 열람 권한 분리
- 전자서명 연동
- 계약/정산 승인 플로우

## 15. 구현 우선순위 메모

1. 리스트 페이지를 “상태 큐” 기준으로 만든다.
2. 상세는 `워크스페이스 -> 거래 흐름 -> 이행 체크 -> 문서/계약 -> 로그/이슈` 순으로 구현한다.
3. `거래 저장 후 다음 단계 생성` UX를 먼저 만든다.
4. 문서 전달 방식과 접근 설정은 MVP부터 스키마를 열어둔다.
5. 애매한 이슈는 notes로 숨기지 말고 별도 모듈로 시작한다.

## 16. 위험요소

- 계약서 1건을 PDF/카카오/링크로 각각 보낼 수 있으므로 전달본을 따로 저장하지 않으면 이력 추적이 무너진다.
- 만료/비밀번호 정책이 전달본이 아니라 원본 문서에만 걸리면 채널별 정책 차이를 담을 수 없다.
- 정산문서가 매출 기록과 직접 연결되지 않으면 월별 집계와 정산 근거를 계속 사람이 맞춰야 한다.
- 카카오 발송 성공과 실제 문서 열람은 다른 이벤트이므로 하나의 상태값으로 합치면 운영 판단이 틀어질 수 있다.
