# Operation Case State Flow

기준 시점: 2026-04-06  
관련 문서: [운영 건 상세](./operation-case-workspace.md), [도메인 모델](./domain-model.md), [데이터 계약](./data-contracts.md)

## 1. 왜 상태 흐름이 중요한가

문서, 수량, 일정, 체크리스트는 각각 따로 존재하지만 실제 운영에서는 `단계 전이`에 묶여 움직인다.  
따라서 상태 흐름이 없으면 화면은 많아져도 운영 기준은 생기지 않는다.

## 2. 추천 단계

- intake
- quote
- contract
- prep
- install
- settlement
- closed

## 3. 단계별 의미

### intake

- 고객사와 운영 건이 생성된 상태
- 요구사항과 기본 조건 수집 단계

### quote

- 견적 검토/작성/발송 단계
- 문서와 수량 기준이 처음으로 외부에 제시된다

### contract

- 계약 검토, 전달, 체결 단계
- 문서 최신본과 상태 관리가 가장 중요해진다

### prep

- 설치/납품 준비 단계
- 체크리스트와 수량 원장이 중심이 된다

### install

- 실제 현장 이행 단계
- 일정, 체크리스트, 설치 완료 수량이 핵심이다

### settlement

- 영수증, 설치 확인서, 정산 상태가 중심이다

### closed

- 문서와 수량, 로그가 정리된 종료 상태

## 4. 단계 전이 최소 조건

### intake -> quote

- 고객사 기본 정보 있음
- 운영 건 제목/범위 정의됨
- 초기 수량 또는 요구사항 메모 있음

### quote -> contract

- 견적 문서 최신본 존재
- 외부 발송 상태 또는 내부 확정 상태가 기록됨
- 주요 품목 수량이 정리됨
- 견적 상태가 최소 `ready`, 권장 기준으로는 `accepted` 또는 `internal_review 승인 완료`

### quote 단계 내부에서 반드시 추적할 것

- 최신 견적 버전
- 마지막 발송 시각
- 열람 여부
- 수정 요청 여부
- accepted / rejected 여부

### contract -> prep

- 계약 문서가 체결 또는 내부 확정 상태
- 설치/납품 일정 초안이 있음
- 준비 체크리스트를 생성할 수 있음

### prep -> install

- 핵심 체크리스트 완료
- 준비 수량이 계약 수량과 허용 범위 내에서 일치
- 설치 일정 확정

### install -> settlement

- 설치 완료 로그 존재
- 설치 완료 수량 기록됨
- 설치 확인 문서 또는 대체 증빙 존재

### settlement -> closed

- 영수증/정산 문서 정리
- 열린 이슈 해소
- 최종 수량 확정

## 5. 단계별 핵심 객체 우선순위

각 단계에서 무엇이 메인이 되는지 명확해야 화면 우선순위가 선다.

| 단계 | 주로 보는 것 | 필수 확인 객체 |
| --- | --- | --- |
| `intake` | 요구사항 정리 | 고객 기본 정보, 초기 메모, 초기 수량 |
| `quote` | 제안 정합성 | 견적 문서, 견적 수량, 고객 접점 로그 |
| `contract` | 합의 확정 | 계약 문서, 발송/열람/체결 상태, 계약 로그 |
| `prep` | 준비 정확성 | 체크리스트, 준비 수량, 설치 일정 |
| `install` | 현장 실행 | 설치 일정, 체크리스트 완료 여부, 설치 수량 |
| `settlement` | 증빙/정산 | 영수증, 설치 확인 문서, 정산 로그 |
| `closed` | 정리 완료 | 최종 수량, 해결된 이슈, 종료 로그 |

## 6. 상태와 리스크는 분리한다

단계와 별개로 운영 건의 상태 배지를 둔다.

추천 상태:

- healthy
- watch
- delayed
- blocked
- done

의미:

- 단계는 `어디까지 왔는가`
- 상태는 `괜찮게 가고 있는가`

## 7. 자동 제안 규칙

아래 항목은 시스템이 다음 액션으로 제안할 수 있다.

- 견적 저장 후 `계약 문서 생성`
- 계약 체결 후 `체크리스트 생성`
- 설치 일정 생성 후 `캘린더 반영`
- 수량 불일치 발생 시 `이슈 생성 제안`
- 계약서 발송 후 미열람 지속 시 `재발송 또는 확인 요청`
- 설치 완료 후 `영수증/정산 문서 생성`

### 추가 후보

- 설치 일정 생성 후 `현장 체크리스트 템플릿 적용`
- 준비 수량 입력 후 `불일치 검사 실행`
- settlement 진입 시 `필수 증빙 누락 검사`
- 견적서 `revised` 진입 시 이전 버전 대비 변경 요약 생성
- 견적서 `accepted` 진입 시 계약 문서 생성 CTA 승격

## 8. 막힘 조건

아래 상태에서는 단계 전이를 강하게 경고하거나 제한하는 편이 좋다.

- 계약 단계인데 계약 문서 최신본 없음
- 준비 단계인데 핵심 품목 수량 미확정
- 설치 단계인데 설치 일정 없음
- 정산 단계인데 영수증/증빙 문서 없음
- 열린 이슈가 심각도 높음인데 해결 메모 없음

## 9. 전이 시 자동으로 남겨야 하는 로그

단계 전이는 기록만 바꾸는 행위가 아니라 운영 이벤트다.

최소 로그:

- 이전 단계
- 새 단계
- 전이 시각
- 전이한 사람
- 전이 사유
- 아직 남은 경고

예시:

- `quote -> contract`
- `견적서 v3 발송 완료, 계약 검토 단계로 전환`
- `남은 경고: 계약 담당자 확인 필요`

## 10. 전이 허용 정책

억지로 다 막는 것보다 아래 3단계 정책이 현실적이다.

- `allow`
  - 바로 전이 가능
- `allow_with_warning`
  - 전이는 허용하되 남은 위험을 보여줌
- `block`
  - 필수 항목이 없어 전이 불가

예:

- 계약서가 아직 `viewed`는 아니지만 발송은 됨: `allow_with_warning`
- 계약 문서 자체가 없음: `block`

## 11. 상태 흐름 설계 원칙

1. 단계 전이는 수동 승인과 자동 제안을 함께 쓴다.
2. 억지로 잠그기보다 경고와 다음 액션 제안을 우선한다.
3. 문서, 수량, 일정, 체크리스트가 전이 조건에 연결돼야 한다.
4. 전이 자체도 로그로 남긴다.
