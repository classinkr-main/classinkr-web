# Hardware Sheet Interpretation

기준 시점: 2026-04-29  
대상 시트: `GOOGLE_BRANCH_HARDWARE_SHEET_ID`

## 1. 결론

현재 하드웨어 시트의 재고 기준은 `3.출고 현황`에 출고/예정 출고 리스트를 적고, `재고현황`에서 물류 번호별 입고와 출고 합계를 보는 구조로 해석한다.

`재고현황`은 단순 현재 재고표가 아니라 아래 3개 블록이 한 시트에 붙어 있는 요약표다.

- `입고 현황`: 각 물류 번호로 들어온 총량
- `출고 현황`: 각 물류 번호에서 이미 나갔거나 나갈 예정으로 잡힌 총량
- `재고 현황`: OPS, 케이블, 터치펜 등 물류 번호별 입출고로 관리하지 않는 부자재 재고

따라서 물류 번호별 재고는 아래처럼 계산한다.

```text
물류 번호별 재고 = 재고현황 입고 현황 블록 - 재고현황 출고 현황 블록
```

예시:

```text
H8 / 86" IFP = 입고 35 - 출고 23 = 재고 12
```

## 2. 탭별 역할

### 2-1. `2.입고 현황`

입고 원장이다. 행 단위로 실제 입고 또는 기존 보유 물량의 출처를 기록한다.

현재 컬럼 해석:

| 컬럼 | 의미 |
| --- | --- |
| A | 물류No. |
| B | 입고일 |
| C | 제품명 |
| D | 수량 |
| E | 단가(USD) |
| F | 금액(USD) |
| G | 금액(CNY) |
| H | 시리얼 번호 |
| I | 보관 장소 |
| J | 수입자 |
| K | Remarks |

주의:

- `FY24-25`, `H1`, `H8` 같은 물류 번호가 재고 lot 역할을 한다.
- `24-25` 같은 입고일 값은 정확한 날짜가 아니므로 날짜 필드로 정규화할 수 없다.
- 금액 CNY는 현재 DB 컬럼에 별도 필드가 없어서 raw payload로만 보존된다.

### 2-2. `3.출고 현황`

출고 원장이다. 실제 설치 완료뿐 아니라 출고 예정 물량도 같은 원장에 들어간다.

현재 컬럼 해석:

| 컬럼 | 의미 |
| --- | --- |
| A | 물류No. |
| B | 출고일 |
| C | 담당자 |
| D | 제품명 |
| E | 수량 |
| F | 단가(USD) |
| G | 매출(USD) |
| H | 매출(CNY) |
| I | 배송/설치 장소 |
| J | 시리얼 번호 |
| K | 진행 상태 |
| L | 유형 |
| M | Remarks |

주의:

- K열 진행 상태가 `배송 예정`이고 셀이 분홍/빨강 계열로 칠해진 행은 나갈 예정인 물량이다.
- 예정 출고도 `재고현황`의 출고 현황 블록에 반영되어 있으므로, 현재 시트 기준 재고는 이미 예약 물량을 차감한 값에 가깝다.
- `2026.4월중`, `2026.5월~` 같은 날짜는 정확한 출고일이 아니므로 날짜 필드에는 넣지 않고 raw 값으로 보존해야 한다.

### 2-3. `재고현황`

물류 번호별 입출고 요약표다.

현재 구조:

- D:K열: `FY24-25`, `H1`, `H2(과사람)`, `H3`, `H4`, `H5`, `H6`, `H7(과사람)`, `H8`
- M열: 합계
- O:P열: 판매 현황, 샘플 현황

해석 규칙:

- 3~11행의 `입고 현황` 블록은 물류 번호별 총 입고량이다.
- 13~21행의 `출고 현황` 블록은 물류 번호별 총 출고/예정 출고량이다.
- 현재 재고는 M열 합계끼리도 `입고 합계 - 출고 합계`로 계산한다.
- O:P열의 판매/샘플 현황은 참고 지표이며 현재 재고 계산에 더하면 안 된다.
- 23행 이후 `재고 현황` 블록은 OPS, 케이블, 터치펜 등 부자재의 현재 수량으로 직접 읽는다.

## 3. 선입선출 해석

기본 운영 원칙은 선입선출이다.

- 새 출고를 시스템이 자동 배정한다면 가장 오래된 물류 번호의 남은 재고부터 차감한다.
- 다만 현재 시트는 `3.출고 현황` A열에 물류 번호를 직접 적고 있으므로, 이미 물류 번호가 지정된 행은 그 값을 우선한다.
- 물류 번호가 비어 있거나 임시인 경우에만 시스템에서 FIFO 추천을 만들고, 사람이 확정하는 흐름이 안전하다.

## 4. 홈페이지/어드민 충돌 지점

확인된 충돌과 수정 기준:

- 기존 파서는 `재고현황`의 모든 숫자 열을 합산해서 입고, 출고, 판매, 샘플 값을 한꺼번에 더했다. 이 방식은 실제 재고를 크게 부풀린다.
- 기존 입고 파서는 G열 `금액(CNY)`를 시리얼 번호로 읽고, H~J열을 한 칸씩 밀어서 보관 장소/수입자/비고를 잘못 저장했다.
- 기존 출고 파서는 F열 `단가(USD)`를 매출로 읽고, I열 배송 장소를 진행 상태로 읽었다. 그래서 `배송 예정` 집계가 실제로는 장소명 집계가 될 수 있었다.
- 기존 날짜 파서는 `2025. 2. 1`처럼 공백이 들어간 날짜를 파싱하지 못했다.
- 기존 API 제품 매칭은 `T1 카메라`, `S1 카메라` 같은 이름만 잡았고 실제 시트의 `T1`, `S1`, `STD1` 표기를 놓쳤다.

반영한 구현 기준:

- `branch_hw_stock.quantity`는 `재고현황`의 입고 블록 합계에서 출고 블록 합계를 뺀 값으로 저장한다.
- `branch_hw_outbound.progress`는 K열 진행 상태를 읽는다.
- K열 진행 상태 셀이 분홍/빨강 계열이면 raw payload에 `planned_by_color`로 남긴다.
- `T1(promoted)`, `STD1(promoted)`는 물리 재고 관점에서는 기본 SKU와 같이 묶어 볼 수 있다. 단, 매출/정산 관점에서는 별도 유형으로 남겨야 한다.
- `/admin/hardware`의 시트 가져오기는 Google Sheet를 강제 동기화한 뒤 `hardware_sheet_import_snapshots`에 이전 `sheet_import` 원장, 새 후보 원장, branch HW payload, checksum을 남기고 `hardware_movements`의 시트 이관분을 교체한다.
- 스냅샷 생성이 실패하면 시트 이관 원장 교체를 실행하지 않는다. 수기 원장(`source = admin_manual`)은 시트 가져오기 교체 대상이 아니다.

## 5. 남은 리스크

- 예정 출고를 현재 재고에서 뺄지, 별도 `예약 재고`로 뺄지 제품 정의가 필요하다. 현재 시트는 예정 출고를 출고 블록에 포함하므로 가용 재고에 가깝다.
- 시트상 `STD1`/`STD1(promoted)`는 물류 번호별 음수 재고가 발생할 수 있다. 실제 스탠드 물량이 같은 물건이라면 SKU 정규화 규칙이 필요하다.
- 시리얼 번호가 비어 있는 행이 많아 unit-level FIFO는 아직 불가능하다. 현재는 quantity-level FIFO만 가능하다.
- `재고현황`을 수동 수정하면 `2.입고 현황`/`3.출고 현황` 원장과 어긋날 수 있다. 장기적으로는 원장을 기준으로 요약표를 생성하는 편이 안전하다.
- `배송 예정` 행은 설치 완료와 같은 출고 원장에 섞여 있으므로, 어드민 UI에서는 `설치 완료`, `배송 예정`, `기타/미정`을 분리해서 보여줘야 한다.
- Google Sheet 동기화는 `/admin/hardware` import에서 강제 실행된다. 운영 감사 기준은 import snapshot에 남은 branch payload와 이전/후보 원장 checksum이며, Google Drive 파일 자체의 버전 백업은 별도 Drive 권한/정책으로 다룬다.
