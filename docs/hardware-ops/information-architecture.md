# Hardware Ops Information Architecture

기준 시점: 2026-04-06  
관련 문서: [정체성과 원칙](./identity.md), [운영 건 상세](./operation-case-workspace.md)

## 1. IA 방향

현재 구현은 `/admin/partners`를 사용하지만, 실제 IA는 아래 질문에 답해야 한다.

`누가 아니라 어떤 운영 건이 지금 손이 가야 하는가?`

즉 상위 IA는 사람 목록보다 운영 큐 중심이 되어야 한다.

## 2. 추천 상위 구조

```text
/admin/partners
  ├─ 운영 대시보드
  ├─ 진행 중 운영 건 큐
  ├─ 고객사/총판 검색
  └─ 빠른 액션

/admin/partners/[customer-or-workspace]
  ├─ 고객사 요약
  ├─ 활성 운영 건 목록
  ├─ 최근 문서/일정/로그
  └─ 본사-총판 공통 상태

/admin/partners/[customer-or-workspace]/cases/[caseId]
  ├─ 개요
  ├─ 문서
  ├─ 일정
  ├─ 체크리스트
  ├─ 수량
  └─ 로그/이슈
```

## 3. 현실적인 단계적 적용

현재 코드베이스에서는 아래 방식으로 점진 적용한다.

### Phase A

- 라우트는 `/admin/partners` 유지
- 리스트 화면은 `운영 큐` 성격 강화
- 상세 화면은 `파트너 상세`처럼 보이더라도 실제로는 `운영 워크스페이스`로 사용

### Phase B

- 고객사와 운영 건을 화면에서 더 전면에 드러냄
- 상세 내부 구조를 `고객사 > 운영 건`으로 재배치
- 기존 파트너 정보는 상단 보조 정보로 축소

### Phase C

- 필요 시 `/admin/hardware-ops` 같은 명시적 라우트 또는 alias 검토

## 4. 첫 화면에서 보여야 하는 것

첫 화면은 등록된 대상을 보여주는 페이지가 아니라 `운영 관제판`이어야 한다.

필수 블록:

- 진행 중 운영 건 수
- 오늘/이번 주 일정
- 지연 중인 건
- 문서 누락/체결 대기
- 수량 불일치 경고
- 최근 로그와 다음 액션

## 5. 고객사와 운영 건의 관계

- 고객사는 관계 단위다.
- 운영 건은 실행 단위다.
- 같은 고객사 아래에 여러 운영 건이 병렬로 존재할 수 있다.

예시:

- 신규 설치 건
- 추가 물량 납품 건
- 계약 갱신 건
- 영수증/정산 이슈 건

## 6. 관리자 다른 탭과의 연결 원칙

### 캘린더

- 원본 일정은 운영 건에서 생성한다.
- `/admin/calendar`는 전체 가시화 레이어다.
- 일정에서 다시 운영 건으로 돌아올 수 있어야 한다.

### Overview

- 운영 위험 신호와 다음 액션을 집약해 보여준다.
- 운영 건 상세로 바로 이어지는 entry point 역할을 한다.

### CRM / 리드

- 리드는 유입 전 단계에 가깝다.
- 실제 하드웨어 운영 건으로 전환되는 순간 운영 허브로 handoff 된다.

## 7. 메뉴 이름에 대한 현재 판단

지금은 구현 일관성을 위해 `파트너 운영`을 써도 되지만, 문서와 개념은 아래 후보를 계속 검토한다.

- 하드웨어 운영
- 운영 허브
- 고객사 운영
- 총판 운영
