# 챗봇 지식베이스 보강 설계 (2026-06-17)

## 목표

클래스인 관련 정보를 **챗봇이 실제로 검색·답변할 수 있는 형태**로 모으고, 진짜 빈 곳을 채우고, 채널톡 헬프센터를 정제 동기화하고, "무엇이 있고 무엇이 더 필요한지"를 마스터 문서로 정리한다.

핵심 전제: 챗봇·하이브리드 RAG·시드·임베딩·핸드오프 파이프라인과 **58개 DocArticle은 이미 가동 중**이다. 이 작업은 그린필드가 아니라 **기존 자산 위에 빈 레이어를 얹는 작업**이다.

## 현장 지식 (이전 대화 반영, 2026-06-17)

> 출처: 창업자/운영자 현장 대화 전사 + 리드마그넷 기획 Q&A (repo 밖 자료, 2026-06-17 사용자 제공). **B1~B5의 1차 원천**으로 사용한다.

**중심 메시지(확정):** ClassIn은 단순 전자칠판/화상수업 툴이 아니라 **수업·녹화·과제·학생관리·데이터·권한관리를 한곳으로 묶는 "학원 수업 OS"**. 자료·답변은 기능 나열보다 **"흩어진 도구가 학원 운영비·강사 리소스를 잡아먹는다"**를 먼저 보여준다.

**1순위 타깃:** 학원 원장 / 관리자 / 기관. 가장 흔한 첫 질문 = "줌/기존 전자칠판이랑 뭐가 달라요?"

**한국 로컬 니즈·페인**
- 흩어진 도구(녹화·학생관리·수업준비)를 한 곳으로 = 학원 시스템 OS 수요
- 구형 전자칠판 사용자 페인: 할 일↑, 녹화와 연동 안 됨, 라이선스 유효기간 소진으로 효용↓, 타 시스템 연동 시 또 다른 시스템 구축 부담
- 인지 부족: 클래스인 자체를 모르는 경우 많음 → HW·SW 유기적 통합·시스템화·리소스 절감은 경험/레퍼런스 없이 설명하기 어렵다

**3축 가치(반드시 강조): 리소스↓ + 퀄리티↑**
- 학생: 인터랙티브 수업, 온·오프 구분 없이 어디서나 동일한 수업 환경/퀄리티
- 강사: 수업 준비·EDB로 리소스 절감, 몰입형 수업, 채팅+LMS 한 곳 관리, 감 대신 데이터로 트래킹
- 원장/기관: 권한 기반 관리자 모니터링(수업 시간·특이사항·네트워크·출결 등), 인증·권한 통제로 기관 데이터 축적 + 유출 위험 관리

**경쟁 우위(핵심 비교)**
- 경쟁 전자칠판: 안드로이드 기반·디스플레이 중심 → 녹화/수업하려면 별도 PC·HDMI·터치케이블·여러 호환 프로그램·기기를 추가 연결 = 번거로움·불확실성(노드 증가)
- ClassIn Board: 윈도우 기반·OPS(PC) 내장·클라우드 기반 → 판서 프로그램 + SW + HW가 유기적으로 작동 = 단일 시스템·안심

**가격 반론 대응:** "전자칠판 가격"이 아니라 "학원 시스템 OS(OPS 내장 PC + 수업 녹화 + 클라우드 + 관리/권한 시스템)"로 비교. OPS·자체 깡스펙으로 단가는 높지만 통합 가치로 설명. (내부 정형 기준은 아직 약함 → 케이스별. **하드 금액 단정 금지, 상담 연결**.)

**솔직히 약한 영역(과장 금지, 사용자 지시=정직):**
- 결제·리포트 UI 약함 → API로 데이터 추출해 자체 제작/외부 도구 연동
- 결제·오프라인 출석은 클래스인 기본 제공 아님 → 기존 시스템과 API/외부 연동 구조로 안내

**EDB(정확 정의 — "ETB" 아님):** 클래스인 전용 확장자 파일 = "칠판의 파일". 필기·이미지·텍스트가 상호작용을 유지하는 파일로 교안 제작·수업 자료 호출에 사용. 칠판 50페이지 + EDB 시너지 → 매번 지우거나 자료를 하나씩 띄울 필요가 없다.

**관리자 모니터링(민감 — 표현 주의):** 관리자/허가된 교사 계정이 권한 기반으로 수업 정보 데이터(수업 시간·특이사항·네트워크 등)를 확인. "1분마다 스크린샷 감시" 뉘앙스 대신 **"권한 기반 운영 데이터 가시성"**으로 표현.

**API/연동(공개 OK, 원장·관리자 자동화 사례로 포장):**
- 1단계: 클래스인 앱 푸시 / 2단계: 하위 코스·수업정보 GET / 3단계: SDK + 가상계정 + 수업 중계
- 공식 문서: https://docs.eeo.cn/api/en/ (EEO)
- 기술 레퍼런스가 아니라 자동화 사례로: 보고서 자동화, 수업 일괄 알림, 학생 데이터 기반 개별 리포트

**로컬 사용 현황**
- 스탠다드 도입 = 전자칠판 + 녹화 수업 + 수업 관리 (가장 흔한 조합)
- 온라인은 LMS+인터랙티브 활용도 높음, 현장은 하이브리드까지 안 가는 경우 많음(대형/선도 학원 제외 시 개인 칠판 수준 활용)
- 한국은 온라인<오프라인, 학생이 개인 기기 수업을 꺼림 → 실시간은 전자칠판 판서 → 녹화 → 다시보기 / LMS 숙제·시험을 클래스인 자체로 해결
- 야간 시간 확장, 실시간 동기화로 시공간 확장
- 평균 도입 기간 3개월(보통 3~4개월, 길게 6개월~1년)
- 국내 약 300 규모(칠판 300대·정확 수치 아님, EEO CRM account 기준 → "국내 300여 기관" 수준 신뢰 문구는 가능, 과도한 단정 금지)

**판매 조합·CTA**
- 잘 팔리는 조합: 칠판 + 카메라 + 스탠드(또는 벽걸이) + 소프트웨어(충전/구독)
- CTA: 목동 쇼룸 초대 / 도입 문의 / 바로 결제 — 모든 CTA에 쇼룸 넣어도 됨(멘트 배리에이션). 기술 문서 자체 니즈는 낮음.

**원자료 위치:** Google 공유 드라이브 / 클래스인 폴더(회사 소개서 등 — 사용자 제공 예정).

## DocArticle 작성 계약 (B1~B5 공통)

각 신규 문서는 `lib/docs.ts`의 `DocArticle` 스키마를 그대로 따른다:
```
{ slug, category, title, description, audience, updatedAt: "2026-06-17", readMinutes,
  featured?, tags[], keywords[], chatbotSummary, sections[{heading, body, steps?}],
  resources?[], relatedSlugs[], status: "published", visibility, docType, productArea, difficulty }
```
필수 규칙:
- **포지셔닝 브랜드 보이스 준수**(`lib/classin-positioning.ts`): 프리미엄 운영 파트너 톤, 약한 영역(결제·오프라인 출결·고급 리포트)은 솔직히 별도 시스템으로 인정, 기능 나열이 아니라 수업 운영 흐름으로 설명.
- **가격 민감 정보 절대 단정 금지**(특히 B3): 정확한 금액·계약 조건은 "상담 연결"로. 견적 구성요소·비교 관점만 정성적으로.
- **SSOT 용어 준수**(특히 B5): `랜덤 선택`(슬롯머신 ✕), `객관식/선착순 퀴즈`(팝업 퀴즈 ✕) 등 feature-inventory.md 금지어 목록 따름.
- **원천에 없는 수치·후기 창작 금지**: 케이스/후기는 원본대로 익명화(배지/이니셜), ProblemCost의 정량 수치는 출처 맥락대로만.
- `chatbotSummary`는 챗봇 답변에 바로 쓰일 1~2문장 요약.
- `relatedSlugs`로 기존 58개 문서와 상호 링크(예: B5 → software-overview, classroom-tools, lesson-activities, ai-learning-tools).

### 각 문서 섹션 개요 (위 "현장 지식" 절을 1차 원천으로 사용)

**B1 customer-stories** — 과목/유형별 사례(국어·영어·과학·입시·온라인·하이브리드), 공통 변화 패턴(기록 누적→표준화→후속관리), 원장·강사 후기 요약 + 스탠다드 도입 조합(전자칠판+녹화+수업관리)·평균 3개월·국내 300여 규모 문맥. 질문 라우팅: 유형별 사례 매칭.

**B2 why-classin-needs** — 흩어진 도구가 운영비·강사 리소스를 잡아먹는 문제(중심 메시지를 도입부로), 구형 전자칠판 페인(할 일↑·녹화 미연동·유효기간·연동 부담), 인지 부족 / 반론 대응("지금도 되는데?", "전자칠판이면 충분?", "줌이면?"). prd.md 페르소나 3종(원장·운영·마케팅) 반영.

**B3 value-and-cost-framing** — 견적 구성요소(칠판+OPS+카메라+스탠드/벽걸이+소프트웨어+온보딩), 가격 반론 프레이밍(전자칠판 가격 ✕ → 학원 시스템 OS ◯), 경쟁 비교(안드로이드 디스플레이형 vs 윈도우/OPS 내장 통합형), 솔직한 약한 영역(결제·리포트·오프라인 출석 = API/외부 연동). **하드 금액 단정 금지, 상담 연결.**

**B4 adoption-journey-90days** — 진단 → 파일럿(목동 쇼룸/체험) → 온보딩(강사 교육·EDB 템플릿) → 정착(녹화→복습→LMS) → 90일/3개월차 성공지표(준비시간↓·표준화·데이터 가시성). 평균 3개월 정착. 쇼룸·도입문의·결제 CTA.

**B5 app-capabilities-map** — 학습활동 9종(수업/숙제/시험/녹화/자료/일일과제/토론/OMR/SCORM) + 교실도구 30+(타이머·랜덤선택·개인칠판·화면공유·보조카메라·퀴즈·토론·협업) + AI 도구 + 권한 기반 관리자 데이터 가시성(표현 주의) + EDB 정확 정의·칠판 50p 시너지 + API 자동화 사례(앱 푸시→코스/수업 GET→SDK·중계, docs.eeo.cn) + "어디서 무엇을"(관리자콘솔/교사/학생). SSOT 용어 준수, 세부는 relatedSlugs로 연결.

## 실행 계획 (서브에이전트 총동원)

`lib/docs.ts`는 단일 파일이라 동시 편집 시 충돌 → **병렬 에이전트는 각자 DocArticle 객체(텍스트)를 반환**하고, 메인 스레드가 한 번에 통합한다.

1. **병렬 작성**(동시 6 에이전트):
   - 에이전트 B1~B5: 각자 담당 DocArticle 객체 리터럴을 스키마대로 작성해 반환(원천 파일 직접 정독 + 작성 계약 준수).
   - 에이전트 A: 마스터 감사 문서(`docs/active/...audit...md`)를 직접 파일로 작성.
2. **통합**(메인): 반환된 B1~B5 객체를 `lib/docs.ts`에 삽입(슬러그 중복·카테고리 검증).
3. **채널톡**(메인): 스크립트 제외목록 편집 → sync 실행 → 임베딩.
4. **활성화/게이트**(메인): 골든셋 추가 → seed → embed → 테스트 3종 → eslint → build.

## 오픈 퀘스천 / 애매한 것들 (감사 문서에 정리 + 일부 사용자 확인 필요)

1. **회사 소개서**: repo에 없음 → 사용자가 파일 제공 예정(Google 공유 드라이브/클래스인 폴더). 받으면 별도 DocArticle 또는 B-시리즈에 흡수.
2. **"이전 대화/정리 노트" — 반영됨(2026-06-17)**: 사용자가 현장 대화 전사 제공 → 위 "현장 지식" 절로 흡수, B1~B5의 1차 원천으로 사용.
2b. **리드마그넷(별도 트랙, 사용자 확인 대기)**: 이전 대화는 리드마그넷 5종(학원 OS 진단·전자칠판 실패방지·Zoom 비교·데이터/API 아이디어북·3개월 로드맵) + 리드 스코어링/후속 자동화도 다뤘다. `data/lead-magnets.json`에 이미 2종 존재. 챗봇 KB와 별개 산출물 → 이번 범위 포함 여부는 사용자 결정.
2c. **경쟁 비교 전용 문서**: 안드로이드 vs OPS/윈도우 비교가 강력 → 별도 doc으로 뺄지 B2/B3 흡수로 둘지. 현재 기본은 B2/B3 흡수.
3. **S65 전자칠판 스펙**: 미확정 → 단정 금지, 갭으로 표기.
